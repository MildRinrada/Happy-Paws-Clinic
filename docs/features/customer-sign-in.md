# การเข้าสู่ระบบของลูกค้า

ลูกค้าสมัครด้วยเบอร์โทรที่พิสูจน์ด้วยรหัส OTP แล้วเข้าสู่ระบบด้วยรหัส OTP หรือรหัสผ่าน ลืมรหัสผ่านขอลิงก์ตั้งรหัสใหม่ได้ ซึ่งพนักงานก็ใช้ได้เหมือนกัน

ส่วนที่ contract ไม่ได้เขียนไว้และเราตีความเอง อยู่ใน [ข้อสมมติ § 39](../assumptions.md) token เซสชัน และการเข้าสู่ระบบของพนักงานอยู่ใน [การยืนยันตัวตน](../authentication.md)

> **รหัส OTP ส่งทาง SMS (ThaiBulkSMS) และลิงก์รีเซ็ตรหัสผ่านส่งทางอีเมล (SMTP) หรือ SMS เมื่อตั้ง `Messaging:*` แล้ว** ดู [ตั้งค่าอีเมลและ SMS](../development.md#ตั้งค่าอีเมลและ-sms) ถ้ายังไม่ตั้ง ไม่มีอะไรส่งถึงใคร ในเครื่อง dev เปิด `Auth:SignIn:LogUndeliveredSecrets` ไว้ รหัสจึงอยู่ใน log ของ API ในบรรทัดที่ขึ้นต้นว่า `Development only. OTP for` ห้ามเปิดค่านี้ในเครื่องที่ log ถูกส่งออกไปที่อื่น

## Endpoint

| Method | Endpoint | ผู้เรียก | ทำอะไร |
|---|---|---|---|
| POST | `/auth/otp/request` | ไม่ต้องเข้าสู่ระบบ | ส่งรหัส 6 หลักไปที่เบอร์ |
| POST | `/auth/register` | ไม่ต้องเข้าสู่ระบบ | สมัครด้วยเบอร์และรหัส แล้วเข้าสู่ระบบทันที |
| POST | `/auth/login` | ไม่ต้องเข้าสู่ระบบ | เข้าสู่ระบบด้วยรหัส OTP หรือรหัสผ่าน |
| POST | `/auth/password/reset` | ไม่ต้องเข้าสู่ระบบ | ขอลิงก์ แล้วตั้งรหัสใหม่ |
| POST | `/booking/guest/start` และ `/booking/guest/verify` | ไม่ต้องเข้าสู่ระบบ | จองโดยไม่ต้องสมัครก่อน เบอร์ที่พิสูจน์แล้วได้บัญชีและเข้าสู่ระบบ (ส่วนขยาย § 27) ดูหัวข้อ [เข้าสู่ระบบจากการจอง](#เข้าสู่ระบบจากการจอง) |

## ขอรหัส OTP

```http
POST /v1/auth/otp/request
{ "phone": "081-234-5678", "purpose": "register" }
```

```json
202 { "expires_at": "2026-10-02T10:05:00+00:00" }
```

| กติกา | ค่า |
|---|---|
| `purpose` | `register` หรือ `login` รหัสของจุดประสงค์หนึ่งใช้กับอีกจุดประสงค์ไม่ได้ จุดประสงค์ที่สาม `booking` ออกได้จาก `POST /booking/guest/start` เท่านั้น ส่ง `booking` มาที่นี่ได้ `422` |
| รหัส | ตัวเลข 6 หลัก อายุ 5 นาที ใช้ได้ครั้งเดียว |
| เดาผิด | ได้ 5 ครั้งต่อรหัส ครั้งที่ 6 แม้ใส่ถูกก็ไม่ผ่าน ต้องขอรหัสใหม่ |
| ขอได้กี่ครั้ง | 3 ครั้งต่อเบอร์ใน 10 นาที นับรวมรหัสทุกจุดประสงค์ รวมรหัสจากการจอง เกินตอบ `429 rate_limited` |
| เบอร์ | อ่านเฉพาะตัวเลข `081-234-5678` กับ `0812345678` คือเบอร์เดียวกัน |

**คำตอบเหมือนกันเสมอ** ไม่ว่าเบอร์จะมีบัญชีหรือไม่ เพื่อไม่ให้ใช้ endpoint นี้ตรวจว่าใครเป็นลูกค้า รหัส `login` ส่งจริงเฉพาะเบอร์ที่มีบัญชี รหัส `register` ส่งทุกครั้ง

## สมัคร

```http
POST /v1/auth/register
{ "phone": "0812345678", "code": "482913", "display_name": "คุณสมใจ ใจดี", "password": "ไม่ใส่ก็ได้", "email": "ไม่ใส่ก็ได้" }
```

ได้ `201` พร้อม access token และคุกกี้ refresh เหมือนการเข้าสู่ระบบ

- **บัญชีผูกกับเรกคอร์ดลูกค้าที่เคาน์เตอร์สร้างไว้แล้ว** ถ้าเบอร์ตรงกัน ลูกค้าที่ลงทะเบียนที่คลินิกเมื่อปีที่แล้วจึงเห็นสัตว์และบิลเดิมทันที ถ้าไม่มีเรกคอร์ดเดิม ระบบสร้างใหม่
- คำเชิญจาก `POST /staff/customers/{id}/invite` ถูกทำเครื่องหมายว่ารับแล้ว
- รหัสผ่านไม่บังคับ ไม่ตั้งไว้ก็เข้าสู่ระบบด้วยรหัส OTP ทุกครั้ง ถ้าตั้ง ยาว 8 ถึง 256 ตัวอักษร
- เบอร์หรืออีเมลที่มีบัญชีแล้วตอบ `409 contact_taken` ระบบบอกเรื่องนี้หลังพิสูจน์เบอร์แล้วเท่านั้น
- รหัสผิดหรือหมดอายุตอบ `422` ที่ช่อง `code`
- บันทึก audit `auth.registered`

## เข้าสู่ระบบ

สองแบบ ส่งแบบใดแบบหนึ่ง

```http
POST /v1/auth/login
{ "phone": "0812345678", "code": "193847" }
```

```http
POST /v1/auth/login
{ "identifier": "0812345678", "password": "..." }
```

`identifier` เป็นอีเมลหรือเบอร์ก็ได้ คำตอบมี `capabilities` คือสิ่งที่ token ที่เพิ่งออกทำได้

```json
{
  "access_token": "...", "token_type": "Bearer", "expires_at": "...", "two_factor_satisfied": false,
  "capabilities": { "customer_id": "cus_...", "scopes": ["portal"], "branches": [] }
}
```

- บัญชีที่เป็นทั้งพนักงานและลูกค้าได้ทั้ง `staff_id` และ `customer_id` ใน token เดียว
- บัญชีที่มี 2FA ได้ `two_factor_required` และ `challenge` แทน แล้วต่อที่ `POST /auth/2fa/verify` เหมือนพนักงาน รหัส OTP พิสูจน์โทรศัพท์ ไม่ได้พิสูจน์แอป authenticator
- ผิดทุกแบบตอบ `401` ข้อความเดียวกัน ไม่บอกว่าบัญชีมีอยู่ไหม

## ลืมรหัสผ่าน

เรียก endpoint เดียวสองครั้ง แบบเดียวกับการรับคำเชิญพนักงาน

**ครั้งที่ 1** ขอลิงก์

```http
POST /v1/auth/password/reset
{ "identifier": "somjai@example.com" }
```

ได้ `202 { "status": "link_sent" }` เสมอ แม้ไม่มีบัญชีนั้น ลิงก์ไปทางอีเมลถ้าบัญชีมีอีเมล ไม่อย่างนั้นไปทาง SMS ลิงก์ชี้ไปหน้าเว็บตาม `Auth:SignIn:PasswordResetUrlTemplate` โดยวาง token ไว้หลัง `#` ขอได้ไม่เกิน 3 ลิงก์ต่อบัญชีใน 10 นาที

**ครั้งที่ 2** ตั้งรหัสใหม่

```http
POST /v1/auth/password/reset
{ "token": "...", "new_password": "..." }
```

ได้ `200 { "status": "reset" }`

- ลิงก์อายุ 30 นาที ใช้ได้ครั้งเดียว ลิงก์ผิด ใช้แล้ว หรือหมดอายุ ตอบ `422` ที่ช่อง `token` ข้อความเดียวกัน
- ทุกเซสชันของบัญชีถูกเพิกถอน เพราะเหตุผลที่คนรีเซ็ตรหัสผ่านมักเป็นว่ามีคนอื่นรู้รหัส
- ปัจจัยที่สองไม่ถูกแตะ การรีเซ็ตรหัสผ่านไม่ใช่ทางเลี่ยงแอป authenticator
- บันทึก audit `auth.password_reset`

## หน้าเว็บ

| หน้า | ที่อยู่ | ทำอะไร |
|---|---|---|
| สมัครสมาชิก | `/register` | ยืนยันเบอร์ด้วยรหัส OTP แล้วตั้งชื่อและรหัสผ่าน |
| ลืมรหัสผ่าน | `/forgot-password` | ขอลิงก์ตั้งรหัสผ่านใหม่ด้วยอีเมลหรือเบอร์ |
| ตั้งรหัสผ่านใหม่ | `/reset-password#token=...` | หน้าที่ลิงก์ในอีเมลหรือ SMS เปิด |

ทั้งสามหน้าใช้กรอบเดียวกับ `/login` คือรูปสไลด์ด้านซ้ายบนจอใหญ่ และฟอร์มด้านขวา บนมือถือเหลือแค่โลโก้กับฟอร์ม ลิงก์ "ลืมรหัสผ่าน?" และ "สมัครสมาชิก" ในหน้าเข้าสู่ระบบ กับปุ่ม "สมัครใช้งานฟรี" บนหัวเว็บ ชี้มาที่หน้าเหล่านี้แล้ว

### สมัครสมาชิก

1. **ใส่เบอร์** หน้าเว็บตรวจว่ามี 9 ถึง 15 หลักก่อน แล้วเรียก `POST /auth/otp/request` ด้วย `purpose: "register"`
2. **ใส่รหัสและข้อมูล** รหัส 6 หลัก ชื่อที่ให้คลินิกเรียก อีเมล (ไม่บังคับ) และรหัสผ่านสองครั้ง แล้วเรียก `POST /auth/register`

```json
{ "phone": "0812345678", "code": "482913", "display_name": "คุณสมใจ", "password": "...", "email": "somjai@example.com" }
```

- **หน้าเว็บบังคับตั้งรหัสผ่าน** แม้ backend ไม่บังคับ เพราะหน้า `/login` ยังเข้าสู่ระบบได้ด้วยรหัสผ่านเท่านั้น บัญชีที่ไม่มีรหัสผ่านจะกลับเข้ามาทางเว็บไม่ได้
- **ช่องรหัสรับเว้นวรรค** พิมพ์หรือวาง "162 544" ได้ ระบบตัดเว้นวรรคด้วย `oneTimeCodeDigits` ก่อนส่ง
- **บอกเวลาหมดอายุ** จาก `expires_at` ที่ backend ตอบ เป็นเวลาคลินิก
- **ปุ่มส่งรหัสอีกครั้ง** กดได้อีกครั้งหลัง 60 วินาที กันการกดซ้ำที่เผาโควตา 3 ครั้งต่อ 10 นาทีของ backend เกินโควตาแล้วแสดงข้อความ `429` ของ backend ตามที่ส่งมา
- **เปลี่ยนเบอร์** กลับไปขั้นที่ 1 และต้องขอรหัสใหม่ เพราะรหัสผูกกับเบอร์
- **ไม่มีคำใบ้เรื่องรหัสใน log บนหน้าเว็บ** คำตอบของ `POST /auth/otp/request` มีแค่ `expires_at` ไม่ได้บอกว่าส่ง SMS จริงหรือเขียนลง log หน้าเว็บจึงไม่เดา นักพัฒนาดูรหัสตามหัวข้อ "ลองบนเครื่องตัวเอง" ด้านล่าง
- **สมัครสำเร็จ** server action เขียน token ลงคุกกี้ httpOnly แบบเดียวกับการเข้าสู่ระบบ แล้วพาไป `/portal` token และรหัสผ่านไม่เคยถูกส่งกลับไปที่เบราว์เซอร์ ถ้าคำตอบไม่มี token หรือไม่มีคุกกี้ refresh จะพาไป `/login?notice=registered` ซึ่งแสดงว่าสมัครแล้วให้เข้าสู่ระบบ
- **ข้อผิดพลาด** ที่ backend ระบุช่อง เช่น รหัสผิดที่ `code` แสดงใต้ช่องนั้น ส่วน `409 contact_taken` แสดงด้านบนฟอร์ม
- คนที่เข้าสู่ระบบอยู่แล้วเปิด `/register` ถูกพาไปหน้าของบัญชีตัวเอง เหมือน `/login`
- ใต้ปุ่มสมัครมีลิงก์ไป `/privacy`

### ลืมรหัสผ่าน

- ช่องเดียว รับอีเมลหรือเบอร์ ส่ง `{ "identifier": "..." }`
- **ข้อความหลังส่งเหมือนกันทุกครั้ง** ไม่ว่ามีบัญชีหรือไม่ ตรงกับคำตอบ `202 link_sent` ของ backend
- ข้อความผิดพลาดมีแค่กรณีที่ไม่เกี่ยวกับบัญชี คือเรียก API ไม่ได้ คำขอถี่เกิน หรือค่าที่ส่งผิดรูป
- ปุ่ม "ขอลิงก์อีกครั้ง" เปิดฟอร์มใหม่

### ตั้งรหัสผ่านใหม่

- **token อยู่หลัง `#`** เบราว์เซอร์ไม่ส่งส่วนนี้ไปที่เซิร์ฟเวอร์ หน้าเว็บจึงอ่านเองใน hook `useLinkToken` (`window.location.hash`) แล้วลบออกจากแถบที่อยู่ทันที ไม่ให้ค้างในประวัติหรือภาพหน้าจอ ถ้าโหลดหน้าใหม่หลังจากนั้น จะเห็นข้อความว่าลิงก์ใช้ไม่ได้พร้อมปุ่มขอลิงก์ใหม่
- กรอกรหัสใหม่สองครั้ง หน้าเว็บตรวจความยาวและว่าตรงกันก่อน แล้ว server action ส่ง `{ "token": "...", "new_password": "..." }`
- `422` ที่ช่อง `token` (ลิงก์ผิด ใช้แล้ว หรือหมดอายุ) แสดงหน้า "ลิงก์นี้ใช้ไม่ได้" พร้อมปุ่มไป `/forgot-password`
- สำเร็จแล้วมีปุ่มไป `/login` หน้านี้ไม่สร้าง session
- หน้านี้ตั้ง `noindex` เพราะเปิดจากลิงก์ส่วนตัวเท่านั้น

## เข้าสู่ระบบจากการจอง

หน้า `/book` ให้คนที่ยังไม่มีบัญชีจองได้เลย (ส่วนขยาย § 27) ขั้นสุดท้ายของการจองคือการพิสูจน์เบอร์ ซึ่งเป็นทางที่สามที่ได้ session นอกจากการสมัครและการเข้าสู่ระบบ

1. `POST /booking/guest/start` กันเวลาและส่งรหัสจุดประสงค์ `booking` ไปทุกเบอร์ แบบเดียวกับรหัส `register` คำตอบเหมือนกันทุกเบอร์
2. `POST /booking/guest/verify` ตรวจรหัส แล้วจึงดูว่าเบอร์เป็นของใคร เบอร์ที่มีบัญชีลูกค้าเข้าสู่ระบบบัญชีนั้น เบอร์ที่เคาน์เตอร์รู้จักได้บัญชีที่ผูกกับเรกคอร์ดเดิม (`CustomerRecordLinker` ตัวเดียวกับการสมัคร) เบอร์ใหม่ได้บัญชีและเรกคอร์ดใหม่ ได้ access token ในคำตอบและคุกกี้ refresh เหมือนการเข้าสู่ระบบ

- เบอร์ของบัญชีพนักงาน บัญชีที่ถูกระงับ และบัญชีที่เปิด 2FA ได้ `409 contact_taken` หลังรหัสถูกแล้ว ไม่มี session ออก เพราะทางนี้มีแค่รหัส SMS
- บัญชีที่เปิดจากทางนี้ไม่มีรหัสผ่าน หน้า `/login` ยังรับแค่รหัสผ่าน คนกลุ่มนี้กลับเข้ามาได้ด้วยการจองที่ `/book` อีกครั้ง หรือ "ลืมรหัสผ่าน" ซึ่งส่งลิงก์ทาง SMS เมื่อบัญชีไม่มีอีเมล
- บัญชีที่เปิดจากทางนี้มีหลักฐานการยอมรับนโยบายความเป็นส่วนตัวในสมุดความยินยอม (`service_messages` และ `marketing` ถ้าติ๊ก พร้อมเลขฉบับ) ต่างจาก `/register`
- audit `auth.registered` พร้อม `via: "guest_booking"`

## ลองบนเครื่องตัวเอง

1. เปิด API ตาม [เริ่มต้นใช้งาน](../getting-started.md)
2. `POST /v1/auth/otp/request` ด้วยเบอร์ใดก็ได้และ `purpose: "register"`
3. ดูรหัสใน Terminal ที่รัน API บรรทัด `Development only. OTP for 0812345678: 482913`
4. `POST /v1/auth/register` ด้วยเบอร์และรหัสนั้น

## ข้อจำกัดที่รู้อยู่

- ตัวส่ง SMS ผ่าน ThaiBulkSMS ทดสอบกับเซิร์ฟเวอร์จำลองเท่านั้น ต้องลองส่งจริงด้วยบัญชีของคลินิกก่อนเปิดใช้
- ยังไม่มีหน้าเข้าสู่ระบบด้วยรหัส OTP หน้าสมัครจึงบังคับตั้งรหัสผ่าน
- หน้าสมัครไม่ได้บันทึกความยินยอม หรือเวอร์ชันของนโยบายความเป็นส่วนตัวที่แสดงตอนสมัคร มีแค่ลิงก์ให้อ่าน (การเปิดบัญชีจากหน้า `/book` บันทึกแล้ว)
- รหัส OTP เก็บเป็น hash แต่มีแค่ล้านแบบ ถ้าฐานข้อมูลหลุดไปพร้อมรหัสที่ยังไม่หมดอายุ hash ไม่ได้กันการเดา สิ่งที่กันจริงคืออายุ 5 นาที
- แถวของรหัสที่หมดอายุไม่ถูกลบ จนกว่าจะมีงานเบื้องหลัง
- ไม่มีการล็อกบัญชีเมื่อใส่รหัสผ่านผิดซ้ำ ด่านเดียวคือ rate limit รวม
