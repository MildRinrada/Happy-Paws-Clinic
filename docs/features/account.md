# บัญชีของตัวเอง

สิ่งที่ทุกบัญชีทำกับตัวเองได้ คือแก้ชื่อ อีเมล เบอร์ ภาษา และช่องทางรับข้อความ ตั้งปัจจัยที่สองเอง และสิ่งที่ผู้ดูแลทำกับบัญชีคนอื่นได้ คือพักหรือปิดบัญชี

ส่วนที่ contract ไม่ได้เขียนไว้และเราตีความเอง อยู่ใน [ข้อสมมติ § 34 และ § 35](../assumptions.md) การเข้าสู่ระบบและเซสชันอยู่ใน [การยืนยันตัวตน](../authentication.md)

## Endpoint

| Method | Endpoint | สิทธิ์ | ทำอะไร |
|---|---|---|---|
| GET | `/me` | เข้าสู่ระบบแล้ว | โปรไฟล์ สมาชิกภาพ scope สถานะ 2FA ภาษา ช่องทางรับข้อความ และ `version` |
| PATCH | `/me` | เข้าสู่ระบบแล้ว | แก้ข้อมูลของตัวเอง |
| POST | `/me/password` | เข้าสู่ระบบแล้ว | เปลี่ยนรหัสผ่าน และเพิกถอนเซสชันอื่นทั้งหมด |
| POST | `/me/2fa/enroll` | เข้าสู่ระบบแล้ว | ตั้งหรือเปลี่ยนปัจจัยที่สอง |
| PATCH | `/staff/users/{id}/status` | `user:manage` และผ่าน 2FA | พัก เปิด หรือปิดบัญชีของคนอื่น |

## แก้ข้อมูลของตัวเอง

```http
PATCH /v1/me
{
  "display_name": "สพ.ญ. มินท์ ศรีสุข",
  "email": "mint@happypaws.co.th",
  "phone": "081-234-5678",
  "language": "th",
  "notifications": { "email": true, "sms": false, "line": true },
  "current_password": "..."
}
```

ส่งเฉพาะช่องที่เปลี่ยน คำตอบเป็นโปรไฟล์แบบเดียวกับ `GET /me`

| ช่อง | กติกา |
|---|---|
| `display_name` | 1 ถึง 200 ตัวอักษร ชื่อนี้ขึ้นในเวชระเบียนที่ลงนามต่อจากนี้ |
| `email` | **ต้องส่ง `current_password` ด้วย** เก็บเป็นตัวพิมพ์เล็ก ใช้เข้าสู่ระบบทันทีหลังเปลี่ยน |
| `phone` | **ต้องส่ง `current_password` ด้วย** เก็บเป็นตัวเลขล้วน 9 ถึง 15 หลัก ส่งค่าว่างเพื่อลบ |
| `language` | `th` หรือ `en` |
| `notifications` | `email`, `sms`, `line` แต่ละช่องเป็นเปิดหรือปิด ช่องที่ไม่ส่งคงค่าเดิม |

**ทำไมอีเมลและเบอร์ต้องใช้รหัสผ่าน** อีเมลคือสิ่งที่พนักงานใช้เข้าสู่ระบบ และเบอร์คือสิ่งที่ลูกค้าจะใช้ คนที่ได้ access token ของคนอื่นไปช่วงสั้น ๆ ต้องเปลี่ยนสองอย่างนี้ไปเป็นของตัวเองแล้วยึดบัญชีไม่ได้ ชื่อ ภาษา และช่องทางรับข้อความไม่เกี่ยวกับการเข้าสู่ระบบ จึงไม่ต้องใช้รหัสผ่าน

- อีเมลหรือเบอร์ที่บัญชีอื่นใช้อยู่ ตอบ `409 contact_taken`
- รหัสผ่านปัจจุบันไม่ถูกหรือไม่ได้ส่ง ตอบ `422` ที่ `current_password`
- ส่ง `If-Match` ด้วย `version` จาก `GET /me` ได้ ถ้าบัญชีถูกแก้ไปก่อนแล้วได้ `409 version_conflict`
- ทุกการแก้บันทึก audit `account.profile_updated` พร้อมชื่อช่องที่เปลี่ยน ถ้าเปลี่ยนอีเมล บันทึกทั้งอีเมลเก่าและใหม่

**ช่องทางรับข้อความ** ตอนนี้ถูกเก็บและแสดงเท่านั้น ตัวส่งข้อความยังไม่ได้อ่านค่านี้ สิ่งที่กันข้อความจริงยังเป็นความยินยอมรายวัตถุประสงค์ ดู [ความยินยอมและข้อมูลส่วนบุคคล](privacy-and-consent.md)

## ตั้งปัจจัยที่สองเอง

ทำสองขั้น ปัจจัยที่สองยังไม่ถูกเปิดจนกว่าจะพิสูจน์ว่าแอปสร้างรหัสได้จริง คนที่ปิดหน้าไปก่อนสแกน QR จึงไม่ถูกล็อกออกจากบัญชี

**ขั้นที่ 1** ส่งรหัสผ่านปัจจุบัน

```http
POST /v1/me/2fa/enroll
{ "current_password": "..." }
```

```json
{ "status": "confirmation_required", "secret": "JBSWY3DP...", "otp_auth_uri": "otpauth://totp/..." }
```

ใส่ `secret` ในแอป authenticator หรือแปลง `otp_auth_uri` เป็น QR code ให้สแกน เรียกขั้นนี้ซ้ำได้ความลับเดิม หน้าที่ถูกโหลดใหม่จึงไม่ทำให้ QR ที่สแกนไปแล้วใช้ไม่ได้

**ขั้นที่ 2** ส่งรหัส 6 หลักจากแอป

```http
POST /v1/me/2fa/enroll
{ "code": "123456" }
```

```json
{ "status": "enabled", "recovery_codes": ["3f9a2-c81d0", "..."] }
```

- **recovery code แสดงครั้งเดียว** 8 รหัส ให้ผู้ใช้จดหรือพิมพ์เก็บไว้ ระบบเก็บแค่ค่า hash
- เซสชันที่ใช้ลงทะเบียนนับว่าผ่าน 2FA แล้ว refresh ต่อได้ตามปกติ เซสชันอื่นของบัญชีเดียวกันที่ยังไม่ผ่าน 2FA จะ refresh ไม่ได้และต้องเข้าสู่ระบบใหม่
- การเข้าสู่ระบบครั้งถัดไปถามรหัสจากแอปทุกครั้ง
- คำตอบมี `Cache-Control: no-store` เพราะความลับและ recovery code คือ credential
- บันทึก audit `auth.two_factor_enrolled`

**ข้อผิดพลาด**

| กรณี | คำตอบ |
|---|---|
| รหัสผ่านไม่ถูกในขั้นที่ 1 | `422` ที่ `current_password` |
| ส่งรหัสโดยไม่ได้เริ่มขั้นที่ 1 | `409 state_conflict` |
| รหัสจากแอปไม่ถูกหรือหมดอายุ | `422` ที่ `code` |
| เปลี่ยนปัจจัยที่สองที่ใช้อยู่ จากเซสชันที่ยังไม่ผ่านปัจจัยเดิม | `403` |

**ใช้ recovery code** ตอนเข้าสู่ระบบ ส่ง recovery code แทนรหัส 6 หลักที่ `POST /auth/2fa/verify` ได้เลย รูปแบบ `xxxxx-xxxxx` พิมพ์ตัวใหญ่หรือเล็กก็ได้ แต่ละรหัสใช้ได้ครั้งเดียว ทุกครั้งที่ใช้บันทึก audit `auth.recovery_code_used` และ `GET /me` บอกจำนวนที่เหลือใน `two_factor.recovery_codes_left` การลงทะเบียนใหม่ออก recovery code ชุดใหม่แทนชุดเดิมทั้งหมด

## พักหรือปิดบัญชีของคนอื่น

```http
PATCH /v1/staff/users/usr_.../status
{ "status": "suspended" }
```

| สถานะ | ความหมาย |
|---|---|
| `active` | เข้าสู่ระบบได้ตามปกติ |
| `suspended` | พักไว้ชั่วคราว เปลี่ยนกลับเป็น `active` ได้ |
| `deactivated` | ปิดถาวร เปลี่ยนกลับด้วย endpoint นี้ไม่ได้ |

- สถานะที่ไม่ใช่ `active` เพิกถอนทุกเซสชันทันที เข้าสู่ระบบ ผ่าน 2FA และ refresh ไม่ได้อีก access token ที่ออกไปแล้วยังใช้ได้จนหมดอายุ ไม่เกิน 15 นาที
- ใช้ได้ทั้งบัญชีพนักงานและลูกค้า ต่างจาก `POST /staff/members/{id}/deactivate` ที่จบการเป็นพนักงาน แต่บัญชียังอยู่
- ถ้าเป็นบัญชีพนักงาน ใช้กติกาเดียวกับการแก้พนักงาน คือผู้เรียกที่ผูกกับสาขาเปลี่ยนได้เฉพาะคนในสาขาของตัวเอง และเปลี่ยนคนที่มีสิทธิ์มากกว่าตัวเองไม่ได้ (`403`)
- พักบัญชีสุดท้ายที่ถือ `*` ไม่ได้ (`409 last_owner`) และเปลี่ยนสถานะของตัวเองไม่ได้ (`409 cannot_deactivate_self`)
- บันทึก audit `user.status_changed` พร้อมสถานะก่อนและหลัง
- `user:manage` เป็น scope ระดับสูง ผู้เรียกต้องผ่าน 2FA ในเซสชันนั้น

## ข้อจำกัดที่รู้อยู่

- ยังไม่มีหน้าจอสำหรับเรื่องเหล่านี้
- เปลี่ยนอีเมลแล้วไม่มีการส่งอีเมลยืนยันไปที่อยู่ใหม่ เพราะยังไม่มีตัวส่งอีเมล
- เจ้าของที่สร้างด้วย `bootstrap` และพนักงานที่รับคำเชิญยังไม่มี recovery code จนกว่าจะลงทะเบียนเองหนึ่งครั้ง
- ความลับ TOTP ยังเก็บในฐานข้อมูลโดยไม่เข้ารหัส ดู [ข้อมูลและความลับ](../security/data-and-secrets.md)
- `POST /me/password` ตอบรหัสผ่านเดิมผิดด้วย `401` ส่วน endpoint ใหม่ตอบ `422` ควรทำให้ตรงกัน
