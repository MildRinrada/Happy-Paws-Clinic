# ประกาศความเป็นส่วนตัวของคลินิก

คลินิกเป็นผู้ควบคุมข้อมูลส่วนบุคคลตาม PDPA จึงต้องเป็นผู้เขียนและเผยแพร่ประกาศความเป็นส่วนตัวของตัวเอง ฟีเจอร์นี้ให้คลินิกเขียนประกาศในหน้าตั้งค่า เก็บทุกฉบับที่เผยแพร่ไว้แบบแก้ไม่ได้ และบันทึกเลขฉบับที่มีผลอยู่ไว้กับทุกความยินยอม คลินิกจึงตอบได้เสมอว่าลูกค้ายินยอมตอนที่ประกาศเขียนว่าอะไร

ก่อนมีฟีเจอร์นี้ ถ้อยคำของประกาศเขียนตายตัวในโค้ดหน้าเว็บ และระบบไม่ได้เก็บถ้อยคำของแต่ละฉบับไว้เลย ฟีเจอร์นี้ไม่อยู่ใน contract เป็นส่วนขยายที่อนุมัติแล้ว เหตุผลและทางเลือกที่ไม่เลือกอยู่ใน [ส่วนขยายของสัญญา ข้อ 35](../contract-extensions.md)

## ใครใช้ ใช้ทำอะไร

| ใคร | ทำอะไรได้ |
|---|---|
| ทุกคน | อ่านประกาศฉบับปัจจุบันที่ `/privacy` และฉบับก่อนหน้าที่ `/privacy/versions/{เลขฉบับ}` |
| พนักงานที่ถือ `settings:read` | ดูทุกฉบับรวมร่าง ที่แท็บ "ประกาศความเป็นส่วนตัว" ในหน้าตั้งค่า (`/settings/privacy-policy`) |
| พนักงานที่ถือ `settings:write` เช่น `clinic_admin` | สร้างร่างจาก template จากฉบับปัจจุบัน หรือจากฉบับใดก็ได้ และแก้ร่าง |
| เจ้าของคลินิก (`settings:danger`) | เผยแพร่ร่างเป็นฉบับใหม่ |

`clinic_admin` ไม่ได้ `settings:danger` ตาม role ตั้งต้น การเผยแพร่จึงเป็นของเจ้าของคลินิกคนเดียว และต้องผ่าน 2FA เพราะ `settings:danger` อยู่ในรายการ scope ที่ต้องยืนยันสองขั้น API key ถือ scope นี้ไม่ได้

## ฉบับ ร่าง และฉบับปัจจุบัน

- **ร่าง** แก้ได้เรื่อย ๆ ไม่มีใครนอกคลินิกเห็น ร่างไม่มีเลขฉบับ
- **ฉบับที่เผยแพร่แล้ว** มีเลขฉบับ วันที่มีผล เวลาเผยแพร่ และผู้เผยแพร่ แก้หรือเผยแพร่ซ้ำไม่ได้ (`409 state_conflict`) ถ้าจะเปลี่ยนถ้อยคำ ให้สร้างร่างใหม่จากฉบับนั้นแล้วเผยแพร่เป็นฉบับใหม่
- **ฉบับปัจจุบัน** คือฉบับที่เผยแพร่ล่าสุด หน้า `/privacy` แสดงฉบับนี้ และความยินยอมที่บันทึกใหม่ได้เลขฉบับนี้
- ไม่มีอะไรถูกลบ ทั้งร่างและฉบับเก่า

## template ที่มากับระบบ

ระบบมี template ประกาศที่ผู้พัฒนาเขียนจากสิ่งที่ระบบทำจริง อยู่ในโค้ดที่ `PrivacyPolicyTemplate` พร้อมเลขรุ่นของตัวเอง ตอนนี้คือ `2026-10-template-1`

- **migration `ClinicPrivacyPolicy` ใส่ template เป็นร่างเท่านั้น** (id `ppv_seed_template`) ไม่เผยแพร่ให้ เจ้าของงานตัดสินแล้วว่าระบบต้องไม่พูดแทนคลินิก ประกาศจึงขึ้นเว็บเมื่อเจ้าของคลินิกกดเผยแพร่เองเท่านั้น
- migration ใส่ template ตามที่อยู่ในโค้ดตอนที่ migration รัน คลินิกที่ติดตั้งใหม่ในอนาคตจึงได้ template รุ่นที่มากับระบบรุ่นนั้น
- template คือถ้อยคำเดิมที่เคยเขียนตายตัวในหน้าเว็บ แปลงเป็นรูปแบบใหม่ และเพิ่มหัวข้อ "ผู้ช่วย AI" ซึ่งบอกว่าผู้ช่วยของพนักงาน ([ผู้ช่วย AI สำหรับพนักงาน](staff-ai.md)) ส่งข้อมูลทางการรักษาให้ผู้ให้บริการโมเดลที่ผู้ให้บริการระบบตั้งค่า เช่น Google Gemini ซึ่งอาจอยู่นอกประเทศ หรือโมเดลที่รันเอง หลังแทนชื่อ เบอร์โทร อีเมล และเลขบัตรประชาชนแล้ว และเมื่อใช้บริการแบบเสียเงิน ข้อมูลไม่ถูกนำไปฝึกโมเดล
- หัวข้อแรกของหน้า "ใครดูแลข้อมูลของคุณ" ไม่อยู่ใน template หน้าเว็บสร้างจาก `GET /clinic` และ `GET /clinic/contacts` เหมือนเดิม ชื่อจุดเชื่อม `controller` จึงสงวนไว้
- **ร่างที่สร้างจาก template มีกล่องเตือนในหน้าแก้** ว่าเป็นถ้อยคำของผู้พัฒนาระบบ ไม่ใช่คำแนะนำทางกฎหมาย และควรให้นักกฎหมายตรวจก่อนเผยแพร่

**เมื่อระบบรุ่นใหม่มี template ใหม่** ผู้พัฒนาแก้ถ้อยคำและเลขรุ่นใน `PrivacyPolicyTemplate` หน้าตั้งค่าจะขึ้นกล่อง "มี template ฉบับใหม่" เมื่อยังไม่มีฉบับใดในระบบที่มาจาก template รุ่นนั้น (ดูจาก `template_version` ซึ่งคัดลอกต่อกันเมื่อสร้างร่างจากฉบับอื่น) พนักงานกด "สร้างร่างจาก template" แล้วเทียบกับฉบับปัจจุบันเอง ระบบไม่เปลี่ยนประกาศของคลินิกเอง

## รูปแบบของเนื้อหา

แต่ละหัวข้อมีสามช่อง คือชื่อจุดเชื่อม (`anchor`) ชื่อหัวข้อ (`heading`) และเนื้อหา (`body`) เนื้อหาเป็นข้อความล้วนแบบเดียวกับบทความ ไม่ใช่ Markdown หรือ HTML มีกติกาแค่สามข้อ

| เขียนแบบนี้ | ได้อะไร |
|---|---|
| เว้นบรรทัดว่าง | ขึ้นย่อหน้าใหม่ บรรทัดที่ติดกันรวมเป็นย่อหน้าเดียว |
| บรรทัดขึ้นต้นด้วย `- ` (ขีดกลางแล้วเว้นวรรค) | รายการ บรรทัดรายการที่ติดกันเป็นรายการเดียว |
| `[ข้อความ](/portal/account)` | ลิงก์ไปหน้าในเว็บของคลินิก ย่อหน้าที่มีแค่ลิงก์เดียวแสดงเป็นปุ่ม |

```text
ตาม PDPA คุณมีสิทธิ์เหล่านี้

- ขอดูหรือขอสำเนาข้อมูล
- ขอแก้ไขข้อมูลที่ไม่ถูกต้อง

[จัดการข้อมูลและความยินยอมของฉัน](/portal/account)
```

**ตรวจตอนบันทึก** (`PrivacyPolicyRules`, `PrivacyPolicyText`) ผิดได้ `422 validation_failed` ช่องที่ผิดเขียนเป็น path เช่น `sections[2].body`

| กติกา | ค่า |
|---|---|
| จำนวนหัวข้อ | 1 ถึง 30 |
| ชื่อจุดเชื่อม | ตัวพิมพ์เล็กภาษาอังกฤษ ตัวเลข และขีดกลางคั่นคำ ขึ้นต้นด้วยตัวอักษร ยาวไม่เกิน 40 ตัว ห้ามซ้ำกันในฉบับเดียว ห้ามใช้ `controller` |
| ชื่อหัวข้อ | 1 ถึง 150 ตัวอักษร บรรทัดเดียว |
| เนื้อหา | ไม่เกิน 10,000 ตัวอักษรต่อหัวข้อ ต้องมีอย่างน้อยหนึ่งย่อหน้าหรือรายการ |
| HTML | ห้าม อะไรที่หน้าตาเป็นแท็ก เช่น `<a`, `</p`, `<!--` ถูกปฏิเสธ ส่วน "อุณหภูมิ < 39" ใช้ได้ |
| ลิงก์ | ต้องขึ้นต้นด้วย `/` ตัวเดียว เป็นหน้าในเว็บของคลินิก ลิงก์ไปเว็บอื่น `//` `mailto:` หรือ `javascript:` ถูกปฏิเสธ ที่อยู่เว็บที่พิมพ์เป็นข้อความธรรมดาใช้ได้ แต่ไม่กลายเป็นลิงก์ |
| รายการ | บรรทัดที่มีแค่ `-` ถูกปฏิเสธ |

ข้อความถูกทำความสะอาดแบบเดียวกับบทความก่อนเก็บ คือตัดอักขระควบคุม อักขระสลับทิศทาง และรวมบรรทัดว่างที่ติดกัน

**ตัวอ่านเข้มงวดของมันเองด้วย** หน้าเว็บอ่านเนื้อหาด้วย `frontend/src/features/privacy/lib/policy-body.ts` ซึ่งทำตามกติกาเดียวกับ `PrivacyPolicyText.Parse` ฝั่ง backend ลิงก์ที่ไม่ใช่ path ของเว็บแสดงเป็นตัวอักษรตามที่พิมพ์ และทุกอย่างเป็น text node ถ้าแก้กติกา ต้องแก้ทั้งสองที่พร้อมกัน

## เผยแพร่

เจ้าของคลินิกกรอกสามอย่าง และติ๊กยืนยันว่าเข้าใจว่าแก้ไม่ได้

| ช่อง | กติกา |
|---|---|
| `label` เลขฉบับ | ตัวอักษรภาษาอังกฤษ ตัวเลข จุด ขีดล่าง และขีดกลาง ขึ้นต้นด้วยตัวอักษรหรือตัวเลข ยาวไม่เกิน 32 ตัว เช่น `2026-11` ห้ามซ้ำกับฉบับที่เผยแพร่แล้ว (`409 privacy_policy_label_taken`) และห้ามใช้ `2026-10` ซึ่งเป็นฉบับเดิมในโค้ดหน้าเว็บ (`422`) |
| `effective_date` วันที่มีผล | `yyyy-MM-dd` วันนี้ตามเวลาคลินิกหรือหลังจากนี้ ก่อนวันนี้ได้ `422` |
| `legal_review_done` | เจ้าของคลินิกบอกว่านักกฎหมายตรวจถ้อยคำฉบับนี้แล้ว |

- **ฉบับที่เผยแพร่เป็นฉบับปัจจุบันทันทีที่กด** ไม่ว่าวันที่มีผลจะเป็นวันไหน วันที่มีผลคือวันที่พิมพ์บนหน้า ไม่ใช่การตั้งเวลา เลือกแบบนี้เพราะง่ายและไม่มีช่วงที่ระบบต้องตัดสินว่าฉบับไหนมีผล ถ้าต้องการประกาศล่วงหน้า ให้แจ้งลูกค้าก่อนแล้วค่อยกดเผยแพร่ในวันนั้น
- **กล่องเตือนเรื่องนักกฎหมายบนหน้าสาธารณะ** แสดงเมื่อฉบับที่เผยแพร่มี `legal_review_done` เป็น `false` เปลี่ยนค่าในฉบับเดิมไม่ได้ ถ้านักกฎหมายตรวจทีหลัง ให้เผยแพร่ฉบับใหม่ที่ติ๊กไว้
- ต้องส่ง `If-Match` ด้วย version ของร่างที่อ่าน เพื่อให้สิ่งที่เผยแพร่คือสิ่งที่เจ้าของคลินิกเห็น
- หน้าแก้ไม่ให้กดเผยแพร่ถ้ามีการแก้ที่ยังไม่บันทึก

## การบันทึกเลขฉบับไว้กับความยินยอม

**ระบบใส่เลขฉบับเอง** ทุกครั้งที่บันทึกความยินยอม `RecordConsentHandler` อ่านเลขฉบับปัจจุบันใน transaction เดียวกันแล้วเก็บใน `policy_version` ของแถว ใช้กับทุกทาง คือ `PUT /portal/consents`, `POST /staff/customers/{id}/consents` และการเปิดบัญชีจากหน้าจอง `POST /booking/guest/verify`

- ช่อง `policy_version` ในคำขอของทั้งสามเส้นยังรับอยู่เพื่อไม่ให้ client เดิมพัง แต่ไม่ถูกใช้และไม่ถูกเก็บ ค่าที่ client ส่งไม่ได้พิสูจน์ว่าลูกค้าเห็นอะไร `POST /booking/guest/verify` ยังตรวจว่ายาวไม่เกิน 32 ตัวอักษรเหมือนเดิม หน้าเว็บเลิกส่งช่องนี้แล้ว
- **ยังไม่มีฉบับที่เผยแพร่ ความยินยอมยังถูกบันทึก** โดย `policy_version` ว่าง การดูแลรักษาและข้อความเรื่องการรักษาต้องไม่หยุดเพราะเอกสารยังไม่เสร็จ และค่าว่างบอกตามจริงว่าตอนนั้นยังไม่มีประกาศที่เผยแพร่
- audit `consent.recorded` และ `consent.withdrawn` มี `policy_version` ใน details ด้วย

**ความยินยอมเก่าที่มี `policy_version = "2026-10"`** หมายถึงถ้อยคำที่เคยเขียนตายตัวในหน้าเว็บก่อนฟีเจอร์นี้ ระบบไม่สร้างแถวฉบับ `2026-10` ย้อนหลัง เพราะจะเป็นการสร้างหลักฐานขึ้นเอง ถ้าลูกค้าถามถึงฉบับนั้น ถ้อยคำอยู่ในประวัติ git ที่ไฟล์ `frontend/src/features/privacy/content/privacy-policy.ts` ไฟล์นี้ถูกเพิ่มใน commit `27cf747` (2026-10-04) และไม่ถูกแก้อีกจนถึง commit `f8ce844` ทุกความยินยอมที่มี `2026-10` จึงหมายถึงถ้อยคำชุดเดียวกัน เปิดดูได้ด้วย `git show 27cf747:frontend/src/features/privacy/content/privacy-policy.ts` ส่วนที่เป็นประกาศคือ `privacySections` (ข้อความแต่ละหัวข้อ) `policyVersion` (เลขฉบับและวันที่มีผล 4 ตุลาคม 2569) `reviewNotice` (กล่องเตือนว่ายังไม่ผ่านนักกฎหมาย) และ `controllerSection` ส่วนข้อมูลคลินิกในหัวข้อแรกตอนนั้นมาจากค่าตั้งของคลินิก เลขฉบับนี้จึงถูกกันไว้ ไม่ให้ฉบับใหม่ใช้ซ้ำ

## หน้าเว็บ

**หน้า `/privacy`** อ่าน `GET /privacy-policy` และเก็บไว้ 60 วินาที การเผยแพร่จากหน้าตั้งค่าสั่งให้หน้าโหลดใหม่ทันที

- หัวข้อแรกคือข้อมูลคลินิกจาก `GET /clinic` และ `GET /clinic/contacts` เสมอ แล้วตามด้วยหัวข้อของฉบับที่เผยแพร่ สารบัญสร้างจากชื่อหัวข้อและจุดเชื่อม
- ด้านบนแสดง "มีผลตั้งแต่ วันที่ (ฉบับ เลขฉบับ)"
- เมื่อมีมากกว่าหนึ่งฉบับ ท้ายหน้ามีรายการฉบับที่ผ่านมา แต่ละฉบับเปิดได้
- **ยังไม่มีฉบับที่เผยแพร่** หน้าแสดงข้อมูลคลินิกและช่องทางติดต่อ พร้อมกล่องบอกว่าคลินิกยังไม่ได้เผยแพร่ประกาศ และปุ่มไปจัดการข้อมูลและความยินยอม ไม่แสดง template
- เรียก API ไม่ได้ หน้าแสดงข้อมูลคลินิกเท่าที่อ่านได้และบอกให้ลองใหม่ภายหลัง

**หน้า `/privacy/versions/{เลขฉบับ}`** แสดงฉบับที่เผยแพร่แล้วตามเลขฉบับ ฉบับที่ไม่ใช่ฉบับปัจจุบันมีกล่องบอกและลิงก์ไปฉบับปัจจุบัน ร่างหรือเลขที่ไม่มีได้หน้า 404 หน้านี้ตั้ง `noindex` ให้ search engine ส่งคนไปฉบับปัจจุบัน

**หน้า `/settings/privacy-policy`**

- กล่องสีแดงเมื่อยังไม่มีฉบับที่เผยแพร่ กล่องสีฟ้าเมื่อมี template รุ่นใหม่
- ปุ่ม "สร้างร่างจากฉบับปัจจุบัน" (มีเมื่อเผยแพร่แล้ว) และ "สร้างร่างจาก template"
- รายการทุกฉบับพร้อมสถานะ ร่าง เผยแพร่แล้ว หรือฉบับปัจจุบัน
- หน้าแก้ร่าง (`/settings/privacy-policy/{id}`) เพิ่ม ลบ และเลื่อนหัวข้อ แก้ชื่อหัวข้อ ชื่อจุดเชื่อม และเนื้อหา มีตัวอย่างที่ใช้ตัวแสดงผลเดียวกับหน้าสาธารณะ และฟอร์มเผยแพร่เฉพาะผู้ถือ `settings:danger`
- ฉบับที่เผยแพร่แล้วเปิดแบบอ่านอย่างเดียว พร้อมปุ่มคัดลอกเป็นร่างใหม่

**หน้าภาพรวม `/dashboard`** มีแถบเล็ก ๆ "คลินิกยังไม่ได้เผยแพร่ประกาศความเป็นส่วนตัว" เฉพาะผู้ถือ `settings:danger` และเฉพาะตอนที่ยังไม่มีฉบับที่เผยแพร่

## Endpoint

| Method | Endpoint | สิทธิ์ | ทำอะไร |
|---|---|---|---|
| GET | `/privacy-policy` | สาธารณะ | ฉบับปัจจุบัน หรือ `published: false` |
| GET | `/privacy-policy/versions/{version}` | สาธารณะ | ฉบับที่เผยแพร่แล้วตามเลขฉบับ ร่างได้ `404` |
| GET | `/staff/privacy-policy/versions` | `settings:read` | ทุกฉบับรวมร่าง พร้อมเนื้อหา ฉบับปัจจุบัน และข้อมูล template |
| POST | `/staff/privacy-policy/versions` | `settings:write` | สร้างร่าง |
| PATCH | `/staff/privacy-policy/versions/{id}` | `settings:write` | แก้ร่าง ต้องส่ง `If-Match` |
| POST | `/staff/privacy-policy/versions/{id}/publish` | `settings:danger` | เผยแพร่ ต้องส่ง `If-Match` |

```http
GET /v1/privacy-policy                                  สาธารณะ

200 { "published": true, "label": "2026-11", "effective_date": "2026-11-01",
      "published_at": "2026-10-20T03:00:00+00:00", "legal_review_done": true, "is_current": true,
      "sections": [ { "anchor": "cookies", "heading": "คุกกี้", "body": "..." } ],
      "history": [ { "label": "2026-11", "effective_date": "2026-11-01", "published_at": "..." } ] }

200 { "published": false, "history": [] }               ยังไม่มีฉบับที่เผยแพร่

POST /v1/staff/privacy-policy/versions                  settings:write
{ "source": "template" }  หรือ  { "source": "current" }  หรือ  { "source": "version", "version_id": "ppv_..." }

201 { "id": "ppv_...", "status": "draft", "is_current": false, "legal_review_done": false,
      "created_from": "template", "template_version": "2026-10-template-1",
      "created_by_staff_id": "stf_...", "created_at": "...", "version": 8123, "sections": [ ... ] }

PATCH /v1/staff/privacy-policy/versions/ppv_...         settings:write, If-Match: "8123"
{ "sections": [ { "anchor": "cookies", "heading": "คุกกี้", "body": "ย่อหน้า\n\n- รายการ" } ] }

POST /v1/staff/privacy-policy/versions/ppv_.../publish  settings:danger, If-Match: "8130"
{ "label": "2026-11", "effective_date": "2026-11-01", "legal_review_done": true }
```

| เส้น | error |
|---|---|
| ทุกเส้นของพนักงาน | `401` ไม่ได้เข้าสู่ระบบ `403 insufficient_scope` ไม่มี scope |
| `POST .../versions` | `422` `source` ไม่ใช่ `template`, `current`, `version` หรือขอ `current` ตอนที่ยังไม่มีฉบับที่เผยแพร่ หรือไม่ส่ง `version_id` `404` ไม่พบฉบับที่จะคัดลอก |
| `PATCH .../versions/{id}` | `404` ไม่พบ `409 state_conflict` เผยแพร่แล้ว `422` ไม่ส่ง `If-Match` หรือเนื้อหาผิดกติกา `409 version_conflict` มีคนบันทึกก่อน |
| `POST .../publish` | `404` ไม่พบ `409 state_conflict` เผยแพร่แล้ว `409 privacy_policy_label_taken` เลขฉบับซ้ำ `422` เลขฉบับหรือวันที่ผิด หรือไม่ส่ง `If-Match` `409 version_conflict` ร่างถูกแก้หลังอ่าน |
| `GET /privacy-policy/versions/{version}` | `404` ไม่มีฉบับที่เผยแพร่ด้วยเลขนี้ |

สองเส้นสาธารณะตอบ `Cache-Control: public, max-age=60` เส้นรายการของพนักงานตอบ `no-store`

## ประวัติการทำงาน

| action | details |
|---|---|
| `privacy_policy.draft_created` | ที่มา (`source`) ฉบับที่คัดลอก รุ่น template และจำนวนหัวข้อ |
| `privacy_policy.draft_updated` | จำนวนหัวข้อและความยาวเนื้อหาก่อนและหลัง และรายชื่อจุดเชื่อม ไม่เก็บถ้อยคำ คำขอที่ไม่เปลี่ยนอะไรไม่เขียน |
| `privacy_policy.published` | เลขฉบับ วันที่มีผล `legal_review_done` ฉบับปัจจุบันก่อนหน้า รุ่น template และจำนวนหัวข้อ |

resource คือ `privacy_policy` ถ้อยคำของแต่ละฉบับอยู่ในตารางเอง จึงไม่ต้องคัดลอกลง audit log

## ตาราง

ตาราง `privacy_policy_versions` หนึ่งแถวต่อฉบับ หัวข้อเก็บเป็น `jsonb` ช่องเดียว (`sections`) เพราะอ่านและแทนทั้งชุดเสมอ check `ck_privacy_policy_versions_published_complete` บังคับว่าเผยแพร่แล้วต้องมีเลขฉบับ วันที่มีผล และเวลาเผยแพร่ครบ ร่างต้องไม่มีทั้งสาม unique `ix_privacy_policy_versions_label` กันเลขฉบับซ้ำ รวมกรณีกดเผยแพร่พร้อมกันสองคน ดู [ฐานข้อมูล](../database.md)

## ข้อจำกัด

- **ไม่มีการตั้งเวลาเผยแพร่** วันที่มีผลในอนาคตเป็นแค่วันที่พิมพ์บนหน้า
- **ไม่มีการลบร่าง** ร่างที่ไม่ใช้ค้างอยู่ในรายการ
- **ความไม่แก้ไขของฉบับที่เผยแพร่บังคับในโค้ด** (entity และ use case) ฐานข้อมูลยังไม่มี trigger กันการ UPDATE ตรง ๆ คนที่เข้าฐานข้อมูลได้ยังแก้แถวได้
- **ไม่มีการเทียบความต่าง** ระหว่างร่างกับฉบับปัจจุบัน หรือระหว่าง template สองรุ่น พนักงานต้องเทียบเอง
- **ไม่ได้ขอความยินยอมใหม่อัตโนมัติ** เมื่อเผยแพร่ฉบับใหม่ ความยินยอมเดิมยังอยู่กับเลขฉบับเดิม การแจ้งลูกค้าหรือขอใหม่เป็นการตัดสินของคลินิก
- template เป็นร่างที่ผู้พัฒนาเขียน ไม่ใช่คำแนะนำทางกฎหมาย
