# ความยินยอมและคำขอเรื่องข้อมูลส่วนบุคคล

คลินิกเก็บข้อมูลติดต่อของเจ้าของและข้อมูลสุขภาพของสัตว์ ภายใต้ PDPA คลินิกต้องพิสูจน์ได้ว่าลูกค้ายินยอมอะไร เมื่อไร และตอบคำขอเรื่องข้อมูลภายในเวลา contract ไม่มี endpoint เรื่องนี้เลย ทุก endpoint ในเอกสารนี้จึงเป็นส่วนขยาย ([contract-extensions.md](../contract-extensions.md) ข้อ 4)

เรื่องนี้มี 3 ส่วนที่แยกกัน คือ บันทึกความยินยอม ประตูกั้นก่อนส่งข้อความ และคำขอเรื่องข้อมูล

## วัตถุประสงค์ 4 อย่าง

ลูกค้ายินยอมและถอนความยินยอมแยกกันทีละวัตถุประสงค์

| ค่าที่เก็บ | ครอบคลุมอะไร | ค่าเริ่มต้น | เหตุผลของค่าเริ่มต้น |
|---|---|---|---|
| `service_messages` | ข้อความเรื่องการดูแลสัตว์ของลูกค้าเอง เช่น เรียกคิว สรุปการตรวจ ใบเสร็จ | ยินยอม | ลูกค้าให้เบอร์โทรไว้เพื่อให้คลินิกติดต่อเรื่องสัตว์ของตัวเอง ถ้าถือว่าไม่ยินยอม การเตือนนัดก็ส่งไม่ได้ |
| `marketing` | โปรโมชัน แคมเปญ จดหมายข่าว | ไม่ยินยอม | การตลาดต้องขอก่อนเสมอ |
| `medical_record_sharing` | ส่งเวชระเบียนให้คลินิกที่รับต่อหรือบริษัทประกัน | ไม่ยินยอม | |
| `extended_data_processing` | เก็บหรือใช้ข้อมูลเกินกว่าที่การรักษาต้องใช้ เช่น วิจัย สถิติรวม เก็บนานกว่าความจำเป็นทางการรักษา | ไม่ยินยอม | |

ค่าเริ่มต้นชี้ไปทางเดียวที่ป้องกันได้ คือเปิดเฉพาะข้อความเรื่องการดูแล ที่เหลือปิดจนกว่าจะมีคนบอกว่าเปิด

## ความยินยอมเป็นสมุดบันทึก ไม่ใช่สวิตช์

- **ทุกการยินยอมและทุกการถอนเป็นแถวใหม่** ไม่แก้แถวเดิม ค่าปัจจุบันของแต่ละวัตถุประสงค์คือแถวล่าสุด ถ้าเวลาเท่ากันใช้รหัสแถวตัดสิน (รหัสเรียงตามเวลา) สวิตช์ที่แก้ได้ตอบได้แค่ "วันนี้ส่งได้ไหม" แต่คำถามตอนมีเรื่องร้องเรียนคือ "ยินยอมวันไหน และถอนวันไหน"
- **ส่งค่าเดิมซ้ำไม่เพิ่มแถว** หน้าจอส่งทุกสวิตช์ที่แสดงอยู่ ถ้าเก็บทุกอันแถวที่สำคัญจะจมอยู่ในแถวที่ไม่ได้บอกอะไร
- **ยืนยันค่าเริ่มต้นได้แถวใหม่** ลูกค้าที่ถูกถามแล้วตอบว่ายินยอม ต่างจากลูกค้าที่ไม่เคยถูกถาม และอย่างแรกคือสิ่งที่คลินิกต้องพิสูจน์ได้
- **แต่ละแถวเก็บ** ค่ายินยอมหรือไม่ เวลา ที่มา (`portal` หรือ `counter`) ผู้บันทึกเมื่อมาจากเคาน์เตอร์ เลขฉบับของประกาศความเป็นส่วนตัวที่มีผลอยู่ตอนบันทึก (`policy_version`) และหมายเหตุ เช่น เลขแบบฟอร์มกระดาษ
- **ระบบใส่เลขฉบับเอง** จากฉบับที่คลินิกเผยแพร่ล่าสุด อ่านใน transaction เดียวกับการบันทึก ([ประกาศความเป็นส่วนตัวของคลินิก](privacy-policy.md)) ยังไม่มีฉบับที่เผยแพร่ แถวยังถูกบันทึกโดย `policy_version` ว่าง เพราะการดูแลรักษาต้องไม่หยุดเพราะเอกสารยังไม่เสร็จ
- **บันทึกที่เคาน์เตอร์ต้องมีผู้บันทึก** ระบบใส่ `recorded_by_user_id` จากผู้ที่เรียก API เอง ความยินยอมที่บันทึกแทนลูกค้าโดยไม่รู้ว่าใครบันทึกไม่ใช่หลักฐานอะไร

## Endpoint ความยินยอม

| Endpoint | สิทธิ์ | ใช้ทำอะไร |
|---|---|---|
| `GET /portal/consents` | ลูกค้าที่เข้าสู่ระบบ | ค่าปัจจุบันและประวัติของตัวเอง |
| `PUT /portal/consents` | ลูกค้าที่เข้าสู่ระบบ | ลูกค้าเปลี่ยนเอง ที่มาเป็น `portal` |
| `GET /staff/customers/{id}/consents` | `customer:read` | ค่าปัจจุบันและประวัติของลูกค้าคนหนึ่ง |
| `POST /staff/customers/{id}/consents` | `customer:write` | บันทึกจากแบบฟอร์มกระดาษหรือคำพูดที่เคาน์เตอร์ ที่มาเป็น `counter` |

```json
{ "consents": { "marketing": true, "service_messages": true } }
```

- `consents` ต้องมีอย่างน้อยหนึ่งรายการ วัตถุประสงค์ที่ไม่ได้ส่งไม่ถูกแตะ ชื่อที่ไม่รู้จักได้ `422 validation_failed`
- เส้นของพนักงานรับ `note` เพิ่ม
- ทั้งสองเส้นยังรับช่อง `policy_version` เพื่อไม่ให้ client เดิมพัง แต่ไม่ใช้ค่านั้นและไม่เก็บ ค่าที่ client ส่งไม่ได้พิสูจน์ว่าลูกค้าเห็นประกาศฉบับไหน
- **การเปิดบัญชีจากหน้าจอง `/book`** (`POST /booking/guest/verify` ส่วนขยาย § 27) บันทึกผ่าน `RecordConsentHandler` ตัวเดียวกัน ที่มา `portal` พร้อมเลขฉบับที่ระบบใส่เอง (`policy_version` ในคำขอถูกตรวจความยาวแล้วไม่ใช้ หน้าจองเลิกส่งแล้ว) คือ `service_messages` ยินยอมเมื่อติ๊กยอมรับนโยบาย (บังคับ) และ `marketing` ยินยอมเฉพาะเมื่อติ๊ก ไม่ติ๊กไม่บันทึกแถว จึงไม่ถอนความยินยอมที่เคาน์เตอร์เคยบันทึกไว้ ลูกค้าที่มีบัญชีอยู่แล้วไม่ถูกบันทึกอะไรเพิ่ม การสมัครที่ `/register` ยังไม่บันทึก
- คำตอบมีทั้ง 4 วัตถุประสงค์เสมอ ที่ยังไม่เคยบันทึกส่งค่าเริ่มต้นพร้อม `is_default: true` และ `recorded_at` เป็น null หน้าจอของลูกค้าที่เข้ามาครั้งแรกจึงเห็นค่าปัจจุบันครบ ไม่ใช่หน้าว่าง ส่วน `history` เรียงใหม่สุดก่อน
- **เส้นของลูกค้าเอารหัสลูกค้าจาก token เสมอ** ไม่รับจาก request ถ้ารับได้ ลูกค้าคนหนึ่งจะอ่านหรือแก้ความยินยอมของคนอื่นได้ controller นี้ไม่ได้ติด `[RequireScope(portal)]` แบบ controller อื่นใต้ `/portal` แต่ต้องเข้าสู่ระบบ และ token ที่ไม่ใช่ของลูกค้าได้ `403`
- เส้นของพนักงานอ่านรหัสลูกค้าที่ไม่มีอยู่จริงได้ค่าเริ่มต้นกลับมา เพราะไม่ได้ตรวจว่ามีลูกค้าคนนั้นก่อน (ตารางมี foreign key ไปที่ลูกค้า การเขียนจึงไม่สร้างแถวลอย)

## ประตูกั้นก่อนส่งข้อความ

ความยินยอมมีผลจริงที่จุดเดียว คือก่อนส่งข้อความถึงลูกค้า

```text
use case ──► INotificationDispatcher ──► ConsentAwareNotificationDispatcher ──► INotificationChannel
                                              │
                                              └─ ConsentGate: ข้อความนี้เป็นวัตถุประสงค์ไหน
                                                 ลูกค้าคนนี้ยินยอมหรือไม่
```

- **ประตูอยู่หน้าช่องทาง ไม่ได้อยู่ในแต่ละ use case** dispatcher ตัวเดียวที่ลงทะเบียนไว้คือตัวที่ตรวจความยินยอม use case จึงไม่มีทางส่งข้อความเลี่ยงประตู กฎที่ตรวจในทุกจุดส่งจะถูกลืมในจุดถัดไป และผลของการลืมคือส่งการตลาดถึงคนที่ถอนความยินยอมแล้ว
- **แต่ละข้อความผูกกับวัตถุประสงค์แบบเขียนชัด** ไม่เดาจากชื่อ ข้อความที่ไม่อยู่ในรายการถือเป็น `marketing` ซึ่งเป็นฝั่งที่เข้มกว่า

| ข้อความ (template) | วัตถุประสงค์ |
|---|---|
| `queue.called` | `service_messages` |
| `consultation.summary` | `service_messages` |
| `pet.deceased_appointments_cancelled` | `service_messages` |
| `receipt.issued` | `service_messages` ใบเสร็จคือบันทึกธุรกรรมที่ลูกค้าทำ ไม่ใช่ข้อความที่คลินิกเลือกส่ง ถ้าระงับเพราะลูกค้าปฏิเสธการตลาดจะเท่ากับระงับเอกสารภาษี |
| `customer.portal_invitation` | `service_messages` เป็นเรื่องความสัมพันธ์การดูแลที่มีอยู่แล้ว ส่งครั้งเดียวต่อคำเชิญ ไม่ใช่แคมเปญ |
| `thread.reply` | `service_messages` คำตอบของพนักงานต่อข้อความที่ลูกค้าเขียนถึงคลินิกเองเรื่องสัตว์ของเขา |
| `customer.lapsed` | `marketing` เขียนไว้ชัด ข้อความ "คิดถึงน้อง" ของกติกา `customer_lapsed` ชวนลูกค้าที่หายไปให้กลับมา ไม่มีอะไรครบกำหนดและลูกค้าไม่ได้ขอ จึงเป็นการตลาด (ส่วนขยาย § 33) |
| อื่น ๆ | `marketing` |

- **ข้อความที่ถูกระงับถูกบันทึก log ระดับ information** พร้อม template ลูกค้า และวัตถุประสงค์ เพราะเคาน์เตอร์จะถามว่า "ทำไมเจ้าของไม่ได้ข้อความ"
- **การระงับไม่ทำให้งานที่สั่งล้ม** เรียกคิวสำเร็จแม้ไม่ได้ส่งข้อความถึงเจ้าของ
- **ถอนแล้วกลับมายินยอมใหม่** ข้อความกลับมาส่งตั้งแต่คำขอถัดไป เพราะประตูอ่านค่าจากฐานข้อมูลทุกครั้ง
- **คำเชิญพนักงานไม่ผ่านประตูนี้** ใช้ port แยก (`IStaffInvitationSender`) เพราะคนที่ถูกเชิญไม่ใช่ลูกค้า และข้อความนั้นมีความลับที่ห้ามลง log

รายละเอียดช่องทางส่งดู [การแจ้งเตือน](notifications.md)

## คำขอเรื่องข้อมูล

ลูกค้าขอใช้สิทธิ์ตาม PDPA คลินิกต้องแสดงได้ว่าได้รับคำขอ นับเวลา และตอบแล้ว

| ชนิด (`type`) | ลูกค้าขออะไร |
|---|---|
| `access` | ขอดูข้อมูลทั้งหมดที่คลินิกเก็บ |
| `correction` | ขอแก้ข้อมูลที่ผิด |
| `erasure` | ขอให้ลบ |
| `portability` | ขอข้อมูลในรูปแบบที่นำไปใช้ที่อื่นได้ |

| Endpoint | สิทธิ์ | ใช้ทำอะไร |
|---|---|---|
| `POST /portal/data-requests` | ลูกค้าที่เข้าสู่ระบบ | ยื่นคำขอ ส่ง `type` และ `detail` (ไม่บังคับ) เริ่มเป็น `open` |
| `GET /staff/data-requests` | `customer:read` | รายการคำขอ กรองด้วย `status` และ `customer_id` |
| `POST /staff/data-requests/{id}/close` | `customer:write` | ปิดคำขอ ส่ง `outcome` เป็น `completed` หรือ `refused` และ `resolution` |

- **สถานะมี 3 แบบ** `open`, `completed`, `refused` ปิดได้ครั้งเดียว ปิดซ้ำได้ `409 state_conflict` ปิดโดยไม่บอกว่าทำอะไรไปถูกปฏิเสธ ส่ง `If-Match` ได้
- **ปฏิเสธเป็นผลลัพธ์ปกติ** ไม่ใช่ error คำขอลบเวชระเบียนที่ลงนามแล้วมักถูกปฏิเสธ เพราะเวชระเบียนคือหลักฐานการรักษาและระบบไม่ลบเวชระเบียนเลย สิ่งที่ถูกกฎหมายคือตอบเป็นลายลักษณ์อักษรพร้อมเหตุผล ไม่ใช่เงียบ
- **ทุกคำขอมี `open_days`** จำนวนวันตั้งแต่ยื่นจนปิด หรือจนถึงตอนนี้ถ้ายังเปิด
- **รายการเรียงเก่าสุดก่อน** ต่างจากทุกรายการอื่นในระบบ เพราะคำขอบนสุดคือคำขอที่ใกล้กำหนดตามกฎหมายที่สุด รายการนี้ยังไม่แบ่งหน้า
- **ไม่มีอะไรถูกลบหรือส่งออกอัตโนมัติ** ระบบรับประกันแค่ว่าคำขอถูกรับ นับเวลา และตอบ การตัดสินว่าจะลบหรือส่งออกอะไรเป็นงานของคนที่ต้องรับผิดชอบการตัดสินนั้น
- ลูกค้าปิดคำขอของตัวเองไม่ได้ (`403`)

## ใครใช้

| ใคร | ทำอะไร |
|---|---|
| ลูกค้า | ดูและเปลี่ยนความยินยอมของตัวเอง ยื่นคำขอเรื่องข้อมูล |
| `receptionist` (`customer:*`) | ดูความยินยอม บันทึกจากแบบฟอร์มที่เคาน์เตอร์ ดูและปิดคำขอ |
| `clinic_owner`, `clinic_admin` | ทุกอย่างข้างบน |
| `cashier`, `veterinarian`, `vet_assistant` | ไม่มีสิทธิ์ตาม role ตั้งต้น |

## ประวัติการทำงาน

`consent.recorded` (ยินยอม) และ `consent.withdrawn` (ถอน) แยกกัน เพราะตอนมีเรื่องร้องเรียนจะค้นหาแยกกัน details มีเลขฉบับประกาศ (`policy_version`) ด้วย `data_request.raised` และ `data_request.closed` (เก็บผล เหตุผล และ `open_days`) ทั้งหมดเขียนใน transaction เดียวกับข้อมูล ดู [audit log และความเป็นส่วนตัว](../security/audit-and-privacy.md)

## หน้านโยบายความเป็นส่วนตัว (`/privacy`)

หน้าสาธารณะที่บอกลูกค้าว่าคลินิกเก็บอะไร ใช้ทำอะไร ส่งให้ใคร เก็บนานแค่ไหน และใช้สิทธิ์ตาม PDPA ได้อย่างไร ลิงก์ "นโยบายความเป็นส่วนตัว" ในแถบดำท้ายเว็บ และลิงก์ใต้ปุ่มสมัครสมาชิก ชี้มาที่หน้านี้

**คลินิกเป็นผู้เขียน ไม่ใช่ผู้พัฒนาระบบ** คลินิกเป็นผู้ควบคุมข้อมูล จึงเขียนและเผยแพร่ประกาศเองที่หน้าตั้งค่า (`/settings/privacy-policy`) ร่างแก้ได้ ฉบับที่เผยแพร่แล้วแก้ไม่ได้ เจ้าของคลินิก (`settings:danger`) เป็นคนเผยแพร่ รายละเอียดทั้งหมดอยู่ใน [ประกาศความเป็นส่วนตัวของคลินิก](privacy-policy.md) (ส่วนขยาย ข้อ 35)

- **หน้า `/privacy` แสดงฉบับที่เผยแพร่ล่าสุด** จาก `GET /privacy-policy` ฉบับก่อนหน้าเปิดได้ที่ `/privacy/versions/{เลขฉบับ}`
- **ยังไม่มีฉบับที่เผยแพร่** หน้าแสดงข้อมูลคลินิกและช่องทางติดต่อ พร้อมข้อความว่าคลินิกยังไม่ได้เผยแพร่ประกาศ ไม่แสดง template
- **template ที่มากับระบบ** เขียนจากสิ่งที่ระบบทำจริง migration ใส่ไว้เป็นร่างเท่านั้น ถ้อยคำครอบคลุมเรื่องเดิมทั้งหมด คือข้อมูลที่เก็บ (ไม่อ้างว่าเก็บที่อยู่หรือเลขบัตรประชาชน เพราะไม่มีช่องนั้น) ผู้รับข้อมูล (ตัวส่ง SMS ตัวส่งอีเมล LINE และผู้ให้บริการโมเดล AI) ระยะเวลาเก็บที่บอกตรง ๆ ว่ายังไม่ได้กำหนด สิทธิ์ตาม PDPA ที่พาไป `/portal/account` และคุกกี้ `hp_at`, `hp_rt`, `hp_signed_in`
- **ผู้ให้บริการโมเดลได้รับข้อมูลทางคลินิกด้วย เมื่อเปิดผู้ช่วย AI สำหรับพนักงาน** ([ผู้ช่วย AI สำหรับพนักงาน](staff-ai.md)) การสรุปประวัติ การร่างบันทึก และการร่างข้อความ ส่งชื่อ ชนิด สายพันธุ์ อายุของสัตว์ การวินิจฉัย ยา ผลแล็บ บันทึกของหมอ และข้อความที่ลูกค้าเขียนถึงคลินิก ไปให้ผู้ให้บริการโมเดล ชื่อ เบอร์โทร และอีเมลของเจ้าของ และชื่อพนักงาน ถูกแทนด้วยตัวแทนก่อนส่ง เบอร์ อีเมล และเลขบัตรที่พิมพ์ไว้ในข้อความถูกแทนตามรูปแบบ แต่การแทนไม่สมบูรณ์ เช่น ชื่อคนอื่นที่เขียนในบันทึกโดยไม่มีคำนำหน้าอาจผ่านไปได้ ถ้าใช้ Gemini ข้อมูลเหล่านี้ไปที่ Google ซึ่งอาจอยู่นอกประเทศ ถ้าใช้โมเดลที่รันเองในเครื่องของเรา ข้อมูลไม่ออกนอกเครื่อง template มีหัวข้อ "ผู้ช่วย AI" ที่บอกเรื่องนี้แล้ว คลินิกต้องตรวจให้ตรงกับที่ตั้งค่าจริงก่อนเผยแพร่

**ใครเป็นผู้ควบคุมข้อมูลมาจาก API** ชื่อคลินิก ผู้ดำเนินการสถานพยาบาล และเลขใบอนุญาตอ่านจาก `GET /clinic` เบอร์โทร อีเมล และที่อยู่อ่านจาก `GET /clinic/contacts` (ที่อยู่ใช้รายการชนิด `map` ก่อน ไม่มีจึงใช้ที่อยู่ของสาขาแรก) ช่องที่คลินิกยังไม่ได้ตั้งไม่แสดง ถ้าเรียก API ไม่ได้เลย หน้าบอกให้ไปดูที่หน้าติดต่อเรา หัวข้อนี้เป็นหัวข้อแรกเสมอ ไม่ว่าจะเผยแพร่ประกาศแล้วหรือยัง

**กล่องเตือนสีเหลืองบนหน้า** บอกว่าประกาศยังไม่ผ่านการตรวจของนักกฎหมาย แสดงเมื่อฉบับที่เผยแพร่ไม่ได้ติ๊ก `legal_review_done` ตอนเผยแพร่

## ข้อจำกัด

- **หน้าลูกค้ามีแล้ว หน้าพนักงานยังไม่มี** ลูกค้าเปลี่ยนความยินยอมและยื่นคำขอได้ที่ `/portal/account` ส่วนการดูและปิดคำขอของพนักงานยังมีแต่ API
- **ยังไม่มีระยะเวลาเก็บข้อมูล** เช่น เก็บเวชระเบียนกี่ปี ข้อมูลติดต่อกี่ปี ต้องเป็นนโยบายที่ที่ปรึกษาของคลินิกกำหนด การตั้งค่าเริ่มต้นเองเท่ากับให้คำแนะนำทางกฎหมาย
- **ใช้จริงแค่สองวัตถุประสงค์** ประตูกั้นตรวจ `service_messages` และ `marketing` ผ่าน template ส่วน `medical_record_sharing` และ `extended_data_processing` บันทึกได้ แต่ยังไม่มีฟีเจอร์ไหนตรวจ เพราะยังไม่มีการส่งเวชระเบียนออกและยังไม่มีงานวิเคราะห์ข้อมูล
- **ประตูดูแค่ความยินยอม** ไม่ได้ดูว่าสัตว์เสียชีวิตแล้ว เรื่องสัตว์เสียชีวิตจัดการที่ use case ของมันเอง ดู [ลูกค้าและสัตว์เลี้ยง](customers-and-pets.md)
- **ความยินยอมก่อนเผยแพร่ฉบับแรกไม่มีเลขฉบับ** และความยินยอมเก่าที่มี `2026-10` อ้างถึงถ้อยคำในประวัติ git ไม่ใช่แถวในฐานข้อมูล
- **template ยังไม่ผ่านนักกฎหมาย** ถ้อยคำเรื่องเหตุผลทางกฎหมาย ระยะเวลาตอบคำขอ 30 วัน และการแจ้งเหตุรั่วไหล เป็นการเขียนตามความเข้าใจ PDPA ทั่วไป คลินิกต้องให้ที่ปรึกษาตรวจก่อนเผยแพร่
