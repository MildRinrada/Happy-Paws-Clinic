# ลูกค้าและสัตว์เลี้ยง

ทะเบียนเจ้าของและคนไข้ของคลินิก เจ้าของหนึ่งคนมีสัตว์ได้หลายตัว และสัตว์หนึ่งตัวมีผู้ดูแลได้หลายคน เคาน์เตอร์ใช้หน้านี้ค้นหาลูกค้า ลงทะเบียนคนใหม่ เพิ่มสัตว์ ชวนลูกค้าเปิดบัญชีออนไลน์ และผูก LINE ของลูกค้าไว้รับการแจ้งเตือน

## ใครใช้

| scope | ทำอะไรได้ |
|---|---|
| `customer:read` | ค้นหาลูกค้าและเปิดหน้าลูกค้า |
| `customer:write` | ลงทะเบียนลูกค้า ส่งคำเชิญเข้า portal และผูกหรือยกเลิก LINE ของลูกค้า (เห็นรายชื่อผู้ติดตาม LINE ล่าสุดด้วย) |
| `customer:merge` | รวมเรกคอร์ดซ้ำ แยกจาก `customer:write` เพราะย้อนกลับผ่าน API ไม่ได้ |
| `patient:read` | ดูทะเบียนสัตว์ |
| `patient:write` | เพิ่มสัตว์ จัดการผู้ดูแลร่วม และบันทึกว่าสัตว์เสียชีวิต |

ลูกค้าไม่ผูกกับสาขา คนที่ลงทะเบียนที่สาขาหนึ่งค้นเจอได้จากทุกสาขา

## ค้นหา

`GET /staff/customers?q=` ช่องเดียวค้นได้สี่อย่าง คือ ชื่อเจ้าของ เบอร์โทร ชื่อสัตว์ และเลข HN เพราะเคาน์เตอร์ได้ยินแค่ "คุณสมชาย" หรือ "มากับลูน่า" และคนพูดไม่รู้ว่าระบบเก็บไว้ช่องไหน ถ้าไม่ใส่คำค้นจะได้รายชื่อที่ลงทะเบียนล่าสุดก่อน เรกคอร์ดที่ถูกรวมไปแล้วไม่ขึ้นในผลค้นหา

## ลงทะเบียนลูกค้า

`POST /staff/customers` รับชื่อ เบอร์โทร และอีเมล (ไม่บังคับ)

- **เบอร์ซ้ำเป็นการหยุดถาม ไม่ใช่กำแพง** ถ้ามีลูกค้าใช้เบอร์นี้อยู่แล้ว API ตอบ `409 duplicate_customer` และแนบรายชื่อที่ตรงกันมาใน `details.existing` เคาน์เตอร์เลือกเปิดเรกคอร์ดเดิม หรือส่งซ้ำพร้อม `allow_duplicate_phone: true` เพื่อสร้างใหม่ เพราะคนในบ้านเดียวกันใช้เบอร์ร่วมกันได้จริง
- ไม่ใช้ unique index กับเบอร์โทร ด้วยเหตุผลเดียวกัน และเพราะรายชื่อซ้ำเกิดขึ้นอยู่ดี จึงมี endpoint รวมเรกคอร์ด

## หน้าลูกค้า

`GET /staff/customers/{id}` ตอบสามอย่างในครั้งเดียว คือ ข้อมูลติดต่อ สัตว์ทั้งหมด และยอดค้างชำระ พร้อมสถานะคำเชิญล่าสุด และสถานะ LINE (`line`) ซึ่งเป็นส่วนขยาย ดูหัวข้อถัดไป ยอดค้างอ่านจากโมดูลการเงินโดยตรง จึงตรงกับหน้าเก็บเงินเสมอ

id ของเรกคอร์ดที่ถูกรวมไปแล้วยังเปิดได้ และมี `merged_into_customer_id` บอกว่าย้ายไปที่ไหน id ที่พิมพ์อยู่บนใบเสร็จเก่าจึงไม่กลายเป็น 404

## เพิ่มสัตว์เลี้ยง

`POST /staff/pets` รับชื่อ ชนิด เจ้าของหลัก สายพันธุ์ และเลขไมโครชิป

- **เลข HN ออกให้อัตโนมัติ** รูปแบบ `HN-YYYY-NNNN`
- **เจ้าของหลักถูกบันทึกสองที่** ครั้งแรกเป็นผู้ติดต่อเรื่องค่าใช้จ่ายของสัตว์ ครั้งที่สองเป็นสิทธิ์ผู้ดูแลที่ดูประวัติได้ สองเรื่องนี้แยกกันได้จริง เช่น สัตว์ย้ายบ้าน หรือผู้ดูแลร่วมที่ไม่ได้เป็นคนจ่ายเงิน
- **ไมโครชิปซ้ำไม่ได้** ชิปหนึ่งเลขคือสัตว์หนึ่งตัว ถ้าซ้ำ API ตอบ `422` ที่ช่อง `microchip_number`
- ชนิดสัตว์เป็นข้อความอิสระยาวไม่เกิน 60 ตัวอักษร
- วันเกิด เพศ และการทำหมันยังไม่มี เพราะ contract ไม่ได้ระบุ ดู [assumptions.md § 25](../assumptions.md)

## ชวนเข้า portal

`POST /staff/customers/{id}/invite` บันทึกคำเชิญและส่งข้อความไปที่เบอร์ของลูกค้า ส่งซ้ำได้ ระบบต่ออายุคำเชิญเดิมแทนการสร้างแถวใหม่ ลูกค้าที่มีบัญชีแล้วหรือเรกคอร์ดที่ถูกรวมไปแล้วจะได้ `409`

ตอนนี้ยังไม่มีตัวส่ง SMS จริง ข้อความไปขึ้นใน log ของ API ([การแจ้งเตือน](notifications.md)) ส่วนครึ่งที่ว่า "ผูก LINE" ไม่ได้ทำโดยตั้งใจ เพราะ LINE เป็นช่องทางส่งข้อความ ไม่ใช่ตัวตน ดู [assumptions.md § A](../assumptions.md)

## ผูก LINE ที่เคาน์เตอร์

ส่วนขยาย [contract-extensions.md § 18](../contract-extensions.md) ที่อยู่ LINE เป็นข้อมูลสำหรับส่งข้อความ เหมือนอีเมล ไม่ใช่การเข้าสู่ระบบหรือการยืนยันตัวตน พนักงานเป็นคนเลือกให้ เพราะ LINE user id พิมพ์เองไม่ได้

1. ลูกค้าเพิ่มเพื่อน LINE ของคลินิก (หรือพิมพ์ข้อความอะไรก็ได้ ถ้าเคยเพิ่มไว้นานแล้ว)
2. พนักงานเปิดหน้าลูกค้า กด **เลือกจากผู้ติดตาม LINE** รายชื่อมาจาก `GET /staff/integrations/line/followers` เรียงคนที่เพิ่งเห็นล่าสุดก่อน แสดงรูป ชื่อใน LINE และเวลา เฉพาะ 14 วันล่าสุดและยังไม่ได้ผูกกับลูกค้าคนใด กด **โหลดใหม่** ถ้ายังไม่เห็นชื่อ หรือค้นด้วยชื่อใน LINE
3. กด **เลือก** ที่คนนั้น ตรวจกับลูกค้าว่าเป็นบัญชีของเขา แล้วกด **ยืนยันผูก** ระบบเรียก `PUT /staff/customers/{id}/line` พร้อม version ของลูกค้า

- LINE ที่ผูกกับลูกค้าคนอื่นอยู่แล้วได้ `409 line_address_taken` หน้าจอบอกและมีลิงก์ไปเรกคอร์ดนั้น ต้องยกเลิกที่นั่นก่อน
- คนที่บล็อกบัญชีแล้ว หรือไม่อยู่ในรายชื่อ 14 วันล่าสุด ผูกไม่ได้ (`422`)
- การ์ด **LINE** บอกว่าผูกแล้ว บล็อกบัญชีอยู่ หรือยังไม่ผูก ถ้าผูกแล้วมีปุ่ม **เปลี่ยน** และ **ยกเลิกการผูก** (`DELETE /staff/customers/{id}/line` ต้องกดยืนยันอีกครั้ง) หลังยกเลิก ข้อความไปทาง SMS หรืออีเมล
- ลูกค้าที่บล็อกบัญชีทีหลังยังผูกอยู่ แต่ข้อความไปทาง SMS จนกว่าจะเพิ่มเพื่อนกลับ
- ทุกการผูกและยกเลิกบันทึกลง audit log (`customer.line_linked`, `customer.line_unlinked`)
- ระบบไม่จับคู่ LINE กับลูกค้าเองจากชื่อหรือเบอร์ และลูกค้าผูกเองจาก portal ไม่ได้ ดู [LINE](line.md#ที่อยู่-line-ของลูกค้า)

## ส่วนอื่นของทะเบียน

- **ผู้ดูแลร่วม** `POST /staff/pets/{id}/owners` กำหนดได้ว่าดูประวัติการรักษาได้ไหม (`may_view_history`) การถอนสิทธิ์ปิดลิงก์ ไม่ลบประวัติ
- **รวมเรกคอร์ดซ้ำ** `POST /staff/customers/{id}/merge` เรกคอร์ดใน path คือตัวที่เก็บไว้ ส่วนใน body คือตัวที่ถูกรวม ย้ายสัตว์ ประวัติ และบิลค้างไปทั้งหมด ดู [assumptions.md § 12](../assumptions.md)
- **การแพ้ยา** `POST /staff/pets/{id}/allergies` แพ้ระดับ `severe` สั่งยานั้นไม่ได้ อีกสองระดับสั่งได้เมื่อยืนยัน
- **สัตว์เสียชีวิต** (มี API แล้ว ยังไม่มีหน้าจอ) `POST /staff/pets/{id}/deceased` ยกเลิกนัดในอนาคตทุกนัดและแจ้งเจ้าของครั้งเดียว ดู [contract-extensions.md § 6](../contract-extensions.md)

## หน้าจอบนเว็บ

เมนู **ลูกค้าและสัตว์** ในหน้าจอพนักงาน เห็นเฉพาะบัญชีที่ถือ `customer:read`

- **`/customers`** ช่องค้นหาเดียว คำค้นอยู่ในที่อยู่ของหน้า (`/customers?q=`) จึงกดย้อนกลับหรือเปิดซ้ำได้ ไม่ใส่คำค้นจะเห็นลูกค้าที่ลงทะเบียนล่าสุด ปุ่ม **ลงทะเบียนลูกค้าใหม่** ขึ้นเมื่อถือ `customer:write`
- **`/customers/new`** ฟอร์มชื่อ เบอร์ อีเมล ถ้าเบอร์ซ้ำ ฟอร์มแสดงลูกค้าที่ใช้เบอร์นั้นพร้อมปุ่มเปิดเรกคอร์ด และปุ่ม "คนละคน สร้างลูกค้าใหม่" ซึ่งส่งซ้ำพร้อม `allow_duplicate_phone` ถ้าแก้เบอร์ กล่องนี้หายไป บันทึกสำเร็จแล้วพาไปหน้าลูกค้าพร้อมเปิดฟอร์มเพิ่มสัตว์ไว้ให้
- **`/customers/<id>`** รายการสัตว์พร้อมเลข HN การ์ดข้อมูลติดต่อ ยอดค้างชำระ (มีลิงก์ไปหน้าเก็บเงินเมื่อถือ `invoice:write`) การ์ดบัญชีออนไลน์ที่มีปุ่มส่งคำเชิญเมื่อถือ `customer:write` และการ์ด LINE ที่มีตัวเลือกผู้ติดตามเมื่อถือ `customer:write` (ดูหัวข้อผูก LINE ที่เคาน์เตอร์)
- **รวมเรกคอร์ดซ้ำ** การ์ดในหน้าลูกค้า ขึ้นเมื่อถือ `customer:merge` เรกคอร์ดที่เปิดอยู่คือตัวที่เก็บไว้
  1. ค้นหาเรกคอร์ดที่ซ้ำ ผลค้นหาไม่มีเรกคอร์ดที่เปิดอยู่
  2. อ่านสิ่งที่จะเกิดขึ้น ข้อความตรงกับที่ backend ทำ ได้แก่ ย้ายสัตว์ ผู้ดูแล นัด คิว เคส เวชระเบียน บิล ความยินยอม และคำขอ PDPA ไปเรกคอร์ดที่เก็บ ข้อมูลติดต่อไม่ถูกคัดลอก เรกคอร์ดซ้ำถูกปิด ไม่ถูกลบ และย้อนกลับไม่ได้
  3. ติ๊กยืนยัน แล้วกดปุ่มแดง **รวมเรกคอร์ด**
  - ถ้าทั้งสองเรกคอร์ดมีบัญชีออนไลน์ backend ปฏิเสธ หน้าจอบอกเหตุผลและซ่อนปุ่มรวม
  - ส่ง `version` ของเรกคอร์ดที่เก็บไปด้วย หน้าที่เก่าจึงได้ข้อความให้โหลดใหม่ รวมเสร็จแล้วแสดงว่าย้ายอะไรไปกี่รายการ
- **ฟอร์มเพิ่มสัตว์** ขึ้นเมื่อถือ `patient:write` เลือกชนิดจากรายการ หรือเลือก "อื่น ๆ" แล้วพิมพ์เอง บันทึกแล้วบอกเลข HN ที่ได้ เพื่อให้เคาน์เตอร์เขียนลงบัตร
- ข้อผิดพลาดจาก API ขึ้นใต้ช่องที่เกี่ยวข้อง เช่น ไมโครชิปซ้ำขึ้นใต้ช่องไมโครชิป ส่วนที่ไม่ได้ระบุช่องขึ้นเป็นกล่องด้านบน
- ทุกฟอร์มเรียก server action ที่ตรวจรูปแบบด้วย zod แล้วเรียก API ครั้งเดียว การซ่อนปุ่มตาม scope เป็นเรื่อง UX เท่านั้น backend ตรวจซ้ำทุกคำขอ

**หน้าสัตว์** `/pets/<id>` เปิดได้เมื่อถือ `patient:read` ชื่อสัตว์ในหน้าลูกค้า ปฏิทินนัด และหน้าตรวจ ลิงก์มาที่หน้านี้

- **การแพ้ยา** อยู่บนสุด กรอบแดงเมื่อมีประวัติ บอกยา อาการ และความรุนแรง ปุ่ม **บันทึกการแพ้** ขึ้นเมื่อถือ `record:write`
- **ประวัติการรักษา** จาก `GET /staff/pets/{id}/history` (ต้องมี `record:read`) ตรวจ ยา วัคซีน และแล็บ เรียงใหม่ไปเก่า ทีละหน้า การเปิดดูถูกบันทึกลง access log ทุกครั้ง บัญชีที่ไม่มี `record:read` เห็นข้อความแทน
- **ข้อมูลสัตว์** ไมโครชิป ชื่อเล่น อาหาร และนิสัยที่เจ้าของกรอกจาก portal
- **เจ้าของและผู้ดูแล** ที่ยังมีสิทธิ์อยู่ เจ้าของหลักก่อน บอกถ้าผู้ดูแลคนนั้นดูประวัติไม่ได้ บัญชีที่ถือ `patient:write` เพิ่มผู้ดูแลร่วมได้ (ค้นหาลูกค้า แล้วเลือกว่าให้ดูประวัติได้ไหม) และกด **ถอนสิทธิ์** ผู้ดูแลที่ไม่ใช่เจ้าของหลักได้ โดยต้องกดยืนยันอีกครั้ง
- **น้ำหนัก** ค่าล่าสุด และกราฟเมื่อมีตั้งแต่สองครั้ง น้ำหนักบันทึกจากสัญญาณชีพในหน้าตรวจเท่านั้น
- **วัคซีน** ครั้งถัดไปของแต่ละวัคซีน (เลยกำหนด ใกล้ครบกำหนด ยังไม่ถึง) และที่ฉีดแล้วพร้อมเลขล็อต บันทึกวัคซีนได้จากการ์ดนี้
- แผนการรักษา เอกสาร และลิงก์ไปประวัติยา ดู [งานรักษาต่อเนื่อง](clinical-records.md#หน้าจอพนักงาน)

## ข้อจำกัด

- **หน้าสัตว์ยังแก้ข้อมูลสัตว์และบันทึกการเสียชีวิตไม่ได้** มี API แล้ว
- **รวมเรกคอร์ดไม่มีตัวอย่างก่อนรวม** จำนวนที่ย้ายรู้ได้หลังรวมเสร็จเท่านั้น
- **แก้ข้อมูลลูกค้าไม่ได้** contract ไม่มี `PATCH /staff/customers/{id}` เบอร์หรือชื่อที่พิมพ์ผิดจึงยังแก้จากเคาน์เตอร์ไม่ได้
- **ข้อความตรวจรูปแบบบางข้อเป็นภาษาอังกฤษ** กฎใน backend ที่ไม่ได้ใส่ข้อความเองจะได้ข้อความตั้งต้นของ FluentValidation เช่น อีเมลผิดรูปแบบ ฟอร์มบนเว็บกันกรณีนี้ด้วยการตรวจของเบราว์เซอร์ก่อนส่ง
