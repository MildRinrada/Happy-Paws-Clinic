# คาดการณ์จากข้อมูลของคลินิก

ระบบเตือนเดิมใช้เกณฑ์ตายตัว เช่น ยาเหลือต่ำกว่าจุดสั่งซื้อ หรือลูกค้าไม่มาเกินกี่วัน ส่วนนี้ใช้ข้อมูลที่คลินิกมีอยู่แล้วมาคาดการณ์ข้างหน้าด้วยสถิติธรรมดา คำนวณบนเซิร์ฟเวอร์ของเราเอง ไม่ใช้โมเดลภาษา ไม่ส่งข้อมูลออกไปที่ไหน ไม่เก็บผลลัพธ์ไว้ คำนวณใหม่ทุกครั้งที่เปิดดู

เป็น [ส่วนขยาย § 33](../contract-extensions.md) ไม่มี scope ใหม่ ไม่มี migration

## มีอะไรบ้าง

| คำถาม | Endpoint | สิทธิ์ | หน้าจอ |
|---|---|---|---|
| ยาตัวไหนจะหมดเมื่อไร ควรสั่งเท่าไร | `GET /staff/inventory/forecast` | `inventory:read` | สต๊อกยา แท็บ "คาดการณ์" (`/inventory/forecast`) |
| วันไหนชั่วโมงไหนจะยุ่ง หมอพอไหม | `GET /staff/stats/demand-forecast` | `stats:read` | ตารางเวร ปุ่ม "คาดการณ์ความหนาแน่น" (`/schedules/forecast`) |
| นัดไหนเสี่ยงไม่มา เพราะอะไร | `GET /staff/appointments/attendance-risk` | `appointment:read` | ปฏิทินนัด (`/appointments`) |
| ใครควรกลับมาแล้วแต่ยังไม่มา | `GET /staff/customers/due-back` | `crm:read` | แพ็กเกจและโปรโมชัน แท็บ "ควรกลับมาแล้ว" (`/crm/due-back`) |
| ส่งข้อความ "คิดถึงน้อง" ให้ลูกค้าที่หายไป | กติกาเตือนอัตโนมัติ `customer_lapsed` | `automation:manage` | เตือนอัตโนมัติ (`/notifications/automations`) |

ทุกเส้นใช้ `branch` เป็นชื่อพารามิเตอร์สาขาเหมือนเส้นอ่านอื่นทั้งระบบ บัญชีที่ผูกสาขาเห็นได้เฉพาะสาขาของตัวเอง ขอสาขาอื่นได้ `403` หน้าเว็บใช้สาขาที่เลือกอยู่บนแถบด้านบน และซ่อนเมนูหรือปุ่มที่บัญชีไม่มีสิทธิ์

## สต๊อกยา: จะหมดเมื่อไรและควรสั่งเท่าไร

```http
GET /v1/staff/inventory/forecast?branch=brn_...&cover_days=30       inventory:read

200 { "branch_id": "brn_...", "as_of": "2026-10-10", "cover_days": 30, "lead_time_days": 7,
      "data": [ { "item_id": "itm_...", "name": "Amoxicillin 250mg", "kind": "medicine", "unit": "เม็ด",
                  "reorder_level": 20, "available": 95, "on_order": 0,
                  "used_30d": 60, "used_90d": 90, "avg_daily_30d": 2.0, "avg_daily_90d": 1.0, "daily_rate": 2.0,
                  "days_until_out": 47, "runs_out_on": "2026-11-26", "suggested_order_qty": 0,
                  "history_days": 100, "confidence": "high" } ] }
```

- **สาขาเดียวต่อครั้ง** ไม่ส่ง `branch` คือสาขาเดียวของบัญชี หรือสาขาเดียวของคลินิก ถ้าเลือกไม่ได้ตอบ `422` สาขาที่ไม่เปิดอยู่ตอบ `422`
- **อะไรนับเป็นการใช้** การจ่ายออก (`issue` คือใช้ในหัตถการ แตก ทิ้ง) และการจ่ายยา (`dispense`) ไม่นับการโอนสาขา เพราะของย้ายที่ ไม่ได้ถูกใช้ และไม่นับการปรับยอดหลังนับ เพราะเป็นการแก้ตัวเลขในบัญชี ไม่ใช่ความต้องการ ของที่แตกหรือหมดอายุแล้วทิ้งผ่านการจ่ายออกจึงนับด้วย เพราะต้องสั่งมาแทนเหมือนกัน
- **ค่าเฉลี่ยต่อวัน** ของ 30 และ 90 วันเต็มล่าสุด ไม่นับวันนี้ที่ยังไม่จบ หารด้วยจำนวนวันที่รายการมีบันทึกที่สาขานี้จริงถ้าสั้นกว่าช่วง ยาที่เพิ่งรับเข้ามาเมื่อสัปดาห์ก่อนจึงไม่ถูกหารด้วย 90
- **อัตราที่ใช้คำนวณ** คือค่าเฉลี่ยที่สูงกว่าระหว่างสองช่วง ยาหมดเสียหายมากกว่าการมียาเกินไม่กี่กล่อง
- **`days_until_out`** คือของที่ใช้ได้ (`available` ตัวเดียวกับหน้ารายการยา คือไม่นับล็อตที่หมดอายุ) หารอัตรา ปัดลง ถ้าไม่มีการใช้เลยจะไม่มีช่องนี้และไม่มี `runs_out_on`
- **`suggested_order_qty`** คืออัตรา คูณ (เวลารอของ 7 วัน บวก `cover_days`) ปัดขึ้น หักของที่ใช้ได้และของที่สั่งไว้แล้ว ไม่ต่ำกว่าศูนย์ `cover_days` ใส่ได้ 1 ถึง 180 ไม่ส่งคือ 30 นอกช่วงตอบ `422`
- **`confidence`** นับจากวันแรกที่รายการมีบันทึกที่สาขานี้ ไม่ถึง 14 วันคือ `low` ไม่ถึง 90 วันคือ `medium` นอกนั้น `high`
- เรียงจากหมดก่อน รายการที่ไม่มีการใช้อยู่ท้าย รายการที่เลิกใช้แล้วไม่อยู่ในรายการ

หน้าจอแสดงแต่ละรายการเป็นแถว บอกวันที่จะหมด ค่าเฉลี่ย ของที่ใช้ได้ ของที่สั่งไว้ และจำนวนที่ควรสั่ง รายการที่ข้อมูลน้อยมีป้ายสีเหลือง รายการที่จะหมดก่อนของมาถึง (ภายใน 7 วัน) มีป้ายแดง "สั่งด่วน" เลือกช่วงที่จะสั่งให้พอได้ 14 30 60 หรือ 90 วัน และเรียงตามหมดก่อน ควรสั่งมาก หรือชื่อ

## ความหนาแน่น: วันไหนจะยุ่ง หมอพอไหม

```http
GET /v1/staff/stats/demand-forecast?branch=brn_...&from=2026-10-12&to=2026-10-18      stats:read

200 { "branch_id": "brn_...", "from": "2026-10-12", "to": "2026-10-18", "history_weeks": 8, "high_load_per_vet": 2.5,
      "days": [ { "date": "2026-10-12", "booked_appointments": 14, "expected_walk_ins": 6.4, "expected_total": 20.4,
                  "high_load_hours": 1,
                  "hours": [ { "hour": 10, "starts_at": "2026-10-12T10:00:00+07:00", "booked_appointments": 3,
                               "expected_walk_ins": 2.0, "expected_total": 5.0, "vets_on_shift": 1,
                               "load_per_vet": 5.0, "high_load": true } ] } ] }
```

- **ดูได้เฉพาะวันนี้และวันข้างหน้า** ไม่ส่ง `from` คือวันนี้ ไม่ส่ง `to` คือ 7 วัน ครั้งละไม่เกิน 14 วัน `from` ก่อนวันนี้ `to` ก่อน `from` หรือเกิน 14 วันตอบ `422` ที่ช่องนั้น เหมือนรูปของรายงานสถิติ
- **สาขาเดียวต่อครั้ง** กติกาเดียวกับสต๊อก เพราะหมอหนึ่งคนอยู่ได้สาขาเดียวในชั่วโมงหนึ่ง
- **วันและชั่วโมงเป็นเวลาคลินิก** ตัดด้วยเขตเวลาของคลินิกแบบเดียวกับ `GET /staff/stats/queue`
- **นัดที่จองแล้ว** คือนัดที่เริ่มในชั่วโมงนั้น ไม่นับ walk-in นัดที่ยกเลิก และไม่มาตามนัด
- **walk-in ที่คาดไว้** คือค่าเฉลี่ยของบัตรคิว walk-in (บัตรที่ไม่ได้มาจากนัด หรือมาจากนัดแบบ walk-in) ที่ออกในชั่วโมงเดียวกันของวันเดียวกันในสัปดาห์ ย้อนหลัง 8 สัปดาห์ก่อนวันนี้ สัปดาห์ก่อนที่สาขาจะออกบัตรคิวใบแรกไม่ถูกนับเป็นศูนย์ สาขาใหม่จึงไม่ถูกคาดว่าเงียบ
- **หมอที่ลงเวร** คือหมอ (ประเภทสัตวแพทย์ หรืออยู่แผนกสัตวแพทย์) ที่มีเวรที่ยังไม่ถูกยกเลิกทับส่วนใดส่วนหนึ่งของชั่วโมงนั้น วันลาตัดเวรออกอยู่แล้วจึงไม่ต้องนับแยก
- **`high_load`** เป็นจริงเมื่อคนไข้ที่คาดต่อหมอหนึ่งคนสูงกว่าเส้นของสาขาเอง คือเปอร์เซ็นไทล์ที่ 80 ของคนไข้ต่อหมอต่อชั่วโมงใน 8 สัปดาห์ที่ผ่านมา นับเฉพาะชั่วโมงที่มีทั้งหมอและคนไข้ (คนไข้คือนัดที่มาจริงหรือยังจองอยู่ บวก walk-in) หรือเมื่อคาดว่ามีคนไข้อย่างน้อยหนึ่งคนแต่ไม่มีหมอลงเวร ถ้าประวัติมีไม่ถึง 10 ชั่วโมงจะไม่มีเส้น (`high_load_per_vet` ไม่อยู่ในคำตอบ) และติดป้ายได้แค่กรณีไม่มีหมอ
- ชั่วโมงที่ไม่มีหมอ ไม่มีนัด และไม่เคยมี walk-in ไม่อยู่ในคำตอบ

หน้าจออยู่ที่ตารางเวร ไม่ได้อยู่บนหน้าภาพรวม แต่ละวันเป็นการ์ดหนึ่งใบ หัวการ์ดบอกยอดรวมและจำนวนชั่วโมงที่หนาแน่น ข้างในเป็นรายชั่วโมง ชั่วโมงที่หนาแน่นพื้นแดงอ่อนและมีป้าย "หนาแน่น" เลือกวันเริ่มและดู 7 หรือ 14 วันได้

## นัดที่เสี่ยงไม่มา

```http
GET /v1/staff/appointments/attendance-risk?branch=brn_...&date=2026-10-12      appointment:read

200 { "date": "2026-10-12", "branch_id": "brn_...", "window_days": 365,
      "data": [ { "appointment_id": "apt_...", "branch_id": "brn_...", "starts_at": "2026-10-12T10:00:00+07:00",
                  "status": "booked", "customer_id": "cus_...", "customer_name": "คุณสมศรี", "pet_id": "pet_...",
                  "pet_name": "ลูน่า", "staff_id": "stf_...", "risk": "high", "score": 6,
                  "reasons": ["ไม่มาตามนัด 2 ครั้งใน 12 เดือนที่ผ่านมา", "ยกเลิกกระชั้น 1 ครั้งใน 12 เดือนที่ผ่านมา", "เจ้าของยังไม่ได้ยืนยันนัด"],
                  "signals": { "no_shows": 2, "late_cancellations": 1, "days_booked_ahead": 2, "confirmed": false } } ] }
```

- **นัดไหนบ้าง** นัด `booked` และ `confirmed` ของวันนั้นที่ไม่ใช่ walk-in ไม่ส่ง `date` คือวันนี้ วันก่อนวันนี้ตอบ `422` เพราะรู้ผลแล้ว ไม่ส่ง `branch` คือทุกสาขาที่บัญชีเห็น
- **ประวัติของลูกค้า** นับแบบเดียวกับ `POST /staff/appointments/{id}/no-show` ทุกตัวอักษร คือนับจากตารางนัด ไม่มาตามนัด และยกเลิกกระชั้นที่ลูกค้ายกเลิกเอง วัดจากเวลาของนัดนั้น ย้อนหลังตาม `window_days` ของนโยบายยกเลิก (ค่าตั้งต้น 365 วัน) นับทุกสาขา เพราะการไม่มาที่สาขาหนึ่งบอกเรื่องลูกค้าคนนั้นเหมือนกัน
- **คะแนน** ไม่มาตามนัดครั้งละ 2 แต้ม ยกเลิกกระชั้นครั้งละ 1 แต้ม จองล่วงหน้าตั้งแต่ 30 วันขึ้นไป 1 แต้ม เจ้าของยังไม่ได้ยืนยันนัด 1 แต้ม
- **ระดับ** `high` เมื่อได้ 4 แต้มขึ้นไป หรือไม่มาตามนัดตั้งแต่ 2 ครั้ง `medium` เมื่อได้ 2 หรือ 3 แต้ม นอกนั้น `low` การยังไม่ยืนยันอย่างเดียวไม่เกิน `low` เพราะเจ้าของหลายคนไม่เคยกดยืนยันเลย
- **เหตุผล** เป็นประโยคภาษาไทยที่ระบบสร้างจากตัวเลข หนึ่งประโยคต่อหนึ่งสัญญาณที่ได้แต้ม เช่น "ไม่มาตามนัด 2 ครั้งใน 12 เดือนที่ผ่านมา" "จองไว้ล่วงหน้า 45 วัน"
- เรียงจากเสี่ยงสูงไปต่ำ ในระดับเดียวกันเรียงตามเวลา

บนปฏิทินนัด นัดที่เสี่ยงปานกลางมีเครื่องหมาย `!` สีเหลือง เสี่ยงสูงสีแดง วางเมาส์ค้างเพื่อดูเหตุผล รายการแบบมือถือมีป้าย "เสี่ยงไม่มา" ใต้สถานะ เปิดนัดแล้วเห็นเหตุผลครบในกล่องสีเหลือง เหนือปฏิทินมีแถบ "นัดที่เสี่ยงไม่มา N นัด" กดเปิดเพื่อดูรายการของวันนั้น พร้อมลิงก์ไปหน้าลูกค้า แถบเปิดเองเมื่อมีนัดเสี่ยงสูง วันที่ผ่านไปแล้วไม่แสดง ระบบไม่เปลี่ยนนัดและไม่ส่งข้อความให้ใคร พนักงานตัดสินใจเองว่าจะโทรยืนยันหรือไม่

## ใครควรกลับมาแล้ว

```http
GET /v1/staff/customers/due-back?reason=lapsed&branch=brn_...&limit=25&cursor=      crm:read

200 { "data": [ { "customer_id": "cus_...", "customer_name": "คุณสมชาย", "reason": "lapsed",
                  "pets": [ { "pet_id": "pet_...", "name": "มิโล", "species": "แมว", "overdue_vaccines": [] } ],
                  "last_visit_on": "2026-08-01", "visit_count": 5, "usual_interval_days": 30, "allowed_days": 60,
                  "due_on": "2026-09-30", "days_overdue": 10 } ],
      "page": { "next_cursor": "..." } }
```

- **`reason` ต้องส่ง** เป็น `vaccine_overdue` หรือ `lapsed` ไม่ส่งหรือค่าอื่นตอบ `422` cursor ที่อ่านไม่ได้ตอบ `422`
- **`vaccine_overdue`** สัตว์ที่ยังมีชีวิต ที่วัคซีนเข็มล่าสุดของชนิดใดชนิดหนึ่ง (เทียบชื่อไม่สนตัวพิมพ์ใหญ่เล็ก แบบเดียวกับกติกาเตือนวัคซีน) มี `next_due_on` ก่อนวันนี้ และสัตว์ตัวนั้นไม่มีนัด `booked` หรือ `confirmed` จากนี้ไป แถวเป็นของเจ้าของหลัก ในแถวมีสัตว์ทุกตัวที่เข้าเงื่อนไขพร้อมวัคซีนที่เลยกำหนด `due_on` คือวันครบกำหนดที่เก่าที่สุด
- **`lapsed`** ลูกค้าที่มาอย่างน้อย 3 วัน และหายไปนานกว่ารอบของตัวเอง ยังมีสัตว์ที่มีชีวิตอย่างน้อยหนึ่งตัว และไม่มีนัด `booked` หรือ `confirmed` จากนี้ไป
  - **การมาหนึ่งครั้ง** คือวันหนึ่งที่มีการเปิดเคสตรวจ หรือมีบิลที่ไม่ได้ยกเลิก แบบเดียวกับกลุ่มลูกค้าและรายงานลูกค้ากลับมา มาสองอย่างในวันเดียวนับเป็นครั้งเดียว ลูกค้าที่ถูกรวมรายชื่อ การมาของรายชื่อเดิมนับให้รายชื่อที่รวมเข้าไป
  - **รอบปกติ** (`usual_interval_days`) คือค่ากลาง (median) ของจำนวนวันระหว่างการมาแต่ละครั้ง
  - **หายไปเมื่อเกิน** (`allowed_days`) ค่าที่มากกว่าระหว่าง 1.5 เท่าของรอบปกติ กับรอบปกติบวก 30 วัน ปัดขึ้นเป็นวันเต็ม การบวก 30 วันกันลูกค้าที่มาทุกเดือนถูกโทรตามเพราะช้าไม่กี่วัน ส่วน 1.5 เท่ายืดเวลาให้ลูกค้าที่มาปีละครั้ง
  - **`due_on`** คือวันมาครั้งล่าสุดบวก `allowed_days` เลยวันนั้นแล้วจึงอยู่ในรายการ
- **ต่างจากกลุ่มลูกค้า** `inactive_days` ของกลุ่มลูกค้าเป็นเกณฑ์เดียวกับทุกคน ส่วนรายการนี้ใช้จังหวะของลูกค้าแต่ละคน หมาที่มาทุกเดือนกับแมวที่มาปีละครั้งไม่ได้ "หายไป" ที่จุดเดียวกัน
- **สาขา** เหมือนกลุ่มลูกค้า ลูกค้าอยู่ในสาขาที่เคยมา เมื่อระบุสาขา (หรือบัญชีผูกสาขา) การมานับเฉพาะที่สาขานั้น
- **ลำดับ** เรียงจากที่เพิ่งเลยกำหนดก่อน คนที่เพิ่งหายไปมีโอกาสกลับมามากที่สุด ส่วนวัคซีนที่เลยกำหนดมาหลายปีจะจมลงไปแทนที่จะอยู่บนสุดตลอดไป แบ่งหน้าด้วย cursor ครั้งละไม่เกิน 100
- ลูกค้าที่ปิดบัญชีหรือถูกรวมไปแล้วไม่อยู่ในรายการ

หน้าจอมีสองแท็บตามเหตุผล แต่ละแถวมีชื่อลูกค้าที่กดไปหน้าลูกค้าได้ ชื่อสัตว์ที่กดไปหน้าสัตว์ได้ วัคซีนที่เลยกำหนด วันครบกำหนดหรือวันที่ควรกลับมา วันมาครั้งล่าสุด และเลยมากี่วัน แถวของ `lapsed` บอกจำนวนครั้งที่มาและรอบปกติด้วย บัญชีที่ถือ `notify:send` เห็นปุ่ม "ส่งข้อความหาลูกค้า" ไปหน้าส่งข้อความ

## กติกาเตือน "คิดถึงน้อง"

trigger ใหม่ `customer_lapsed` ใน `POST /staff/automations` ใช้เงื่อนไข lapsed ชุดเดียวกับรายการด้านบน (SQL ตัวเดียวกัน)

```http
POST /v1/staff/automations
{ "name": "คิดถึงน้อง 7 วันหลังเลยรอบ", "trigger": { "type": "customer_lapsed", "offset_days": -7, "send_time": "10:00" },
  "condition": { "branch_id": "brn_...", "species": "แมว" } }
```

- **นับเป็นวันหลังวันที่ควรกลับมาเท่านั้น** `offset_days` ใส่ได้ -1 ถึง -90 (ค่าติดลบคือหลัง เหมือนการตามวัคซีนที่เลยกำหนด) `offset_hours` และเงื่อนไข `service_id` `vaccine_name` `unconfirmed_only` ใช้ไม่ได้ ตอบ `422`
- **ส่งครั้งเดียวต่อการหายไปหนึ่งรอบ** เรื่องที่เตือนคือลูกค้าคนนั้น (`subject.type` เป็น `customer`) วันครบกำหนดคือ `due_on` ถ้าลูกค้ากลับมาแล้วหายไปอีก `due_on` เปลี่ยน จึงได้ข้อความรอบใหม่ได้
- **ใช้ความยินยอมด้านการตลาด** เทมเพลต `customer.lapsed` อยู่ในกลุ่ม `marketing` ของประตูความยินยอม ไม่ใช่กลุ่มข้อความเรื่องการรักษา ลูกค้าที่ไม่เคยบันทึกอะไร (ค่าตั้งต้นของการตลาดคือไม่ยินยอม) หรือรับเฉพาะข้อความเรื่องการรักษา จะถูกข้ามและบันทึกว่า `no_consent` ดูที่ [ความยินยอม](privacy-and-consent.md)
- ข้อความใช้ชื่อสัตว์ที่ยังมีชีวิตของลูกค้าทุกตัว
- ดูตัวอย่างผู้รับ (`POST /staff/automations/{id}/simulate`) และคิวข้อความ (`GET /staff/reminders/upcoming`) ใช้ตัวประเมินเดียวกันจึงเห็นแถวเหล่านี้ด้วย

ฟอร์มสร้างกติกามีตัวเลือก "ลูกค้าหายไปนานกว่าปกติ (คิดถึงน้อง)" เลือกแล้วช่องจำนวนวันเปลี่ยนเป็น -7 และมีกล่องสีเหลืองบอกว่าใช้ความยินยอมรับข่าวสาร พร้อมเงื่อนไขของลูกค้าที่หายไป

## สิ่งที่ตั้งใจไม่ทำ

- ไม่ใช้โมเดลภาษาหรือบริการภายนอก ทุกตัวเลขอธิบายได้ด้วยกติกาในหน้านี้
- ไม่เก็บผลคาดการณ์ ไม่มีตารางใหม่ ไม่มี migration
- ไม่สั่งซื้อให้เอง ไม่เปลี่ยนนัดเอง ไม่ส่งข้อความเอง ยกเว้นกติกา `customer_lapsed` ที่คลินิกต้องสร้างและเปิดเอง
- เวลารอของเป็น 7 วันเท่ากันทุกผู้ขาย ยังไม่มีที่เก็บเวลารอของรายผู้ขาย
- ไม่ดูฤดูกาลหรือวันหยุดยาว ค่าเฉลี่ยของวันเดียวกันในสัปดาห์ย้อนหลัง 8 สัปดาห์คือทั้งหมดที่ใช้

## index ที่ควรเพิ่มเมื่อข้อมูลโต

รอบนี้ไม่ได้เพิ่ม index ทุกเส้นคำนวณสดและใช้ index ที่มีอยู่ ได้แก่ `ix_appointments_branch_id_starts_at_status`, index ของบัตรคิวตาม `(branch_id, service_date, ...)`, `(branch_id, starts_at, ends_at)` ของเวร, `(customer_id, issued_at)` ของบิล และ index บางส่วนของ `pet_vaccinations.next_due_on` ถ้าวันหนึ่งช้า ตัวที่ควรเพิ่มก่อนคือ

| ตาราง | index | ช่วยเส้นไหน |
|---|---|---|
| `stock_movements` | `(branch_id, item_id, occurred_at)` | คาดการณ์สต๊อก ตอนนี้อ่านบันทึกทั้งหมดของสาขาเพื่อหาวันแรก |
| `consultations` | `(customer_id, opened_at)` | ใครควรกลับมาแล้ว และกติกา `customer_lapsed` (หาวันที่มาของลูกค้าแต่ละคน) |
| `appointments` | `(customer_id, status, starts_at)` | ประวัติไม่มาตามนัดของนัดทั้งวัน และ "ไม่มีนัดล่วงหน้า" |
| `appointments` | `(pet_id, status, starts_at)` | "สัตว์ตัวนี้ไม่มีนัดล่วงหน้า" ของวัคซีนที่เลยกำหนด |
