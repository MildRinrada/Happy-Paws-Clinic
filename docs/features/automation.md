# เตือนอัตโนมัติ

ระบบส่งข้อความเตือนลูกค้าเองตามกติกาที่คลินิกตั้ง เช่น "ครบกำหนดวัคซีน 14 วัน ส่ง LINE" หรือ "เตือนนัดล่วงหน้า 24 ชั่วโมง" กติกาหนึ่งข้อคือ `trigger + condition + action` และประเมินที่ฝั่ง server โดยตัวตั้งเวลาเบื้องหลัง (`Infrastructure/Jobs/`) ข้อความทุกฉบับเดินทางผ่าน `INotificationDispatcher` ตัวเดียวกับข้อความอื่น จึงผ่านด่านความยินยอม เลือกช่องทาง LINE แล้ว SMS แล้วอีเมล และลงประวัติการส่งเหมือนกันทุกอย่าง ดู [การแจ้งเตือน](notifications.md)

## endpoint

| Method | Path | Scope | หน้าที่ |
|---|---|---|---|
| GET | `/staff/automations` | `automation:read` | กติกาทั้งหมดพร้อมสถิติการส่งย้อนหลัง |
| POST | `/staff/automations` | `automation:manage` | สร้างกติกา |
| POST | `/staff/automations/{id}/simulate` | `automation:manage` | ดูว่าจะส่งถึงใคร ด้วยข้อความอะไร ก่อนเปิดใช้จริง |
| PATCH | `/staff/automations/{id}` | `automation:manage` | เปิด ปิด หรือแก้ชื่อ เวลา เงื่อนไข และช่องทาง (ส่วนขยาย § 19) |
| DELETE | `/staff/automations/{id}` | `automation:manage` | ลบกติกา ประวัติที่ส่งไปแล้วยังอยู่ (ส่วนขยาย § 19) |
| GET | `/staff/reminders/upcoming` | `automation:read` | ข้อความที่กติกาซึ่งเปิดอยู่จะส่งใน 7 วันข้างหน้า |

## กติกาหนึ่งข้อ

```json
POST /v1/staff/automations
{
  "name": "เตือนวัคซีนล่วงหน้า 14 วัน",
  "trigger":   { "type": "vaccine_due", "offset_days": 14, "send_time": "09:00" },
  "condition": { "branch_id": "brn_...", "species": "สุนัข", "vaccine_name": "Rabies" },
  "action":    { "type": "send_notification", "channel": "line" },
  "enabled": false
}
```

**trigger** คือเรื่องที่เฝ้าดู และเวลาที่จะส่ง

| `type` | เฝ้าดูอะไร | เทมเพลตที่ส่ง |
|---|---|---|
| `vaccine_due` | วันครบกำหนดของเข็มล่าสุดของวัคซีนแต่ละชนิด (`pet_vaccinations.next_due_on`) | `vaccine.due` |
| `appointment_upcoming` | นัดสถานะ `booked` หรือ `confirmed` ที่ไม่ใช่ walk-in | `appointment.reminder` |
| `treatment_plan_session` | แต่ละครั้งของแผนการรักษา ทั้งครั้งที่จองนัดแล้วและยังไม่ได้จอง | `treatment_plan.session` (ใหม่ในรอบนี้) |
| `customer_lapsed` | ลูกค้าที่หายไปนานกว่ารอบปกติของตัวเอง ตามกติกาเดียวกับรายการ "ควรกลับมาแล้ว" ([ส่วนขยาย § 33](../contract-extensions.md)) วันของเรื่องคือวันที่ควรกลับมา | `customer.lapsed` (ใช้ความยินยอมด้านการตลาด) |

เวลาที่ส่งเขียนได้สองแบบ ต้องเลือกแบบเดียว

- `offset_days` กับ `send_time` คือส่งกี่วันก่อนวันของเรื่องนั้น ตามเวลาคลินิก เช่น 14 วันก่อนครบกำหนดตอน 09:00 หรือ 0 วันตอน 08:00 คือเช้าวันนัด ถ้าไม่ส่ง `send_time` ได้ 09:00 วัคซีนใส่ค่าติดลบได้ถึง -30 คือเตือนหลังเลยกำหนด เรื่องอื่นได้ 0 ถึง 30 วัน วัคซีนได้สูงสุด 90 วัน
- `customer_lapsed` นับเป็นวันหลังวันที่ควรกลับมาเท่านั้น `offset_days` ใส่ได้ -1 ถึง -90 เช่น -7 คือ 7 วันหลังจากนั้น
- `offset_hours` คือกี่ชั่วโมงก่อนเวลาเริ่ม 1 ถึง 168 ใช้กับนัดและแผนการรักษาเท่านั้น เพราะวันครบกำหนดวัคซีนไม่มีเวลา ตัวอย่างใน contract คือ T-24h และ T-2h

**condition** ไม่บังคับทุกช่อง

| ช่อง | ใช้กับ | ความหมาย |
|---|---|---|
| `branch_id` | ทุกแบบ | สาขาของกติกา ถ้าไม่ส่ง พนักงานที่ประจำสาขาเดียวได้สาขานั้น ผู้ที่ไม่ถูกจำกัดสาขาได้กติกาทั้งคลินิก พนักงานหลายสาขาต้องระบุ (`422`) |
| `species` | ทุกแบบ | เฉพาะชนิดสัตว์ เทียบแบบไม่สนตัวพิมพ์ |
| `vaccine_name` | วัคซีน | เฉพาะวัคซีนชื่อนี้ เทียบแบบไม่สนตัวพิมพ์ |
| `service_id` | นัดและแผน | เฉพาะบริการนี้ ไม่มีบริการนี้ได้ `422` |
| `unconfirmed_only` | นัด | เฉพาะนัดที่ลูกค้ายังไม่กดยืนยัน |

**action** มีแบบเดียวคือ `send_notification` เลือก `channel` ได้ `auto` (ค่าเริ่มต้น) `line` `sms` หรือ `email` เลือกช่องทางเดียวคือไม่ส่งทางอื่นแทน เทมเพลตผูกกับ trigger ตายตัว เพราะเทมเพลตเตือนนัดต้องมีเวลาและชื่อหมอ ซึ่งวันครบกำหนดวัคซีนไม่มี ส่ง `template` อื่นมาได้ `422`

**enabled** เป็น `false` ถ้าไม่ส่ง กติกาที่เพิ่งสร้างจะส่งข้อความถึงลูกค้าจริงในรอบถัดไป ค่าเริ่มต้นที่ปลอดภัยกว่าคือปิดไว้ แล้วใช้ simulate ดูก่อน

คำตอบเป็น `201` พร้อมกติกา การสร้างเขียน `automation.created` ลง audit log กติกาทุกตัวในคำตอบมี `version` ไว้ส่งเป็น `If-Match` ตอนแก้หรือลบ

## แก้ เปิดปิด และลบกติกา

contract มีแค่สร้าง อ่าน และ simulate สองเส้นนี้เป็นส่วนขยาย [contract-extensions.md § 19](../contract-extensions.md)

```json
PATCH /v1/staff/automations/atm_starter_visit_24h
{ "enabled": true }

PATCH /v1/staff/automations/atm_...
{ "name": "เตือนวัคซีน 7 วัน", "trigger": { "offset_days": 7, "send_time": "10:00" }, "condition": { "species": "" }, "action": { "channel": "line" } }
```

- **รูปเดียวกับตอนสร้าง ทุกส่วนไม่บังคับ** ส่วนที่ไม่ส่งคงเดิม ระบบวางส่วนที่ส่งทับกติกาเดิม แล้วตรวจด้วย validator ตัวเดียวกับ `POST` error จึงชี้ช่องเดียวกัน
- **`trigger.type` เปลี่ยนไม่ได้** (`422`) เทมเพลตและชนิดของเรื่องผูกกับ trigger ถ้าต้องการเตือนเรื่องอื่นให้สร้างกติกาใหม่
- ส่ง `offset_days` หรือ `offset_hours` คือแทนเวลาทั้งชุด ส่งแค่ `send_time` คือเลื่อนเวลาของกติกาที่นับเป็นวัน
- เงื่อนไขที่ส่งเป็นสตริงว่างคือลบเงื่อนไขนั้น `branch_id` ว่างคือทั้งคลินิก ซึ่งทำได้เฉพาะผู้ที่ไม่ถูกจำกัดสาขา
- ส่ง `If-Match` ได้ ถ้า version ไม่ตรงตอบ `409 version_conflict`
- การแก้เขียน `automation.updated` พร้อมรายชื่อช่องที่เปลี่ยน การลบเขียน `automation.deleted`

**แก้แล้วไม่ส่งซ้ำ** กุญแจ "ส่งแล้ว" คือกติกา เรื่อง และวันครบกำหนดหรือเวลาเริ่มของเรื่อง ไม่มีเวลาส่งอยู่ในนั้น นัดที่ได้ข้อความ "ก่อน 24 ชั่วโมง" ไปแล้ว จึงไม่ได้ "ก่อน 2 ชั่วโมง" อีกจากกติกาเดิมหลังแก้ ปิดแล้วเปิดใหม่ก็ไม่ส่งซ้ำ ถ้าต้องการเตือนสองครั้ง ให้มีสองกติกา เลื่อนเวลาให้เร็วขึ้น หรือเปิดกติกาที่ปิดไว้นาน ใช้กติกาส่งตามหลัง 12 ชั่วโมงเดิม เรื่องที่จุดเตือนผ่านไปนานกว่านั้นไม่ได้ข้อความ

**ลบคือซ่อนและหยุด ไม่ใช่ลบแถว** กติกาที่ลบถูกปิด มี `deleted_at` และ `deleted_by_staff_id` หายจากรายการ simulate upcoming และการรันจริง และ `PATCH` หรือ `DELETE` ซ้ำได้ `404` แต่แถวกับ `automation_dispatches` ยังอยู่ ประวัติการส่งจึงยังบอกได้ว่าข้อความเดือนก่อนมาจากกติกาไหน ไม่มีทางกู้กติกาที่ลบแล้ว

รอบของตัวตั้งเวลาที่โหลดกติกาไปแล้วก่อนการปิดหรือลบ อาจส่งรอบนั้นจนจบ รอบถัดไปไม่เห็นกติกานั้นแล้ว

## ใครได้ข้อความ

- **วัคซีน** ไปที่เจ้าของหลักของสัตว์ ใช้เข็มล่าสุดของวัคซีนแต่ละชนิดเท่านั้น สุนัขที่ฉีดพิษสุนัขบ้าทุกปีจึงได้เตือนครั้งเดียวตามเข็มล่าสุด สาขาของเรื่องคือสาขาของการตรวจที่ฉีดเข็มนั้น ถ้าฉีดนอกการตรวจ ใช้สาขาของนัดล่าสุดของสัตว์
- **นัด** ไปที่ลูกค้าของนัด ข้อความมีปุ่มยืนยันและยกเลิกนัดใน LINE ให้เอง เพราะแนบ `appointment_id`
- **แผนการรักษา** ไปที่เจ้าของหลัก เวลาคือเวลาของนัดถ้าจองแล้ว ถ้ายังไม่จองใช้เวลาที่วางแผนไว้ ครั้งที่นัดถูกยกเลิก ไม่มา หรือตรวจไปแล้วไม่ถูกเตือน
- **ลูกค้าที่หายไป** (`customer_lapsed`) ไปที่ตัวลูกค้า ข้อความใช้ชื่อสัตว์ที่ยังมีชีวิตทุกตัว ส่งครั้งเดียวต่อการหายไปหนึ่งรอบ และต้องมีความยินยอมด้านการตลาด ลูกค้าที่ยินยอมเฉพาะข้อความเรื่องการรักษาถูกข้ามด้วย `no_consent` รายละเอียดอยู่ใน [คาดการณ์จากข้อมูลของคลินิก](forecasts.md)
- ไม่เตือนสัตว์ที่เสียชีวิต และเรกคอร์ดลูกค้าที่ถูกรวมไปแล้ว
- นัดที่เริ่มไปแล้ว หรือข้อความที่จะไปถึงหลังนัดเริ่ม (เช่น "เช้าวันนัด 08:00" กับนัด 07:30) ไม่ถูกส่ง

นัดของแผนการรักษาที่จองแล้วเป็นนัดด้วย ถ้าเปิดทั้งกติกาเตือนนัดและกติกาเตือนแผน ลูกค้าได้ทั้งสองข้อความ คลินิกเลือกเปิดตามที่ต้องการ

## ตัวประเมินตัวเดียว

`AutomationEvaluator.EvaluateAsync(rule, now, horizon)` เป็นที่เดียวที่คิดว่ากติกาหนึ่งจะส่งอะไร เมื่อไร ถึงใคร ด้วยถ้อยคำอะไร ทั้งสามทางเรียกตัวนี้

| ทาง | เรียกอย่างไร |
|---|---|
| ตัวตั้งเวลา (ส่งจริง) | `EvaluateAsync(rule, now, now)` แล้วส่งทุกแถวที่ยังไม่เคยส่ง |
| simulate | `EvaluateAsync(rule, now, now + days)` ไม่ส่งอะไร แถวที่ `due_now` คือชุดที่การรันจริงตอนนี้จะส่ง |
| upcoming | `EvaluateAsync` ของทุกกติกาที่เปิดอยู่ ตัดแถวที่ส่งไปแล้วออก |

ผลจึงต่างกันไม่ได้ เพราะช่วงเวลา เงื่อนไข query การตรวจว่าส่งแล้วหรือยัง และถ้อยคำ คำนวณที่เดียว integration test ยืนยันว่าแถว `due_now` ของ simulate ตรงกับสิ่งที่การรันจริงส่งทุกแถว รวมถึงถ้อยคำ

**ความยินยอม** ตัวประเมินถาม `ConsentGate` ตัวเดียวกับ dispatcher แถวที่ลูกค้าไม่ยินยอมแสดงเป็น `would_skip` พร้อม `skip_reason: no_consent` การรันจริงยังส่งแถวนั้นให้ dispatcher ซึ่งบันทึกในประวัติการส่งว่า `skipped` `no_consent` ไม่มีทางข้ามด่านความยินยอม และหน้าประวัติการส่งตอบได้ว่าทำไมลูกค้าไม่ได้ข้อความ

### simulate

```json
POST /v1/staff/automations/atm_.../simulate
{ "days": 7 }
```

body ไม่บังคับ `days` ได้ 1 ถึง 30 ค่าเริ่มต้น 7 ใช้กับกติกาที่ปิดอยู่ได้ คำตอบมี `due_now` (จะส่งทันทีถ้ารันตอนนี้) `would_send` `would_skip` `already_sent` และ `recipients` ทีละแถว แต่ละแถวมีลูกค้า สัตว์ เรื่องที่เตือน เวลาส่ง สถานะ และ `message` ที่เป็นถ้อยคำจริง แสดงไม่เกิน 500 แถว เกินจะมี `truncated: true`

### upcoming

`GET /staff/reminders/upcoming?days=7&branch=&automation_id=` คิดจากข้อมูลล่าสุดทุกครั้ง ไม่มีตารางคิวเก็บไว้ นัดที่ยกเลิกเมื่อนาทีก่อนจึงหายจากรายการทันที ใช้ `days` 1 ถึง 30 เหมือน simulate

### สาขา

- กติกาเป็นของสาขาเดียวหรือทั้งคลินิก พนักงานที่ผูกสาขาเห็นกติกาของสาขาตัวเองกับกติกาทั้งคลินิก กติกาของสาขาอื่นได้ `403` ทั้งตอน simulate ตอนสร้าง ตอนแก้ และตอนลบ
- พนักงานที่ผูกสาขาแก้ เปิดปิด หรือลบกติกาทั้งคลินิกไม่ได้ (`403`) รวมกติกาเริ่มต้นทั้งสี่ แต่ยังดูและ simulate ได้
- ใน simulate และ upcoming พนักงานที่ผูกสาขาเห็นเฉพาะแถวของสาขาตัวเอง และแถวที่ไม่ผูกสาขา กติกายังส่งครบ การกรองมีผลแค่สิ่งที่แสดง

## ตัวตั้งเวลา

`RecurringJobHost<TJob>` เป็น `BackgroundService` ธรรมดาหนึ่งตัวต่องาน ไม่ได้เพิ่มไลบรารีตั้งเวลา เพราะงานรอบละไม่กี่วินาทีถึงชั่วโมง และแต่ละงานจองงานของตัวเองในฐานข้อมูลอยู่แล้ว

| งาน | ทุก | ทำอะไร |
|---|---|---|
| `automations` | 60 วินาที | รันกติกาที่เปิดอยู่ทั้งหมด |
| `report-exports` | 15 วินาที และทันทีเมื่อมีคำขอใหม่ | สร้างไฟล์รายงาน ดู [ภาพรวมและรายงาน](dashboard.md#ส่งออกรายงาน) |
| `housekeeping` | 1 ชั่วโมง | ลบ hold ที่หมดอายุเกินหนึ่งวัน และ idempotency key ที่หมดอายุเกินหนึ่งวัน |

ปิดได้ทั้งหมดด้วย `Jobs:Enabled = false` หรือทีละงาน ดู [วิธีรันและพัฒนา](../development.md#ตัวตั้งเวลาเบื้องหลัง) ในชุด integration test ปิดไว้เสมอ เทสต์เรียกงานเองโดยตรง

ตาราง `automation_dispatches` เป็นบันทึก "ส่งแล้ว" หนึ่งแถวต่อหนึ่งข้อความเตือน มี unique index `(rule_id, subject_kind, subject_id, due_key)`

1. ก่อนส่ง worker ใส่แถวด้วย `INSERT ... ON CONFLICT DO NOTHING` ใน context ของตัวเองซึ่ง commit ทันที
2. ถ้าใส่ได้ worker นั้นเป็นเจ้าของข้อความและส่ง ถ้าใส่ไม่ได้ แปลว่า instance อื่นหรือรอบก่อนหน้าส่งไปแล้ว ข้ามไป
3. ส่งผ่าน dispatcher โดยใช้ id ของแถวเป็น `batch_id` แล้วอ่านผลจากประวัติการส่งกลับมาบันทึกในแถว (`sent`, `skipped`, `failed`)

`due_key` คือวันครบกำหนดหรือเวลาเริ่ม นัดที่ถูกเลื่อนจึงได้เตือนใหม่สำหรับเวลาใหม่ ส่วนนัดเดิมเวลาเดิมไม่ได้สองครั้งจากกติกาเดียว API หลาย instance เปิดตัวตั้งเวลาพร้อมกันได้ ฐานข้อมูลตัดสินให้มีผู้ชนะคนเดียวต่อข้อความ มีเทสต์ที่ให้ห้า worker แย่งกันพร้อมกัน

**ส่งได้มากสุดหนึ่งครั้ง ไม่ใช่อย่างน้อยหนึ่งครั้ง** แถวถูก commit ก่อนข้อความออก ถ้า process ตายระหว่างนั้น แถวค้างสถานะ `claimed` รอบถัดไปหลัง 10 นาทีตรวจประวัติการส่ง ถ้ามีแถวก็บันทึกผลตามนั้น ถ้าไม่มีบันทึกเป็น `lost` และไม่ส่งซ้ำ ลืมเตือนหนึ่งครั้งเสียแค่โทรศัพท์หนึ่งสาย แต่เตือนซ้ำสองครั้งดูเหมือนระบบพัง

**ส่งตามหลัง** ข้อความที่ถึงเวลาแล้วแต่ยังไม่ได้ส่ง เช่นตอน API รีสตาร์ต ยังส่งได้ภายใน 12 ชั่วโมงหลังเวลาที่ตั้งไว้ (`Jobs:Automations:CatchUpHours`) เกินนั้นไม่ส่ง เพราะ "พรุ่งนี้ 10:30" ที่มาช้าสิบสี่ชั่วโมงอ่านผิดความหมาย กติกาที่เพิ่งเปิดจึงไม่ไล่ส่งย้อนหลังให้ทุกคนที่เลยจุดเตือนไปนานแล้ว

## กติกาเริ่มต้น

migration ใส่กติกาให้สี่ข้อ ทั้งหมด **ปิดไว้** เพราะ contract ไม่ได้บอกว่าคลินิกใหม่ควรเริ่มส่งข้อความถึงลูกค้าเองหรือไม่ และการส่งโดยไม่มีใครสั่งเป็นค่าเริ่มต้นที่แย่กว่า

| id | กติกา |
|---|---|
| `atm_starter_vaccine_14d` | เตือนวัคซีนล่วงหน้า 14 วัน เวลา 09:00 |
| `atm_starter_visit_24h` | เตือนนัดล่วงหน้า 24 ชั่วโมง |
| `atm_starter_visit_2h` | เตือนนัดล่วงหน้า 2 ชั่วโมง |
| `atm_starter_plan_1d` | เตือนรอบแผนการรักษาล่วงหน้า 1 วัน เวลา 09:00 |

ทางเปิดใช้คือ simulate กติกาเริ่มต้นเพื่อดูผลก่อน แล้วเปิดสวิตช์ (`PATCH` ด้วย `{ "enabled": true }`) กติกาเริ่มต้นเป็นของทั้งคลินิก จึงเปิดได้เฉพาะผู้ที่ไม่ถูกจำกัดสาขา

## หน้าจอ

อยู่ใต้เมนู "แจ้งเตือนลูกค้า" สองแท็บ รายการแท็บอยู่ใน `frontend/src/features/notifications/content/notification-tabs.ts`

| แท็บ | path | scope |
|---|---|---|
| เตือนอัตโนมัติ | `/notifications/automations` | `automation:read` ฟอร์มสร้างและปุ่มดูตัวอย่างผู้รับต้องมี `automation:manage` |
| ข้อความที่จะส่ง | `/notifications/reminders` | `automation:read` |

- การ์ดของกติกาบอกเรื่อง เวลา สาขา เงื่อนไข ช่องทาง และสถิติ (ส่งแล้ว ข้าม ไม่สำเร็จ 30 วันล่าสุด ครั้งล่าสุด)
- ปุ่ม **ดูตัวอย่างผู้รับ** เลือกดูล่วงหน้า 1 ถึง 30 วัน แสดงผู้รับ ข้อความ และสถานะของแต่ละแถว
- กติกาที่สร้างจากหน้าเว็บผูกกับสาขาที่เลือกอยู่ในคอนโซล กติกาทั้งคลินิกสร้างได้ผ่าน API เท่านั้น
- **สวิตช์เปิดปิด** มุมขวาบนของการ์ด ปิดกดครั้งเดียว เปิดต้องกดยืนยันอีกครั้ง เพราะกติกาจะเริ่มส่งข้อความถึงลูกค้าจริงในรอบถัดไป
- **แก้ไข** เปิดฟอร์มในการ์ด ใช้ช่องชุดเดียวกับฟอร์มสร้าง (ชื่อ เวลา เงื่อนไข ช่องทาง) เรื่องที่เฝ้าดูแสดงไว้แต่เปลี่ยนไม่ได้
- **ลบ** ต้องกดยืนยันอีกครั้ง กติกาหายจากรายการ ประวัติการส่งยังอยู่
- ทั้งสามอย่างขึ้นเมื่อถือ `automation:manage` และกติกาทั้งคลินิกขึ้นเฉพาะผู้ที่ไม่ถูกจำกัดสาขา คนอื่นเห็นข้อความบอกแทน
- ทุกอย่างส่ง `version` ของกติกาไปด้วย หน้าที่เก่าได้ข้อความให้โหลดใหม่
- หน้าประวัติการส่งมีที่มาใหม่ `automation` (เตือนอัตโนมัติ) ไว้กรอง
- เลือกเรื่อง "ลูกค้าหายไปนานกว่าปกติ (คิดถึงน้อง)" แล้วช่องจำนวนวันเปลี่ยนเป็น -7 และมีกล่องสีเหลืองบอกว่าข้อความนี้ใช้ความยินยอมรับข่าวสาร ไม่ใช่ความยินยอมเรื่องการรักษา ฟอร์มแก้ไขของกติกาแบบนี้มีกล่องเดียวกัน

## ข้อจำกัดที่รู้อยู่

| เรื่อง | สถานะ |
|---|---|
| แก้หลังส่งไปแล้ว | เรื่องที่ได้ข้อความจากกติกาไปแล้วไม่ได้ข้อความตามเวลาใหม่ ต้องสร้างกติกาที่สอง |
| กู้กติกาที่ลบ | ทำไม่ได้ สร้างใหม่แทน |
| ถ้อยคำของข้อความ | ใช้เทมเพลตกลางใน `NotificationTemplateCatalogue` กติกาเลือกถ้อยคำเองไม่ได้ |
| ส่งตามหลังหลังระบบดับนาน | เกิน 12 ชั่วโมงไม่ส่ง ปรับได้ที่ `Jobs:Automations:CatchUpHours` (1 ถึง 72) |
| ข้อความที่ worker ตายกลางทาง | บันทึกเป็น `lost` ไม่ส่งซ้ำ |
| LINE | ข้อความไปทาง LINE เมื่อเคาน์เตอร์ผูก LINE ของลูกค้าแล้ว ลูกค้าที่ยังไม่ผูกได้ทาง SMS หรืออีเมล ดู [LINE](line.md#ที่อยู่-line-ของลูกค้า) |
| trigger อื่น | ลูกค้าหายไปนานมีแล้ว (`customer_lapsed`, ส่วนขยาย § 33) วันเกิดและยาใกล้หมดยังไม่มี เพิ่มได้ที่ `AutomationTrigger` และ `AutomationSubjectReader` |
