# ส่วนขยาย contract

`API Reference.dc.html` คือ contract และกติกาหลักของโปรเจกต์คือ ห้ามเปลี่ยนชื่อ path ห้ามเปลี่ยน method ห้ามแต่ง endpoint เอกสารนี้คือทะเบียนข้อยกเว้น คือ **endpoint 36 เส้นและกฎพฤติกรรมสองข้อที่ไม่อยู่ใน reference** ข้อ 1 ถึง 7, 11 ถึง 14 และ 17 ถึง 20 ปิดช่องโหว่ที่เจอตอนสร้างระบบตาม contract ส่วนข้อ 9 10 15 16 และ 21 เป็นฟีเจอร์ที่เจ้าของงานขอเพิ่มเอง

ทุกข้อมีอยู่เพราะเจ้าของ contract อนุมัติหลังได้รับรายงานช่องโหว่ และทุกข้อมีหมายเหตุในโค้ด คือ comment ของ controller, domain type หรือ handler เขียนว่า *"not in the API reference"* หรือชี้กลับมาที่หัวข้อในหน้านี้ (เช่น `docs/contract-extensions.md § 7`) คนที่อ่านทีหลังจึงแยกได้ทันทีว่าส่วนไหนของ API คือ contract และส่วนไหนคือคำตอบของโปรเจกต์นี้ต่อช่องโหว่

> **ถ้าคุณเป็นเจ้าของ contract** หัวข้อทั้งหมดด้านล่างเป็นข้อเสนอที่มีโค้ดทำงานจริงรองรับ ไม่ใช่การตัดสินแทนคุณ แต่ละข้อบอกช่องโหว่ การตัดสิน และสิ่งที่ตั้งใจ *ไม่* ทำ รับ แก้ หรือปฏิเสธได้ โค้ดทำตาม contract การปฏิเสธจึงหมายถึงการลบ ไม่ใช่การเขียนใหม่

## 1. คิวไม่มีทางบอกว่า "คนนี้ก่อน"

**ช่องโหว่** คิวของ contract มาก่อนได้ก่อนล้วน ๆ บวกการข้าม `POST /staff/queue/{id}/skip` ย้ายคิวไปท้าย แต่ไม่มีอะไรย้ายไปหน้า ขณะเดียวกัน `PUT /staff/appointment-types` แยก "นัดปกติ ฉุกเฉิน ติดตามผล ผ่าตัด  กติกาต่างกัน" contract จึงรู้ว่าเคสฉุกเฉินต่างจากเคสอื่น แล้วทิ้งความต่างนั้นไปตอนคนไข้เช็กอิน

**ทำไมสำคัญ** คลินิกที่ให้สุนัขถูกรถชนแซงคิวตัดเล็บในระบบไม่ได้ ก็จะทำอยู่ดี บนกระดาษหรือตะโกนข้ามเคาน์เตอร์ กระดานจึงแสดงลำดับที่คลินิกไม่ได้ใช้ ซึ่งแย่กว่าไม่มีกระดาน จอในห้องรอกลายเป็นสิ่งที่เจ้าของสัตว์เรียนรู้ที่จะไม่สนใจ และตัวเลขเวลารอทุกตัวที่คำนวณจากกระดานเป็นเรื่องแต่ง

**การตัดสิน** สามระดับ คือ `normal`, `urgent`, `emergency` ไม่ใช่ห้าระดับ ทุกระดับที่เพิ่มคือการตัดสินใจอีกครั้งที่เคาน์เตอร์ช่วงยุ่ง และคำถามที่มีความหมายทางคลินิกมีแค่ "ตอนนี้ เร็ว ๆ นี้ หรือตามคิว"

**Endpoint**

```http
POST /staff/queue/{id}/priority        queue:write
{ "priority": "emergency", "reason": "ถูกรถชน เลือดออกไม่หยุด" }
```

และฟิลด์เลือกได้ใหม่สองฟิลด์บน endpoint walk-in เดิม เพื่อให้บอกความเร่งด่วนได้ตั้งแต่ตอนพิมพ์บัตรคิว ไม่ใช่แก้ทีหลังอย่างเดียว

```http
POST /staff/queue/tickets              queue:write
{ ..., "priority": "urgent", "priority_reason": "อาเจียนต่อเนื่อง" }
```

**รายละเอียดที่ควรถกกัน จึงเขียนไว้ตรง ๆ**

- **ลำดับคือ `priority` แล้วคิวที่ยังไม่ถูกข้าม แล้วเวลาที่ถูกข้าม แล้ว `number`** priority อยู่หน้าลำดับการข้าม เคสฉุกเฉินที่มาตอนสาย ๆ จึงไม่ต้องต่อหลังคนที่ถูกข้ามไปแล้ว
- **ระดับสูงกว่า `normal` ต้องมีเหตุผล** ทั้งสอง endpoint และการเปลี่ยนถูกบันทึกลง audit log พร้อมค่าก่อนและหลัง การแซงคิวคือการตัดสินใจที่เจ้าของสัตว์คนอื่นมีสิทธิ์ถามภายหลัง
- **priority ไม่ใช่การเปลี่ยนสถานะ** คิวยังได้เลขเดิมและสถานะเดิม เปลี่ยนแค่ตำแหน่งในลำดับ
- **ใช้ `queue:write` ไม่ใช่ `queue:call`** การจัดกระดานเป็นงานของพนักงานต้อนรับ เป็นสิทธิ์เดียวกับการกำหนดห้อง
- **การเช็กอินไม่ได้อนุมาน priority จากประเภทนัด** contract นิยามประเภทนัดเป็น endpoint ตั้งค่าที่ไม่มี schema จึงไม่มีอะไรให้อ่าน เมื่อ `PUT /staff/appointment-types` มี schema แล้ว การจับคู่ประเภทนัดกับ priority เริ่มต้นเป็นการแก้สองบรรทัดใน `CheckInAppointmentHandler` ซึ่งเป็นที่ที่ถูกต้อง

## 2. `left` อยู่ใน state machine แต่ไม่มีอะไรไปถึง

**ช่องโหว่** state machine ของคิวใน contract คือ `waiting → called → in_room → served` โดยมี `skipped` และ `left` เป็นทางออก มี endpoint คิวเจ็ดเส้น ไม่มีเส้นไหนทำให้เกิด `left`

**ทำไมสำคัญ** เจ้าของที่รอไม่ไหวแล้วกลับบ้านจะค้างอยู่บนกระดานไปเรื่อย ๆ ด้วย contract ตามที่เขียน มีทางออกแค่สองทางและผิดทั้งคู่ คือปล่อยให้รอตลอดไป ซึ่งทำให้กระดานและค่าเฉลี่ยเวลารอเป็นเท็จ หรือตั้งเป็น `served` ซึ่งใส่การมาพบที่ไม่ได้เกิดขึ้นลงในตัวเลขของวันและตัวเลขผลงานของสัตวแพทย์

**การตัดสิน** endpoint เรียบ ๆ และ `reason` ที่ควรเก็บ เพราะ "รอไม่ไหว" กับ "นัดใหม่แล้ว" เป็นข้อเท็จจริงคนละเรื่องเกี่ยวกับคลินิก

```http
POST /staff/queue/{id}/leave           queue:write
{ "reason": "รอไม่ไหว ขอนัดใหม่" }
```

`left` เป็นสถานะสิ้นสุด ตามแผนภาพของ contract เอง การแยกจาก `served` คือเหตุผลทั้งหมดของ endpoint นี้

## 3. `void` อยู่ใน state machine ของใบแจ้งหนี้ แต่ไม่มีอะไรไปถึง

**ช่องโหว่** รูปเดียวกับ § 2 ในเรื่องเงิน state machine ของใบแจ้งหนี้มี `void` Billing มีสร้าง ส่วนลด ชำระ คืนเงิน และใบเสร็จ แต่ไม่มี void

**ทำไมสำคัญ** บิลที่ออกผิด ทำได้แค่คืนเงิน ซึ่งในทางบัญชีไม่ใช่เหตุการณ์เดียวกัน การคืนเงินบอกว่าเงินเข้ามาแล้วออกไป การ void บอกว่าใบแจ้งหนี้ไม่ควรมีตั้งแต่แรก รายงานที่แยกสองอย่างนี้ไม่ได้จะบอกรายได้และการคืนเงินสูงเกินจริงทั้งคู่ และเป็นปัญหาตั้งแต่ครั้งแรกที่มีคนกระทบยอดสิ้นเดือน

**Endpoint**

```http
POST /staff/invoices/{id}/void         invoice:write
{ "reason": "ออกบิลผิดคน" }
```

- **ทำได้จาก `open` เท่านั้น** สถานะของใบแจ้งหนี้คำนวณจากเงิน ไม่ได้เก็บแยก "open" กับ "ยังไม่ได้รับเงิน" จึงเป็นข้อความเดียวกัน กฎนี้จึงไม่ต้องตรวจซ้ำอีกทาง และไม่มีทางเพี้ยนจากกัน เมื่อลูกค้าจ่ายแล้ว การ void จะลบธุรกรรมที่เกิดขึ้นจริง และเงินในลิ้นชักจะขาดเท่ายอดนั้น การแก้กรณีนั้นคือการคืนเงิน ซึ่งบอกว่าคืนอะไรและทำไม
- ต้องมีเหตุผล แถวใบแจ้งหนี้ยังอยู่ด้วย `status: void`
- บันทึก audit เป็น `invoice.voided` พร้อมเลขที่และยอดรวมใน details

**ใช้ scope `invoice:write` ไม่ใช่ `invoice:void` ที่สร้างใหม่** รายการ scope ของ contract ปิดตาย `PUT /staff/roles/{id}/permissions` ถูกกำหนดให้ปฏิเสธ scope ที่ไม่รู้จัก scope ที่แต่งขึ้นที่นี่จะทำให้ไม่มี role ใดใน reference เรียก endpoint ได้ คนที่ออกบิลได้ย่อมยกเลิกบิลที่ยังไม่ได้รับเงินได้

**สร้างพร้อมโมดูล Billing** ตามที่หัวข้อนี้บอกไว้ สเปกด้านบนไม่เปลี่ยนจากตอนเขียน การสร้างจริงไม่ได้เผยเหตุผลให้ต้องแก้

## 4. ไม่มีความยินยอม ระยะเก็บข้อมูล หรือการลบข้อมูลที่ไหนใน contract

**ช่องโหว่** 164 endpoint ไม่มีเส้นไหนบันทึกว่าเจ้าของยินยอมอะไร บอกระยะเก็บข้อมูล หรือรับคำขอดูหรือลบข้อมูลส่วนบุคคล ค้นคำว่า consent, PDPA, retention หรือ erasure ใน reference ไม่เจออะไรเลย

**ทำไมสำคัญ** นี่คือข้อที่เสี่ยงที่สุดในรายการ และไม่ใช่ฟีเจอร์ คลินิกเก็บข้อมูลติดต่อและข้อมูลสุขภาพของคนที่ระบุตัวได้ ในประเทศไทย ภายใต้ PDPA หน้าที่ตามกฎหมายมีอยู่ไม่ว่า API จะรองรับหรือไม่ สิ่งที่ API ตัดสินคือคลินิก *พิสูจน์* ได้หรือไม่ว่าทำตามแล้ว ถ้าไม่มีส่วนนี้ ลูกค้าที่ขอหยุดรับข้อความเป็นแค่กระดาษโน้ต และลูกค้าที่ถามว่าเก็บข้อมูลอะไรของเขาไว้ เป็นอีเมลที่อีกแปดเดือนไม่มีใครหาเจอ

**การตัดสิน มีสองเรื่อง และแยกจากกัน**

### ความยินยอมเป็นสมุดบัญชี ไม่ใช่ธง

ทุกการให้และทุกการถอนเป็นแถวใหม่ สถานะปัจจุบันคือแถวล่าสุดของแต่ละวัตถุประสงค์ boolean ที่แก้ได้ตอบได้แค่ "วันนี้ส่งข้อความหาเขาได้ไหม" แต่คำถามตอนมีเรื่องร้องเรียนคือ *"เขายินยอมวันไหน และถอนเมื่อไร"* ซึ่งคอลัมน์เดียวตอบไม่ได้

สี่วัตถุประสงค์ ยินยอมและถอนแยกกัน

| วัตถุประสงค์ | ค่าเริ่มต้น | ทำไมเป็นค่านี้ |
|---|---|---|
| `service_messages` | **ยินยอม** | เตือนนัด เรียกคิว สรุปการมาพบ เจ้าของให้เบอร์โทรกับคลินิกเพื่อให้ติดต่อเรื่องสัตว์ของเขา ถ้าถือว่ายังไม่ยินยอม ข้อความเตือนนัดจะเงียบไป |
| `marketing` | ไม่ยินยอม | โปรโมชันต้อง opt-in เสมอ |
| `medical_record_sharing` | ไม่ยินยอม | ส่งเวชระเบียนให้คลินิกที่ส่งต่อหรือบริษัทประกัน |
| `extended_data_processing` | ไม่ยินยอม | เก็บข้อมูลเกินที่การรักษาต้องใช้ เช่น วิจัย ข้อมูลรวม เก็บนานกว่าความจำเป็นทางคลินิก |

```http
GET  /portal/consents                        portal
PUT  /portal/consents                        portal
GET  /staff/customers/{id}/consents          customer:read
POST /staff/customers/{id}/consents          customer:write
```

route ฝั่งพนักงานมีเพราะคลินิกในไทยส่วนใหญ่รับความยินยอมเป็นกระดาษที่เคาน์เตอร์ แถวนั้นบันทึกว่า **ใคร** เป็นคนกรอก ความยินยอมที่บันทึกแทนคนอื่นโดยไม่รู้ว่าใครบันทึก ไม่เป็นหลักฐานของอะไรเลย

**ส่วนที่ทำให้เป็นของจริง** ความยินยอมบังคับที่ notification port ไม่ใช่ในแต่ละ use case `ConsentAwareNotificationDispatcher` ครอบหน้าทุกช่องทาง และ `INotificationDispatcher` ซึ่งเป็นสิ่งเดียวที่ use case resolve ได้ *ก็คือ* decorator ตัวนั้น จึงไม่มีทางส่งข้อความโดยไม่ผ่านด่าน กฎที่ตรวจที่จุดเรียกแต่ละจุดในสี่จุดตอนนี้ จะพลาดที่จุดที่ห้า และผลของการพลาดคือข้อความการตลาดถึงคนที่ขอไม่รับแล้ว

ข้อความที่ถูกกันไว้บันทึก log ระดับ information ไม่ได้ทิ้งเงียบ ๆ เพราะ "ทำไมเจ้าของไม่ได้ข้อความเตือน" เป็นคำถามที่เคาน์เตอร์จะถาม

### คำขอของเจ้าของข้อมูลเป็น workflow ไม่ใช่ action

```http
POST /portal/data-requests                   portal
GET  /staff/data-requests?status=open        customer:read
POST /staff/data-requests/{id}/close         customer:write
```

**ไม่มีอะไรตรงนี้ลบข้อมูล โดยตั้งใจ** คำขอลบข้อมูลที่คลินิกสัตว์ชนตรง ๆ กับการเก็บเวชระเบียน เวชระเบียนที่ลงนามแล้วเป็นหลักฐานการรักษาที่ให้กับสัตว์ และกฎของระบบนี้เองคือไม่ลบเวชระเบียน การหาจุดลงตัวเป็นการตัดสินใจที่คนต้องทำและรับผิดชอบ สิ่งที่ API รับประกันจึงเป็นส่วนที่ก่อนหน้านี้ทำไม่ได้ คือคำขอ **ถูกรับ ถูกจับเวลา และได้คำตอบ** ทุกแถวมี `open_days` และรายการฝั่งพนักงานเรียง **เก่าสุดก่อน** ต่างจากรายการอื่นทั้งหมดในระบบ เพราะแถวบนสุดของรายการนี้คือคำขอที่ใกล้เส้นตายตามกฎหมายที่สุด

`refused` เป็นผลลัพธ์ชั้นหนึ่งคู่กับ `completed` และต้องมี `resolution` การปฏิเสธคำขอลบเพราะกฎหมายบังคับให้เก็บเวชระเบียนทำได้ แต่การปฏิเสธเงียบ ๆ ทำไม่ได้

**ตั้งใจไม่ทำ** *ระยะเวลา* การเก็บข้อมูล การบอกว่า "เก็บเวชระเบียน N ปี ข้อมูลติดต่อ M ปี" ต้องใช้นโยบายที่ที่ปรึกษาของคลินิกกำหนด การตั้งค่าเริ่มต้นเองคือการให้คำแนะนำทางกฎหมายเอง สมุดความยินยอมกับ workflow คำขอเป็นสองชิ้นที่ผิดถ้าปล่อยไว้จนมีคนถาม ส่วนตารางระยะเก็บเป็นเรื่องค่าตั้งของ `PATCH /clinic/settings/*` เมื่อ schema ถูกกำหนด

## 5. ไม่มีที่ไหนบอกว่าต้อง audit action ไหน

**ช่องโหว่** `GET /staff/audit-logs` และ `GET /staff/audit-logs/access` อ่านข้อมูล audit และ `GET /staff/medical-records/{id}/audit` แสดง diff รายเวชระเบียน contract ไม่เคยบอกว่าต้องเขียนอะไรลงไปเลย

**ทำไมสำคัญ** ถ้าไม่มีรายชื่อ คำว่า "มี audit" จะกลายเป็นเท่าที่แต่ละโมดูลจำได้ ซึ่งแยกไม่ออกจากการไม่มี audit และพังแบบมองไม่เห็นที่สุด เพราะ endpoint ยังตอบ 200 ด้วยรายการที่สั้นกว่าความจริง

**การตัดสิน** ไม่มี endpoint ใหม่ เป็นรายชื่อในไฟล์เดียว `Domain/Auditing/AuditActions.cs` ที่ `AuditEntry.Write` ตรวจกับรายชื่อนี้ การเขียน action ที่ไม่อยู่ในรายชื่อจึงโยน exception แทนที่จะสร้างหมวดที่ไม่มีใคร query เงียบ ๆ กฎสองข้อกำหนดว่าอะไรอยู่ในรายชื่อ

> action ถูก audit ถ้า **แตะข้อมูลส่วนบุคคลหรือข้อมูลสุขภาพ** หรือ **เปลี่ยนว่าใครทำอะไรได้** ไม่มีอะไรถูก audit เพียงเพราะนักพัฒนาสนใจ log ถูกอ่านตอนเกิดเหตุ และปริมาณคือสิ่งที่ทำให้ log อ่านไม่ได้

รายชื่อเป็น **ข้อกำหนด ไม่ใช่บัญชีของที่มี** หลายรายการเป็นของ endpoint ที่ยังไม่สร้าง และคงไว้เพื่อให้การสร้าง endpoint นั้นโดยไม่มีแถว audit เห็นชัดว่าตกหล่น

**มีสองเรื่องที่ยืนยันด้วยเทสต์ ไม่ได้ปล่อยให้เป็นธรรมเนียม** action ประเภท "access" ทุกตัวต้องเป็น action ที่รู้จัก log การเข้าถึงจึงกรองหาสิ่งที่ตัวเขียนไม่ยอมบันทึกไม่ได้ และชื่อ action ที่ไม่รู้จักถูกปฏิเสธทันที

**สิ่งเดียวที่ตั้งใจไม่ audit** คือ autosave ร่างการตรวจ ซึ่งยิงทุกสิบวินาทีต่อเคสที่เปิดอยู่ ถ้าบันทึกทุกครั้งจะกลบทุกอย่างที่สำคัญ เวชระเบียนที่ลงนามและ amendment บอกอยู่แล้วว่าเคสจบที่อะไร การตัดสินนี้เขียนไว้ข้างรายชื่อ จึงอ่านเป็นการเลือก ไม่ใช่การลืม

**การอ่านที่สำคัญที่สุดคือสิ่งที่ไม่มีอะไรอื่นจับได้** `GET /staff/medical-records/{id}` เขียน `record.viewed` ก่อนคืนค่า ซึ่งเป็นเหตุผลที่การเปิดเวชระเบียนเป็น use case ไม่ใช่ controller ที่หยิบจาก repository ตรง ๆ [authorization.md](./authorization.md) ระบุเรื่องนี้ไว้ และส่วนนี้ทำให้เกิดขึ้นจริง

## 6. นัดในอนาคตของสัตว์ที่เสียชีวิตไม่มีนิยาม

**ช่องโหว่** `POST /staff/pets/{id}/deceased` บรรยายว่า "ปิดเรกคอร์ดอย่างสุภาพ  หยุดแจ้งเตือนทุกชนิด" แต่ไม่ได้พูดถึงนัดที่อยู่ในปฏิทินแล้ว

**ทำไมสำคัญ** ความเงียบปล่อยค่า default ที่แย่ที่สุดไว้ นัดยังถูกจอง automation เตือนนัดยิงก่อน 24 ชั่วโมง และเจ้าของที่กำลังเสียใจถูกขอให้ยืนยันนัดของสัตว์ที่ตายไปแล้ว ถ้าข้อความเตือนถูกกันไว้ เคาน์เตอร์ก็จะโทรไปแทน เพราะ slot ยังอยู่บนกระดาน

**การตัดสิน ยกเลิก และบอกครั้งเดียว** พิจารณาทางเลือกทั้งหมดแล้ว

| ทางเลือก | ผล |
|---|---|
| ปล่อยนัดไว้ | โทรศัพท์ตามที่เล่าข้างบน และกันเวลาคลินิกที่ไม่มีใครใช้ |
| ยกเลิกเงียบ ๆ | เจ้าของรู้เองตอนเห็นปฏิทินว่าง |
| **ยกเลิกและส่งข้อความเดียว** | **เลือกแบบนี้** ข้อความเดียว ไม่ใช่ข้อความละนัด |

ไม่มี endpoint ใหม่ endpoint เป็นของ contract สิ่งที่ใหม่คือกฎที่เขียนชัด และทำใน transaction เดียว คือ ตั้งสัตว์เป็นเสียชีวิต ยกเลิกนัดในอนาคตทุกนัดด้วยเหตุผล `สัตว์เลี้ยงเสียชีวิต` บันทึก audit ทุกการยกเลิก แล้วส่งการแจ้งเตือนเดียวหลัง commit

**ตั้งใจไม่ทำ** ประวัติไม่ถูกแตะ การมาพบที่ผ่านมา เวชระเบียนที่ลงนาม และใบแจ้งหนี้ อยู่ที่เดิมทั้งหมด "ปิดเรกคอร์ดอย่างสุภาพ" หมายถึงหยุดให้คลินิกติดต่อออกไป ไม่ได้หมายถึงลบตัวตนของสัตว์

## 7. Billing มีแต่ `POST` หกเส้น แคชเชียร์ดูบิลไม่ได้

**ช่องโหว่** หมวด Billing ของ contract มีหกเส้นและทุกเส้นเป็นการเขียน คือ `POST /staff/invoices`, `/discounts`, `/payments`, `/refunds`, `/receipt` บวก `GET /portal/invoices` ของลูกค้า ไม่มี `GET /staff/invoices` และไม่มี `GET /staff/invoices/{id}` พนักงานสร้างบิล ให้ส่วนลด รับเงิน และพิมพ์ได้ แต่ไม่มีทางในเอกสารที่จะอ่านบิล

**ทำไมสำคัญ** id ของใบแจ้งหนี้มีอยู่แค่ใน response ของคำขอล่าสุดที่แตะมัน สัตวแพทย์ปิดเคสชั้นบนตอน 11:00 บิลถูกออก ลูกค้ามาถึงเคาน์เตอร์ 11:05 และแคชเชียร์ไม่มีทางหาบิลเจอ ทุก workflow ในโมดูลต้องมี id อยู่ในมือก่อน แต่ไม่มีอะไรแจก id ให้ นี่ไม่ใช่ช่องโหว่เรื่องความสะดวก แต่เป็นความต่างระหว่างโมดูลที่ใช้งานได้ กับโมดูลที่ผ่านแค่เทสต์ของตัวเอง

contract ไม่ได้ไม่รู้เรื่องนี้ `GET /staff/customers/{id}` สัญญา "ยอดค้างชำระ" ไว้ แต่นั่นคือยอดรวมของลูกค้าคนเดียว ไม่ใช่รายการบิล และอยู่ใน endpoint ของอีกหมวดหนึ่ง (ตอนนี้สร้างแล้ว และคืนยอดค้างผ่าน `OutstandingSatang` ใน `CustomerDto`)

**Endpoint**

```http
GET /staff/invoices/{id}                                        invoice:write
GET /staff/invoices?status=open&branch=&customer_id=&from=&to=   invoice:write
```

- **ใช้ scope `invoice:write`** ด้วยเหตุผลเดียวกับ § 3 รายการ scope ปิดตาย ไม่มี `invoice:read` และ role ที่ถือ `invoice:*` คือ role ที่ต้องดูบิลพอดี นี่คือทางที่ประดิษฐ์น้อยที่สุด ไม่ใช่ทางที่ดีที่สุด ถ้า contract เพิ่ม `invoice:read` การแก้คือหนึ่ง attribute ต่อ action
- **รายการจำกัดสาขาใน repository** ไม่ใช่ใน handler ตัวกรองและการเทียบ keyset จึงอยู่ใน query เดียวกัน handler ที่กรองทีหลังจะคืนหน้าที่สั้นกว่าที่ควร และ `next_cursor` ที่ชี้เข้าบิลของสาขาอื่น
- **ใหม่สุดก่อน** keyset บน `(issued_at, id)` เหมือนรายการอื่นทั้งหมดในระบบ

**ตั้งใจไม่ทำ** การอ่านบิลใบเดียวฝั่งลูกค้า `GET /portal/invoices` อยู่ใน contract และแสดงบิลของลูกค้าเองครบ ซึ่งพอสำหรับ portal ถ้าเพิ่ม `GET /portal/invoices/{id}` จะเป็นการแต่งโดยไม่มีที่ใช้

สองข้อนี้ไม่ใช่ช่องโหว่แบบข้างบน contract ขอให้มีอยู่แล้ว แต่ไม่ได้บอกว่าต้องทำอะไร และคำตอบมีผลมากพอที่จะบันทึกที่นี่ ไม่ใช่แค่ใน comment ของโค้ด

### `POST /staff/consultations/{id}/prescriptions` "ตรวจแพ้ยา"

contract ให้ endpoint สั่งยาตรวจการแพ้ แต่ไม่บอกว่าการตรวจต้องทำอะไร สุดขั้วทั้งสองทางผิด การปฏิเสธเด็ดขาดคือระบบตัดสินแทนสัตวแพทย์ที่ตัดสินแล้วว่าต้องใช้ยานั้น ซึ่งเกิดขึ้นจริงและใบสั่งยากระดาษก็ยอมให้ทำ ส่วนการเตือนเงียบ ๆ ทำให้การตรวจเป็นแค่ของประดับ

**คำตอบ** ครั้งแรกปฏิเสธด้วย `409 allergy_conflict` พร้อมระบุการแพ้ใน `details` ผู้เรียกส่งคำขอซ้ำพร้อม `acknowledge_allergy` ได้ ค่านี้เก็บไว้ในใบสั่งยาและบันทึก audit ภายใต้ action ของตัวเอง การแพ้ระดับ **รุนแรง** ข้ามผ่าน API ไม่ได้เลย การตัดสินแบบนั้นต้องคุยกัน ไม่ใช่ลองใหม่

ข้อจำกัดของการตรวจเขียนไว้ตรง ๆ ทุกที่ที่ปรากฏ คือจับคู่ที่ชื่อยา ไม่รู้จักกลุ่มยา แพ้ penicillin จะไม่ถูกเตือนเมื่อสั่ง amoxicillin การปิดช่องนี้ต้องมีฐานข้อมูลยาซึ่งระบบนี้ไม่มี และการแกล้งทำเป็นว่ามีจะแย่กว่าการบอกข้อจำกัดตามจริง

### `POST /staff/consultations` เปิดเคสให้คนไข้ที่ยังไม่มีใครเรียก

flow ของ contract แสดง `call` แล้วจึง `consultations` และ state machine ของคิวอนุญาตแค่ `called → in_room` แต่สัตวแพทย์ที่เดินออกไปรับคนไข้เองเป็นเรื่องปกติ ทั้งในคลินิกเล็กและคลินิกที่ยุ่งตอนเครื่องเรียกคิวเสีย การปฏิเสธคือการบังคับให้กดปุ่มที่ไม่ได้เพิ่มอะไร

**คำตอบ** การเปิดเคส *คือ* การเรียก นับเป็นของสัตวแพทย์ที่เปิด `called_at` จึงมีค่าจริงสำหรับสถิติเวลารอ ไม่เป็น null และ state machine ยังเข้มเหมือนเดิม

## 9. บทความสุขภาพสัตว์

contract ไม่มีเรื่องบทความเลย แต่หน้าแรกของคลินิกมีคอลัมน์ "บทความจากทีมสัตวแพทย์" และเมนูบทความ เดิมคอลัมน์นี้เป็นข้อความตายตัวในโค้ดหน้าเว็บ เจ้าของงานขอให้เป็นข้อมูลจริงที่หน้าเว็บอ่านจาก API และมีข้อมูลตัวอย่าง (2026-10-01)

ข้อนี้ต่างจากข้ออื่นในหน้านี้ ไม่ใช่ช่องโหว่ที่เจอระหว่างทำตาม contract แต่เป็นฟีเจอร์ที่ขอเพิ่ม จึงทำแค่เท่าที่ขอ

**คำตอบ** endpoint สาธารณะสองเส้น ไม่ต้องเข้าสู่ระบบ

| Method | Endpoint | ทำอะไร |
|---|---|---|
| GET | `/articles?limit=` | บทความที่เผยแพร่แล้ว ใหม่สุดก่อน `limit` 1 ถึง 50 ค่าเริ่มต้น 10 ไม่มีเนื้อหาเต็ม |
| GET | `/articles/{slug}` | บทความหนึ่งเรื่องพร้อมเนื้อหา บทความที่ไม่มีหรือยังไม่ถึงเวลาเผยแพร่ตอบ 404 เหมือนกัน |

บทความเข้าระบบทางเดียว คือคำสั่ง operator `seed-articles` ที่ใส่บทความตัวอย่างสี่เรื่องจาก `SampleArticles.cs` รันซ้ำได้ เรื่องที่มี slug อยู่แล้วถูกข้าม ไม่ถูกเขียนทับ

**สิ่งที่ตั้งใจไม่ทำ**

- **ไม่มี endpoint เขียนบทความ** การสร้าง แก้ ซ่อน บทความผ่าน API ต้องมี scope ใหม่ ซึ่งชนกับกติกาว่ารายการ scope ของ contract ปิดตาย จึงรอให้ตัดสินก่อน ภายหลังเจ้าของ contract อนุมัติ scope `content:manage` และเส้นเขียนบทความแล้ว ดู § 26
- **ไม่ใช้ cursor** รายการบทความสั้นและหน้าแรกอ่านแค่สามเรื่อง ถ้าบทความเยอะขึ้น เพิ่ม cursor ทีหลังได้โดยไม่ทำให้ผู้ใช้เดิมพัง
- **เนื้อหาเป็นข้อความล้วน ไม่ใช่ HTML หรือ Markdown** บรรทัดว่างคั่นย่อหน้า หน้าเว็บแสดงเป็นข้อความ บทความจึงพา script หรือลิงก์แปลกปลอมเข้าหน้าเว็บไม่ได้ และไม่ต้องดูแลตัว sanitize
- **รูปปกเป็น path ใต้ `/public` ของหน้าเว็บเท่านั้น** ไม่รับ URL ภายนอก หน้าเว็บจึงไม่โหลดรูปจากที่ที่คลินิกไม่ได้ควบคุม

รายละเอียดการใช้งานอยู่ใน [บทความ](features/articles.md)

## 10. แผนก โปรไฟล์สาธารณะ และหน้าทีมของเรา

contract แยกพนักงานได้สองแบบ คือ `staff_type` (ตำแหน่งที่คลินิกตั้งชื่อเอง) และ role (ชุดสิทธิ์) แต่ไม่มีอะไรบอกว่าใครอยู่ทีมไหน และไม่มี endpoint สาธารณะที่แนะนำคนของคลินิกเลย การ์ดสัตวแพทย์บนหน้าแรกจึงเป็นข้อความตายตัวในโค้ดหน้าเว็บ เจ้าของงานขอหน้ารวมบุคลากรที่แยกหมวดชัดเจน และ API ที่แยก role กับแผนกออกจากกัน (2026-10-01)

ข้อนี้เป็นฟีเจอร์ที่ขอเพิ่มเหมือน § 9 ไม่ใช่ช่องโหว่ที่เจอตอนทำตาม contract

**การตัดสิน** แผนกเป็นคนละเรื่องกับ role และไม่เคยถูกใช้ตัดสินสิทธิ์

| | role | แผนก |
|---|---|---|
| ตอบคำถาม | คนนี้ทำอะไรในระบบได้ | คนนี้อยู่ทีมไหน |
| ใครกำหนด | คลินิกสร้างเองได้ ผ่าน `/staff/roles` | รายการตายตัวหกแผนก |
| ถูกตรวจทุกคำขอ | ใช่ | ไม่เลย |

แผนกมีหกแผนก คือ `veterinary` ทีมสัตวแพทย์, `nursing` ผู้ช่วยสัตวแพทย์, `front_desk` ต้อนรับและนัดหมาย, `finance` การเงิน, `management` บริหารคลินิก และ `support` ทีมสนับสนุน เป็นรายการตายตัวเพราะหน้าสาธารณะต้องเรียงและอธิบายแต่ละแผนกได้ ส่วน `staff_type` ยังเป็นป้ายที่คลินิกตั้งเองเหมือนเดิม

**Endpoint ใหม่**

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/team?department=` | ไม่ต้องเข้าสู่ระบบ | คนที่ตั้งให้แสดงบนเว็บ จัดกลุ่มตามแผนก |
| GET | `/staff/departments` | `staff:read` | ทุกแผนกพร้อมจำนวนคนที่ทำงานอยู่ |
| PUT | `/staff/members/{id}/public-profile` | `staff:manage` | แทนที่โปรไฟล์สาธารณะทั้งก้อน และเปิดปิดการแสดงบนเว็บ |

**ส่วนที่เพิ่มบน endpoint เดิมของ contract** ไม่เปลี่ยนของเดิม แค่เพิ่ม

- `GET /staff/members` รับ `?department=` และ `?role=` เพิ่ม ทั้งสองใช้คู่กับตัวกรองเดิมได้ แผนกที่ไม่มีในรายการตอบ `422` ส่วนชื่อ role ที่ไม่มีใครถือได้รายการว่าง เหมือน `staff_type` ที่ไม่มีใครใช้
- ทุกแถวของรายชื่อพนักงานมีช่อง `department` และ `public_profile` เพิ่ม
- `PATCH /staff/members/{id}` รับ `department` เพิ่ม

**สมาชิกใหม่อยู่แผนกไหน** คำเชิญไม่มีช่องแผนก สมาชิกที่รับคำเชิญจึงเริ่มที่แผนกตาม `staff_type` เช่น `veterinarian` ไป `veterinary` และ `staff_type` ที่ไม่รู้จักไป `support` แล้วคลินิกย้ายได้ด้วย `PATCH` migration ใช้กติกาเดียวกันกับพนักงานที่มีอยู่ก่อน

ข้อมูลตัวอย่างเข้าระบบด้วยคำสั่ง operator `seed-staff` ซึ่งใส่บุคลากร 14 คนครบทุกแผนก บัญชีเหล่านี้เข้าสู่ระบบไม่ได้ เพราะรหัสผ่านถูกสุ่มแล้วทิ้ง

**สิ่งที่ตั้งใจไม่ทำ**

- **ไม่แสดงใครโดยอัตโนมัติ** การเป็นพนักงานไม่ได้แปลว่ายินยอมให้ชื่อและหน้าขึ้นเว็บ `show_on_website` จึงปิดไว้ก่อนเสมอ
- **หน้าสาธารณะไม่มีข้อมูลภายใน** `GET /team` ไม่ส่งอีเมล เบอร์โทร role สาขา เลขใบอนุญาต หรือสถานะบัญชี
- **ไม่มีป้าย "ว่างวันนี้" บนหน้าสาธารณะ** การ์ดเดิมบนหน้าแรกมีป้ายนี้ ตอนทำส่วนนี้ยังไม่มี API สร้างกะทำงาน ป้ายจึงถูกแทนด้วยตำแหน่งแทนที่จะแสดงข้อมูลที่ไม่จริง ตอนนี้ตารางเวรมีแล้ว ([ตารางเวร](features/schedules.md)) ป้ายนี้ทำได้ แต่ต้องมี endpoint สาธารณะเพิ่มที่บอกว่าใครว่างวันไหน ซึ่งยังไม่ได้ขอ
- **ไม่เพิ่ม scope ใหม่** แก้โปรไฟล์ใช้ `staff:manage` ตัวเดียวกับการแก้พนักงาน และถูกจำกัดด้วยกติกาเดิม คือแก้ได้เฉพาะคนในสาขาของตัวเอง และแก้คนที่มีสิทธิ์มากกว่าตัวเองไม่ได้
- **รูปเป็น path ใต้ `/public` เท่านั้น** เหตุผลเดียวกับรูปปกบทความ

รายละเอียดการใช้งานอยู่ใน [ทีมของเรา](features/team.md)

## 11. ผลแล็บที่ยังไม่มีคนอ่าน ไม่มีทางบอกว่าอ่านแล้ว

`GET /staff/lab-requests?status=pending` บรรยายว่า "งานค้างของหมอ ผลที่ยังไม่มีคนอ่าน" มีสองสถานะในประโยคเดียว คือรอแล็บ และรอหมออ่าน แต่ไม่มี endpoint ใดทำให้ผลพ้นจากรายการ "ยังไม่มีคนอ่าน" ได้ การเปิดดูรายการก็ไม่ใช่การอ่านผล เพราะคนที่เลื่อนผ่านรายการยังไม่ได้เห็นค่าที่ผิดปกติ

**คำตอบ** `POST /staff/lab-requests/{id}/review` ด้วย `lab:read` บันทึกว่าใครอ่าน เมื่อไร และเขียน audit `lab.results_reviewed` ผลที่ส่งเข้ามาเพิ่มหลังจากนั้นทำให้คำขอกลับไปอยู่ในรายการ "ยังไม่มีคนอ่าน" อีกครั้ง

**ทำไมใช้ `lab:read`** การอ่านผลคือการอ่าน ไม่ได้สร้างหรือแก้ข้อมูลทางคลินิก และ role `veterinarian` ใน contract ถือ `lab:*` อยู่แล้ว ไม่ต้องคิด scope ใหม่

**สิ่งที่ตั้งใจไม่ทำ** ไม่ทำเครื่องหมายอ่านแล้วอัตโนมัติเมื่อเปิดรายการ และไม่ลบผลที่อ่านแล้วออกจากระบบ

## 12. อัปโหลดผ่าน pre-signed URL แต่ไม่มีที่เก็บไฟล์

`POST /staff/pets/{id}/documents` บรรยายว่า "อัปโหลดผ่าน pre-signed URL" ซึ่งเป็นวิธีของที่เก็บไฟล์แบบ S3 คือ API ออก URL ที่ลงชื่อแล้ว และ client ส่งไฟล์ไปที่ URL นั้นตรง ๆ แต่โปรเจกต์นี้ยังไม่มีที่เก็บไฟล์ภายนอก

**คำตอบ** ที่เก็บไฟล์ในเครื่อง (`LocalFileStorage`) ทำงานแบบเดียวกับ S3 คือออก URL ที่ลงชื่อด้วย HMAC-SHA256 มีอายุ จำกัดชนิดไฟล์ และขนาดสูงสุด ตัว URL ชี้กลับมาที่ API สองเส้นนี้

| Method | Endpoint | ทำอะไร |
|---|---|---|
| PUT | `/storage/uploads/{token}` | รับไฟล์ ตอบ `204` หรือ `403` ถ้า token ผิด หมดอายุ ชนิดไม่ตรง หรือไฟล์ใหญ่เกิน |
| GET | `/storage/files/{token}` | ส่งไฟล์กลับ ตอบ `404` ถ้า token หรือไฟล์ไม่ถูก |

สองเส้นนี้ **ไม่ใช่ API ของคลินิก** แต่เป็นตัวแทนของที่เก็บไฟล์ ไม่มี scope ไม่มีเซสชัน เพราะ token ใน path คือสิทธิ์ทั้งหมด เหมือน pre-signed URL ของ S3 ถ้าเปลี่ยนไปใช้ S3 จริง URL จะชี้ไปที่ bucket และสองเส้นนี้จะไม่ถูกใช้อีก use case ทุกตัวไม่ต้องแก้

ไฟล์ส่งออกรายงาน (`POST /staff/reports/exports`) ใช้ที่เก็บเดียวกัน ไฟล์ถูกเขียนโดย API เองผ่าน `IFileStorage.SaveAsync` ที่ key `exports/{id}.csv` (หรือ `.xlsx` `.pdf` ตามรูปแบบ ดู § 21) และลิงก์ดาวน์โหลดเป็น `/storage/files/{token}` อายุ 1 ชั่วโมงตาม contract ไฟล์ที่เก็บพร้อมชื่อ (เฉพาะไฟล์ส่งออก) ถูกส่งพร้อม `Content-Disposition` ชื่อไฟล์นั้น ส่วนเอกสารที่อัปโหลดยังส่งแบบไม่มีชื่อเหมือนเดิม ไม่มี endpoint ใหม่

**สิ่งที่ตั้งใจไม่ทำ** ไม่รับไฟล์ผ่าน endpoint ของ contract เอง (multipart) เพราะ contract บอกวิธีไว้แล้วว่าเป็น pre-signed URL และไม่ใส่ชื่อไฟล์ของผู้ใช้ลงใน path ของไฟล์

## 13. กล่องแจ้งเตือนบอกว่า "mark as read" แต่มีแค่ GET

`GET /portal/notifications` บรรยายว่า "กล่องแจ้งเตือนในเว็บ mark as read" การทำเครื่องหมายว่าอ่านแล้วเป็นการเขียน ถ้าทำใน `GET` รายการจะเปลี่ยนตัวเองทุกครั้งที่ถูกเปิด หน้าเว็บที่โหลดซ้ำจะทำให้ตัวเลขข้อความใหม่หายไปทั้งที่ผู้ใช้ยังไม่ได้อ่าน

**คำตอบ** `POST /portal/notifications/read` รับ `ids` ที่จะทำเครื่องหมาย หรือไม่ส่งเพื่อทำทั้งหมด ทำได้เฉพาะข้อความของตัวเอง id ของคนอื่นไม่มีผลและไม่เป็น error คำตอบบอกว่าทำไปกี่ข้อความ และเหลือที่ยังไม่อ่านกี่ข้อความ

## 14. หมวดการตรวจมีแต่การเขียนแปดเส้น อ่านเคสไม่ได้

หมวด Consultation ใน contract มี `POST` และ `PATCH` แปดเส้น ไม่มี `GET` เลย id ของเคสรู้ได้จากคำตอบของคำขอล่าสุดที่แตะเคสนั้นเท่านั้น หมอที่รีเฟรชหน้า หรือกลับมาเปิดเคสที่ค้างไว้หลังพักเที่ยง จึงไม่มีทางเห็นว่าในเคสมีอะไรอยู่แล้ว เป็นช่องโหว่แบบเดียวกับบิลใน § 7

**คำตอบ** `GET /staff/consultations/{id}` ด้วย `consult:read` ตอบ `ConsultationDto` ตัวเดียวกับที่การเขียนทุกเส้นในหมวดนี้ตอบอยู่แล้ว พร้อม `ETag` ใช้กติกาสาขาเดียวกับการเขียน (`ConsultationAccess`) ได้รับอนุมัติก่อนสร้าง

**audit** เมื่อคนที่อ่านไม่ใช่หมอเจ้าของเคส ระบบเขียน `consultation.viewed` ลง access log action นี้ประกาศไว้ใน `AuditActions` ตั้งแต่แรกแต่ยังไม่มีใครเรียก หมอที่เปิดเคสของตัวเองซ้ำไม่ถูกบันทึก ด้วยเหตุผลเดียวกับที่ autosave ไม่ถูกบันทึก คือแถวทุกครั้งที่รีเฟรชงานของตัวเองจะกลบแถวที่ access log มีไว้ให้เห็น

**สิ่งที่ตั้งใจไม่ทำ** ไม่เพิ่มรายการเคส (`GET /staff/consultations?pet_id=`) ทางเข้าเคสคือปุ่มบนกระดานคิวและปฏิทินนัด ซึ่งเปิดเคสซ้ำแล้วได้เคสเดิม (`POST /staff/consultations` คืนเคสที่เปิดอยู่) เคสที่ปิดแล้วอยู่ในไทม์ไลน์ของสัตว์

## 15. ไม่มีที่เก็บเบอร์โทรและช่องทางติดต่อของคลินิก

โปรไฟล์คลินิกใน contract (`GET /clinic`) มีชื่อ โลโก้ สี ใบอนุญาต และผู้ควบคุมกิจการ สาขามีที่อยู่และพิกัด แต่ไม่มีที่ไหนเก็บเบอร์ที่ลูกค้าโทรหา อีเมล บัญชี LINE หรือลิงก์แผนที่ หน้าเว็บสาธารณะจึงเขียนค่าเหล่านี้ไว้ในโค้ดสองที่ (footer และการ์ดบนหน้าแรก) และสองที่นั้นเริ่มไม่ตรงกันแล้ว

**คำตอบ** รายการช่องทางติดต่อ (`ClinicContact`) ตารางใหม่ `clinic_contacts` สี่ endpoint ได้รับอนุมัติก่อนสร้าง

| Method | Endpoint | Scope |
|---|---|---|
| GET | `/clinic/contacts` | สาธารณะ เหมือน `GET /clinic` |
| POST | `/clinic/contacts` | `settings:write` |
| PATCH | `/clinic/contacts/{id}` | `settings:write` |
| DELETE | `/clinic/contacts/{id}` | `settings:write` |

**ทำไมเป็นรายการ ไม่ใช่ช่องเพิ่มใน `PATCH /clinic`** คลินิกแต่ละแห่งมีช่องทางไม่เหมือนกัน บางแห่งมีสองเบอร์ บางแห่งไม่มี Instagram การเพิ่มช่องตายตัวในโปรไฟล์จะเปลี่ยนรูปของคำตอบที่ contract กำหนดไว้ และยังรองรับกรณีนี้ไม่ได้ แต่ละรายการมี `kind` บอกว่าเป็นอะไร หน้าเว็บจึงแสดงแต่ละแบบได้ถูก และผูกกับสาขาได้

**ทำไมใช้ `settings:write`** เป็น scope เดียวกับการเขียนข้อมูลคลินิกส่วนอื่นที่หน้าสาธารณะแสดง (`ClinicSetupController`) ไม่ต้องคิด scope ใหม่

**สิ่งที่ตั้งใจไม่ทำ** ไม่บันทึกการแก้ลง audit log เพราะโปรไฟล์และเวลาทำการก็ไม่บันทึก ไม่รับลิงก์ที่ไม่ใช่ `http` หรือ `https` และไม่รับลิงก์ฝังแผนที่จากที่อื่นนอกจาก Google Maps embed เพราะ iframe บนหน้าสาธารณะคือการให้เว็บอื่นวาดลงบนหน้าของคลินิก ไม่ใส่ข้อมูลตั้งต้นใน migration ข้อมูลตัวอย่างมาจากคำสั่ง `seed-contacts` แทน รายละเอียดอยู่ใน [ข้อมูลติดต่อ](features/contact.md)

## 16. ผู้ช่วย AI บนหน้าเว็บ

contract ไม่มีส่วนแชทหรือผู้ช่วยอัตโนมัติ เจ้าของงานขอให้เพิ่ม chatbot บนหน้าเว็บสาธารณะ โดยตัว agent เป็นของระบบเอง และโมเดลสลับได้ระหว่าง API แบบเสียเงินกับโมเดล open source ที่รันเอง

**คำตอบ** สอง endpoint สาธารณะ ได้รับอนุมัติก่อนสร้าง

| Method | Endpoint | Scope |
|---|---|---|
| GET | `/assistant` | สาธารณะ บอกว่าผู้ช่วยเปิดอยู่ไหม |
| POST | `/assistant/chat` | สาธารณะ จำกัด 10 ข้อความต่อนาทีต่อผู้เยี่ยมชม และโควตารายวันของทั้งคลินิก |

**ขอบเขตคือข้อมูลสาธารณะเท่านั้น** เครื่องมือของผู้ช่วยเรียก use case เดียวกับหน้าเว็บสาธารณะ (ข้อมูลคลินิก ช่องทางติดต่อ เวลาทำการ บริการ เวลาว่าง) ผู้ช่วยจึงบอกอะไรไม่ได้มากกว่าที่หน้าเว็บแสดงอยู่แล้ว และไม่มีทางเข้าถึงเวชระเบียนหรือข้อมูลลูกค้า ไม่ว่าจะถูกหลอกถามอย่างไร

**ไม่เก็บบทสนทนา** หน้าเว็บส่งบทสนทนาทั้งหมดมาทุกครั้ง เซิร์ฟเวอร์ไม่เก็บ และ log ไม่มีข้อความ มีแค่จำนวน token

**สิ่งที่ตั้งใจไม่ทำ** ไม่ให้ผู้ช่วยจองนัดเอง (ส่งไปหน้าจองที่ต้องเข้าสู่ระบบ) ไม่ให้โมเดลสร้างลิงก์ที่หน้าเว็บแสดง (ปุ่มมาจากเครื่องมือเท่านั้น) และไม่ผูกกับผู้ให้บริการโมเดลรายเดียว รายละเอียดอยู่ใน [ผู้ช่วย AI](features/assistant.md)

## 17. จัดการบริการได้แค่ราคากับการเปิดจองออนไลน์

contract ให้ `POST /staff/services` สร้างบริการ `PATCH …/pricing` เปลี่ยนราคา และ `PATCH …/availability` เปิดปิดการจองออนไลน์ แต่รายการบริการมีเส้นเดียวคือ `GET /services` ซึ่งเป็นเมนูสาธารณะ แสดงเฉพาะบริการที่เปิดจองออนไลน์ บริการที่จองได้ที่เคาน์เตอร์อย่างเดียว ซึ่งเป็นค่าเริ่มต้นของบริการใหม่ทุกตัว จึงหาไม่เจอในหน้าจัดการ และเมนูสาธารณะไม่มี `version` ให้ส่งเป็น `If-Match` นอกจากนี้ไม่มีทางแก้ชื่อ หมวด ระยะเวลา หรือผู้ให้บริการ และไม่มีทางเลิกขายบริการ ทั้งที่ช่อง `is_active` มีอยู่ใน `ServiceDto` แล้ว

**คำตอบ** สอง endpoint ได้รับอนุมัติก่อนสร้าง

| Method | Endpoint | Scope |
|---|---|---|
| GET | `/staff/services?category=` | `service:manage` ตอบทุกบริการ รวมบริการที่จองที่เคาน์เตอร์อย่างเดียวและที่ปิดใช้งาน ในรูป `ServiceDto` ตัวเดียวกับการเขียนสามเส้น |
| PATCH | `/staff/services/{id}` | `service:manage` แก้ `name` `category_code` `duration_minutes` `eligible_staff_ids` `is_active` ช่องที่ไม่ส่งไม่เปลี่ยน รองรับ `If-Match` |

**ทำไมไม่รวมราคาไว้ใน `PATCH` นี้** contract แยกราคาไว้เส้นของตัวเองเพราะราคามีวันที่มีผล การแก้ราคาผ่านเส้นนี้จะข้ามกติกานั้น เส้นนี้จึงแก้เฉพาะสิ่งที่ไม่มีวันที่

**ปิดใช้งานแทนการลบ** `is_active: false` ทำให้จองใหม่ไม่ได้ทั้งเคาน์เตอร์และออนไลน์ (`BookingSlotResolver` และ `GET /booking/availability` เช็กช่องนี้อยู่แล้ว) แต่นัดและบิลเดิมยังอ้างถึงบริการได้ ระยะเวลาใหม่มีผลกับนัดที่จองหลังจากนี้ นัดเดิมไม่หดหรือยืด

**สิ่งที่ตั้งใจไม่ทำ** ไม่เพิ่ม `DELETE` และไม่เปิดรายการนี้ให้ scope อื่น หน้าจองที่เคาน์เตอร์ยังใช้เมนูสาธารณะเหมือนเดิม ([assumptions.md § 27](./assumptions.md)) รายละเอียดหน้าจออยู่ใน [บริการ](features/services.md)

## 18. ระบบส่ง LINE ได้ แต่บันทึกที่อยู่ LINE ของลูกค้าไม่ได้

**ช่องโหว่** ระบบส่งข้อความทาง LINE ได้ครบแล้ว (ตัวส่ง ประวัติการส่ง webhook และปุ่มในแชต) และ `customers.line_user_id` มีอยู่แล้ว แต่ไม่มี endpoint ไหนใน contract ใส่ค่านี้ได้ เส้นเดียวที่ทำได้คือ `POST /portal/line/link` ซึ่งใช้ LINE เป็นตัวตน และถูกตัดออกตาม [assumptions.md § A](./assumptions.md) ส่วน LINE user id เป็นรหัสเฉพาะของแต่ละบัญชี Official Account พนักงานพิมพ์เองไม่ได้ ผลคือไม่มีลูกค้าคนไหนได้ข้อความทาง LINE เลย ทุกข้อความไปทาง SMS หรืออีเมล

**ทำไมสำคัญ** LINE เป็นช่องทางที่ลูกค้าในไทยอ่านจริงและถูกที่สุด ระบบที่สร้างช่องทางนี้ครบทุกชิ้นแต่ใช้ไม่ได้ คือค่า SMS ทุกข้อความที่ไม่จำเป็นต้องจ่าย

**การตัดสิน** ที่อยู่ LINE เป็นข้อมูลสำหรับส่ง เหมือนอีเมล พนักงานที่เคาน์เตอร์เป็นคนเลือกให้ ไม่ใช่ลูกค้ายืนยันตัวตนเอง

1. webhook จดผู้ติดตามไว้ในตาราง `line_followers` ทุกครั้งที่มี `follow` พร้อมชื่อและรูปจาก LINE profile API (`GET /v2/bot/profile/{userId}` เมื่อตั้ง access token ไว้) และทุกครั้งที่มี `message` จะเลื่อนคนนั้นขึ้นบนสุด คนที่เพิ่มเพื่อนไว้ก่อนมีตารางนี้จึงพิมพ์ข้อความอะไรก็ได้ถึงบัญชีคลินิก แล้วจะขึ้นในรายชื่อ
2. ที่หน้าลูกค้า พนักงานกดเลือกจากผู้ติดตาม เห็นรายชื่อคนที่เพิ่งเพิ่มเพื่อนหรือเพิ่งพิมพ์ (ชื่อ รูป และเวลา) คนที่ยืนอยู่ตรงหน้ามักอยู่บนสุด กดเลือก ตรวจกับลูกค้า แล้วยืนยัน
3. ระบบบันทึก `line_user_id` ลงเรกคอร์ดลูกค้า ข้อความถัดไปไปทาง LINE ก่อนตามลำดับเดิม

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/staff/integrations/line/followers?unlinked=true&q=&limit=&cursor=` | `customer:write` | ผู้ติดตามที่ยังติดตามอยู่และเห็นล่าสุดใน 14 วัน ใหม่สุดก่อน แบ่งหน้าด้วย cursor `unlinked` เป็น `true` ถ้าไม่ส่ง คือไม่แสดงคนที่ผูกกับลูกค้าแล้ว ส่ง `false` จะเห็นด้วยพร้อม `linked_customer_id` ส่วน `q` ค้นชื่อใน LINE |
| PUT | `/staff/customers/{id}/line` | `customer:write` | `{ "line_user_id": "U..." }` บันทึกที่อยู่ ตอบสถานะ LINE ของลูกค้า (`linked`, `can_receive`, `unfollowed_at`, `display_name`, `picture_url`, `version`) รองรับ `If-Match` ด้วย version ของลูกค้า |
| DELETE | `/staff/customers/{id}/line` | `customer:write` | เอาที่อยู่ออก ตอบ `204` แม้ไม่มีที่อยู่อยู่แล้ว รองรับ `If-Match` |

แต่ละแถวของรายชื่อมี `line_user_id`, `display_name`, `picture_url`, `followed_at`, `last_seen_at` และ `linked_customer_id` (เฉพาะเมื่อขอทั้งหมด) `GET /staff/customers/{id}` มีช่อง `line` เพิ่ม รูปเดียวกับคำตอบของ `PUT` ไม่มีรหัส LINE user id ในนั้น เพราะรหัสนี้คนอ่านไม่ได้ประโยชน์อะไร

**ทำไมใช้ `customer:write` ทั้งสามเส้น** รายชื่อผู้ติดตามมีไว้เพื่อกรอกที่อยู่ LINE ของลูกค้าอย่างเดียว ซึ่งเป็นการแก้ข้อมูลติดต่อของลูกค้า คนที่ทำได้คือคนที่ถือ `customer:write` อยู่แล้ว (พนักงานต้อนรับ) ไม่ใช้ `customer:read` เพราะ role ที่อ่านทะเบียนลูกค้าได้ เช่น สัตวแพทย์และผู้ช่วย ไม่จำเป็นต้องเห็นชื่อและรูปของคนที่ยังไม่ใช่ลูกค้า และไม่ใช้ `integration:manage` เพราะนั่นคือสิทธิ์ตั้งค่า token ของบัญชี LINE ซึ่งเคาน์เตอร์ไม่ควรมี รายการ scope ของ contract ปิดตาย จึงไม่คิด scope ใหม่

**ทำไมแยก `PUT` กับ `DELETE` ไม่ใช้ `PUT` ที่ส่ง `null`** body ที่พิมพ์ผิดหรือขาดช่องจะได้ `422` ไม่ใช่การยกเลิกการผูกแบบเงียบ ๆ และการเอาที่อยู่ออกอ่านตรงความหมายทั้งใน log และใน controller

**กฎของการผูก**

- **ต้องเป็นที่อยู่ที่ LINE ส่งมาให้เห็นแล้ว** คือมีในรายชื่อผู้ติดตาม เห็นล่าสุดไม่เกิน 14 วัน และยังติดตามอยู่ ไม่อย่างนั้นตอบ `422` ที่ช่อง `line_user_id` รหัสที่มาจากที่อื่นตรวจไม่ได้ว่าเป็นผู้ติดตามจริงของบัญชีนี้ และรหัสผิดจะทำให้ทุกข้อความถึงลูกค้าคนนั้นเป็น push ที่ล้มเหลว
- **หนึ่งที่อยู่ต่อหนึ่งเรกคอร์ด** ที่อยู่ที่อยู่บนลูกค้าคนอื่นแล้ว (รวมเรกคอร์ดที่ถูกรวมไปแล้ว เพราะ unique index ครอบด้วย) ตอบ `409 line_address_taken` พร้อม `details.customer_id` ของเรกคอร์ดนั้น เคาน์เตอร์ต้องยกเลิกที่นั่นก่อน สองเคาน์เตอร์ที่ผูกพร้อมกันก็ได้คำตอบเดียวกัน เพราะ `PostgresErrorTranslator` แปล unique index `ix_customers_line_user_id` เป็นรหัสนี้
- ผูกที่อยู่เดิมซ้ำไม่เปลี่ยนอะไรและไม่เขียน audit ผูกที่อยู่ใหม่คือแทนที่ของเดิม เรกคอร์ดที่ถูกรวมแล้วผูกไม่ได้ (`409 state_conflict`) แต่ยกเลิกได้ เพื่อปล่อยที่อยู่ที่เรกคอร์ดเก่ายังถืออยู่
- **audit** `customer.line_linked` (พร้อม `line_user_id` และ `replaced`) และ `customer.line_unlinked`
- **ลูกค้าที่ผูกแล้วบล็อกบัญชีทีหลัง** ใช้ทางเดิมของ webhook คือ `unfollow` ตั้ง `line_unfollowed_at` ข้อความไปทาง SMS แทน และ `follow` ครั้งใหม่ทำให้ส่งได้อีก หน้าลูกค้าแสดงว่า "บล็อกบัญชีอยู่"

**ข้อมูลส่วนบุคคลและระยะเก็บ** ชื่อและรูปใน LINE เป็นข้อมูลส่วนบุคคลของคนที่อาจไม่เคยเป็นลูกค้า

- งาน `housekeeping` (ทุกชั่วโมง) ลบผู้ติดตามที่ไม่ได้ผูกกับลูกค้าคนใด เมื่อไม่เห็นเกิน 14 วัน รายชื่อก็มองย้อนได้ไม่เกินนั้น
- `unfollow` ลบชื่อและรูปทันที และแถวนั้นไม่ขึ้นในรายชื่ออีก
- แถวของผู้ติดตามที่ผูกแล้วเก็บไว้ตราบที่ยังผูกอยู่ หน้าลูกค้าจึงบอกได้ว่าเป็น LINE ของใคร พอยกเลิกการผูก แถวนั้นนับอายุ 14 วันเหมือนแถวอื่น
- ไม่เก็บข้อความที่คนที่ยังไม่ได้ผูกพิมพ์มา (ข้อความของลูกค้าที่ผูกแล้วเข้ากล่องข้อความตาม contract ดู [ข้อความลูกค้า](features/messaging.md)) ไม่เก็บ status message ของ LINE และรูปต้องเป็น `https` เท่านั้น
- หน้าเว็บโหลดรายชื่อเมื่อพนักงานกดเปิดตัวเลือกเท่านั้น ไม่โหลดมาพร้อมหน้าลูกค้าทุกครั้ง

**ตั้งใจไม่ทำ**

- **ไม่จับคู่อัตโนมัติ** ไม่เทียบเบอร์โทรหรือชื่อกับผู้ติดตาม เพราะนั่นคือการใช้ LINE ยืนยันตัวตน ซึ่งหัวข้อ A ตัดออก และชื่อใน LINE ซ้ำกันได้
- **ไม่ให้ลูกค้าผูกเองจาก portal** ทางนั้นต้องมีรหัสยืนยันผ่านแชต และเป็นเส้นที่ contract ตัดออกไปแล้ว ถ้าต้องการในอนาคต ควรขออนุมัติเป็นส่วนขยายแยก
- **ไม่ส่งข้อความหาลูกค้าตอนผูก** การผูกเป็นการแก้ข้อมูลติดต่อ ไม่ใช่การแจ้งเตือน
- หน้าจอไม่แสดงและไม่รับ LINE user id พนักงานเลือกจากชื่อและรูปเท่านั้น

**ข้อจำกัด** ถ้าไม่ได้ตั้ง access token หรือ LINE ไม่ตอบ profile API ผู้ติดตามยังถูกจด แต่ไม่มีชื่อและรูป หน้าจอแสดงว่า "ไม่ทราบชื่อใน LINE" พร้อมเวลา ซึ่งยังเลือกได้ถ้าเวลาตรงกับที่ลูกค้าเพิ่งเพิ่มเพื่อน รายละเอียดอยู่ใน [LINE](features/line.md#ที่อยู่-line-ของลูกค้า)

## 19. กติกาเตือนอัตโนมัติเปิด ปิด แก้ หรือลบไม่ได้

**ช่องโหว่** หมวด Reminders และ Automation ใน contract มี `GET /staff/automations`, `POST /staff/automations` และ `POST /staff/automations/{id}/simulate` ไม่มีเส้นไหนเปลี่ยนกติกาที่สร้างแล้ว กติกาเริ่มต้นสี่ข้อที่ migration ใส่ไว้ปิดอยู่ จึงปิดตลอดไป กติกาที่สร้างผิดก็แก้ไม่ได้ และกติกาที่ไม่ต้องการแล้วก็ลบไม่ได้ ทางเดียวที่มีคือสร้างกติกาซ้ำแบบเปิดใช้ ซึ่งทิ้งกติกาเก่าค้างไว้ในรายการ

**ทำไมสำคัญ** กติกาส่งข้อความถึงลูกค้าเองในนามคลินิก ปุ่มหยุดคือสิ่งแรกที่คลินิกต้องมี ถ้ากติกาส่งข้อความผิด สิ่งที่คลินิกทำได้ตาม contract คือปล่อยให้มันส่งต่อไป

**Endpoint**

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| PATCH | `/staff/automations/{id}` | `automation:manage` | รูปเดียวกับตอนสร้าง ทุกส่วนไม่บังคับ ส่วนที่ไม่ส่งคงเดิม แก้ `enabled`, `name`, เวลาใน `trigger`, `condition` และ `action.channel` ได้ ตอบกติกาพร้อม `version` และ `ETag` รองรับ `If-Match` |
| DELETE | `/staff/automations/{id}` | `automation:manage` | ลบกติกา ตอบ `204` รองรับ `If-Match` |

```http
PATCH /staff/automations/atm_starter_visit_24h      automation:manage
{ "enabled": true }

PATCH /staff/automations/atm_...
{ "trigger": { "offset_days": 7, "send_time": "10:00" }, "condition": { "species": "" }, "action": { "channel": "line" } }
```

คำตอบของ `GET` และ `POST /staff/automations` มีช่อง `version` เพิ่ม เพื่อส่งเป็น `If-Match` ได้ ค่านี้มาจาก `xmin` เหมือนทุกโมดูล ไม่ต้องเพิ่มคอลัมน์

**กฎของการแก้**

- **ตรวจด้วยกฎเดียวกับตอนสร้าง ไม่ใช่สำเนา** handler วางส่วนที่ส่งมาทับกติกาเดิม แล้วส่งผลลัพธ์ผ่าน `CreateAutomationValidator` ตัวเดียวกับ `POST` กติกาที่สร้างไม่ได้จึงแก้ให้เป็นแบบนั้นไม่ได้เช่นกัน และ error บอกชื่อช่องเดียวกัน เช่น `trigger.offset_days`
- **เรื่องที่เฝ้าดูเปลี่ยนไม่ได้** `trigger.type` ส่งมาได้แต่ต้องตรงกับของเดิม ไม่อย่างนั้นตอบ `422` เทมเพลตและชนิดของเรื่องที่เตือนผูกกับ trigger ถ้าต้องการเตือนเรื่องอื่นให้สร้างกติกาใหม่
- **เวลา** ส่ง `offset_days` หรือ `offset_hours` คือแทนเวลาทั้งชุด ส่งแค่ `send_time` คือเลื่อนเวลาของกติกาที่นับเป็นวัน
- **เงื่อนไข** ช่องที่ไม่ส่งคงเดิม สตริงว่างคือลบเงื่อนไขนั้น `branch_id` ว่างคือเปลี่ยนเป็นกติกาทั้งคลินิก
- **สาขา** เหมือนตอนสร้าง กติกาของสาขาอื่นตอบ `403` พนักงานที่ผูกสาขาแก้หรือลบกติกาทั้งคลินิกไม่ได้ (`403`) รวมกติกาเริ่มต้นทั้งสี่ เพราะกติกาแบบนั้นส่งถึงลูกค้าทุกสาขา และเปลี่ยนกติกาของตัวเองให้เป็นทั้งคลินิกก็ไม่ได้ (`422`) ส่วนการอ่านและ simulate ยังทำได้เหมือนเดิม
- **audit** `automation.updated` พร้อมรายชื่อช่องที่เปลี่ยน (`changed`) และค่า `enabled` หลังแก้ การแก้ที่ไม่เปลี่ยนอะไรไม่เขียน audit

**แก้เวลาแล้วไม่ส่งซ้ำ** กุญแจของบันทึก "ส่งแล้ว" คือ `(rule_id, subject_kind, subject_id, due_key)` โดย `due_key` คือวันครบกำหนดหรือเวลาเริ่มของเรื่องนั้น ไม่ใช่เวลาที่ส่ง การแก้ไม่แตะส่วนไหนของกุญแจเลย (trigger เปลี่ยนไม่ได้ และเวลาส่งไม่อยู่ในกุญแจ) นัดที่ได้ข้อความ "ก่อน 24 ชั่วโมง" ไปแล้ว จึงไม่ได้ข้อความ "ก่อน 2 ชั่วโมง" ซ้ำจากกติกาเดิมหลังแก้ ปิดแล้วเปิดใหม่ก็เช่นกัน ผลอีกด้านคือ เรื่องที่ได้ข้อความไปแล้วจะไม่ได้ข้อความตามเวลาใหม่ ถ้าต้องการเตือนอีกครั้งให้สร้างกติกาที่สอง ซึ่งเป็นการตัดสินใจที่เห็นชัดกว่า

**เลื่อนเวลาให้เร็วขึ้น** ใช้กติกาส่งตามหลังเดิม คือส่งได้ภายใน 12 ชั่วโมงหลังเวลาที่ตั้ง (`Jobs:Automations:CatchUpHours`) เรื่องที่จุดเตือนใหม่ผ่านไปนานกว่านั้นแล้วไม่ได้ข้อความจากกติกานี้ เปิดกติกาที่ปิดไว้นานก็เหมือนกัน ระบบไม่ไล่ส่งย้อนหลังให้ทุกคนที่เลยจุดเตือนไปแล้ว

**ลบแล้วประวัติยังอยู่** การลบไม่ลบแถว แต่ตั้ง `deleted_at` และ `deleted_by_staff_id` และปิดกติกา กติกาที่ลบแล้วหายจากรายการ simulate upcoming และการรันจริง `PATCH` หรือ `DELETE` ซ้ำตอบ `404` แถวยังอยู่เพราะ `automation_dispatches` ชี้มาที่กติกา และแต่ละข้อความที่ส่งไปแล้วอยู่ในประวัติการส่งโดยมี dispatch เป็น `batch_id` คำถาม "ใครส่งข้อความนี้ถึงเจ้าของเมื่อเดือนก่อน" จึงยังตอบได้ด้วยชื่อกติกาเดิม ถ้าลบแถวจริง ต้องลบประวัตินั้นไปด้วย หรือปล่อยให้ชี้ไปที่ของที่ไม่มีแล้ว การลบเขียน audit `automation.deleted`

**สิ่งที่ควรรู้** รอบของตัวตั้งเวลาที่โหลดกติกาไปแล้วก่อนการปิดหรือลบ อาจส่งรอบนั้นจนจบ รอบถัดไป (60 วินาทีต่อมา) ไม่เห็นกติกานั้นแล้ว

**ตั้งใจไม่ทำ** ไม่มีทางกู้กติกาที่ลบแล้ว (สร้างใหม่ได้) ไม่แก้ถ้อยคำของข้อความผ่านกติกา (ยังเป็นเทมเพลตกลาง) และไม่เพิ่ม scope ใหม่ ใช้ `automation:manage` ตัวเดียวกับการสร้าง รายละเอียดอยู่ใน [เตือนอัตโนมัติ](features/automation.md)

## 20. ใบสั่งยามีแค่ชื่อยา การจ่ายยาจึงตัดสต๊อกได้เมื่อชื่อตรงทุกตัวอักษรเท่านั้น

**ช่องโหว่** `POST /staff/consultations/{id}/prescriptions` รับชื่อยาเป็นข้อความ ไม่มีรหัสรายการในคลัง การจ่ายยาจึงหารายการด้วยชื่อ แบบตรงทั้งชื่อหลังตัดช่องว่างซ้ำและไม่สนตัวพิมพ์ ([assumptions.md § 42](./assumptions.md)) หมอพิมพ์ "Amoxicillin 250 mg" ขณะที่คลังชื่อ "Amoxicillin 250mg" ยาก็ถูกจ่ายไปโดยไม่ตัดสต๊อกและไม่คิดเงิน และไม่มีใครรู้จนห้องยาเห็นป้าย "ไม่ได้ตัดสต๊อก" อีกด้านหนึ่ง role `veterinarian` ของ contract ไม่มี `inventory:read` คนที่สั่งยาจึงไม่มีทางรู้ว่าคลังเรียกยาตัวนี้ว่าอะไร มีของไหม หรือราคาเท่าไร

**ทำไมสำคัญ** ทุกใบที่ชื่อไม่ตรงคือยาที่ออกจากชั้นโดยยอดในระบบไม่ลด และค่ายาที่ไม่ได้เก็บ ทั้งสองเรื่องเงียบ ยอดสต๊อกเพี้ยนไปเรื่อย ๆ จนถึงวันนับสต๊อก และรายได้ค่ายาหายไปโดยไม่มีบรรทัดไหนบอก การจับคู่ชื่อแบบหลวมกว่านี้ไม่ใช่ทางแก้ เพราะการจับผิดคือหยิบยาผิดตัวและคิดราคาผิด

**การตัดสิน** ให้คนสั่งยาเลือกยาจากคลังได้ตอนสั่ง และให้การจ่ายใช้รหัสที่เลือก ไม่ต้องเดาจากชื่ออีก ได้รับอนุมัติก่อนสร้าง

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/staff/prescriptions/drug-options?q=&branch=&limit=` | `rx:write` | ยาในคลังที่เลือกได้ เรียงตามชื่อ พร้อมราคาขายและสถานะสต๊อกของสาขาเดียว |
| POST | `/staff/consultations/{id}/prescriptions` (เส้นเดิมของ contract) | `rx:write` | รับ `inventory_item_id` เพิ่ม ไม่บังคับ |

```http
GET /staff/prescriptions/drug-options?q=amox&branch=brn_...      rx:write

{ "branch_id": "brn_...",
  "data": [ { "item_id": "itm_...", "name": "Amoxicillin 250mg", "unit": "เม็ด",
              "unit_price_satang": 500, "available": 36, "status": "ok" } ] }

POST /staff/consultations/con_.../prescriptions                   rx:write
{ "inventory_item_id": "itm_...", "dose": "1 เม็ด", "frequency": "วันละ 2 ครั้ง", "duration_days": 7, "quantity": 14 }
```

**ทำไมตัวเลือกยาเป็นรูปนี้** แต่ละแถวมีแค่สิ่งที่คนสั่งยาต้องใช้

- `item_id` ส่งกลับเป็น `inventory_item_id` ตอนสั่ง
- `name` และ `unit` ชื่อที่จะเขียนในใบ และหน่วยที่ `quantity` นับ
- `unit_price_satang` ราคาขายที่เจ้าของจะจ่าย หมอมักถูกถามเรื่องนี้ในห้องตรวจ
- `available` และ `status` (`ok`, `low`, `out`) ของสาขาเดียว คิดแบบเดียวกับหน้าสต๊อก หมอจึงรู้ว่าสั่งแล้วห้องยามีจ่ายไหม
- `branch_id` ระดับบน บอกว่าตัวเลขเป็นของสาขาไหน เพราะถ้าไม่ส่ง `branch` ระบบเลือกให้
- ไม่มีต้นทุน ล็อต วันหมดอายุ ซัพพลายเออร์ ใบสั่งซื้อ หรือสาขาอื่น และไม่มีเวชภัณฑ์ เพราะเวชภัณฑ์ไม่ถูกสั่งจ่าย ไม่มีช่องขนาดหรือรูปแบบยาแยก เพราะคลังไม่ได้เก็บแยก ขนาดอยู่ในชื่อรายการ

**กฎของตัวเลือกยา**

- **สาขาเดียว** สาขาที่ขอต้องเปิดอยู่และผู้เรียกสังกัด ไม่อย่างนั้นตอบ `403` ถ้าไม่ส่ง ใช้สาขาเดียวของผู้เรียก หรือสาขาเดียวของคลินิก ไม่อย่างนั้นตอบ `422` หน้าตรวจส่งสาขาของเคสเสมอ เพราะยาถูกจ่ายที่สาขานั้น
- ยาที่หมดยังขึ้นพร้อม `out` หมออาจยังต้องสั่ง เช่นของกำลังมา การจ่ายจะบอกว่าของไม่พอเหมือนเดิม
- `q` ค้นส่วนของชื่อ `limit` 1 ถึง 50 ค่าเริ่มต้น 20 หน้าตรวจขอทีละ 8

**กฎของการสั่งยาที่มี `inventory_item_id`**

- รหัสที่ไม่มีในคลังตอบ `404` รหัสของเวชภัณฑ์ (`kind: supply`) ตอบ `422` ที่ `inventory_item_id` คลังยังไม่มีการปิดรายการ ยาทุกตัวที่อยู่ในคลังจึงถือว่าใช้งานอยู่
- **ชื่อยา** ไม่ส่ง `drug_name` ระบบเขียนชื่อของรายการ ส่งมาด้วยระบบเก็บตามที่ส่ง เพราะชื่อในใบคือข้อความบนฉลาก หมออาจเขียนชื่อการค้าที่เจ้าของคุ้น รหัสคือสิ่งที่ใช้ตัดสต๊อกและคิดเงิน
- **การตรวจแพ้ยา** เทียบทั้งชื่อที่ส่งและชื่อของรายการ ชื่อการค้าที่พิมพ์ทับจึงไม่ทำให้หลุดการตรวจ ขั้นตอน `409 allergy_conflict` และ `acknowledge_allergy` เหมือนเดิม
- audit `consultation.prescription_added` มี `inventory_item_id` เพิ่ม
- คำขอที่ไม่มี `inventory_item_id` ทำงานเหมือนเดิมทุกอย่าง รวมถึงข้อความ error

**ลำดับการจับคู่ตอนจ่ายยา** ใบที่มีรหัส ใช้รายการนั้นเลย ไม่เทียบชื่อ ใบที่ไม่มีรหัส เทียบชื่อแบบเดิม ผล `deducted`, `not_matched`, `insufficient` และการคิดเงินไม่เปลี่ยน ใบที่ผูกแล้วจ่ายกับรายการอื่นไม่ได้ domain ตรวจไว้อีกชั้น

**ไม่มี migration** `prescriptions.inventory_item_id` มีอยู่แล้วพร้อม foreign key ไปที่ `inventory_items` ตั้งแต่ตอนทำการจ่ายยา เดิมคอลัมน์นี้ถูกเขียนตอนจ่ายว่าจับคู่กับรายการไหน ตอนนี้ถูกเขียนตั้งแต่ตอนสั่งถ้าหมอเลือกจากคลัง ความหมายยังเป็น "ใบนี้เป็นของรายการไหน" ใบสั่งยาในคำตอบของเคสมีช่อง `inventory_item_id` เพิ่ม ก่อนจ่าย ช่องนี้มีค่าเฉพาะใบที่เลือกจากคลัง

**ทางเลือกที่ไม่เลือก**

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| ให้ role `veterinarian` ถือ `inventory:read` | เห็นต้นทุน ล็อต ซัพพลายเออร์ และใบสั่งซื้อของทุกสาขาที่สังกัด ซึ่งหมอไม่ต้องใช้ และทุกคลินิกต้องแก้ role เอง |
| เปิด `GET /staff/inventory/items` ให้ `rx:write` ด้วย | เส้นเดียวต้องตอบสองแบบตามสิทธิ์ ถ้าวันหนึ่งมีคนเพิ่มช่องต้นทุนในรายการ ช่องนั้นก็หลุดไปถึงหมอ |
| จับคู่ชื่อแบบหลวมขึ้น เช่นไม่สนช่องว่างเลย หรือเทียบคำแรก | "Amoxicillin 250mg" กับ "Amoxicillin 500mg" คำแรกเหมือนกัน การหยิบผิดขนาดแย่กว่าไม่หยิบ |
| บังคับให้ทุกใบเลือกจากคลัง | ยาที่คลินิกไม่ได้เก็บ เช่นยาที่ให้เจ้าของไปซื้อเอง ต้องสั่งได้ และใบสั่งยาแบบเดิมของ contract ต้องทำงานเหมือนเดิม |
| endpoint ใหม่ใต้ `/staff/inventory` | ตัวเลือกยาเป็นเครื่องมือของคนสั่งยา ใช้ scope ของการสั่งยา จึงอยู่ใต้ `/staff/prescriptions` คู่กับประวัติยา |

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่คิด scope ใหม่ และไม่เพิ่ม scope ให้ role ใด เพราะรายการ scope ของ contract ปิดตาย
- ไม่ผูกใบสั่งยาเก่าย้อนหลัง ใบที่สั่งไปแล้วยังจับคู่ด้วยชื่อตอนจ่าย
- ไม่ตรวจว่าจำนวนที่สั่งมีพอในสาขา และไม่จองของไว้ให้ใบที่ยังไม่จ่าย การจ่ายยังเป็นจุดเดียวที่ตัดสต๊อก ("ตัดสต๊อกเมื่อจ่ายจริง")
- ไม่ผูกชื่อที่พิมพ์เองกับรายการให้อัตโนมัติตอนสั่ง หน้าจอแสดงตัวเลือก หมอเป็นคนเลือก
- ไม่เก็บราคาตอนสั่ง ราคายังถูกเก็บตอนจ่ายเหมือนเดิม

**หน้าจอ** ช่องชื่อยาในฟอร์มสั่งยาของหน้าตรวจค้นยาในคลังของสาขาของเคสขณะพิมพ์ แต่ละตัวมีป้าย มีของ ใกล้หมด หรือหมด พร้อมจำนวนที่เหลือและราคาต่อหน่วย เลือกแล้วชื่อถูกเติมและผูกกับรายการ พิมพ์ชื่อเองยังได้ และใต้ช่องขึ้นว่า "ไม่ผูกกับสต๊อก ตอนจ่ายจะจับคู่ด้วยชื่อ ถ้าชื่อไม่ตรงกับในคลังทุกตัวอักษร จะไม่ตัดสต๊อกและไม่คิดเงิน" (ใบแบบนี้ยังตัดสต๊อกได้ถ้าชื่อตรงกับรายการทุกตัวอักษร แต่หน้าจอไม่สัญญาสิ่งที่ไม่แน่นอน) พิมพ์ทับชื่อที่เลือกไว้คือยกเลิกการผูก รายการยาของเคสมีป้ายผูกหรือไม่ผูกกับสต๊อกทุกแถว และหน้าจ่ายยามีป้ายเดียวกันที่ใบที่รอจ่าย รายละเอียดอยู่ใน [สต๊อกยาและเวชภัณฑ์](features/inventory.md#เลือกยาจากคลังตอนสั่งยา) และ [งานรักษาต่อเนื่อง](features/clinical-records.md)

## 21. ส่งออกรายงานได้แค่ CSV

`POST /staff/reports/exports` ใน contract บรรยายแค่ "งานส่งออกแบบ async คืน job id" ไม่ได้บอกรูปแบบไฟล์ ระบบจึงเริ่มด้วย CSV อย่างเดียว ([ภาพรวมและรายงาน](features/dashboard.md#ส่งออกรายงาน)) เจ้าของงานขอให้ส่งออกเป็น Excel และ PDF ได้ด้วย (2026-10-09)

ข้อนี้เป็นฟีเจอร์ที่ขอเพิ่มเหมือน § 9 ไม่ใช่ช่องโหว่ที่เจอตอนทำตาม contract

**คำตอบ** ไม่มี endpoint ใหม่ ช่อง `format` ที่ไม่บังคับในคำขอเดิมรับเพิ่มสองค่า

| `format` | ไฟล์ | เหมาะกับ |
|---|---|---|
| `csv` (ค่าเริ่มต้น เหมือนเดิม) | `.csv` | นำเข้าโปรแกรมอื่น |
| `xlsx` | `.xlsx` | เปิดใน Excel แล้วรวม กรอง หรือทำ pivot ต่อได้ทันที |
| `pdf` | `.pdf` | พิมพ์ หรือแนบส่งให้เจ้าของคลินิก |

```http
POST /staff/reports/exports            report:export
{ "report": "revenue", "format": "xlsx", "from": "2026-09-01", "to": "2026-09-30" }
```

คำตอบรูปเดิม ช่อง `format` ตอบค่าที่สั่ง `file_name` ลงท้ายตามรูปแบบ และลิงก์ดาวน์โหลดส่งไฟล์พร้อม media type ของรูปแบบนั้น ค่าอื่นได้ `422` ที่ช่อง `format` เหมือนเดิม

**สิ่งที่ไม่เปลี่ยน** การจองงาน การลองใหม่ ที่เก็บไฟล์ ลิงก์อายุ 1 ชั่วโมง scope ของรายงาน และการตรึงสาขาตอนสั่ง เป็นทางเดียวกันทั้งสามรูปแบบ ทุกรูปแบบเขียนจากตารางเดียวกัน (`ReportTable`) แถวและหัวคอลัมน์จึงตรงกันทุกไฟล์ ต่างกันแค่ตัวเขียนไฟล์ (`IReportFileWriter`) ไม่มี migration เพราะคอลัมน์ `format` เก็บชื่อเป็นข้อความอยู่แล้ว

**การตัดสิน**

- **Excel เขียนทุกช่องเป็นค่า ไม่มีสูตรเลย** ข้อความเป็น inline string ซึ่ง Excel แสดงแต่ไม่รัน ชื่อที่พิมพ์ว่า `=HYPERLINK(...)` จึงเป็นตัวอักษรตามนั้น ไม่ต้องเติม `'` แบบ CSV ข้อมูลจึงตรงกับที่พิมพ์ทุกตัว ตัวอักษรที่ XML เก็บไม่ได้ (อักขระควบคุม) ถูกตัดทิ้ง
- **ช่องใน Excel มีชนิด** จำนวนเป็นตัวเลข เงินเป็นบาทสองตำแหน่ง วันที่เป็นวันที่จริง ค่าใช่หรือไม่เป็น TRUE FALSE รวมและกรองได้โดยไม่ต้องแปลง ชนิดมาจากคอลัมน์ของตาราง ไม่ได้เดาจากหัวคอลัมน์ และตารางไม่ยอมรับค่าผิดชนิดตั้งแต่ตอนสร้างแถว
- **แถวแรกของ Excel คือหัวคอลัมน์ที่ตรึงไว้** ชื่อคลินิก สาขา และช่วงวันอยู่ใน properties ของไฟล์ ไม่อยู่เหนือตาราง เพราะ pivot และตัวกรองหาหัวตารางที่แถวแรก
- **PDF มีหัวและท้ายทุกหน้า** ชื่อคลินิก ชื่อรายงาน สาขา ช่วงวัน เวลาที่สร้าง และเลขหน้า หน้าที่หลุดจากแฟ้มยังบอกได้ว่าเป็นอะไร หัวคอลัมน์ซ้ำทุกหน้า วันที่เป็นภาษาไทยแบบปีพุทธศักราชเหมือนเอกสารของสัตว์

**ไลบรารี** Excel ใช้ `DocumentFormat.OpenXml` (Open XML SDK ของ Microsoft สัญญาอนุญาต MIT) ซึ่งพาแค่ `DocumentFormat.OpenXml.Framework` และ `System.IO.Packaging` มาด้วย (MIT ทั้งคู่) PDF ใช้ QuestPDF ตัวเดิมของเอกสารของสัตว์ สัญญาอนุญาต Community มีเงื่อนไขเรื่องรายได้ขององค์กรเหมือนเดิม ดู [งานรักษาต่อเนื่อง](features/clinical-records.md)

**ทางเลือกที่ไม่เลือก**

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| ClosedXML | เขียนง่ายกว่า แต่พาแพ็กเกจทางอ้อมมาหลายตัว รวมไลบรารีวัดฟอนต์ที่รุ่นใหม่เปลี่ยนสัญญาอนุญาตแล้ว ต้องคอยตรวจทุกครั้งที่อัปเกรด งานนี้ต้องการแค่ชีตเดียว จึงใช้ SDK ตรง |
| endpoint แยกต่อรูปแบบ เช่น `/exports/xlsx` | มีเส้นเดียวและช่อง `format` อยู่แล้ว การเพิ่มค่าคือการเปลี่ยนที่เล็กที่สุด |
| สร้าง PDF จาก HTML ด้วยเบราว์เซอร์บนเซิร์ฟเวอร์ | ต้องมี Chromium ใน image ทั้งที่ระบบมี QuestPDF ที่จัดภาษาไทยถูกอยู่แล้ว |

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่ทำกราฟใน Excel หรือ PDF ไฟล์เป็นแถวละเอียดสุดชุดเดียวกับ CSV ให้ spreadsheet รวมเอง
- ไม่ย่อแถวใน PDF ช่วงยาวของรายงานที่ละเอียดมาก เช่นคิวรายชั่วโมงทั้งปี จึงอาจได้หลายสิบหน้า
- ไม่เพิ่ม scope ใหม่ และยังไม่มีงานลบไฟล์เก่า เหมือน CSV

**หน้าจอ** กล่องส่งออกรายงานบนหน้าภาพรวมมีตัวเลือกไฟล์ Excel (ค่าเริ่มต้น) CSV หรือ PDF รายละเอียดอยู่ใน [ภาพรวมและรายงาน](features/dashboard.md#ส่งออกรายงาน)

## 22. webhook และ API key สร้างได้อย่างเดียว key ที่หลุดใช้ได้จนหมดอายุ

**ช่องโหว่** หมวด Webhooks และ Integrations ของ contract มี `POST /staff/webhooks`, `GET /staff/webhooks/{id}/deliveries` และ `POST /staff/api-keys` คือสร้างได้ แต่ไม่มีเส้นไหนอ่านรายการ แก้ ปิด หรือลบสิ่งที่สร้างแล้ว คลินิกต้องจดรหัส webhook เอง ปลายทางที่ย้าย URL ต้องสร้าง webhook ใหม่และปล่อยตัวเก่าส่งต่อไปเรื่อย ๆ secret ที่หลุดเปลี่ยนไม่ได้ delivery ที่ล้มเหลวครบหกครั้งส่งซ้ำไม่ได้ API key ที่หลุดใช้ได้จนหมดอายุ ซึ่งนานได้ถึง 365 วัน และลิงก์ปฏิทินที่หลุดใช้ได้จนเจ้าของถูกปิดบัญชี

**ทำไมสำคัญ** ทั้งสามอย่างเป็น credential ที่อยู่นอกระบบ ทางเดียวที่มีตอนนี้เมื่อ key หลุด คือปิดบัญชีของคนที่สร้าง หรือเอา scope ออกจาก role ของเขา ซึ่งกระทบงานของทุกคนใน role นั้น การหยุด credential ที่หลุดต้องเป็นปุ่มเดียว ไม่ใช่การแก้สิทธิ์ของคน

**การตัดสิน** เพิ่มแปดเส้น ได้รับอนุมัติก่อนสร้าง ทุกเส้นใช้ `integration:manage` ตัวเดียวกับการสร้าง ยกเว้นการสร้างลิงก์ปฏิทินใหม่ ซึ่งใช้กติกาเดียวกับฟีด คือพนักงานทุกคน เฉพาะลิงก์ของตัวเอง ไม่มี migration

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/staff/webhooks` | `integration:manage` | webhook ทุกตัวที่ยังไม่ถูกลบ ใหม่สุดก่อน มี `version` ไม่มี secret |
| PATCH | `/staff/webhooks/{id}` | `integration:manage` | แก้ `url`, `events`, `description` หรือ `active` ช่องที่ไม่ส่งไม่เปลี่ยน ตอบ webhook พร้อม `ETag` รองรับ `If-Match` |
| DELETE | `/staff/webhooks/{id}` | `integration:manage` | ลบ ตอบ `204` ประวัติการส่งยังอ่านได้ รองรับ `If-Match` |
| POST | `/staff/webhooks/{id}/rotate-secret` | `integration:manage` | secret ใหม่ แสดงครั้งเดียว secret เดิมหยุดทันที รองรับ `If-Match` |
| POST | `/staff/webhooks/{id}/deliveries/{deliveryId}/redeliver` | `integration:manage` | ส่ง delivery ที่ `failed` อีกครั้ง ตอบ `202` พร้อม delivery ที่กลับเป็น `pending` |
| GET | `/staff/api-keys` | `integration:manage` | key ที่ผู้เรียกจัดการได้ ใหม่สุดก่อน ไม่มีตัว key |
| DELETE | `/staff/api-keys/{id}` | `integration:manage` | ยกเลิก key ตอบ `204` คำขอถัดไปของ key นั้นได้ `401` |
| POST | `/staff/integrations/calendar/token` | พนักงานทุกคน ลิงก์ของตัวเองเท่านั้น | ลิงก์ปฏิทินใหม่ ลิงก์เดิมได้ `401` ทันที |


**กฎของการแก้ webhook**

- **URL ใหม่ตรวจด้วยกฎเดียวกับตอนสร้าง** คือ `WebhookUrl.Problem` ตัวเดียวกัน `http://` ที่อยู่ภายใน metadata ของ cloud ชื่อที่ลงท้าย `.internal` หรือ URL ที่มีรหัสผ่าน ได้ `422` ที่ช่อง `url` ตรวจเฉพาะช่องที่ส่งมา การปิด webhook จึงทำได้เสมอ แม้ URL ที่เก็บไว้จะไม่ผ่านกฎที่เข้มขึ้นในรุ่นหลัง การตรวจตอนส่ง (resolve ชื่อ และตรวจซ้ำตอนต่อ socket) ทำกับ URL ใหม่เหมือนเดิม
- **URL ใหม่มีผลกับการส่งครั้งถัดไปทุกครั้ง** รวมการลองใหม่ของ event ที่เกิดก่อนแก้
- **ปิดคือหยุดจริง** การแตก event ข้าม webhook ที่ปิดอยู่แล้ว การปิดยังหยุด delivery ที่รอส่งทั้งหมดใน transaction เดียวกัน เป็น `failed` ด้วย `last_error` เป็น `webhook_disabled` และตัวส่งตรวจอีกครั้งก่อนส่งทุกครั้ง แถวที่ถูกจองไปก่อนกดปิดจึงถูกหยุดโดยไม่ส่ง และไม่นับเป็นครั้งที่ลอง คำขอที่ออกไปแล้วก่อนกดปิดอาจยังถึงปลายทาง
- **เปิดใหม่ไม่ส่งย้อนหลัง** event ที่เกิดระหว่างปิดไม่ถูกแตกให้ webhook นั้นเลย delivery ที่ถูกหยุดส่งซ้ำได้ทีละรายการ
- **audit** `integration.webhook_updated` พร้อมรายชื่อช่องที่เปลี่ยน ปลายทางใหม่ (ไม่รวม query string) รายการ event และ `active` การแก้ที่ไม่เปลี่ยนอะไรไม่เขียน audit

**ลบแล้วประวัติยังอยู่ โดยไม่มี migration** `webhook_deliveries` ผูกกับ webhook ด้วย foreign key แบบ cascade ถ้าลบแถวจริง ประวัติการส่งหายไปด้วย และคำถาม "ปลายทางเคยได้ event นี้ไหม" จะตอบไม่ได้ ส่วนคอลัมน์ `deleted_at` ต้องมี migration ซึ่งรอบนี้ไม่ทำ การลบจึงเก็บแถวไว้ ปิด webhook ล้างค่า secret ที่เข้ารหัสเป็นสตริงว่าง และตัด query string ออกจาก URL เพราะอาจมี token ของผู้รับ secret ว่างคือเครื่องหมายว่าถูกลบ (`WebhookSubscription.IsDeleted`) เพราะ webhook ที่ยังใช้งานมี secret เสมอ และ webhook ที่ไม่มี secret ก็ลงนามอะไรไม่ได้อยู่แล้ว ผลคือ

- webhook ที่ลบหายจากรายการ delivery ที่รอส่งหยุดเป็น `failed` ด้วย `webhook_deleted`
- `PATCH`, `DELETE`, `rotate-secret` และ `redeliver` หลังลบได้ `404`
- `GET /staff/webhooks/{id}/deliveries` ยังอ่านได้ด้วยรหัสเดิม จนงาน housekeeping ลบ event ที่เก่ากว่า 30 วันพร้อม delivery ตามปกติ
- audit `integration.webhook_deleted` พร้อมปลายทาง รายการ event และสถานะก่อนลบ
- แถวที่ลบแล้วไม่ถูกลบจริงภายหลัง แต่ไม่มีความลับเหลือ และมีขนาดเล็ก

**secret ใหม่ไม่มีช่วงซ้อน** มีคอลัมน์ secret คอลัมน์เดียว secret เดิมจึงหยุดลงนามทันที ปลายทางที่ยังใช้ค่าเดิมจะปฏิเสธการส่งระหว่างนั้น และการส่งจะลองใหม่ตามรอบปกติ (1, 5, 25 นาที และต่อไป) ปลายทางที่เปลี่ยนค่าทันในช่วงนั้นจึงไม่เสีย event คำตอบมี `Cache-Control: no-store` และ audit `integration.webhook_secret_rotated` ไม่เก็บ secret หมุนได้แม้ webhook ปิดอยู่ เพื่อเปลี่ยน secret ก่อนเปิดใช้อีกครั้ง

**ส่งซ้ำได้ครั้งเดียวต่อการกด** ส่งซ้ำได้เฉพาะ delivery ที่ `failed` แถวเดิมกลับเป็น `pending` และถึงเวลาส่งทันที งานเบื้องหลังส่งในรอบถัดไปด้วย event id และ body เดิม ผู้รับจึงกันซ้ำด้วย `X-Webhook-Id` ได้เหมือนการลองใหม่ปกติ

- กดซ้ำระหว่างที่ยังรอส่งได้ `409 state_conflict` สองคนกดพร้อมกัน คนหลังได้ `409` จาก version ของแถว จึงไม่มีทางเข้าคิวสองครั้ง
- delivery ที่ลองครบหกครั้งแล้วได้ลองอีกหนึ่งครั้ง ไม่สำเร็จก็กลับเป็น `failed` (`attempts` จึงเกิน `max_attempts` ได้) delivery ที่ถูกหยุดเพราะปิด webhook ได้ลองต่อตามรอบที่ยังเหลือ
- delivery ของ webhook อื่น หรือของ webhook ที่ลบแล้ว ได้ `404` ส่วน webhook ที่ปิดอยู่ได้ `409` เพราะตัวส่งจะหยุดมันอีกก่อนออกไป
- audit `integration.webhook_redelivered` พร้อมรหัส delivery รหัส event ชนิดของ event และ error เดิม

**กฎของ API key**

- **รายการไม่มีตัว key** มี prefix (`hp_` และ 10 ตัว) ชื่อ scope สาขา `status` (`active`, `expired`, `revoked`) ผู้สร้าง และเวลาสร้าง หมดอายุ ใช้ล่าสุด และยกเลิก ไม่มีตัว key หรือ hash ซึ่งระบบไม่มีตัว key อยู่แล้ว key ที่หมดอายุและที่ยกเลิกแล้วยังอยู่ในรายการ เพื่อให้แถว audit ที่มี `via_api_key` ยังรู้ว่าเป็น key ไหน
- **จัดการได้เฉพาะ key ที่ตัวเองสร้างได้** ผู้ที่ไม่ผูกสาขาเห็นและยกเลิกได้ทุก key ผู้ที่ผูกสาขาเห็นเฉพาะ key ที่ทุกสาขาของ key อยู่ในสาขาของตัวเอง key ของสาขาอื่นหรือของทุกสาขาไม่ขึ้นในรายการ และยกเลิกได้ `404` เหมือนไม่มีอยู่ เป็นกฎเดียวกับการสร้าง
- **ยกเลิกแล้วคำขอถัดไปถูกปฏิเสธ** การยืนยันตัวด้วย key อ่านแถวจากฐานข้อมูลทุกคำขอ (`ApiKeyAuthenticator`) ไม่มี cache ทั้งในหน่วยความจำและใน token เมื่อ `DELETE` commit แล้ว คำขอถัดไปของ key นั้นได้ `401` คำขอที่ผ่านการยืนยันตัวไปก่อนแล้วทำต่อจนจบ
- **ยกเลิกด้วยคำสั่งเดียว ไม่ใช้ `If-Match`** key ที่ใช้งานอยู่เขียน `last_used_at` ทุกนาที version ของแถวจึงเปลี่ยนตลอด ถ้าบังคับ version การยกเลิก key ที่ถูกใช้ถี่ ซึ่งก็คือ key ที่หลุด จะชนกับการใช้งานเรื่อย ๆ ระบบจึงตั้ง `revoked_at` ด้วย UPDATE เดียวที่มีเงื่อนไข `revoked_at IS NULL` และรายการไม่มีช่อง `version`
- ยกเลิก key ที่ยกเลิกไปแล้วได้ `204` และไม่เขียน audit ซ้ำ audit `integration.api_key_revoked` เก็บชื่อ prefix ผู้สร้าง และสถานะก่อนยกเลิก
- ใช้คอลัมน์ `revoked_at` และการตรวจตอนยืนยันตัวที่มีอยู่แล้ว

**ลิงก์ปฏิทินใหม่** `POST /staff/integrations/calendar/token` สร้าง token ใหม่ให้ผู้เรียก แทนทั้ง hash และ ciphertext และล้าง `last_used_at` ใน UPDATE เดียว แอปปฏิทินที่ดึงฟีดพร้อมกันจึงไม่ทำให้ชน version ลิงก์เดิมหา token ไม่เจอและได้ `401` ทันที คำตอบรูปเดียวกับ `GET /staff/integrations/calendar/ics` แบบ JSON และมี `Cache-Control: private, no-store` ยังไม่มีลิงก์ก็สร้างลิงก์แรกให้ (audit `integration.calendar_feed_created`) มีแล้วเขียน `integration.calendar_feed_rotated` ไม่มีทางสร้างลิงก์ใหม่ให้คนอื่น เพราะการปิดบัญชีของคนนั้นหยุดลิงก์ของเขาอยู่แล้ว API key ได้ `403` เพราะ key ไม่มีปฏิทินของตัวเอง

**ทางเลือกที่ไม่เลือก**

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| ลบ webhook โดยลบแถวจริง | foreign key แบบ cascade ลบประวัติการส่งไปด้วย หลักฐานว่าเคยส่งอะไรไปที่ไหนจะเหลือแค่ใน audit |
| เพิ่มคอลัมน์ `deleted_at` หรือ secret ตัวที่สองสำหรับช่วงซ้อน | ต้องมี migration ซึ่งรอบนี้ไม่ทำ เพิ่มทีหลังได้โดยไม่เปลี่ยน endpoint |
| เปิด webhook อีกครั้งแล้วส่ง event ที่เกิดระหว่างปิดย้อนหลัง | การปิดมักแปลว่าปลายทางมีปัญหา หรือไม่ควรได้ข้อมูลช่วงนั้น การส่งย้อนหลังเองคือการเดาแทนคลินิก ส่งซ้ำทีละรายการได้ |
| ส่งซ้ำโดยสร้าง delivery แถวใหม่ | unique `(event_id, subscription_id)` กันไว้ และแถวเดิมเก็บผลครั้งล่าสุดอยู่แล้ว ใช้แถวเดิมจึงไม่ต้องแก้ schema |
| บังคับ `If-Match` ตอนยกเลิก key | version เปลี่ยนทุกนาทีที่ key ถูกใช้ การหยุด key ที่หลุดต้องไม่แพ้การแข่งกับคนที่ใช้มันอยู่ |
| `PATCH /staff/api-keys/{id}` ที่ตั้ง `revoked: true` | การยกเลิกย้อนกลับไม่ได้ `DELETE` บอกความหมายนั้นตรงกว่า และไม่ต้องตอบคำถามว่าเปิดคืนได้ไหม |
| ให้ `integration:manage` สร้างลิงก์ปฏิทินใหม่ให้คนอื่น | ลิงก์เป็นของคน ไม่ใช่ของคลินิก และการปิดบัญชีหยุดลิงก์อยู่แล้ว |

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่มี `GET /staff/webhooks/{id}` และ `GET /staff/api-keys/{id}` แบบตัวเดียว รายการสั้นพอให้หาจากรายการ
- ไม่คืน secret เดิมหรือตัว key ทางใดเลย หมุนหรือสร้างใหม่เท่านั้น
- ไม่มีทางกู้ webhook ที่ลบหรือ key ที่ยกเลิก สร้างใหม่ได้
- ไม่แก้ชื่อ scope สาขา หรือวันหมดอายุของ key ที่ออกแล้ว ต้องการต่างจากเดิมให้ออก key ใหม่แล้วยกเลิกตัวเก่า เพราะ key ที่ขยายสิทธิ์ได้หลังออก คือ key ที่ระบบปลายทางไม่รู้ว่าทำอะไรได้บ้าง
- ไม่ส่งซ้ำทีละหลายรายการ
- ไม่เพิ่ม scope ใหม่ และไม่มี migration

**หน้าจอ** หน้า webhook มีรายการ webhook ทั้งหมด แต่ละตัวมีปุ่มประวัติการส่ง แก้ไข ปิดหรือเปิดใช้งาน สร้าง secret ใหม่ (แสดงครั้งเดียวพร้อมคำเตือน) และลบ การปิด การสร้าง secret ใหม่ และการลบ ถามยืนยันอีกครั้งพร้อมบอกผลที่จะเกิด ช่องใส่รหัส webhook ยังอยู่ ไว้เปิดประวัติของ webhook ที่ลบแล้ว หน้าประวัติการส่งมีปุ่มส่งอีกครั้งที่รายการที่ไม่สำเร็จ เมื่อ webhook เปิดอยู่ หน้า API key มีรายการ key พร้อมสถานะ และปุ่มยกเลิก key ที่ถามยืนยันก่อน หน้าปฏิทินมีปุ่ม "สร้างลิงก์ใหม่" ที่ถามยืนยันว่าลิงก์เดิมจะใช้ไม่ได้ รายละเอียดอยู่ใน [การเชื่อมต่อระบบ](features/integrations.md) และ [การเชื่อมต่อระบบภายนอก (ความปลอดภัย)](security/integrations.md)

## 23. ค่าตั้งของนัดอ่านกลับไม่ได้ และคิวรอเพิ่มได้อย่างเดียว

**ช่องโหว่** นโยบายยกเลิกและประเภทนัดมีเส้นเดียวใน contract คือ `PUT` ค่าที่เก็บไว้จึงเห็นได้แค่ในคำตอบของ `PUT` ครั้งล่าสุด หน้าตั้งค่าต้องเริ่มฟอร์มจากค่าตั้งต้นของระบบ และการบันทึกแทนที่ค่าเดิมทั้งชุดโดยไม่เคยเห็นค่าเดิม หน้าจองของเคาน์เตอร์และของลูกค้าก็เลือกประเภทนัดจากรายการจริงไม่ได้ หน้าจองของลูกค้าเขียน `regular` กับ `follow_up` ไว้ในหน้าเว็บ ถ้าคลินิกปิดจองออนไลน์ของ `follow_up` ลูกค้ายังกดได้แล้วโดน `422` และประเภทใหม่ที่เปิดจองออนไลน์ไว้ ลูกค้าก็ไม่มีทางเลือก ส่วนคิวรอมีแค่ `POST /staff/waiting-list` ดูไม่ได้ว่าใครรออยู่ และถอนคนที่ไม่ต้องการรอแล้วออกไม่ได้ คนนั้นจึงได้ข้อความคิวว่างไปจนถึงวันสุดท้ายที่รอ

**ทำไมสำคัญ** ค่าปรับคือเงินที่ลูกค้าอาจถูกเรียกเก็บ การแก้นโยบายโดยไม่เห็นค่าเดิมคือการเดา และการบันทึกทับทั้งชุดอาจลบประเภทนัดที่คลินิกตั้งไว้โดยไม่รู้ตัว ส่วนข้อความคิวว่างที่ส่งถึงคนที่จองที่อื่นไปแล้ว ทำให้ข้อความของคลินิกถูกมองข้าม

**คำตอบ** ห้า endpoint ได้รับอนุมัติก่อนสร้าง ไม่มี migration

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/staff/policies/cancellation` | `settings:read` | นโยบายตามที่เก็บ รูปเดียวกับคำตอบของ `PUT` พร้อม `version` และ `ETag` |
| GET | `/staff/appointment-types` | `appointment:read` | ทุกประเภทพร้อมกติกา รูปเดียวกับคำตอบของ `PUT` พร้อม `version` และ `ETag` |
| GET | `/portal/appointment-types` | `portal` | เฉพาะประเภทที่เปิดจองออนไลน์ เรียงตามที่คลินิกตั้ง แต่ละแถวมีแค่ `code` `name` และ `duration_minutes` |
| GET | `/staff/waiting-list?branch=&service_id=&status=&limit=&cursor=` | `appointment:write` | รายการคิวรอ เก่าสุดก่อน แบ่งหน้าด้วย cursor |
| DELETE | `/staff/waiting-list/{id}` | `appointment:write` | ถอนออกจากคิวรอ ตอบ `204` ถอนซ้ำตอบ `404` |

คลินิกที่ยังไม่เคยบันทึกนโยบายหรือประเภทนัด อ่านได้ค่าตั้งต้นพร้อม `version` เป็น 0 และ `PUT` ครั้งแรกรับ `If-Match: "0"` เหมือนค่าตั้งของคลินิกอื่น ๆ

**ทำไมใช้ scope เหล่านี้**

- **นโยบาย `settings:read`** เป็นคู่อ่านของ `settings:write` ที่ `PUT` ใช้ แบบเดียวกับ `GET /clinic/settings/booking`
- **ประเภทนัด `appointment:read`** คนที่ต้องใช้รายการนี้มากที่สุดคือคนจอง และการเลือกประเภทเป็นส่วนหนึ่งของการจอง role ตั้งต้นที่จองได้ทุก role ถือ scope นี้ (พนักงานต้อนรับผ่าน `appointment:*` ผู้ดูแล และเจ้าของ) ส่วน `settings:read` พนักงานต้อนรับไม่มี role ตั้งต้นที่แก้ประเภทนัดได้ถือ `appointment:read` อยู่แล้ว role ที่คลินิกตั้งเองและมีแค่ `settings:write` จะเห็นในหน้าตั้งค่าว่าอ่านไม่ได้ และหน้าไม่เปิดให้บันทึกทับโดยไม่เห็นค่าเดิม ระบบรับ scope ได้ทีละตัวต่อเส้น จึงไม่ทำแบบ "ตัวไหนก็ได้"
- **ประเภทนัดฝั่งลูกค้า `portal`** หน้าจองของลูกค้าต้องเข้าระบบอยู่แล้ว รายการนี้ตัดเหลือเฉพาะประเภทที่ `POST /portal/appointments` ยอมรับ ไม่มีความเร่งด่วนของคิวหรือเวลาจองล่วงหน้า เพราะเป็นกติกาของคลินิก ไม่ใช่ของลูกค้า ไม่ทำเป็นเส้นสาธารณะ เพราะไม่มีหน้าไหนที่ไม่เข้าระบบใช้
- **คิวรอ `appointment:write`** เท่ากับ `POST` ที่มีอยู่ รายการนี้เป็นเครื่องมือของเคาน์เตอร์สำหรับจัดการสิ่งที่ตัวเองใส่ไว้

**กฎของรายการคิวรอ**

- **สถานะคิดเอา ไม่ได้เก็บ** `waiting` คือยังไม่เลย `latest_on` และ `lapsed` คือเลยแล้ว ไม่ส่ง `status` คือทั้งสองแบบ ค่าอื่นตอบ `422` ที่ช่อง `status`
- **เรียงจากเก่าไปใหม่** ซึ่งเป็นลำดับเดียวกับที่ระบบแจ้งคนที่รอ
- **แต่ละแถวมีชื่อมาด้วย** `pet_name` และ `service_name` เพิ่มจากรูปของคำตอบ `POST` เพราะหน้าจอต้องแสดงชื่อ และพนักงานต้อนรับไม่มี `patient:read` ให้อ่านชื่อสัตว์ทีละตัว ชื่อลูกค้าไม่มีในแถว มีแค่ `customer_id` ให้เปิดหน้าลูกค้าด้วย `customer:read`
- **สาขา** `branch` คือรายการที่คิวว่างของสาขานั้นจะแจ้งถึง คือรายการของสาขานั้นและรายการที่รอทุกสาขา พนักงานที่ผูกสาขาเห็นแค่รายการของสาขาตัวเองและรายการที่รอทุกสาขา ขอสาขาอื่นตอบ `403` ข้อจำกัดนี้อยู่ในคำค้น ไม่ได้กรองหลังอ่าน แบ่งหน้าไปเท่าไรก็ไม่หลุด

**การถอนคือการลบแถว** เลือก `DELETE` ไม่ใช่ `POST .../cancel` เพราะรายการคิวรอไม่มีสถานะให้เปลี่ยน การเพิ่มสถานะ "ถอนแล้ว" ต้องมี migration ไม่มีตารางไหนชี้มาที่แถวนี้ และข้อความที่ส่งไปแล้วอยู่ในประวัติการส่งของมันเอง สิ่งที่ควรเก็บคือใครถอนและถอนอะไร ซึ่ง audit `waiting_list.removed` เก็บไว้พร้อมลูกค้า บริการ หมอ ช่วงวัน และจำนวนครั้งที่เคยแจ้ง

- ถอนซ้ำตอบ `404` แบบเดียวกับการลบกติกาเตือนซ้ำ (§ 19)
- รายการที่ระบุสาขาที่ผู้เรียกไม่ได้สังกัดตอบ `403` รายการที่รอทุกสาขาเป็นของทุกสาขา เคาน์เตอร์สาขาไหนก็ถอนได้ เหมือนที่ทุกสาขาเห็นในรายการ
- ไม่มี `If-Match` เพราะรายการคิวรอไม่มีช่องไหนที่คนแก้ได้
- ถอนแล้วใส่สัตว์ตัวเดิมกับบริการเดิมใหม่ได้ทันที

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่มีการแก้รายการคิวรอ ถ้าช่วงวันหรือหมอผิดให้ถอนแล้วใส่ใหม่
- ไม่ลบรายการที่หมดอายุเอง รายการเหล่านั้นไม่ได้รับข้อความแล้ว และดูย้อนหลังได้ที่ `status=lapsed`
- ไม่ให้ลูกค้าดูหรือถอนคิวรอเองจาก portal
- เวลาว่างในหน้าจองยังคิดจากระยะเวลาของบริการ ไม่ใช่ของประเภทนัด ระบบตรวจช่วงเวลาจริงตามประเภทอีกครั้งตอนจอง หน้าจองของเคาน์เตอร์บอกเรื่องนี้ใต้ช่องประเภท
- ไม่คิด scope ใหม่ และไม่เพิ่ม scope ให้ role ใด

**หน้าจอ** หน้าตั้งค่านโยบายยกเลิกและประเภทนัดโหลดค่าปัจจุบันและส่ง `version` เป็น `If-Match` หน้าจองนัดของเคาน์เตอร์มีช่องเลือกประเภทนัดจากรายการจริง ปฏิทินนัดมีปุ่ม "ตรวจนัดชนทั้งวัน" ที่ใช้ `GET /staff/appointments/conflicts?date=` ตัวเดิม หน้าคิวรอแสดงรายการพร้อมปุ่มถอนออก และหน้าจองของลูกค้าแสดงประเภทนัดจาก `GET /portal/appointment-types` รายละเอียดอยู่ใน [นัดขั้นสูง](features/advanced-booking.md)

## 24. ลูกค้าเขียนถึงคลินิกได้ทาง LINE ทางเดียว และอ่านบทสนทนาใน portal ไม่ได้

**ช่องโหว่** contract เขียนว่ากล่องข้อความคือ "กล่องข้อความรวมทุกช่องทางต่อลูกค้าหนึ่งคน" แต่ทางเดียวที่ลูกค้าเขียนเข้ามาได้คือแชตกับบัญชี LINE ของคลินิก และต้องให้เคาน์เตอร์ผูก LINE ให้ก่อน ลูกค้าที่ไม่ใช้ LINE หรือยังไม่ได้ผูก เขียนถึงคลินิกในระบบไม่ได้เลย ปุ่ม "แชทกับคลินิก" บนการ์ดนัดใน portal จึงต้องพาไปหน้าติดต่อเรา และลูกค้าที่เข้าระบบอยู่ก็อ่านบทสนทนาของตัวเองไม่ได้ เห็นแค่สำเนาคำตอบในกล่องแจ้งเตือน โดยไม่มีคำถามของตัวเองอยู่ข้างกัน

**ทำไมสำคัญ** portal เป็นที่เดียวที่ระบบรู้แน่ว่าผู้เขียนเป็นใคร เพราะลูกค้าเข้าระบบด้วยบัญชีของตัวเอง ไม่ต้องเดาจากที่อยู่ผู้ส่งแบบ LINE คำถามที่ไม่มีทางเขียนในระบบจะไปจบที่โทรศัพท์หรือแชตส่วนตัวของพนักงาน ซึ่งไม่มีใครเห็นต่อ ไม่มีประวัติ และไม่ผ่านด่านความยินยอม

**การตัดสิน** สองเส้น ได้รับอนุมัติก่อนสร้าง ใช้ scope `portal` ไม่มี scope ใหม่ และไม่มี migration

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/portal/thread?limit=&cursor=` | `portal` | กล่องของลูกค้าที่เข้าระบบ พร้อมข้อความหนึ่งหน้า ใหม่ไปเก่า `next_cursor` พาไปข้อความที่เก่ากว่า ลูกค้าที่ยังไม่เคยเขียนได้คำตอบที่ไม่มี `id` และ `data` ว่าง การอ่านไม่สร้างอะไร |
| POST | `/portal/thread/messages` | `portal` | เขียนถึงคลินิก `{ "text": "..." }` ช่องทางของข้อความคือ `portal` ข้อความแรกเปิดกล่อง ตอบ `201` พร้อมข้อความที่เก็บ อยู่ใต้ policy `messaging` |

```http
GET /v1/portal/thread?limit=50                       portal
{ "id": "thr_...", "status": "replied",
  "data": [ { "id": "msg_...", "direction": "outbound", "kind": "text", "text": "พามาได้ทุกวันค่ะ",
              "sent_at": "...", "sent_by_name": "หมอเอ" },
            { "id": "msg_...", "direction": "inbound", "channel": "portal", "kind": "text",
              "text": "ขอสอบถามเรื่องวัคซีนค่ะ", "sent_at": "..." } ],
  "page": { "next_cursor": null } }

POST /v1/portal/thread/messages                      portal
{ "text": "ขอสอบถามเรื่องวัคซีนค่ะ" }
201 { "id": "msg_...", "direction": "inbound", "channel": "portal", "kind": "text", "text": "ขอสอบถามเรื่องวัคซีนค่ะ", "sent_at": "..." }
```

**กฎของสองเส้นนี้**

- **ของใครของมัน** รหัสลูกค้ามาจาก token เท่านั้น ไม่มี parameter ไหนชี้ไปกล่องของคนอื่นได้ ผู้ดูแลสัตว์ร่วม (carer) เป็นลูกค้าอีกคนที่มีบัญชีและกล่องของตัวเอง จึงไม่เห็นกล่องของเจ้าของ และเจ้าของก็ไม่เห็นกล่องของเขา token ของพนักงานได้ `403` แม้ถือ `*` เพราะไม่มีรหัสลูกค้า
- **เส้นทางเดียวกับข้อความจาก LINE** ข้อความเข้า `ReceiveCustomerMessageHandler` ตัวเดียวกัน จึงอยู่ในกล่องเดียวของลูกค้าไม่ว่ามาทางไหน กล่องถูกจัดไว้ที่สาขาที่ลูกค้าจองครั้งล่าสุดตามกฎเดิม และข้อความแรกสองข้อความที่แย่งกันสร้างกล่องได้ลองใหม่เองเหมือนเดิม
- **ข้อความ** ต้องไม่ว่าง และยาวไม่เกิน 1,000 ตัวอักษรหลังตัดช่องว่างหัวท้าย เท่ากับคำตอบของพนักงาน ข้อความที่ผิดตอบ `422` ที่ช่อง `text` และไม่เก็บอะไร cursor ที่อ่านไม่ได้ตอบ `422`
- **ไม่ตอบอัตโนมัติ** บน LINE คำตอบอัตโนมัติบอกคนที่พิมพ์ในแอปแชตว่าจะมีคนตอบ หน้าแชทของ portal บอกเรื่องนี้เองอยู่แล้ว กล่องเปลี่ยนเป็นรอคำตอบ และขึ้นด้านบนในหน้า "ข้อความลูกค้า" ของพนักงาน
- **สิ่งที่ลูกค้าเห็น** ไม่มีรหัสพนักงานและไม่มีผลการส่ง ข้อความของคลินิกมี `sent_by_name` คือชื่อที่แสดงของผู้ตอบ หน้าจอขึ้นว่า "คลินิก" เมื่อไม่มีชื่อ ข้อความของลูกค้ามี `channel` บอกว่าเขียนมาทางไหน ข้อความจาก LINE ที่เป็นรูปหรือสติกเกอร์ขึ้นเป็นชนิดของสิ่งที่ส่ง เหมือนฝั่งพนักงาน
- **เรกคอร์ดที่ถูกรวมแล้ว** token ที่ออกก่อนการรวมเขียนได้ `409 state_conflict` ไม่สร้างกล่องใหม่ให้เรกคอร์ดที่ไม่ใช้แล้ว การรวมย้ายข้อความทุกช่องทาง รวมทั้ง `portal` ไปกล่องของเรกคอร์ดที่เก็บด้วย `FoldThreadAsync` ตัวเดิม
- **rate limit** `POST` อยู่ใต้ policy `messaging` 60 ครั้งต่อนาทีต่อ token ตัวเดียวกับคำตอบของพนักงาน `GET` ใช้เพดาน 600 ครั้งต่อนาทีของทั้งระบบ หน้าแชทอ่านใหม่ทุก 15 วินาทีขณะเปิดอยู่ คือ 4 ครั้งต่อนาที
- **ไม่บันทึก audit** เหมือนส่วนอื่นของกล่องข้อความ ข้อความคือสิ่งที่ลูกค้าเลือกเขียนถึงคลินิก ไม่ใช่เวชระเบียน

**ช่องทาง `portal` ไม่ใช่ช่องทางส่ง** ข้อความในกล่องใช้ชนิดใหม่ `MessageChannel` ที่มี `line`, `sms`, `email` และ `portal` แยกจาก `DeliveryChannel` ของระบบแจ้งเตือนซึ่งยังมีแค่สามค่า ชื่อสามค่าแรกเหมือนเดิมทุกตัวอักษร ค่าที่เก็บในคอลัมน์ `channel` และ `last_inbound_channel` จึงเหมือนเดิม และไม่ต้องมี migration ผลคือ `portal` ไม่มีทางหลุดเข้า dispatcher ประวัติการส่ง ตัวกรอง `channel` ของประวัติการส่ง หรือช่อง `channel` ของ `POST /staff/notifications/send`

**คำตอบของพนักงานถึงกล่องที่ลูกค้าเขียนล่าสุดจาก portal** คำตอบยังใช้กฎเดิมคือ "ลองช่องทางที่ลูกค้าใช้ล่าสุดก่อน" แต่ `portal` ไม่ใช่ช่องทางส่ง จึงไม่มีช่องทางให้ลองก่อน และเป็นไปตาม [การแจ้งเตือน](features/notifications.md) ทุกข้อ

1. คำตอบถูกเก็บในกล่องก่อนส่งเสมอ จึงขึ้นในหน้าแชทของลูกค้าในการอ่านครั้งถัดไป ไม่ว่าการส่งจะเป็นอย่างไร
2. ส่งผ่าน `INotificationDispatcher` ด้วยเทมเพลต `thread.reply` ถ้าลูกค้ายินยอมเรื่อง `service_messages` สำเนาเข้ากล่องแจ้งเตือนในเว็บ (หัวเรื่อง "ข้อความตอบกลับจากคลินิก") แล้วส่งทาง LINE, SMS หรืออีเมลตามลำดับปกติ ข้ามช่องทางที่ส่งไม่ได้ และลองช่องทางถัดไปเมื่อส่งไม่สำเร็จ ลูกค้าที่ปิดหน้าเว็บไปแล้วจึงรู้ว่าคลินิกตอบ
3. ถ้าลูกค้าถอนความยินยอม ไม่มีสำเนาในกล่องแจ้งเตือนและไม่ส่งทางไหน `delivery` เป็น `skipped` กับ `no_consent` เหมือนเดิม แต่คำตอบยังขึ้นในหน้าแชทเมื่อลูกค้าเปิดเอง เพราะเป็นคำตอบของคำถามที่ลูกค้าถามเอง และลูกค้าเป็นคนเปิดอ่าน ไม่ใช่คลินิกส่งไปหา
4. `delivery` ในคำตอบของ `POST /staff/threads/{id}/messages` บอกผลการส่งทาง LINE, SMS หรืออีเมล ไม่ได้บอกเรื่องหน้าแชท ซึ่งขึ้นเสมอ
5. คำตอบที่ไปทาง SMS เสียเครดิตตามจำนวนส่วนเหมือนเดิม ลูกค้าที่ไม่อยากได้ SMS ปิดช่องทางนั้นเองได้ในหน้าบัญชี

**อ่านแล้วฝั่งลูกค้า โดยไม่มีคอลัมน์ใหม่** กล่องไม่มีที่เก็บว่าลูกค้าอ่านถึงไหน และการเพิ่มต้องมี migration แต่คำตอบทุกฉบับที่ผ่านด่านความยินยอมมีสำเนา `thread.reply` ในกล่องแจ้งเตือน ซึ่งมี `read_at` อยู่แล้ว หน้าแชทจึงกดว่าอ่านแล้วให้สำเนาเหล่านั้นผ่าน `GET /portal/notifications?unread=true` และ `POST /portal/notifications/read` (§ 13) เมื่อมีคำตอบใหม่ขึ้นบนจอ ตัวเลขบนกระดิ่งจึงลดลงเอง ไม่มีเส้นใหม่ ส่วนพนักงานยังไม่เห็นว่าลูกค้าอ่านคำตอบแล้วหรือยัง

**ทางเลือกที่ไม่เลือก**

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เพิ่ม `portal` เป็นค่าที่สี่ของ `DeliveryChannel` | `DeliveryChannel` คือทางที่ระบบใช้ส่งข้อความ ใช้ทั้งใน dispatcher ประวัติการส่ง และค่าที่รับจากพนักงาน ค่าที่ส่งอะไรไม่ได้จะหลุดเข้าไปในที่เหล่านั้น เช่นกรองประวัติการส่งด้วย `channel=portal` ได้ทั้งที่ไม่มีแถวไหนเป็นไปได้ |
| คำตอบของกล่องที่มาจาก portal เข้าแค่หน้าแชทและกล่องแจ้งเตือน ไม่ส่ง LINE, SMS หรืออีเมล | ลูกค้าที่ถามแล้วปิดหน้าเว็บจะไม่รู้ว่าคลินิกตอบแล้ว และกฎ "ทุกข้อความผ่านเส้นทางเดียวกัน" ของการแจ้งเตือนจะมีข้อยกเว้นแรก |
| เพิ่มคอลัมน์ "ลูกค้าอ่านถึงไหน" หรือเส้น `POST /portal/thread/read` | ต้องมี migration หรือ endpoint ที่สามซึ่งไม่ได้ขออนุมัติ สำเนาในกล่องแจ้งเตือนมี `read_at` อยู่แล้ว และกระดิ่งก็นับจากที่นั่น |
| ให้ `GET` สร้างกล่องว่างเมื่อยังไม่มี | กล่องว่างจะขึ้นในหน้า "ข้อความลูกค้า" ของพนักงานทั้งที่ไม่มีใครเขียน ลูกค้าทุกคนที่เคยเปิดหน้าแชทจะมีกล่อง |
| stream แบบ server-sent events ให้ portal | portal ยังไม่มี stream ของตัวเอง การ์ดนัดใช้การอ่านใหม่ทุก 15 วินาทีขณะเปิดอยู่แล้ว แชทที่คลินิกตอบในเวลาทำการไม่ต้องเร็วกว่านั้น |
| ให้ผู้ดูแลสัตว์ร่วมเห็นกล่องของเจ้าของ | กล่องเป็นของคน ไม่ใช่ของสัตว์ ข้อความอาจมีเรื่องอื่นนอกจากสัตว์ตัวที่ดูแลร่วม เช่นเรื่องเงิน |

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่แนบรูปหรือไฟล์จาก portal ส่งได้แค่ข้อความ ไฟล์ของสัตว์ส่งได้จากหน้าส่งเอกสาร
- ไม่แก้หรือลบข้อความที่ส่งแล้ว
- ไม่มีคำตอบอัตโนมัติ และไม่บอกพนักงานว่าลูกค้าอ่านแล้ว
- ไม่มีเส้นที่สามสำหรับอ่านแล้ว
- ไม่เพิ่ม scope ใหม่ และไม่มี migration

**หน้าจอ** portal มีหน้า "แชทกับคลินิก" (`/portal/messages`) ข้อความของลูกค้าอยู่ขวา ของคลินิกอยู่ซ้ายพร้อมชื่อผู้ตอบหรือคำว่า "คลินิก" ช่องพิมพ์อยู่ใต้บทสนทนา หน้าอ่านใหม่ทุก 15 วินาทีขณะเปิดอยู่ และดูข้อความก่อนหน้าได้ทีละหน้า ปุ่ม "แชทกับคลินิก" บนการ์ดนัดและเมนูบัญชีพาไปหน้านี้ หน้า "ข้อความลูกค้า" ของพนักงานแสดงข้อความที่มาจาก portal ด้วยป้ายช่องทาง "เว็บไซต์" รายละเอียดอยู่ใน [ข้อความลูกค้า](features/messaging.md) และ [portal ลูกค้า](features/portal.md)

## 25. สิ่งที่โมดูลแพ็กเกจ คูปอง และสต๊อกยาสร้างไว้ ดูกลับหรือแก้ไม่ได้

**ช่องโหว่** หมวด Loyalty, Packages และ Promotions มีแต่เส้นสร้าง คูปองที่ออกไปแล้วดูรายการไม่ได้ และปิดก่อนวันสิ้นสุดไม่ได้ โค้ดที่หลุดไปในกลุ่มแชตจึงใช้ได้จนหมดอายุหรือครบจำนวน กลุ่มลูกค้าที่บันทึกแล้วเลือกกลับมาไม่ได้ แพ็กเกจของลูกค้าอ่านได้ทางเดียวผ่านบัญชีแต้ม แต้มให้หรือหักด้วยมือไม่ได้ และอัตราแต้ม มูลค่าแต้ม เกณฑ์ระดับ กับอายุแต้มเขียนตายตัวไว้ในโค้ด ([assumptions.md § 43](./assumptions.md)) ด้านสต๊อกยา หมวด Inventory ไม่มีเส้นแก้รายการในคลัง ราคาขายที่ตั้งตอนรับของครั้งแรกจึงแก้ไม่ได้อีกเลย ยาที่เลิกขายยังขึ้นในตัวเลือกยาของหมอ และใบสั่งซื้ออ่านย้อนหลังหรือยกเลิกไม่ได้ ของที่ซัพพลายเออร์แจ้งว่าไม่มาจึงค้างอยู่ใน "สั่งไว้" ตลอดไป ([assumptions.md § 42](./assumptions.md))

**ทำไมสำคัญ** ทั้งหมดเป็นเงิน คูปองที่ปิดไม่ได้คือส่วนลดที่คลินิกหยุดไม่ได้ ราคายาที่แก้ไม่ได้คือค่ายาที่ผิดทุกครั้งที่จ่าย และใบสั่งซื้อที่ยกเลิกไม่ได้ทำให้ตัวเลข "สั่งไว้" หลอกคนสั่งของว่าของกำลังมา จนไม่สั่งใหม่

**คำตอบ** สิบเส้น ได้รับอนุมัติก่อนสร้าง มี migration หนึ่งตัว คือ `ManageCrmAndInventory`

**ทำไมใช้ scope เหล่านี้**

- **อ่านใช้ `crm:read` เขียนใช้ `crm:manage`** ตามคู่ที่โมดูลใช้อยู่ ปิดคูปองและปรับแต้มเป็นการเขียน
- **กติกาแต้มใช้ `settings:read` และ `settings:write`** เพราะอยู่ใต้ `/clinic/settings` เหมือนค่าตั้งการจองและคิว มูลค่าแต้มและอัตราได้แต้มเป็นกติกาของคลินิก คนที่ตั้งกติกาของคลินิกเป็นคนตั้ง ส่วน `crm:manage` ทำโปรโมชันภายใต้กติกานั้น ระบบรับ scope ได้ทีละตัวต่อเส้น จึงไม่ทำแบบ "ตัวไหนก็ได้"
- **แก้รายการในคลังใช้ `inventory:write`** ตัวเดียวกับการรับเข้า ซึ่งเป็นที่ที่รายการเกิด
- **ใบสั่งซื้อใช้ `inventory:purchase`** ตัวเดียวกับการออกใบ รายการมีต้นทุนต่อหน่วย ซึ่งรายการสต๊อกไม่แสดง

**คูปอง**

- สถานะคิดเอาทุกครั้งที่อ่าน ตามลำดับ ปิดแล้ว (`deactivated`) หมดอายุ (`expired`) ใช้ครบ (`used_up`) ยังไม่เริ่ม (`scheduled`) แล้วจึงใช้ได้ (`active`) ตัวกรอง `status` ใช้ลำดับเดียวกันในคำค้น ค่าอื่นตอบ `422`
- `redeemed_count` คือการใช้ที่ยังอยู่ (บิลที่ยกเลิกคืนการใช้) `remaining` คือส่วนที่เหลือของ `max_redemptions` ไม่มีเมื่อไม่จำกัด
- **ปิดแล้วการใช้ที่มีอยู่ไม่เปลี่ยน** บิลที่ใช้คูปองไปแล้วยังมีส่วนลดเดิม การใช้ครั้งถัดไปตอบ `409 coupon_deactivated` ซึ่งตรวจก่อนข้ออื่นทั้งหมด ปิดซ้ำตอบ `409 state_conflict` ไม่มีทางเปิดกลับ โค้ดที่ควรใช้ได้อีกให้ออกใหม่ บันทึกว่าปิดช่วงไหนจึงไม่ถูกเขียนทับ
- การปิดถือ lock ของคูปองตัวเดียวกับการใช้ แคชเชียร์ที่ใช้คูปองพร้อมกันจึงได้ก่อนแล้วการใช้นั้นอยู่ หรือรอแล้วถูกปฏิเสธ
- **สาขา** กติกาเดียวกับการสร้าง พนักงานที่ผูกสาขาเห็นคูปองของสาขาตัวเองและคูปองทุกสาขา เพราะบิลที่เคาน์เตอร์ใช้ได้ทั้งสองแบบ ขอสาขาอื่นตอบ `403` ปิดได้เฉพาะคูปองของสาขาตัวเอง คูปองทุกสาขาปิดได้เฉพาะบัญชีที่ไม่ผูกสาขา
- audit `coupon.deactivated` พร้อมโค้ด เหตุผล และจำนวนที่ใช้ไป

**กลุ่มลูกค้า**

- รายการคืนจำนวนตอนบันทึก พร้อม `counted_at` ที่บอกว่านับเมื่อไร การนับใหม่ทุกแถวคือรัน SQL ของกลุ่มหนึ่งครั้งต่อแถว
- `GET /staff/segments/{id}` นับใหม่ด้วย SQL ตัวเดียวกับที่การประกาศใช้ส่ง ตัวเลขบนหน้าจอจึงตรงกับคนที่ประกาศจะถึง การอ่านไม่เขียนจำนวนกลับลงกลุ่ม
- **สาขา** พนักงานที่ผูกสาขาเห็นเฉพาะกลุ่มของสาขาตัวเอง กลุ่มทุกสาขาและกลุ่มของสาขาอื่นตอบ `403` ด้วยเหตุผลเดียวกับที่สร้างไม่ได้ คือจำนวนคนบอกข้อมูลลูกค้าของสาขาที่บัญชีนั้นมองไม่เห็น

**แพ็กเกจ** `customer_id` บังคับ ไม่ส่งตอบ `422` ไม่มีลูกค้าตอบ `404` คืนทั้งหมดใน `{ "data": [...] }` เรียงแบบหน้าแต้ม คือใช้ได้ก่อน รอชำระ แล้วที่เหลือ ไม่แบ่งหน้าเพราะลูกค้าหนึ่งคนมีแพ็กเกจไม่กี่ตัว อ่านได้ทุกสาขาเหมือนบัญชีแต้ม เพราะแพ็กเกจที่ขายสาขาหนึ่งใช้อีกสาขาได้ `branch` จึงเป็นตัวกรองว่าขายที่ไหน ไม่ใช่สิทธิ์

**ปรับแต้มด้วยมือ**

- `points` มีเครื่องหมาย บวกคือให้ ลบคือหัก ไม่เป็นศูนย์ และไม่เกิน 100,000 ต่อครั้ง `reason` บังคับ ไม่เกิน 200 ตัวอักษร
- เขียนแถวชนิดใหม่ `adjust` ในสมุดแต้มหนึ่งแถว พร้อมเหตุผลและผู้บันทึก ไม่แก้แถวอื่น
- **หักจนติดลบไม่ได้** ตรวจภายใต้ lock ต่อลูกค้าตัวเดียวกับการแลกแต้ม หักเกินที่มีตอบ `409 insufficient_points` ทางเดียวที่ยอดติดลบได้ยังเป็นทางเดิม คือคืนเงินบิลที่ให้แต้มซึ่งแต้มถูกแลกไปแล้ว
- **เปลี่ยนแต้มคงเหลือ ไม่เปลี่ยนระดับ** แต้มตลอดชีพยังนับเฉพาะ `earn` และ `reverse` ระดับสมาชิกจึงให้ด้วยมือไม่ได้
- ต้องส่ง `Idempotency-Key` เพราะการให้แต้มที่ส่งซ้ำต้องไม่ให้สองครั้ง ตอบ `201` พร้อมแถวที่เขียนและแต้มคงเหลือ audit `loyalty.adjusted` พร้อมยอดก่อนและหลัง

| `silver_min_points` | 200 | อย่างน้อย 1 |
| `gold_min_points` | 1,000 | มากกว่า silver |
| `points_expire_after_months` | ไม่มี (ไม่หมดอายุ) | 1 ถึง 120 เดือน หรือไม่ส่ง |

คลินิกที่ยังไม่เคยบันทึก อ่านได้ค่าตั้งต้นพร้อม `version` เป็น 0 เหมือนค่าตั้งอื่น ค่าตั้งต้นเท่ากับค่าที่เคยเขียนไว้ใน `LoyaltyRules.cs` ทุกตัว คลินิกที่ไม่แตะหน้านี้จึงทำงานเหมือนเดิมทุกอย่าง

**ค่าใหม่ใช้จากนี้ไป ไม่ย้อนแก้สมุดแต้ม**

- **ได้แต้ม** ใช้อัตรา ณ ตอนบิลชำระครบ แถว `earn` เก็บอัตรานั้นไว้ในคอลัมน์ `satang_per_point` การคืนเงินภายหลังหักแต้มคืนตามอัตราตอนได้ ไม่ใช่อัตราวันนี้ แถวเก่าที่ไม่มีอัตราคือแถวที่ได้ที่ ฿100 ต่อแต้ม
- **แลกแต้ม** ใช้มูลค่า ณ ตอนแลก ส่วนลดที่ลงบิลไปแล้วไม่เปลี่ยน
- **อายุแต้ม** ทุกแถวที่เพิ่มแต้ม (`earn`, `restore`, `adjust` ที่เป็นบวก) เก็บวันหมดอายุตามค่าตั้ง ณ ตอนเขียน (`expires_at`) เปิดอายุแต้มจึงไม่ทำให้แต้มเก่าหมดอายุ ปิดอายุแต้มก็ไม่ทำให้แต้มที่มีวันหมดอายุแล้วอยู่ต่อ
- **ระดับ** ไม่ได้เก็บ คำนวณจากแต้มตลอดชีพทุกครั้งที่อ่าน เกณฑ์ใหม่จึงเปลี่ยนป้ายระดับของลูกค้าทุกคนทันที รวมถึงเงื่อนไข `tiers` ของกลุ่มลูกค้า ซึ่งเป็นป้าย ไม่ใช่เงิน
- **แต้มที่หมดอายุ** แต้มคงเหลือคิดจากสมุดแต้มตามลำดับเวลา แถวที่เพิ่มแต้มคือก้อนแต้มที่มีวันหมดอายุของตัวเอง แถวที่ลดแต้มใช้ก้อนที่ยังไม่หมดอายุ ณ ตอนนั้น ก้อนที่หมดอายุเร็วสุดก่อน ก้อนที่ไม่หมดอายุใช้ทีหลัง ก้อนที่เลยวันหมดอายุโดยยังเหลือแต้มไม่นับอีก ไม่มีงานเบื้องหลังเขียนแถวหมดอายุ เมื่อไม่มีแถวใดมีวันหมดอายุ ผลเท่ากับผลรวมของสมุดเหมือนเดิม
- `GET /staff/loyalty/{customer_id}` มีช่องเพิ่ม `expired_points` (แต้มที่หมดอายุไปแล้ว) `next_expiry` (แต้มที่จะหมดอายุก่อนและวันที่) และ `rules.points_expire_after_months` แถวในประวัติมี `expires_at` และ `staff_id`
- audit `settings.loyalty_changed` พร้อมค่าก่อนและหลัง ค่าเดิมที่ส่งซ้ำไม่เปลี่ยน `version`

**แก้และเลิกใช้รายการในคลัง**

- ช่องที่ไม่ส่งไม่เปลี่ยน ทุกช่องตรวจด้วยกติกาเดียวกับตอนสร้าง ค่าผิดตอบ `422` แก้แล้วไม่มีอะไรเปลี่ยนไม่เขียน audit
- **ราคา** ใช้กับการจ่ายยาครั้งถัดไป การจ่ายยาเก็บราคาที่คิดไว้ที่ใบสั่งยาอยู่แล้ว (`charged_unit_price_satang`) และบิลของเคสคิดจากราคานั้น ยาที่จ่ายไปแล้วจึงไม่ถูกคิดราคาใหม่ แม้เคสยังไม่ปิด
- **ชื่อ** คือชื่อที่ใช้จับคู่ใบสั่งยาที่พิมพ์เอง ชื่อที่ซ้ำกับรายการอื่นหลังตัดช่องว่างซ้ำและไม่สนตัวพิมพ์ตอบ `409 inventory_item_exists` พร้อม `details.item_id` ใบที่พิมพ์ชื่อเองและยังไม่จ่ายจะจับคู่กับชื่อใหม่ ใบที่เลือกจากคลังผูกด้วยรหัสอยู่แล้วจึงไม่กระทบ
- **หน่วย** คือการแก้ชื่อหน่วย ไม่แปลงจำนวนในคลัง ใช้แก้หน่วยที่พิมพ์ผิด ไม่ใช่เปลี่ยนขนาดบรรจุ
- **เลิกใช้** (`active: false`) รายการหายจากตัวเลือกยาของ § 20 การสั่งยาด้วย `inventory_item_id` ของรายการนั้น การรับเข้า และแถวของใบสั่งซื้อ ตอบ `409 inventory_item_retired` รายการไม่ขึ้นแจ้งเตือนใกล้หมดหรือหมด และไม่ส่ง webhook `inventory.low_stock` ส่วนของที่ยังอยู่บนชั้นยังจ่ายออก โอน ปรับยอด และจ่ายตามใบสั่งยาที่สั่งไว้ก่อนได้ ทั้งด้วยรหัสและด้วยชื่อ และล็อตของรายการยังขึ้นแจ้งเตือนวันหมดอายุ เพราะของยังต้องถูกเอาออกจากชั้น ประวัติทุกแถวยังชี้มาที่รายการเดิม
- **กลับมาใช้** (`active: true`) ทำได้ทุกเมื่อ รายการเดิมกลับเข้าตัวเลือกยา
- ชื่อของรายการที่เลิกใช้ยังเป็นของรายการนั้น สร้างรายการใหม่ชื่อเดียวกันตอบ `409 inventory_item_exists` พร้อม `details.retired: true` หน้าจอจึงแนะนำให้นำรายการเดิมกลับมาใช้
- รายการเป็นของทั้งคลินิก คนที่สร้างรายการได้ผ่านการรับเข้าก็แก้ได้ รองรับ `If-Match` คำตอบคือรายการพร้อมคงเหลือของสาขาที่ผู้เรียกเห็น และ `ETag` audit `inventory.item_updated` พร้อมค่าก่อนและหลังของทุกช่องที่เปลี่ยน

**ใบสั่งซื้อ**

- รายการครอบคลุมสาขาที่ผู้เรียกเห็น `branch` ต้องเป็นสาขาที่สังกัด ไม่อย่างนั้นตอบ `403` ตัวกรอง `status` รับ `ordered`, `partially_received`, `received`, `cancelled` `supplier` ค้นส่วนของชื่อ แต่ละใบมี `received_cost_satang` (ต้นทุนของที่รับแล้ว) เพิ่ม
- **ยกเลิกคือยกเลิกส่วนที่ค้าง ไม่ใช่ทั้งใบ** ยกเลิกได้เมื่อยังมีของค้าง ไม่ว่ายังไม่ได้รับเลยหรือรับมาบางส่วน สถานะเป็น `cancelled` แต่ละแถวเก็บจำนวนที่รับแล้วไว้ และมี `cancelled_quantity` คือจำนวนที่ค้างตอนยกเลิก ของที่รับแล้วยังอยู่ในคลัง ส่วนที่ค้างหายจาก `on_order` และ `open_orders` ของรายการสต๊อก
- รับของตามใบที่ยกเลิกแล้วตอบ `409 state_conflict` ใบที่รับครบแล้วไม่มีอะไรให้ยกเลิก ตอบ `409 state_conflict` ยกเลิกซ้ำก็เช่นกัน
- การยกเลิกถือ row lock ของใบสั่งซื้อตัวเดียวกับการรับของ การรับและการยกเลิกพร้อมกันจึงทำทีละครั้ง การรับที่มาก่อนนับ การรับที่มาทีหลังเห็นว่าใบถูกยกเลิก
- ใบของสาขาอื่นตอบ `403` รองรับ `If-Match` เหตุผลไม่บังคับ audit `inventory.purchase_order_cancelled` พร้อมสถานะก่อนยกเลิก จำนวนแถว และต้นทุนที่ยกเลิก

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่มีการแก้คูปองหรือกลุ่มลูกค้า และไม่มีการลบ ต้องการค่าอื่นให้สร้างใหม่
- ไม่มีการยกเลิกการใช้คูปองโดยไม่ยกเลิกบิล
- ไม่แก้ชนิดรายการ (`kind`) เพราะเปลี่ยนว่าสั่งยาได้หรือไม่
- ไม่แก้ใบสั่งซื้อ และไม่มี `GET` ใบเดียว ใบที่ต้องการค่าอื่นให้ยกเลิกส่วนที่ค้างแล้วออกใบใหม่
- ไม่เพิ่ม scope ใหม่ และไม่เพิ่ม scope ให้ role ใด

**หน้าจอ** `/crm` มีแท็บ "แพ็กเกจของลูกค้า" ใหม่ (ค้นลูกค้าแล้วดูแพ็กเกจทุกสาขา กรองตามสถานะ) แท็บคูปองมีรายการคูปองพร้อมจำนวนที่ใช้ สถานะ ตัวกรอง และปุ่มปิดคูปองที่ถามยืนยันอีกครั้ง แท็บกลุ่มลูกค้ามีรายการกลุ่มที่บันทึกไว้ เปิดกลุ่มแล้วเห็นจำนวนล่าสุด เงื่อนไข และลิงก์ส่งประกาศ LINE แท็บแต้มมีบรรทัดแต้มที่จะหมดอายุ และฟอร์มให้หรือหักแต้มพร้อมเหตุผลสำหรับผู้ถือ `crm:manage` หน้าตั้งค่ามีแท็บ "แต้มสะสม" (`/settings/loyalty`) หน้าสต๊อกยามีปุ่มแก้ไขและเลิกใช้ในแต่ละแถวสำหรับผู้ถือ `inventory:write` และป้าย "เลิกใช้" หน้าสั่งซื้อมีรายการใบสั่งซื้อพร้อมตัวกรองและปุ่มยกเลิกส่วนที่ค้าง และไม่เสนอรายการที่เลิกใช้ในฟอร์มสั่งซื้อ รายละเอียดอยู่ใน [แพ็กเกจ คูปอง และแต้มสะสม](features/crm.md) และ [สต๊อกยาและเวชภัณฑ์](features/inventory.md)

## 26. พนักงานเขียนและเผยแพร่บทความเองไม่ได้

**ช่องโหว่** บทความ (§ 9) อ่านได้อย่างเดียว ทางที่บทความเข้าระบบมีแค่คำสั่ง `seed-articles` ซึ่งมีผลเฉพาะ slug ใหม่ หรือการแก้แถวในตาราง `articles` ตรง ๆ สัตวแพทย์ที่อยากเขียนเรื่องใหม่ แก้คำผิด หรือเอาบทความที่ล้าสมัยลง ต้องรอคนที่เข้าถึงเซิร์ฟเวอร์ได้ เจ้าของงานขอให้พนักงานเขียน เผยแพร่ และนำลงเองได้ และอนุมัติ scope ใหม่สำหรับงานนี้ (2026-10-10)

ข้อนี้เป็นฟีเจอร์ที่ขอเพิ่มเหมือน § 9 ไม่ใช่ช่องโหว่ที่เจอตอนทำตาม contract

**ทำไมสำคัญ** บทความคือสิ่งที่คลินิกพูดต่อสาธารณะในนามสัตวแพทย์ คำแนะนำที่ผิดหรือล้าสมัยต้องเอาลงได้ภายในไม่กี่นาที ไม่ใช่รอรอบ deploy และร่างที่ยังไม่เสร็จต้องไม่หลุดไปถึงคนนอกแม้แต่บรรทัดเดียว

**คำตอบ** แปดเส้น ได้รับอนุมัติก่อนสร้าง ทุกเส้นใช้ scope ใหม่ `content:manage` มี migration หนึ่งตัว คือ `StaffArticles`

| Method | Endpoint | Scope | ทำอะไร |
|---|---|---|---|
| GET | `/staff/articles?status=&q=&limit=&cursor=` | `content:manage` | ทุกบทความที่ยังไม่ถูกลบ รวมร่าง เขียนใหม่สุดก่อน แบ่งหน้าด้วย cursor `status` รับ `draft`, `scheduled`, `published` `q` ค้นชื่อเรื่องหรือ slug ไม่มีเนื้อหาเต็ม |
| GET | `/staff/articles/{id}` | `content:manage` | บทความเดียวพร้อมเนื้อหาและลิงก์ดูรูปปก พร้อม `ETag` |
| POST | `/staff/articles` | `content:manage` | เขียนร่าง ตอบ `201` ร่างไม่ขึ้นหน้าเว็บ |
| PATCH | `/staff/articles/{id}` | `content:manage` | แก้ช่องที่ส่งมา ช่องที่ไม่ส่งไม่เปลี่ยน ต้องส่ง `If-Match` |
| POST | `/staff/articles/{id}/publish` | `content:manage` | ขึ้นหน้าเว็บทันที รองรับ `If-Match` |
| POST | `/staff/articles/{id}/unpublish` | `content:manage` | นำลงจากหน้าเว็บ กลับเป็นร่าง รองรับ `If-Match` |

**ทำไมเป็น scope ใหม่ ไม่ใช้ scope เดิม** รายการ scope ของ contract ปิดตาย ทุกข้อก่อนหน้านี้จึงยืม scope ที่มีอยู่ ข้อนี้ไม่มีตัวที่เข้า `settings:write` คือสิทธิ์แก้กติกาของคลินิก `service:manage` คือราคาและบริการ ไม่มีตัวไหนแปลว่า "พูดในนามคลินิกบนหน้าเว็บ" ถ้ายืมตัวใดตัวหนึ่ง คนที่ได้สิทธิ์เขียนบทความจะได้สิทธิ์อื่นติดไปด้วย เจ้าของ contract จึงอนุมัติ `content:manage` ตัวเดียว ใช้ทั้งอ่านร่างและเขียน เพราะคนที่ต้องเห็นร่างคือคนที่เขียนเท่านั้น

- `ScopeCatalogue` อ่านจาก `Scopes.cs` เอง scope ใหม่จึงอยู่ใน `GET /staff/permissions` และให้ role ได้ทันที
- `clinic_owner` ถือ `*` อยู่แล้ว `clinic_admin` ได้จากแคตตาล็อกตอน `bootstrap` ส่วนคลินิกที่ตั้งระบบไว้ก่อนแล้ว migration `StaffArticles` เติม `content:manage` ให้แถว `clinic_admin` ที่เป็น role ตั้งต้น role อื่นไม่ได้อะไรเพิ่ม เจ้าของคลินิกให้สัตวแพทย์ที่เขียนบทความเองได้
- ไม่ใช่ scope อ่อนไหว ไม่ต้องผ่าน 2FA

**รูปแบบเนื้อหา ข้อความล้วนเหมือนเดิม** หน้าบทความสาธารณะแสดงเนื้อหาเป็นข้อความ แยกย่อหน้าที่บรรทัดว่าง (`ArticleBody` ใส่แต่ละย่อหน้าใน `<p>` เป็น text node) ส่วนนี้ไม่เปลี่ยน จึงไม่มีทั้ง Markdown และ HTML และไม่ต้องมีตัว sanitize

- `<script>` หรือ `<img onerror>` ในบทความถูกเก็บและแสดงเป็นตัวอักษรตามที่พิมพ์ ไม่มีที่ไหนแปลเป็น markup API ตอบเป็น JSON และหน้าเว็บเขียนแค่ text node จึงไม่ตัด `<` หรือ `>` ทิ้ง เพราะ "อุณหภูมิ < 39 องศา" คือประโยคที่หมอเขียนจริง
- สิ่งที่ถูกตัดออกก่อนเก็บ (`ArticleText`) คือสิ่งที่ไม่ควรอยู่ในข้อความที่คนแปลกหน้าอ่าน ได้แก่ อักขระควบคุมนอกจากการขึ้นบรรทัด (NUL เก็บใน PostgreSQL ไม่ได้อยู่แล้ว) อักขระสลับทิศทาง U+202A ถึง U+202E และ U+2066 ถึง U+2069 ที่ทำให้ข้อความแสดงคนละลำดับกับที่เก็บ BOM และครึ่งของ surrogate pair ที่ขาด ช่องว่างกว้างศูนย์ (U+200B) ที่คนเขียนภาษาไทยใช้บอกจุดตัดบรรทัดยังอยู่
- การขึ้นบรรทัดทุกแบบกลายเป็น `\n` ช่องว่างท้ายบรรทัดถูกตัด บรรทัดว่างติดกันหลายบรรทัดเหลือหนึ่ง ชื่อเรื่อง คำโปรย และชื่อผู้เขียนเป็นบรรทัดเดียว ช่องว่างซ้ำเหลือหนึ่ง
- ความยาวตรวจหลังทำความสะอาด เพราะสิ่งที่เก็บคือข้อความหลังทำความสะอาด
- ไม่ส่ง `reading_minutes` ตอนเขียนร่าง ระบบประมาณจากความยาว 800 ตัวอักษรต่อนาที ปัดขึ้น อยู่ในช่วง 1 ถึง 120

**slug**

- ตัวพิมพ์เล็กภาษาอังกฤษ ตัวเลข และขีดกลางเดี่ยว ยาวไม่เกิน 80 ตัวอักษร กติกาเดิมของ § 9 สิ่งที่พิมพ์มาถูกจัดให้ก่อน คือตัดช่องว่างหัวท้าย เปลี่ยนเป็นตัวพิมพ์เล็ก เปลี่ยนช่องว่างและขีดล่างเป็นขีดกลาง และรวมขีดกลางที่ติดกัน ตัวอักษรนอกกติกา เช่น ภาษาไทยหรือ `/` ไม่ถูกตัดทิ้งเงียบ ๆ แต่ตอบ `422` ที่ช่อง `slug`
- ไม่ส่ง `slug` ระบบสร้างจากตัวอักษรภาษาอังกฤษและตัวเลขในชื่อเรื่อง ตัดเครื่องหมายเสียงออก (`café` เป็น `cafe`) ชื่อยาวถูกตัดที่ขอบคำ **ชื่อเรื่องภาษาไทยล้วนสร้าง slug ไม่ได้** ตอบ `422` ที่ช่อง `slug` ให้ตั้งเอง ระบบไม่ถอดเสียงภาษาไทยเป็นอักษรโรมัน เพราะต้องมีพจนานุกรมตัดพยางค์ และการถอดผิดแย่กว่าการถาม slug ภาษาไทยก็ไม่รับ เพราะกลายเป็นที่อยู่ที่เข้ารหัสยาวสามเท่าที่ไม่มีใครอ่านออกเสียงหรือพิมพ์ตามได้
- **ห้ามซ้ำกับบทความอื่น รวมบทความที่ลบแล้ว** ซ้ำตอบ `409 article_slug_taken` พร้อม `details.article_id` และ `details.deleted` ที่อยู่ของบทความที่ลบไปแล้วจึงไม่มีวันเปิดเป็นเรื่องอื่น สองคนที่ตั้ง slug เดียวกันพร้อมกันได้คำตอบเดียวกัน เพราะ `PostgresErrorTranslator` แปล unique index `ix_articles_slug` เป็นรหัสนี้
- **เปลี่ยนได้จนกว่าจะเผยแพร่ครั้งแรก** หลังจากนั้น slug ถูกตรึง (`slug_locked`) แม้จะนำลงแล้ว เปลี่ยนตอบ `409 state_conflict` เพราะลิงก์เดิมอาจอยู่ในข้อความ LINE หรือผลค้นหาแล้ว และจะพาไปหน้า 404 ส่ง slug เดิมซ้ำได้ ไม่นับเป็นการเปลี่ยน

**เผยแพร่และนำลง**

- บทความเป็นสาธารณะเมื่อ `published_at` มีค่าและถึงเวลาแล้ว ร่างไม่มีค่านี้ การนำลงคือล้างค่านี้ `status` คิดจากค่านี้ทุกครั้ง คือ `draft` ไม่มีค่า `scheduled` เป็นเวลาในอนาคต (มาจากการแก้ในฐานข้อมูลเท่านั้น API ไม่มีการตั้งเวลา) และ `published`
- เผยแพร่ครั้งแรกบันทึก `first_published_at` เผยแพร่ซ้ำหลังนำลงใช้วันที่เดิม บทความที่นำลงไปแก้คำผิดจึงไม่กระโดดขึ้นบนสุดของรายการ บทความที่ตั้งเวลาไว้ถูกเลื่อนมาเผยแพร่ตอนนี้
- เผยแพร่บทความที่ขึ้นเว็บอยู่แล้ว หรือนำลงร่าง ตอบ `409 state_conflict`
- **ร่างไม่หลุดไปที่หน้าสาธารณะ** `GET /articles` และ `GET /articles/{slug}` อ่านเฉพาะแถวที่ `published_at <= now` และ `deleted_at IS NULL` ร่าง บทความที่ตั้งเวลาไว้ และบทความที่ลบแล้วตอบ `404` เหมือนบทความที่ไม่มี และ check constraint `ck_articles_deleted_not_public` กันไม่ให้แถวที่ลบแล้วมี `published_at` ไม่ว่าใครเขียนแถวนั้น
- การแก้บทความที่เผยแพร่อยู่ขึ้นเว็บทันทีที่บันทึก

**`If-Match` บังคับที่ `PATCH`** ต่างจากการแก้ส่วนใหญ่ในระบบ บทความเป็นข้อความยาวที่สองคนอาจเปิดค้างไว้พร้อมกัน การบันทึกทับโดยไม่เห็นของอีกคนคือการลบย่อหน้าของเขาทิ้งเงียบ ๆ ไม่ส่งตอบ `422` ที่ช่อง `If-Match` ส่งค่าเก่าตอบ `409 version_conflict` เส้นอื่นรองรับ `If-Match` เมื่อส่งมา

**ลบคือซ่อนแถว ไม่ลบจริง** ตั้ง `deleted_at` และ `deleted_by_staff_id` ล้าง `published_at` และ upload ที่ค้างอยู่ ลบได้ทุกสถานะ บทความที่เผยแพร่อยู่หายจากเว็บในขั้นเดียวกัน จากนั้นทุกเส้นฝั่งพนักงานตอบ `404` รวมการลบซ้ำ เหตุผลที่เก็บแถวไว้

- slug ยังถูกจองไว้ (unique index ครอบแถวที่ลบด้วย) ที่อยู่เดิมจึงไม่กลายเป็นบทความเรื่องอื่น
- `seed-articles` นับแถวที่ลบด้วย บทความตัวอย่างที่คลินิกลบไปจึงไม่ถูกใส่กลับ คำสั่งยังทำงานเหมือนเดิม คือใส่เฉพาะ slug ใหม่
- แถว audit ยังชี้ไปที่สิ่งที่มีอยู่

ไม่มีการกู้คืน ต้องการกลับมาให้เขียนใหม่ด้วย slug ใหม่ ถ้าแค่ไม่อยากให้ขึ้นเว็บให้นำลงแทน

**รูปปก** ใช้ที่เก็บไฟล์และ URL ที่ลงชื่อแล้วตัวเดียวกับเอกสารของสัตว์ (§ 12)

1. `POST /staff/articles/{id}/cover` รับ `image/jpeg`, `image/png` หรือ `image/webp` ไม่เกิน 5 MB ตอบ URL อายุ 15 นาทีที่รับไฟล์ชนิดและขนาดนั้นเท่านั้น ที่ key `articles/{id}/cover-{สุ่ม}.{นามสกุล}` ที่ระบบสร้าง ชื่อไฟล์ของผู้ใช้ไม่อยู่ใน key
2. หน้าเว็บส่งไฟล์ไปที่ URL นั้นตรง ๆ จากเบราว์เซอร์ (`uploadToSignedUrl`)
3. เมื่อไฟล์มาถึง `StoredFilesHandler` ส่งต่อให้ `ArticleCoverReceiver` ซึ่งตั้งรูปใหม่เป็นรูปปก แทนรูปเดิมหรือรูปจาก `cover_image_path` แบบเดียวกับที่ S3 event notification ทำ ระหว่างรอ รูปเดิมยังแสดงอยู่ (`cover_pending`) และ upload ที่ไม่มาไม่เปลี่ยนอะไร ไฟล์ที่มาถึงด้วย key ที่บทความไม่ได้รอแล้วถูกเก็บไว้แต่ไม่แสดง
4. `PATCH` ด้วย `"remove_cover": true` เอารูปปกออก

SVG ไม่รับ เพราะ SVG คือเอกสารที่ฝัง script ได้ ไฟล์ถูกส่งกลับด้วยชนิดที่ประกาศตอนขอ URL พร้อม `X-Content-Type-Options: nosniff` เบราว์เซอร์จึงไม่ตีความเป็นอย่างอื่น

**หน้าสาธารณะเห็นรูปได้โดยไม่ต้องมี token ของพนักงาน** ด้วยทางเดียวกับรูปสัตว์ใน portal คือลิงก์ที่ลงชื่อแล้วซึ่งสร้างใหม่ทุกครั้งที่อ่าน `GET /articles` และ `GET /articles/{slug}` มีช่อง `cover_image_url` อายุหนึ่งชั่วโมง สร้างเฉพาะตอนที่บทความเผยแพร่อยู่ ไม่มี URL สาธารณะถาวรของไฟล์ในที่เก็บ ผลคือ

- รูปของร่างไม่มีลิงก์ในที่ใดที่คนนอกเปิดได้
- รูปของบทความที่นำลงแล้วใช้ได้ต่ออีกไม่เกินหนึ่งชั่วโมงสำหรับคนที่ได้ลิงก์ไปก่อน แล้วหยุดเอง
- หน้าเว็บสาธารณะ render ใหม่ทุกครั้งที่เปิด ผู้เข้าชมทุกคนจึงได้ลิงก์ใหม่ ถ้าวันหนึ่งหน้าเหล่านี้ถูก cache ต้องให้รอบ revalidate สั้นกว่าอายุลิงก์
- ถ้าเปลี่ยนไปใช้ S3 ลิงก์จะชี้ไปที่ bucket โดยไม่ต้องแก้ use case
- `cover_image_path` ของ § 9 ยังใช้ได้กับบทความจาก seed และหน้าเว็บใช้ `cover_image_url` ก่อนเมื่อมีทั้งสองช่อง ฝั่งพนักงานได้ลิงก์อายุ 30 นาทีไว้ดูตัวอย่าง

**หน้าเว็บอัปเดตทันที** server action ฝั่งพนักงานเรียก `revalidatePath` ของ `/`, `/articles`, `/articles/[slug]` และหน้าพนักงาน ทุกครั้งที่เขียนร่าง แก้ เผยแพร่ นำลง ลบ หรือรูปปกมาถึง ตอนนี้หน้าสาธารณะอ่าน API ใหม่ทุกครั้งที่เปิดอยู่แล้ว การ revalidate จึงเป็นประกันไว้สำหรับวันที่หน้าเหล่านี้ถูก cache

ย้อน migration ได้โดยไม่มีร่างหลุดขึ้นเว็บ ร่างและบทความที่ลบได้ `published_at` เป็นปี 9999 ซึ่งโค้ดรุ่นก่อนอ่านเป็นบทความตั้งเวลา และ `content:manage` ถูกเอาออกจากทุก role

**ทางเลือกที่ไม่เลือก**

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| เนื้อหาเป็น Markdown หรือ HTML พร้อมตัว sanitize | หน้าเว็บแสดงข้อความล้วนอยู่แล้ว ตัว sanitize คือ dependency ที่ต้องตามอัปเดต และพลาดครั้งเดียวคือ script บนหน้าที่ทุกคนเปิดได้ ข้อความล้วนไม่มีทางพลาดแบบนั้น |
| ยืม `settings:write` แทน scope ใหม่ | คนที่เขียนบทความจะแก้เวลาทำการ กติกาการจอง และข้อมูลติดต่อได้ด้วย |
| แยก `content:read` กับ `content:manage` | คนที่ต้องอ่านร่างคือคนเขียน scope สองตัวที่ให้คู่กันเสมอคือการตั้งค่าเกินจำเป็น |
| ถอดเสียงชื่อเรื่องภาษาไทยเป็น slug เอง | ต้องมีพจนานุกรมตัดพยางค์ การถอดผิดคือที่อยู่ที่อ่านแล้วงง ถามคนเขียนครั้งเดียวดีกว่า |
| เปลี่ยน slug หลังเผยแพร่พร้อมเก็บที่อยู่เก่าไว้ redirect | ต้องมีตารางที่อยู่เก่า และกติกาว่าที่อยู่เก่าของเรื่องหนึ่งชนกับ slug ใหม่ของอีกเรื่องได้ไหม ตรึง slug ไว้ง่ายกว่าและไม่มีลิงก์ไหนเสีย |
| ลบแถวจริง | slug จะว่างให้บทความอื่นใช้ ลิงก์เก่าจะเปิดเป็นเรื่องอื่น และ `seed-articles` จะใส่บทความตัวอย่างที่คลินิกลบไปกลับมา |
| URL สาธารณะถาวรของรูปปก หรือ endpoint ส่งไฟล์รูปโดยไม่มี token | ต้องมีทางอ่านไฟล์ในที่เก็บที่ไม่ผ่านการลงชื่อเป็นทางแรก และต้องตรวจสถานะการเผยแพร่ซ้ำอีกที่ ลิงก์ที่ลงชื่อตอนอ่านใช้ทางที่มีอยู่และตรวจที่เดียว |
| ตั้งเวลาเผยแพร่ผ่าน API | ไม่ได้ขอ หน้าจอต้องมีตัวเลือกวันเวลาและการแสดงเขตเวลา ช่อง `published_at` รองรับอยู่แล้ว เพิ่มทีหลังได้โดยไม่ต้องมี migration |

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่มีหมวดหมู่ แท็ก ประวัติฉบับแก้ หรือการกู้บทความที่ลบ
- ไม่ลบไฟล์รูปปกเก่าออกจากที่เก็บ `IFileStorage` ยังไม่มีคำสั่งลบ ไฟล์เก่าไม่มีลิงก์ใดชี้ไปและไม่ถูกแสดง
- ไม่ตรวจเนื้อไฟล์ว่าเป็นรูปจริง ชนิดที่ประกาศและ `nosniff` คือสิ่งที่กัน ไฟล์ที่ไม่ใช่รูปจะแสดงเป็นรูปเสีย
- ไม่ผูกบทความกับบัญชีพนักงาน ชื่อผู้เขียนยังเป็นข้อความตาม § 9 ใครทำอะไรอยู่ใน audit
- ไม่ให้ role อื่นนอกจาก `clinic_admin` ได้ `content:manage` เอง

**หน้าจอ** หน้าตั้งค่ามีแท็บ "บทความ" (`/settings/articles`) สำหรับผู้ถือ `content:manage` มีรายการบทความพร้อมป้ายสถานะ ตัวกรองสถานะ ช่องค้น และปุ่ม "เขียนบทความใหม่" หน้าเขียนบทความบันทึกเป็นร่างแล้วพาไปหน้าแก้ หน้าแก้มีช่องชื่อเรื่อง slug (ปิดเมื่อเคยเผยแพร่แล้ว) คำโปรย ผู้เขียน เวลาอ่าน และเนื้อหาที่สลับดูตัวอย่างได้ ตัวอย่างใช้ `ArticleBody` ตัวเดียวกับหน้าเว็บ ด้านข้างมีกล่องการเผยแพร่ (เผยแพร่ หรือนำลงพร้อมถามยืนยัน) กล่องรูปปก (เลือกรูป เอารูปออก) และกล่องลบที่ถามยืนยันอีกครั้ง รายละเอียดอยู่ใน [บทความ](features/articles.md)
