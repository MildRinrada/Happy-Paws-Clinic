# ข้อสมมติและคำถามที่ยังเปิดอยู่

จุดกำกวมใน [`API Reference.dc.html`](../API%20Reference.dc.html) ที่เจอระหว่างออกแบบและสร้างระบบ ไม่มีข้อไหนแก้ด้วยการออกแบบ API ใหม่ แต่ละข้อบันทึกว่าเราตีความอย่างไร และโค้ดตอนนี้ทำตามการตีความนั้น

ข้อที่เขียนว่า **ต้องตัดสินใจ** ควรได้คำตอบก่อนสร้างหรือแก้โมดูลที่เกี่ยวข้อง

เลขข้อคงไว้ตามเดิมเพราะโค้ดอ้างเลขเหล่านี้ เช่น `docs/assumptions.md § 27` จึงไม่มีข้อ 13 ข้อความภาษาไทยที่ยกมาจาก contract คงไว้ตามต้นฉบับ ยกเว้นอักขระขีดและจุดกลางที่แทนด้วยเว้นวรรค

## 1. จำนวน endpoint หัวเอกสารบอก 214 แต่ตารางมี 164

หัวของ reference เขียนว่า *"ครอบคลุม Tier 1 ถึง 3 รวม 214 endpoints"* (ยกมาโดยแทนขีดด้วยคำ) แต่ในเอกสารไม่มี 214 endpoint

**ยืนยันโดยนับจาก HTML ต้นฉบับ ไม่ได้นับจากหน้าที่แสดงผล**

| สิ่งที่นับ | จำนวน |
|---|---|
| ป้าย HTTP method ทั้งเอกสาร | **179** |
| ในนั้นเป็นแถวในตาราง endpoint | **164** |
| ในนั้นเป็นการอ้างถึงในส่วน *ตัวอย่าง flow ปลายทาง* | **15** |
| แถว `method + path` ที่ซ้ำข้ามหมวด | **0** |
| คู่ `method + path` ที่ไม่ซ้ำ | **164** |
| path ที่ไม่ซ้ำ (ตัด query string ออก) | 150 |
| path ที่มีรูปเป็น endpoint ในเนื้อความแต่ไม่อยู่ในตาราง | **0** |

15 รายการในส่วน flow ไม่ใช่ endpoint เพิ่ม เป็น endpoint เดิมที่เล่นซ้ำเป็นตัวอย่างโดยใส่ id จริง เช่น `POST /booking/holds`, `POST /appointments/apt_24810/confirm` (คือ `/appointments/{id}/confirm`), `POST /staff/queue/tkt_A014/call` ทุกรายการตรงกับแถวที่นับไว้แล้วใน 164

**สรุป endpoint ที่หายไปราว 50 เส้นไม่อยู่ในเอกสารนี้** ไม่อยู่ในตาราง ไม่อยู่ใน flow ไม่อยู่ในเนื้อความ ไม่ได้ซ่อนอยู่ในแถวที่ยุบหรือซ้ำ นับป้าย method ทุกอันแบบให้มากที่สุดแล้วยังได้แค่ 179 ตัวเลขอื่นในเอกสารก็ไม่ได้ 50 หรือ 214 (scope ไม่ซ้ำ 71 ตัว event ของ webhook 16 ตัว 29 หมวด) จึงสร้างตัวเลขนี้ขึ้นจาก reference ไม่ได้ไม่ว่าจะอ่านแบบไหน

**ไม่มี endpoint ใดถูกอนุมาน ประมาณ หรือแต่งขึ้นเพื่อปิดช่องนี้** [api-mapping.md](./api-mapping.md) มีเฉพาะ endpoint ที่อยู่ในเอกสารจริง

**ขอบเขตงานคือ 164 endpoint ที่มีเอกสาร** โครงสร้าง การวาง controller และขอบเขตโมดูล สร้างตามนี้

> **ถึงเจ้าของ contract**
>
> ตัวเลข **214** ยังไม่มีคำอธิบาย ต้องยืนยันว่าข้อไหนจริง
>
> 1. **164 ถูก** และหัวเอกสารเก่า ให้แก้หัวเอกสาร
> 2. **214 ถูก** และมีราว 50 endpoint ที่ไม่เคยเขียนลงเอกสาร ให้ส่งมา เพราะอนุมานจากสิ่งที่มีไม่ได้
>
> ระหว่างที่ยังไม่มีคำตอบ ให้ถือ 164 เป็น contract อย่าให้ใคร "เติมช่อง" ด้วยการเดา CRUD ที่น่าจะมี endpoint ที่แต่งขึ้นในระบบคลินิกคือพื้นผิวที่ไม่มีใครรีวิว และสิทธิ์ที่ไม่มีใครรีวิว

## 2. หก endpoint ไม่ได้ระบุ scope

หมวด *Webhooks และ Integrations* เป็นหมวดเดียวที่ตารางไม่มีคอลัมน์ scope

- `POST /staff/webhooks`
- `GET /staff/webhooks/{id}/deliveries`
- `POST /staff/api-keys`
- `PUT /staff/integrations/payment`
- `PUT /staff/integrations/lab`
- `GET /staff/integrations/calendar/ics`

**สมมติว่าเป็น** `integration:manage` ซึ่ง contract นิยามไว้แล้ว (ที่ `PUT /staff/integrations/line`) endpoint เหล่านี้สร้าง API key และตั้งค่า credential ของการชำระเงิน ซึ่งอ่อนไหวที่สุดในระบบ การให้ scope ที่เข้มที่สุดที่มีอยู่จึงเป็นการอ่านที่ปลอดภัย

**ข้อยกเว้น** `GET /staff/integrations/calendar/ics` เป็นฟีดปฏิทินรายคน ไม่ใช่งานผู้ดูแล ถ้าบังคับ `integration:manage` สัตวแพทย์จะ subscribe ตารางของตัวเองไม่ได้ ใน mapping จึงเขียนว่า *(ไม่ระบุ)* รอการตัดสิน คำตอบที่น่าจะใช่คือ token ฟีดรายคนที่ลงนามไว้ เพราะโปรแกรมปฏิทินส่ง bearer header ไม่ได้

**ต้องตัดสินใจ** โดยเฉพาะเรื่องฟีด ICS

## 3. `invoice:collect` กับ `payment:collect`

role `receptionist` ได้ `invoice:collect` แต่ endpoint รับเงิน `POST /staff/invoices/{id}/payments` ต้องใช้ `payment:collect` ส่วน `cashier` ถือ `payment:*` จึงไม่กระทบ

ถ้าอ่านตามตัวอักษร พนักงานต้อนรับรับเงินไม่ได้ ซึ่งขัดกับการที่ `invoice:collect` อยู่ใน role นี้ตั้งแต่แรก

**สมมติว่า** scope ทั้งสองมีอยู่ตามที่เขียน และ `invoice:collect` ไม่มี endpoint ใดใช้ ทั้งสองอยู่ใน `Domain/Access/Scopes.cs`

**ตอนนี้ใช้งานจริงแล้ว และผลชัดเจน** `POST /staff/invoices/{id}/payments` สร้างแล้วและต้องใช้ `payment:collect` ตรงตาม reference ดังนั้นตาม contract ที่เขียนไว้ **พนักงานต้อนรับรับเงินไม่ได้** มีแต่แคชเชียร์ที่รับได้ ในคลินิกเล็กที่คนเดียวประจำเคาน์เตอร์ นี่คือ role ที่ contract นิยามแต่ไม่มีใครทำหน้าที่ได้

ไม่ได้แต่งอะไรขึ้นมากลบปัญหานี้ endpoint ต้องการสิ่งที่แถวของมันบอก การแก้คือเปลี่ยนคำเดียว ในทิศที่เจ้าของ contract เลือก

**ต้องตัดสินใจ** ว่า role receptionist ควรถือ `payment:collect` หรือ `invoice:collect` เป็นความสามารถแยกที่ endpoint ใดควรใช้

## 4. `billing:payout` ไม่มี endpoint

`clinic_admin` นิยามว่า "ทุกอย่างยกเว้น `billing:payout`, `settings:danger`" แต่ไม่มี endpoint ใดในเอกสารใช้ scope ทั้งสอง และ `billing:*` ไม่ปรากฏที่อื่นเลย

**สมมติว่า** ทั้งสองสงวนไว้สำหรับความสามารถที่ยังไม่อยู่ใน contract (การจ่ายเงินออกหรือ settlement และการตั้งค่าที่ทำลายข้อมูล เช่น ลบคลินิก ส่งออกหรือล้างข้อมูล) ประกาศไว้ในรายการ scope เพื่อให้นิยาม `clinic_admin` ด้วยการหักออกได้ตามที่ contract บอก

## 5. ไม่มีรหัส error สำหรับ `If-Match` ไม่ตรง

ส่วนข้อตกลงบอกว่า `version` ไม่ตรงให้ตอบ 409 แต่ตั้งชื่อรหัสไว้แค่ `slot_unavailable`, `insufficient_scope`, `state_conflict`, `record_locked` และ `unauthenticated` ส่วน `409 state_conflict` เขียนไว้ว่าเป็นเรื่องการเปลี่ยนสถานะที่ไม่อนุญาต ซึ่งเป็นความล้มเหลวคนละแบบ

**สมมติว่า** ใช้รหัสแยกคือ `version_conflict` ประกาศใน `Application/Common/Errors/ErrorCodes.cs` และมีคู่ใน `ApiErrorCode` ของ frontend เป็นชื่อเดียวในโค้ดที่ **ไม่ได้** มาจาก reference ตรงตัว

**ต้องตัดสินใจ** ยืนยัน `version_conflict` หรือรวมความล้มเหลวจาก optimistic concurrency เข้ากับ `state_conflict`

## 6. `PUT` บน path ระดับ collection

สาม endpoint เป็น `PUT` บน path ระดับ collection แทนที่จะเป็น resource เดียว

- `PUT /staff/appointment-types`
- `PUT /staff/policies/cancellation`
- `PUT /staff/schedules/assignment-rules`

สอดคล้องกับ `PUT /clinic/hours` ("ตั้งทั้งสัปดาห์ในคำขอเดียว") จึงเป็นการแทนทั้งชุด

**สมมติว่า** แต่ละเส้นแทนชุดค่าทั้งหมดในคำขอเดียว use case ตั้งชื่อขึ้นต้นด้วย `Replace` ให้เห็นชัด ไม่ใช่ข้อบกพร่อง แค่ควรเขียนไว้ เพราะถ้าอ่านเป็นการแก้บางส่วน จะลบค่าตั้งของคลินิกไปเงียบ ๆ

## 7. `GET /staff/customers?q=` มี query string อยู่ใน path

reference เขียน query string ไว้ในช่อง path ของหลาย endpoint (`?q=`, `?date=&status=`, `?branch=&room=`, `?from=&to=`, `?status=pending`, `?pet_id=`)

**สมมติว่า** เป็นตัวอย่างตัวกรองบน path หลัก ไม่ใช่พารามิเตอร์บังคับ และข้อตกลงทั่วไป (`?limit=`, `?cursor=`, `?q=`, `?status=`, `?date=`, `?vet_id=`) ใช้ได้ทุกที่ route ลงทะเบียนบน path หลัก

## 8. ขอบเขตของ idempotency บรรยายไว้ แต่ไม่ได้แจกแจง

*"Idempotency-Key: `<uuid>` (ทุก POST ที่สร้างเงิน/นัด/คิว)"* คือทุก POST ที่สร้างเงิน นัด หรือคิว มีแค่ `POST /portal/appointments` ที่เขียนไว้ชัดในแถวของตัวเอง

**สมมติไว้ตอนออกแบบ** ว่า header จำเป็นบน `POST /portal/appointments`, `POST /staff/appointments`, `POST /staff/appointments/recurring`, `POST /staff/queue/tickets`, `POST /appointments/{id}/check-in` (สร้างคิว), `POST /staff/invoices`, `POST /staff/invoices/{id}/payments`, `POST /staff/invoices/{id}/refunds` และ `POST /booking/holds`

**ที่โค้ดทำจริงตอนนี้** endpoint ที่ติด `[Idempotent]` มี 13 เส้น คือ `POST /portal/appointments`, `POST /staff/appointments`, `POST /staff/appointments/recurring`, `POST /staff/pets/{id}/treatment-plans` (จองนัดทั้งคอร์ส), `POST /appointments/{id}/check-in`, `POST /staff/queue/tickets`, `POST /staff/invoices`, `POST /staff/invoices/{id}/payments`, `POST /staff/invoices/{id}/refunds` และงานตรวจอีกสี่เส้น `POST /staff/consultations`, `.../treatments`, `.../prescriptions`, `.../close` (`close` ออกใบแจ้งหนี้ใน transaction เดียวกัน) ส่วน `POST /booking/holds` ไม่ได้ติด เพราะ hold ราคาถูก หมดอายุเอง และ client ที่ส่งซ้ำแค่เสีย slot นั้นไป 10 นาที

**ตัดสินแล้วในโค้ด** endpoint ที่ติด attribute แต่ไม่ส่ง header ถูกปฏิเสธด้วย `400 idempotency_key_required` (`Api/Idempotency/IdempotencyMiddleware.cs`) ไม่ได้ปล่อยผ่านแบบไม่มีการป้องกัน ยังควรยืนยันกับเจ้าของ contract

## 9. การจำกัดสิทธิ์พนักงานตามสาขามีแค่นัย ไม่ได้ระบุ

พนักงานมี `branches: ["brn_sukhumvit39"]` และหลาย endpoint กรองด้วย `?branch=` แต่ contract ไม่เคยบอกว่าพนักงาน *ห้าม* อ่านข้อมูลของสาขาอื่นหรือไม่

**สมมติว่า** สาขาที่สังกัดจำกัดการเข้าถึงจริง ไม่ใช่แค่ตัวกรอง default เป็นการอ่านแบบระวังสำหรับข้อมูลทางการแพทย์ ทำเป็นการตรวจระดับ resource การผ่อนภายหลังจึงแก้ที่เดียว

**ต้องตัดสินใจ** ก่อนสร้างโมดูลคิวและนัด

## 10. ส่วนของเวชระเบียนที่เจ้าของเห็นตั้งค่าได้ แต่ไม่ได้แจกแจง

`PATCH /clinic/settings/medical-record` ตั้งค่า "ฟิลด์บังคับ แบบฟอร์มตรวจ การ sign" และ `GET /portal/pets/{id}/records` คืน "เฉพาะส่วนที่คลินิกตั้งค่าให้เจ้าของเห็น" แต่ไม่ได้บอกว่าเปิดปิดส่วนไหนได้บ้าง

**สมมติว่า** การมองเห็นกำหนดราย *ส่วน* ของเวชระเบียน (vitals, examination, diagnosis, treatment, prescription, lab result, attachments) ตั้งค่าต่อคลินิก และบังคับด้วยการ project ลง DTO ฝั่งเจ้าของ ไม่ใช่การกรองฟิลด์ออกจาก DTO ฝั่งพนักงานตอน serialize

## 11. การยืนยันตัวตนของ SSE คิว

`SSE /queue/stream?branch=` เปิดให้ทั้งสองกลุ่ม แต่ `EventSource` ส่ง header `Authorization` ไม่ได้

**ตัดสินและสร้างแล้ว** stream รับ bearer token ปกติ เบราว์เซอร์เข้าผ่าน server ของ Next.js ซึ่งถือคุกกี้เซสชันและแนบ token ให้ เป็นเส้นทางเดียวกับคำขอที่ต้องเข้าสู่ระบบทุกคำขอ ([authentication.md](./authentication.md)) พนักงานเข้าได้ด้วย `queue:read` ภายในสาขาของตัวเอง ลูกค้าเข้าได้ในมุมมองที่กรองเหลือคิวของตัวเอง

ไม่ใช้ token ใน query string เพราะ `?access_token=` จะเขียน credential ลงทุก access log, proxy cache และประวัติเบราว์เซอร์ระหว่างทาง และการเชื่อมต่อ SSE อยู่นานพอที่ token ยังใช้ได้ตอนมีคนอ่าน log

**ยังควรยืนยัน** ว่า contract ตั้งใจให้เบราว์เซอร์เรียก `/queue/stream` ตรงหรือไม่ ถ้าใช่ ตัวส่งต้องมีกลไกที่การออกแบบนี้ไม่มี ส่วนอื่นไม่เปลี่ยน

## 12. `POST /staff/customers/{id}/merge` ไม่มีกฎเมื่อค่าชนกัน

การรวมย้ายสัตว์เลี้ยงและประวัติ contract ไม่บอกว่าเมื่อทั้งสองเรกคอร์ดมีค่าในฟิลด์เดียวกันจะเป็นอย่างไร และไม่บอกว่าย้อนกลับได้หรือไม่

**สมมติว่า** เรกคอร์ดปลายทางชนะเมื่อชนกัน เรกคอร์ดต้นทางเก็บไว้เป็น tombstone ที่ชี้ไปปลายทาง และบันทึกการรวมลง audit log ย้อนกลับผ่าน API ไม่ได้

**ต้องตัดสินใจ** ก่อนสร้างโมดูลลูกค้า เพราะการรวมเป็นการกระทำที่ทำลายข้อมูลและแตะประวัติการรักษา

## 14. error envelope ต้องมีรหัสที่ reference ไม่ได้ตั้งชื่อ

reference ตั้งชื่อรหัสไว้ห้าตัว (`unauthenticated`, `insufficient_scope`, `state_conflict`, `record_locked`, `slot_unavailable`) แต่บอกว่า *ทุก* endpoint ใช้ envelope เดียวกัน ระบบทำงานด้วยห้ารหัสไม่ได้ ไม่มีรหัสสำหรับข้อมูลไม่ผ่านการตรวจ resource ไม่มี หรือ idempotency key ถูกใช้ซ้ำ และ client ตัดสินจาก `code` ถ้าไม่ตั้งชื่อ ทุก client จะต้องจับคู่ข้อความกันเอง

**เพิ่มแล้วและใช้งานอยู่** (`Application/Common/Errors/ErrorCodes.cs` ยกเว้น `cutoff_passed` อยู่ใน `Application/Appointments/CutoffPassedException.cs` และ `allergy_conflict` อยู่ใน `Application/Consultations/AllergyConflictException.cs`)

| รหัส | สถานะ | เกิดเมื่อ |
|---|---|---|
| `version_conflict` | 409 | `If-Match` ไม่ตรงกับ `version` ที่เก็บไว้ (ดู § 5) |
| `validation_failed` | 422 | body หรือ query ไม่ผ่านการตรวจ |
| `not_found` | 404 | ไม่มี resource หรือซ่อนไว้เพราะผู้เรียกไม่ควรรู้ว่ามีอยู่ |
| `forbidden` | 403 | ผู้เรียกมี scope แต่ไม่มีสิทธิ์กับเรกคอร์ดนี้ |
| `idempotency_key_required` | 400 | POST ที่สร้างเงิน นัด หรือคิว มาโดยไม่มี header |
| `idempotency_key_reused` | 409 | key เดิม แต่ body ต่างกัน |
| `request_in_flight` | 409 | คำขอเดียวกันยังทำงานอยู่ |
| `rate_limited` | 429 | เกิน rate limit |
| `cutoff_passed` | 409 | ลูกค้าเลื่อนนัดหลังเลยเวลาตัดรอบ (ดู § 15) |
| `allergy_conflict` | 409 | ใบสั่งยาระบุยาที่สัตว์มีประวัติแพ้ (ดู § 19) |
| `internal_error` | 500 | ข้อผิดพลาดที่ไม่คาดไว้ ไม่มีรายละเอียดภายในติดไปด้วย |

Billing เพิ่มอีกห้ารหัส ทั้งหมดเป็น `409` และทั้งหมดเกิดจาก aggregate ใบแจ้งหนี้ปฏิเสธคำขอที่รูปแบบถูกต้องแต่ไม่เข้ากับสถานะตอนนั้น (ดู § 24) คือ `invalid_payment`, `invalid_refund`, `invalid_discount`, `invalid_receipt`, `invalid_void` ตามแบบที่ `invalid_treatment` และ `invalid_examination` วางไว้แล้ว คือรหัสของ domain ตั้งชื่อตามสิ่งที่ผิด ไม่ใช่ตาม endpoint ที่ทำให้เกิด

**ต้องรับรอง** รหัสเหล่านี้เป็นส่วนเพิ่มของ contract ที่ client เห็น จึงควรอยู่ใน reference ไม่มีรหัสใดแทนหรือนิยามรหัสที่มีในเอกสารใหม่

## 15. Booking and Appointment ไม่ได้ระบุ request body

reference ระบุทุก endpoint ในหมวดนี้ คือ path, method, ผู้เรียก, scope และพฤติกรรมหนึ่งประโยค แต่ไม่มี schema ของ request หรือ response เลย การสร้างหมวดนี้จึงต้องอนุมาน payload

**ชื่อฟิลด์มาจากคำที่เอกสารใช้เอง** ไม่ได้แต่งอิสระ คือ `starts_at` (เป็นฟิลด์ที่ผิดในตัวอย่าง `slot_unavailable` ของ reference เอง), `service`, `date`, `vet_id`, `branch`, `q`, `status` และ prefix ของ id ในตัวอย่าง flow (`apt_`, `hold_`, `tkt_`, `svc_`, `pet_`, `cus_`, `brn_`) รูปข้อมูลอยู่ใน `Api/Contracts/Appointments/AppointmentContracts.cs` และ `Application/Appointments/Dtos/AppointmentDto.cs`

มีพฤติกรรมสี่ข้อที่ต้องตัดสินเอง อ่านจากเอกสารไม่ได้

| การตัดสิน | เหตุผล | ย้อนได้ไหม |
|---|---|---|
| เวลาตัดรอบการเปลี่ยนนัดอยู่ใน **booking settings** ไม่ใช่ใน cancellation policy ของ Tier 2 | `PATCH /clinic/settings/booking` บรรยายว่า "slot 15/20/30 นาที  **ยกเลิกล่วงหน้ากี่ชั่วโมง**" reference จึงวางเวลาตัดรอบไว้ที่นั่นแล้ว ส่วน `PUT /staff/policies/cancellation` เพิ่มค่าปรับและโควตาซ้อนอีกชั้น | ได้ ย้ายฟิลด์เดียว |
| เวลาตัดรอบกัน **การเลื่อน** แต่ไม่กัน **การยกเลิก** | reference ระบุเวลาตัดรอบเฉพาะการเลื่อน ("ลูกค้าเลื่อนได้ถ้ายังไม่ถึง cutoff") ส่วนการยกเลิกขอแค่บันทึกเหตุผลและผู้ยกเลิก การกันการยกเลิกยังแย่สำหรับคลินิกกว่าการได้รู้ล่วงหน้า | ได้ |
| การเลื่อนที่ถูกปฏิเสธตอบ **409 `cutoff_passed`** ไม่ใช่ 403 | สิทธิ์ของผู้เรียกไม่มีอะไรผิด เป็นเจ้าของสัตว์และเจ้าของนัด และถ้าขอเร็วกว่านี้หนึ่งชั่วโมงก็จะสำเร็จ 403 ทำให้ frontend ไปทางเรื่องสิทธิ์ ทั้งที่ข้อความที่ถูกคือ "โทรหาคลินิก" | ได้ รหัสเป็นของใหม่ (§ 14) |
| การจองเวลาเจาะจง **ไม่ต้องตรงกับตาราง availability** | ฟีดเสนอตำแหน่งตามตาราง และ client ที่ดีใช้ตำแหน่งเหล่านั้น แต่ reference ไม่เคยบอกว่าเวลานอกตารางผิด และพนักงานจอง walk-in เวลา 14:07 เป็นเรื่องปกติ การบังคับให้ตรงตารางเข้มกว่า contract | ได้ |

**ต้องยืนยัน** ถ้าเจ้าของ contract มี schema ในใจที่ต่างไป

## 16. `POST /appointments/{id}/check-in` ระบุ scope ที่ลูกค้าถือไม่ได้

reference ระบุ scope ของ endpoint นี้เป็น `appointment:checkin` และในแถวเดียวกันบอกว่า "เช็กอินที่เคาน์เตอร์หรือ**ลูกค้าเช็กอินเอง**" คือลูกค้าเช็กอินเองได้ แต่ตาราง role ให้ role `customer` "portal scope เท่านั้น" ลูกค้าไม่มี scope `appointment:*` ใด ๆ ถ้าอ่านตามตัวอักษร สองครึ่งของแถวขัดกันเอง

**ตีความว่า** ตั้งใจให้เรียกได้ทั้งสองฝั่ง และคอลัมน์ scope บรรยายทางของพนักงาน route ไม่มี `[RequireScope]` `AppointmentAccess` รับพนักงานที่ถือ `appointment:checkin` ในสาขาของตัวเอง และรับลูกค้าที่เป็นผู้ดูแลสัตว์ คนอื่นได้ 404

อีกสี่ route ที่ reference เขียนว่า "ทั้งสองฝั่ง" คือ get, reschedule, cancel, confirm ใช้รูปเดียวกัน แต่มีแค่ check-in ที่ระบุทั้ง scope ของพนักงาน *และ* ความสามารถของลูกค้าไว้พร้อมกัน จึงยกมาเขียนแยก

**ต้องยืนยัน** ถ้าไม่ได้ตั้งใจให้ลูกค้าเช็กอินเอง การถอดออกคือแก้บรรทัดเดียว (เพิ่ม `[RequireScope(Scopes.Appointment.CheckIn)]`) แต่ถ้ากลับกัน คือมารู้หลังเปิดใช้ว่าเจ้าของเช็กอินจาก LINE ไม่ได้ จะแก้ยากกว่า

## 17. `skipped` วาดเป็นทางออก แต่บรรยายเป็นการต่อคิวใหม่

state machine วาดคิวเป็น `waiting → called → in_room → served` โดยมี **`skipped`** และ `left` เป็นทางออก แต่ `POST /staff/queue/{id}/skip` บรรยายว่า "ข้ามคิวที่ยังไม่มา  **เลื่อนไปท้ายแถว**" คือย้ายไปท้ายแถว สถานะสิ้นสุดถูกย้ายไปท้ายอะไรไม่ได้ สองข้อความนี้จึงจริงตามตัวอักษรพร้อมกันไม่ได้

**ตีความว่า** คำบรรยายคือพฤติกรรม และแผนภาพเป็นแบบย่อ `skipped` เป็นสถานะ *รอ* คิวยังอยู่บนกระดาน เรียงหลังทุกคนที่ยังไม่ถูกข้าม และเรียกได้อีก (`skipped → called`) ถ้าถือเป็นสถานะสิ้นสุด เจ้าของที่เดินออกไปสองนาทีต้องไปต่อคิวใหม่ที่เคาน์เตอร์ ซึ่งไม่มีคลินิกไหนทำ

ผลที่ตามมาและทำในโค้ดแล้ว

| กฎ | เหตุผล |
|---|---|
| เรียงลำดับเป็น *(ยังไม่ถูกข้าม ตามเลข)* แล้ว *(ถูกข้าม ตามเวลาที่ถูกข้าม)* | ถูกข้ามสองครั้งอยู่หลังคนที่ถูกข้ามครั้งเดียว โดยไม่ต้องเปลี่ยนเลขแถวอื่น |
| `skipped → skipped` **ถูกปฏิเสธ** ด้วย 409 | คิวที่อยู่ท้ายแล้วไม่มีอะไรให้ย้ายไปอยู่หลัง และการกดซ้ำจะเพิ่ม `SkipCount` ซึ่งคลินิกอ่านว่า "เจ้าของคนนี้ไม่มาเมื่อถูกเรียกกี่ครั้ง" |
| คิวที่ถูกข้ามนับใน `waiting_count` | ยังรออยู่ |

**ต้องยืนยัน** ถ้าตั้งใจให้ `skipped` เป็นสถานะสิ้นสุดจริง เคาน์เตอร์ต้องมีวิธีออกคิวใหม่ ซึ่ง contract ตอนนี้ไม่มี

## 18. สามสถานะคิวไม่มี endpoint ไปถึง (แก้แล้ว)

`in_room`, `served` และ `left` อยู่ใน state machine ของ contract แต่ไม่มี endpoint ในเอกสารที่ทำให้เกิดสถานะเหล่านี้

- **`in_room` และ `served`** ตอนนี้โมดูล Consultation เป็นผู้ทำ ตามที่คาด `POST /staff/consultations` พาคนไข้เข้าห้อง และ `POST /staff/consultations/{id}/close` จบการมาพบ
- **`left`** ไม่มี endpoint และไม่มีโมดูลไหนเป็นเจ้าของชัดเจน ตอนนี้คือ `POST /staff/queue/{id}/leave` ด้วย `queue:write` เป็นส่วนเพิ่มของ contract ที่ได้รับอนุมัติ อธิบายใน [contract-extensions.md § 2](./contract-extensions.md)

## 19. "ตรวจแพ้ยา" contract บังคับให้ตรวจ แต่ไม่บอกผล

`POST /staff/consultations/{id}/prescriptions` บรรยายว่า "ตรวจแพ้ยาและตัดสต๊อกเมื่อจ่ายจริง" การตรวจเป็นข้อบังคับ แต่ไม่ได้บอกว่าเมื่อตรงกันต้อง *ทำ* อะไร และสุดขั้วทั้งสองทางผิด การปฏิเสธเด็ดขาดคือระบบตัดสินแทนสัตวแพทย์ที่ตัดสินแล้วว่าต้องใช้ยานั้น ส่วนการเตือนเงียบ ๆ ทำให้การตรวจเป็นแค่ของประดับ

**ตีความว่า** ครั้งแรกปฏิเสธด้วย `409 allergy_conflict` พร้อมระบุการแพ้ใน `details` ครั้งที่ส่งซ้ำพร้อม `acknowledge_allergy` รับได้ เก็บการรับทราบไว้ในใบสั่งยา และบันทึก audit ภายใต้ action ของตัวเอง การแพ้ระดับ **รุนแรง** ข้ามผ่าน API ไม่ได้

การตรวจจับคู่ที่ชื่อยา ไม่รู้จักกลุ่มยา แพ้ penicillin จะไม่ถูกเตือนเมื่อสั่ง amoxicillin ข้อจำกัดนี้เขียนไว้ทุกที่ที่การตรวจปรากฏ ไม่ได้ปิดบัง

เหตุผลเต็มอยู่ใน [contract-extensions.md](./contract-extensions.md) (§ 8)

## 20. request body ของการตรวจไม่ได้ระบุ

รูปเดียวกับ § 15 ในหมวดถัดไป reference ระบุ endpoint การตรวจและเวชระเบียนทั้งสิบเส้น คือ path, method, scope และพฤติกรรมหนึ่งประโยค แต่ไม่มี schema

**ตีความว่า** ชื่อฟิลด์ตามคำของ reference เอง `chief_complaint` จาก "อาการที่แจ้ง", `body_system` และ `is_normal` จาก "ผลตรวจรายระบบ ปกติ/ผิดปกติ", `is_primary` จาก "วินิจฉัยหลัก/รอง" มีการตัดสินสี่ข้อใน body ที่ควรเขียนไว้ เพราะอ่านแบบอื่นได้

| การตัดสิน | ทางเลือกที่ไม่เลือก |
|---|---|
| `POST .../examination` **แทน** ทั้งแบบฟอร์ม | ถ้าต่อท้าย ระบบร่างกายหนึ่งระบบจะมีสองคำตอบที่ขัดกัน |
| `POST .../vitals` **ต่อท้าย** | สัตว์ที่อยู่ระหว่างสังเกตอาการถูกชั่งมากกว่าหนึ่งครั้งต่อการมาพบ ค่าล่าสุดคือค่าปัจจุบัน |
| amendment แก้ได้เฉพาะฟิลด์บรรยาย | การรักษาคิดเงินไปแล้ว และยาอาจจ่ายไปแล้ว สองอย่างนี้แก้ผ่านบิลหรือเคสใหม่ ไม่ใช่เขียนประวัติใหม่ |
| `PATCH` ถือว่าฟิลด์ที่ไม่ส่งคือ "ไม่ได้ส่ง" | autosave ส่งเฉพาะสิ่งที่สัตวแพทย์แตะ ถ้าถือว่าไม่ส่งคือ "ล้าง" บันทึกจะถูกลบทุกสิบวินาที |

## 21. เปิดเคสให้คนไข้ที่ยังไม่มีใครเรียก

flow ของ contract แสดง `call` แล้วจึง `POST /staff/consultations` และ state machine ของคิวอนุญาตแค่ `called → in_room` ถ้าอ่านตามตัวอักษร สัตวแพทย์ที่เดินออกไปรับคนไข้เองจะเปิดเคสไม่ได้ ซึ่งเป็นเรื่องปกติในคลินิกเล็ก และในคลินิกไหนก็ตามที่เครื่องเรียกคิวเสีย

**ตีความว่า** ถ้ายังไม่มีใครกดเรียก การเปิดเคส *คือ* การเรียก นับเป็นของสัตวแพทย์ที่เปิดเคส state machine ยังเข้มเหมือนเดิม และ `called_at` ยังมีค่า สถิติเวลารอจึงยังมีความหมาย ไม่เต็มไปด้วย null

## 22. ใบแจ้งหนี้ที่คืนเงินบางส่วนไม่มีสถานะของตัวเอง

state machine ของใบแจ้งหนี้วาดเป็นเส้นตรง `open → partially_paid → paid → refunded` และมี `void` เป็นทางออก ส่วน `POST /staff/invoices/{id}/refunds` บรรยายว่า "คืนเงินบางส่วนหรือทั้งใบ" คือบางส่วน **หรือ** ทั้งใบ บิลที่จ่ายครบแล้วคืนครึ่งหนึ่งจึงไม่มีสถานะในแผนภาพที่ตรง

อ่านได้สองแบบ และต่างกันจริง

| การอ่าน | ผล |
|---|---|
| กลับไป `partially_paid` (จ่ายสุทธิ < ยอดรวม) | บิลกลับมาอยู่ในรายการที่เคาน์เตอร์ต้องตามเก็บ สำหรับเงินที่คลินิกคืนไปเอง |
| **`refunded` ไม่ว่าบางส่วนหรือทั้งหมด** | **เลือกแบบนี้** ไปทางเดียวกับแผนภาพ และใช้ยอดเงินแยกว่าคืนบางส่วนหรือทั้งหมด |

**ตีความว่า** การคืนเงินใด ๆ ย้ายใบแจ้งหนี้ไป `refunded` และอยู่ตรงนั้น DTO มีทั้ง `paid_satang` และ `refunded_satang` client จึงแยกสองกรณีได้โดยไม่ต้องมีสถานะแยก `refunded` เป็นสถานะสิ้นสุด บิลที่คืนเงินแล้วรับชำระเพิ่มไม่ได้ และคืนบางส่วนเพิ่มได้จนถึงยอดที่เก็บมา

**ต้องตัดสินใจ** ถ้าบัญชีของคลินิกต้องการให้บิลที่คืนบางส่วนยังเก็บเงินต่อได้

## 23. ไม่มีที่ไหนบอกว่า request body ที่อ่านไม่ได้ต้องตอบอะไร

reference ระบุ `422` สำหรับการตรวจข้อมูล และ `400` สำหรับไม่มี `Idempotency-Key` แต่ body ที่ขาดฟิลด์บังคับไปไม่ถึง validator เพราะ filter model-state ของ `[ApiController]` ตัดก่อน กลายเป็น `ValidationProblemDetails` ของ ASP.NET ที่ `400` ความผิดแบบเดียวกันจึงถูกตอบสองแบบ คือ `422` พร้อม envelope ร่วมจาก use case และ `400` คนละรูปจาก framework client จะต้อง parse ทั้งสองแบบ

เจอตอนสร้าง Billing ซึ่งส่วนลดที่ไม่มี `approved_by_staff_id` คือกรณีนี้พอดี

**ตีความว่า** ความล้มเหลวของ model binding โยน `ValidationFailedException` ตัวเดียวกับที่ validator ใช้ จึงตอบ `422 validation_failed` พร้อม envelope ร่วม ทำโดยการโยน exception ไม่ใช่เขียน response ชุดที่สอง ใน `Api/Errors/ModelStateErrors.cs` body จึงไม่มีทางเพี้ยนไปจากที่ `ApiExceptionHandler` สร้าง

นี่คือ **การเปลี่ยนพฤติกรรมของทุก endpoint** ไม่ใช่แค่ billing body ผิดรูปที่เคยตอบ `400` ตอนนี้ตอบ `422` บันทึกไว้ที่นี่แทน [contract-extensions.md](./contract-extensions.md) เพราะไม่ได้แต่ง endpoint ขึ้นมา แค่ทำให้ข้อตกลงที่มีอยู่ใช้ได้ในที่ที่ควรใช้อยู่แล้ว

## 24. สิ่งที่ปฏิเสธการชำระเงินคือ `409` ไม่ใช่ `422`

เกี่ยวกับ § 23 และควรเขียนไว้เพราะ billing เป็นที่แรกที่เจอ ระบบขีดเส้นไว้ดังนี้

- **`422 validation_failed`** รูปของคำขอผิด เช่น ไม่มีเหตุผล จำนวนติดลบ วิธีชำระไม่ใช่หนึ่งในสามแบบ
- **`409`** พร้อมรหัสของ domain คำขอรูปถูกต้อง แต่ aggregate ปฏิเสธ *ตามสถานะตอนนั้น* จ่าย ฿2,000 กับบิลที่เรียก ฿1,460 คือกรณีที่ชัด ฿2,000 เป็นจำนวนที่ถูกต้อง แค่ไม่ใช่กับบิลนี้ตอนนี้

เป็นไปตาม mapping ที่มีอยู่แล้วใน `ApiExceptionHandler` คือ `DomainException` เปล่า ๆ เป็น `409` พร้อมรหัสของตัวเอง ไม่ได้สร้างกฎเฉพาะ billing รหัสในโมดูลนี้คือ `invalid_payment`, `invalid_refund`, `invalid_discount`, `invalid_receipt`, `invalid_void` คู่กับ `state_conflict` สำหรับการเปลี่ยนสถานะ

## 25. เรกคอร์ดสัตว์มีเฉพาะฟิลด์ที่ contract ระบุ

`GET /staff/pets/{id}` บรรยายว่าคืน "สายพันธุ์ น้ำหนักล่าสุด แพ้ยา ไมโครชิป" และไม่มี request body ของ `POST /staff/pets` วันเกิด เพศ และการทำหมัน เป็นสิ่งที่เวชระเบียนสัตว์ทุกแห่งต้องการ แต่ reference ไม่ได้ระบุเลย

**ตีความว่า** สัตว์หนึ่งตัวมีชื่อ ชนิด สายพันธุ์ ไมโครชิป เจ้าของ และสิ่งที่โมดูลทางคลินิกแนบมา (น้ำหนักล่าสุด การแพ้) ไม่ได้เพิ่มอะไร เพราะการเพิ่มคือการแต่ง schema ที่ทุก client ต้องตามด้วย

**ต้องยืนยันกับเจ้าของ contract** ว่าวันเกิด เพศ และการทำหมันควรอยู่ในเรกคอร์ดหรือไม่ เมื่อตั้งชื่อแล้วเพิ่มได้ง่าย (migration หนึ่งตัวกับฟิลด์เลือกได้สามฟิลด์) แต่เดายาก

## 26. เปลี่ยน role ผ่าน `PATCH /staff/members/{id}`

endpoint นี้บรรยายว่าเปลี่ยน "ตำแหน่ง สาขา ใบอนุญาต" role ผูกกับสมาชิกตอนเชิญ และไม่มี endpoint ใดบอกว่าเปลี่ยนได้ภายหลัง ถ้าอ่านตามที่เขียน การเลื่อนตำแหน่งพยาบาลคือปิดบัญชีแล้วเชิญใหม่

**ตีความว่า** `PATCH /staff/members/{id}` รับ `roles` ด้วย และแทนชุด role ของสมาชิกทั้งชุด "ตำแหน่ง" ในคลินิกหมายถึงสิ่งที่ทำได้พอ ๆ กับชื่อเรียก และนี่คือ endpoint เดียวที่แก้ข้อมูลสมาชิก กฎสองข้อเดียวกับที่คุมการให้สิทธิ์ทุกทางคุมที่นี่ด้วย คือให้ scope ที่ตัวเองไม่ได้ถือไม่ได้ และห้ามเปลี่ยนจนคลินิกไม่เหลือเจ้าของที่ใช้งานอยู่

การเปลี่ยน role หรือสาขามีผลกับสมาชิกเมื่อได้ access token ใบถัดไป เพราะทั้งสองอย่างอยู่ใน token

## 27. ข้อมูลที่ contract ไม่มีทางอ่าน

หลายอย่างเขียนผ่าน contract ได้แต่อ่านกลับไม่ได้ ไม่มีข้อไหนได้ endpoint ใหม่ แต่ละข้ออ่านจาก endpoint ที่ใกล้ที่สุดที่ contract มี

| สิ่งที่อ่านไม่ได้ | อ่านอย่างไรในระบบนี้ |
|---|---|
| ค่าตั้งคิว ค่าตั้งเวชระเบียน มีแค่ `PATCH` ไม่มี `GET` | ส่ง `PATCH` ด้วย body ว่าง (`{}`) ไม่เปลี่ยนอะไรและคืนค่าตั้งปัจจุบัน |
| วันหยุด มีแค่ `POST /clinic/holidays` | `GET /clinic/hours` คืนวันหยุดที่จะมาถึงพร้อมเวลาทำการรายสัปดาห์ สาธารณะต้องรู้ทั้งสองอย่างจึงรู้ว่าคลินิกเปิดไหม |
| คำเชิญที่ค้างอยู่ มี `POST` สร้าง ไม่มีทางดูรายการ | `GET /staff/members?status=invited` แสดงคำเชิญที่ยังไม่ตอบรับ |
| สาขาหลังสร้าง มีแค่ `POST /clinic/branches` | ไม่ครอบคลุม แก้หรือปิดสาขาผ่าน API ไม่ได้ ที่อยู่และห้องตรวจกำหนดตายตัวตอนสร้าง |
| บริการที่ไม่เปิดจองออนไลน์ `GET /services` คือเมนูสาธารณะ | หน้าจัดการบริการอ่านจาก `GET /staff/services` ซึ่งเป็นส่วนขยายที่อนุมัติแล้ว ([contract-extensions.md § 17](./contract-extensions.md)) แต่หน้าจองที่เคาน์เตอร์ยังใช้เมนูสาธารณะ เพราะเส้นใหม่ต้องใช้ `service:manage` ซึ่งพนักงานต้อนรับไม่มี |

สองข้อหลังเป็นช่องโหว่จริง ไม่ใช่การตีความ เรื่องสาขายังเปิดอยู่ ต้องใช้ `PATCH /clinic/branches/{id}` ที่ reference ไม่มี **ต้องยกไปคุยกับเจ้าของ contract** เรื่องบริการปิดไปครึ่งหนึ่งด้วย § 17 ของส่วนขยาย ส่วนการจองที่เคาน์เตอร์ยังรอคำตอบว่าควรมี scope อ่านบริการแยกหรือไม่

## 28. รายการที่ "คลินิกนิยามเอง" แต่ไม่มี endpoint ให้นิยาม

สามรายการบรรยายว่าเป็นของคลินิกเอง มี endpoint อ่านแต่ไม่มีเขียน

- **ประเภทพนักงาน** (`GET /staff/staff-types`, "ประเภทพนักงานที่คลินิกนิยามเอง") ตีความว่า ประเภทพนักงานเกิดจากการใช้ ตำแหน่งที่เขียนในคำเชิญหรือข้อมูลสมาชิกกลายเป็นประเภทพนักงานตั้งแต่นั้น รายการคืนแต่ละประเภทพร้อมจำนวนคนที่ถือ ตำแหน่งสี่ตำแหน่งในตาราง role ของ contract อยู่ในรายการเสมอเป็นตัวเลือกแนะนำ ทั้งหมดเป็นแค่ป้ายชื่อ สิทธิ์ตัดสินจาก scope เสมอ ไม่ใช่ตำแหน่ง
- **หมวดบริการ** (`GET /services/categories`) ตีความว่าตายตัว contract แจกแจงไว้หกหมวดพอดี คือ ตรวจ วัคซีน ทันตกรรม ผ่าตัด แล็บ กรูมมิ่ง และ `category_code` ของบริการถูกตรวจกับรายการนี้
- **เวลาทำการ** (`PUT /clinic/hours`) ตีความว่าเป็นสัปดาห์เดียวของทั้งคลินิก ไม่ใช่ต่อสาขา เพราะ path ไม่มีสาขา นี่คือเวลาที่คลินิกบอกสาธารณะ เวลาที่จองได้ยังมาจากตารางเวร ตามที่ contract บอก ("ตารางเวรเป็นตัวกำหนด slot") สิ่งที่ปิดการจองคือ *วันหยุด*

**id ของสาขาสร้างจากรหัสสาขา** `sukhumvit39` กลายเป็น `brn_sukhumvit39` เพราะเป็นรูปที่ทุกตัวอย่างใน reference ใช้

## 29. role ตั้งต้น `veterinarian` ปิดเคสของตัวเองไม่ได้

ตาราง "Role ตั้งต้น" ให้ `veterinarian` มี scope `consult:*`, `record:write`, `lab:*`, `rx:write`, `queue:call` การปิดเคสคือการลงนามเวชระเบียนซึ่งต้องใช้ `record:sign` และการอ่านข้อมูลสัตว์ต้องใช้ `patient:read` ทั้งสองไม่อยู่ในรายการ

**ตีความว่า seed ตามที่เขียนทุกตัว** role ตั้งต้นคัดลอกจากตารางทีละแถว (`Domain/Access/DefaultRoles.cs`) สัตวแพทย์ที่ถือแค่ role ตั้งต้นจึงทำการตรวจได้แต่ปิดเคสไม่ได้ จนกว่าเจ้าของจะเพิ่ม `record:sign` ให้ role ซึ่งทำได้ผ่าน `PUT /staff/roles/{id}/permissions`

การแอบเพิ่มสอง scope นี้จะทำให้ demo ราบรื่นขึ้น แต่ seed จะโกหกเรื่อง contract **ต้องยืนยันกับเจ้าของ contract** ดูเหมือนตารางตกหล่น ไม่ใช่ตั้งใจให้สัตวแพทย์ลงนามไม่ได้

## 30. การรับคำเชิญคือการเรียก endpoint เดียวสองครั้ง

`POST /staff/members/invitations/{id}/accept` บรรยายว่า "ผู้ถูกเชิญตั้งรหัสผ่านและ 2FA" ในบรรทัดเดียว ไม่มี body

**ตีความว่า** ครั้งแรกส่งแค่ token จากลิงก์ ได้ความลับ TOTP กลับมา (`two_factor_setup_required`) ครั้งที่สองส่งรหัสผ่านพร้อมรหัสที่สร้างจากความลับนั้น แล้วบัญชีถูกสร้าง (`accepted`) ทั้งสองครั้งไม่คืนเซสชัน สมาชิกใหม่เข้าสู่ระบบผ่าน `POST /auth/staff/login` เหมือนทุกคน

ถ้าเรียกครั้งเดียว ต้องคืนความลับและลงทะเบียนในคราวเดียว ผู้ถูกเชิญที่ทำ response นั้นหายจะได้บัญชีที่มีปัจจัยที่สองที่ตัวเองไม่เคยได้รับ การเรียกสองครั้งทำให้ยังไม่มีอะไรเกิดขึ้นจนกว่าผู้ถูกเชิญพิสูจน์ว่า authenticator ใช้ได้

endpoint ไม่ระบุ scope เพราะผู้เรียกยังไม่มีบัญชี token ในลิงก์คือ credential เก็บแค่ค่า hash ใช้ได้ครั้งเดียว และหมดอายุ

## 31. prefix `/v1` และรูปแบบของหน้า

สองจุดที่ API ที่รันอยู่เพี้ยนไปจาก reference เจอตอนเขียน client ตัวแรก

- **path base** base URL ของ reference ลงท้ายด้วย `/v1` แต่ API เคยรันจาก root ตอนนี้ตั้ง `/v1` เป็น path base แล้ว ทุก path ในเอกสารเรียกเป็น `/v1/...` route template ไม่เปลี่ยน
- **pagination** reference แสดงรายการเป็น `{ "data": [...], "page": { "next_cursor": ... } }` เคยมี endpoint รายการเจ็ดเส้นคืนรูปภายในของตัวแบ่งหน้าแทน ตอนนี้ JSON converter ตัวเดียว (`Api/Http/CursorPageJsonConverter.cs`) เขียนทุก `CursorPage<T>` ในรูปตามเอกสาร endpoint แต่ละเส้นจึงทำผิดเองไม่ได้

ทั้งสองข้อเป็นการแก้ให้ตรง contract ไม่ใช่การตีความ

## 32. รหัส error ที่เพิ่มสำหรับการตั้งค่าคลินิก พนักงาน และบริการ

เหมือน § 14 และ § 24 คือ `422 validation_failed` เมื่อรูปคำขอผิด และ `409` พร้อมรหัสของ domain เมื่อคำขอรูปถูกต้องถูกปฏิเสธตามสถานะปัจจุบัน รหัสที่โมดูลเหล่านี้เพิ่ม

| รหัส | ปฏิเสธ |
|---|---|
| `duplicate_branch`, `duplicate_holiday`, `duplicate_role`, `duplicate_service` | สร้างสิ่งที่รหัส วันที่ หรือชื่อถูกใช้แล้ว |
| `staff_already_exists` | เชิญที่อยู่อีเมลที่มีบัญชีในคลินิกนี้แล้ว (เชิญที่อยู่ที่มีคำเชิญ *ค้างอยู่* ไม่ถูกปฏิเสธ แต่ออกคำเชิญใหม่แทน) |
| `role_not_editable` | แก้ scope ของ role ตั้งต้น `customer` ซึ่งบรรยายกลุ่มผู้ใช้ portal ไม่ใช่ชุด scope |
| `last_owner` | การเปลี่ยนใดที่ทำให้คลินิกไม่เหลือเจ้าของที่ใช้งานอยู่ |
| `cannot_deactivate_self` | ปิดบัญชีสมาชิกของตัวเอง |
| `incomplete_consultation` | ปิดเคสที่ขาดสิ่งที่ค่าตั้งเวชระเบียนของคลินิกบังคับ `details` บอกว่าขาดอะไร |
| `invalid_branch`, `invalid_holiday`, `invalid_opening_hours`, `invalid_queue_settings`, `invalid_medical_record_settings`, `invalid_service`, `invalid_service_availability`, `invalid_pricing`, `invalid_staff_member` | ค่าที่ aggregate ปฏิเสธเอง |

การให้ scope ที่ผู้เรียกไม่ได้ถือตอบ `403 insufficient_scope` เหมือนการใช้ scope นั้น เพราะทั้งสองกรณีคือผู้เรียกเอื้อมเกินสิทธิ์ของตัวเอง

## 33. ตารางเวรห้าเส้นบรรยายไว้บรรทัดเดียว ไม่มี body

หมวด Schedules และ Shifts มีห้า endpoint แต่ละเส้นมีคำอธิบายบรรทัดเดียว ไม่มีตัวอย่าง JSON ไม่มีกฎ ตีความดังนี้ รายละเอียดการใช้งานอยู่ใน [ตารางเวร](features/schedules.md)

| เรื่อง | contract เขียนว่า | ตีความว่า |
|---|---|---|
| RRULE | "สร้างเวรเดี่ยวหรือทั้งสัปดาห์ด้วย RRULE" | รับเฉพาะส่วนที่ตารางเวรต้องใช้ คือ `FREQ=DAILY` หรือ `WEEKLY`, `INTERVAL`, `BYDAY` และ `COUNT` หรือ `UNTIL` อย่างใดอย่างหนึ่ง ส่วนอื่นตอบ `422` ไม่อ่านแค่บางส่วน ไม่เกิน 200 เวรและ 366 วันต่อคำขอ ขยายตามเวลาของคลินิก 09:00 คือ 09:00 ทุกครั้ง |
| เวลาพัก | "ช่องว่างจริงหลังหักนัดและเวลาพัก" | เวลาพักส่งมากับเวรได้ช่วงเดียว และถูกเก็บเป็นช่องว่าง คือเวรถูกแบ่งเป็นสองเวร การคำนวณช่วงว่างของการจองจึงไม่ต้องรู้จักเวลาพัก |
| เวรทับกัน | ไม่ได้พูดถึง | ปฏิเสธทั้งคำขอด้วย `409 shift_overlap` ถ้าเวรใดที่จะสร้างทับเวรเดิมของคนเดียวกัน (ทุกสาขา) และ `409 staff_on_time_off` ถ้าทับวันลา ไม่สร้างบางส่วน คำขอที่ถูกส่งซ้ำจึงไม่สร้างเวรซ้ำ จึงไม่บังคับ `Idempotency-Key` |
| วันลา | "ลา" และ "ระบบเตือนนัดที่ชนและเสนอหมอแทน" | การบันทึกวันลาคือการอนุมัติ เพราะ contract ไม่มีขั้นอนุมัติ เวรที่ถูกทับถูกยกเลิก (เก็บไว้ในประวัติ) และส่วนที่ยังทำงานกลายเป็นเวรใหม่ นัดที่จองไว้แล้วไม่ถูกย้าย คำตอบบอกนัดที่ชนพร้อมหมอที่รับแทนได้ |
| ช่วงว่าง | "ช่องว่างจริงหลังหักนัดและเวลาพัก" | ต่างจาก `GET /booking/availability` ที่ตอบเป็นช่องของบริการหนึ่ง เส้นนี้ตอบช่วงเวลาว่างของแต่ละคนในวันเดียวที่สาขาเดียว ไม่ผูกกับบริการ |
| กติกาจ่ายเคส | "กติกาจ่ายเคสอัตโนมัติ เช่น หมอแมวรับเคสแมวก่อน" | กติกาเป็นลำดับความชอบ ไม่ใช่ข้อจำกัด แต่ละข้อจับคู่ด้วยชนิดสัตว์ บริการ หรือทั้งสองอย่าง ข้อแรกที่ตรงชนะ ใช้ตอนจองโดยไม่ระบุหมอ และตอนเสนอหมอแทนวันลา คิวยังจ่ายด้วยมือ |
| `from` และ `to` | `?from=&to=` | เป็นตัวกรองที่มีค่าเริ่มต้น (§ 7) ไม่ส่งได้สัปดาห์นี้ ช่วงยาวสุด 31 วัน |

**ต้องถาม** contract มีแค่ `PUT` ของกติกาจ่ายเคส ไม่มีทางอ่านกลับ client จึงรู้กติกาปัจจุบันได้จากคำตอบของ `PUT` ครั้งล่าสุดเท่านั้น ถ้าหน้าจอตั้งค่าต้องการ ต้องขอเพิ่ม `GET /staff/schedules/assignment-rules` เป็นส่วนขยาย

## 34. `PATCH /me` และ `POST /me/2fa/enroll`

| เรื่อง | ตีความว่า |
|---|---|
| ฟิลด์ของ `PATCH /me` | "ชื่อ อีเมล เบอร์ ภาษา การแจ้งเตือน" กลายเป็น `display_name`, `email`, `phone`, `language` (`th` หรือ `en`) และ `notifications` ที่มี `email`, `sms`, `line` เป็นเปิดหรือปิด ส่งเฉพาะที่เปลี่ยน `GET /me` คืนค่าทั้งหมดนี้พร้อม `version` สำหรับ `If-Match` |
| เปลี่ยนอีเมลหรือเบอร์ | ต้องส่ง `current_password` ด้วย เพราะทั้งสองเป็นตัวระบุตอนเข้าสู่ระบบ คนที่ได้ access token ไปสิบห้านาทีต้องย้ายบัญชีไปที่อยู่ของตัวเองไม่ได้ ซ้ำกับบัญชีอื่นตอบ `409 contact_taken` |
| การแจ้งเตือน | ค่าถูกเก็บและแสดง และตัวส่งข้อความถึงลูกค้าอ่านแล้ว ช่องทางที่ปิดถูกข้ามด้วยเหตุผล `opted_out` ตัวกั้นหลักยังเป็นความยินยอมรายวัตถุประสงค์ (contract-extensions § 4) |
| ลงทะเบียน 2FA | เรียกสองครั้งแบบเดียวกับการรับคำเชิญ (§ 30) ครั้งแรกส่งรหัสผ่าน ได้ความลับ ครั้งที่สองส่งรหัสจากแอป แล้วจึงเปิดใช้ และได้ recovery code 8 รหัสที่แสดงครั้งเดียว ปัจจัยที่สองไม่เคยถูกเปิดก่อนที่จะใช้ได้จริงหนึ่งครั้ง |
| เปลี่ยนปัจจัยที่สองที่มีอยู่ | ต้องใช้เซสชันที่ผ่านปัจจัยเดิมแล้ว ไม่อย่างนั้นได้ `403` |
| recovery code | contract บอกแค่ว่า endpoint คืนค่านี้ ตีความว่าใช้แทนรหัสจากแอปที่ `POST /auth/2fa/verify` ได้ ใช้ได้รหัสละครั้ง และการลงทะเบียนใหม่ออกชุดใหม่แทนชุดเดิมทั้งหมด |
| รหัสผ่านปัจจุบันผิด | ตอบ `422` ที่ `current_password` ไม่ใช่ `401` เพราะเซสชันยังดีอยู่ แค่คำขอขาดหลักฐาน `POST /me/password` ที่ทำไว้ก่อนตอบ `401` ควรเปลี่ยนให้ตรงกันในอนาคต |

## 35. `PATCH /staff/users/{id}/status`

contract เขียนแค่ชื่อสามสถานะ คือ `active`, `suspended` และ `deactivated`

- `{id}` คือ id ของบัญชี (`usr_...`) ใช้ได้ทั้งพนักงานและลูกค้า ต่างจาก `POST /staff/members/{id}/deactivate` ที่จบการเป็นพนักงาน แต่บัญชียังอยู่
- `suspended` ยกเลิกได้ `deactivated` เป็นการปิดถาวร เปลี่ยนกลับด้วย endpoint นี้ไม่ได้ (`409 state_conflict`)
- สถานะที่ไม่ใช่ `active` เพิกถอนทุกเซสชันทันที access token ที่ออกไปแล้วยังใช้ได้จนหมดอายุ ไม่เกิน 15 นาที เหมือนการปิดบัญชีพนักงาน
- ถ้าบัญชีเป็นพนักงาน ใช้กติกาเดิมของการแก้พนักงาน คือผู้เรียกที่ผูกกับสาขาเปลี่ยนได้เฉพาะคนในสาขาของตัวเอง เปลี่ยนคนที่มีสิทธิ์มากกว่าตัวเองไม่ได้ และพักบัญชีสุดท้ายที่ถือ `*` ไม่ได้ (`409 last_owner`)
- เปลี่ยนสถานะของตัวเองไม่ได้ (`409 cannot_deactivate_self`)

รหัส error ที่ส่วนนี้และ § 33 ถึง § 34 เพิ่ม คือ `shift_overlap`, `staff_on_time_off`, `contact_taken` และรหัสของ domain `invalid_time_off`, `invalid_assignment_rules`, `invalid_profile`

## 36. งานรักษาต่อเนื่อง: วัคซีน น้ำหนัก แล็บ ยา เทมเพลต และเอกสาร PDF

ทุกเส้นในกลุ่มนี้มีคำอธิบายบรรทัดเดียว ตีความดังนี้ รายละเอียดอยู่ใน [งานรักษาต่อเนื่อง](features/clinical-records.md)

| เรื่อง | contract เขียนว่า | ตีความว่า |
|---|---|---|
| รอบถัดไปของวัคซีน | "ตั้งรอบถัดไปอัตโนมัติ" | ส่ง `next_due_on` หรือ `valid_for_days` ได้ ถ้าไม่ส่งทั้งสองอย่างคือหนึ่งปี `valid_for_days: 0` คือไม่ต้องฉีดอีก การเตือนเป็นกติกา `vaccine_due` ของโมดูล Automation อ่านวันครบกำหนดของเข็มล่าสุด ดู [เตือนอัตโนมัติ](features/automation.md) |
| ล็อตและวันหมดอายุ | "ล็อตวัคซีน วันหมดอายุ" | บังคับทั้งสองอย่าง เพราะเป็นสิ่งที่ใช้ตามหาสัตว์เมื่อผู้ผลิตเรียกคืนวัคซีน วัคซีนที่หมดอายุแล้วในวันฉีดถูกปฏิเสธ |
| วัคซีนที่ครบกำหนด | "รอบถัดไปที่ครบกำหนด" | หนึ่งรายการต่อชนิดวัคซีน จากเข็มล่าสุด สถานะ `overdue`, `due_soon` (ภายใน 30 วัน) หรือ `upcoming` สัตว์ที่เสียชีวิตไม่มีรายการนี้ |
| กราฟน้ำหนัก | "ชุดข้อมูลกราฟน้ำหนักย้อนหลัง" | อ่านจาก vitals ของแต่ละการตรวจ เรียงเก่าไปใหม่ ไม่เกิน 400 จุด ไม่มีตารางน้ำหนักแยก |
| สาขาของคำขอแล็บ | ไม่ได้พูดถึง | มาจากการตรวจที่อ้างถึง ถ้าไม่มีใช้ `branch_id` หรือสาขาเดียวของผู้เรียก รายการงานแล็บจำกัดตามสาขาของผู้เรียก |
| ธงค่าผิดปกติ | "ค่าที่วัดได้ + ช่วงอ้างอิง ธงค่าผิดปกติ" | คำนวณจากค่ากับช่วงอ้างอิงเมื่อเป็นตัวเลข (`low`, `normal`, `high`) ใช้ค่า `abnormal` ของผู้ส่งเฉพาะผลที่เป็นข้อความ ส่งผลซ้ำได้หลายครั้ง ผลใหม่ทำให้คำขอกลับไปเป็น "ยังไม่มีคนอ่าน" |
| ผลที่ยังไม่มีคนอ่าน | "งานค้างของหมอ ผลที่ยังไม่มีคนอ่าน" | สามสถานะ `pending`, `resulted`, `reviewed` และส่วนขยาย `POST /staff/lab-requests/{id}/review` ([contract-extensions.md § 11](./contract-extensions.md)) |
| ตรวจซ้ำซ้อน | "ยาที่เคยจ่ายทั้งหมด ตรวจซ้ำซ้อน" | ยาชื่อเดียวกัน (ดูคำแรกของชื่อ) ที่ช่วงใช้ยาทับกัน ใส่ใน `duplicate_of` ของแต่ละรายการ ไม่รู้จักชื่อการค้าต่างกันของยาตัวเดียวกัน เหมือนการตรวจแพ้ยา (§ 19) |
| จ่ายยา | "จ่ายยาจริง ตัดสต๊อกและพิมพ์ฉลาก" | บันทึกว่าจ่ายแล้วและคืนข้อมูลฉลาก แต่ **ไม่ตัดสต๊อก** เพราะยังไม่มีโมดูล Inventory คำตอบมี `stock_deducted: false` จ่ายซ้ำตอบ `409` |
| เทมเพลตแผนรักษา | "เทมเพลตแผนรักษาที่คลินิกทำไว้เอง" | contract มีแค่ `GET` ไม่มีทางสร้าง ตอนนี้ใส่เทมเพลตด้วยคำสั่ง operator `seed-treatment-templates` เทมเพลตไม่เก็บราคา หัตถการที่ชี้บริการใช้ราคาของบริการในวันที่ใช้ |
| เอกสาร PDF | "ใบรับรองสุขภาพ ใบส่งตัว สมุดวัคซีน เป็น PDF" | ตอบเป็นไฟล์ PDF ตรง ๆ ไม่เก็บไว้ ใบรับรองและใบส่งตัวต้องออกโดยคนที่มีเลขใบอนุญาตในข้อมูลพนักงาน เพราะชื่อผู้ออกถูกพิมพ์เป็นผู้ลงนาม ทุกครั้งที่ออกเขียนลง access log |

**ต้องถาม** endpoint สำหรับสร้างและแก้เทมเพลต และ scope ที่ควรใช้

## 37. นัดขั้นสูงหกเส้น

| เรื่อง | contract เขียนว่า | ตีความว่า |
|---|---|---|
| ไม่มาตามนัด | "บันทึกไม่มาตามนัด นับสถิติรายลูกค้า" | บันทึกได้หลังถึงเวลานัดเท่านั้น (`409 no_show_too_early`) คำตอบมีสถิติของลูกค้าที่นับจากตารางนัดเอง ไม่ได้เก็บเป็นตัวนับแยก |
| นโยบายยกเลิก | "cutoff ค่าปรับ และจำนวนครั้งที่ยอมให้" | สี่ค่า คือ `cutoff_hours`, `fee_satang`, `free_allowance` และ `window_days` ที่เพิ่มเพราะ "กี่ครั้ง" ต้องมี "ภายในเท่าไร" |
| cutoff สองตัว | § 15 วาง cutoff การเลื่อนนัดไว้ใน booking settings | เป็นคนละเรื่องกัน cutoff ของ booking settings ตัดสินว่าลูกค้า **เลื่อน** เองได้ไหม cutoff ของนโยบายตัดสินว่าการยกเลิก **ถูกนับ** ไหม การยกเลิกไม่เคยถูกห้าม |
| ใครถูกนับ | ไม่ได้พูดถึง | เฉพาะลูกค้าที่ยกเลิกเองในช่วงกระชั้น และการไม่มาตามนัด การยกเลิกโดยพนักงานไม่นับ เพราะอาจเป็นคลินิกเองที่ยกเลิก |
| ค่าปรับ | "ค่าปรับ" | คำนวณและรายงาน แต่ **ไม่ออกบิลเอง** การเก็บเงินลูกค้าเป็นการตัดสินที่เคาน์เตอร์ ผ่าน endpoint ใบแจ้งหนี้ |
| ประเภทนัด | "นัดปกติ ฉุกเฉิน ติดตามผล ผ่าตัด กติกาต่างกัน" | สี่ประเภทนี้เป็นค่าเริ่มต้น แต่ละประเภทมีกติกาสี่ข้อ คือระยะเวลา จองออนไลน์ได้ไหม เวลาจองล่วงหน้า และความเร่งด่วนของคิวตอนเช็กอิน ต้องมี `regular` เสมอ ไม่มี `GET` จึงอ่านค่าปัจจุบันได้จากคำตอบของ `PUT` เหมือนกติกาจ่ายเคส (§ 33) |
| ตรวจนัดชน | "ตรวจนัดชน หมอลา ห้องไม่ว่าง ก่อนยืนยัน" | สองแบบ คือตรวจเวลาที่จะจอง (`starts_at`) และตรวจนัดทั้งวัน (`date`) ปัญหามีห้าแบบ คือคลินิกปิด หมอไม่มีเวร หมอลา หมอมีนัดซ้อน สัตว์มีนัดซ้อน **ไม่ตรวจห้อง** เพราะนัดในระบบนี้ไม่ได้จองห้อง ห้องถูกจ่ายบนกระดานคิว |
| นัดซ้ำ | "คอร์สรักษาต่อเนื่อง เช่น เคมีบำบัดทุก 3 สัปดาห์" | ใช้ RRULE ชุดเดียวกับตารางเวร 2 ถึง 52 ครั้ง จองทั้งชุดหรือไม่จองเลย ใช้หมอคนเดียวตลอดคอร์ส ไม่ติดเพดาน "จองล่วงหน้าได้กี่วัน" ของหน้าจอง ต้องส่ง `Idempotency-Key` |
| คิวรอ | "คิวรอคิวว่าง ยิง LINE อัตโนมัติเมื่อมีคนยกเลิก" | แจ้งคนที่รออยู่ไม่เกินสามคนตามลำดับที่เข้าคิว ไม่จองให้ ใครจองก่อนได้ก่อน รายการหมดอายุเองหลังวันสุดท้ายที่รอ เพราะ contract ไม่มีทางถอนออก ส่งผ่านช่องทางจริง (LINE, SMS หรืออีเมล) และกล่องแจ้งเตือน |

รหัส error ที่ส่วนนี้เพิ่ม คือ `no_show_too_early`, `already_waiting` และรหัสของ domain `invalid_appointment_types`, `invalid_cancellation_policy`, `invalid_waiting_list`

| ชนิดและขนาด | ไม่ได้พูดถึง | JPEG PNG WEBP HEIC และ PDF ไม่เกิน 10 MB |
| ให้เจ้าของเห็น | "เลือกให้เจ้าของเห็นได้" | `visible_to_owner` ปิดไว้ก่อนสำหรับเอกสารของคลินิก ไฟล์ที่เจ้าของส่งเองเห็นได้เสมอ |

## 39. การเข้าสู่ระบบของลูกค้า

| เรื่อง | contract เขียนว่า | ตีความว่า |
|---|---|---|
| OTP | "rate limit 3 ครั้ง/เบอร์/10 นาที" | รหัส 6 หลัก อายุ 5 นาที ใช้ได้ครั้งเดียว เดาผิดได้ 5 ครั้ง นับ 3 ครั้งต่อเบอร์ใน 10 นาทีจากฐานข้อมูล (`RateLimits:OtpPerPhonePer10Minutes`) เกินตอบ `429 rate_limited` รหัสระบุจุดประสงค์ `register` หรือ `login` และใช้ข้ามกันไม่ได้ |
| ไม่บอกว่าเบอร์มีบัญชีไหม | ไม่ได้พูดถึง | ขอรหัสตอบ `202` เหมือนกันเสมอ รหัส `login` ส่งจริงเฉพาะเบอร์ที่มีบัญชี เพื่อไม่ต้องเสียค่า SMS ให้คนแปลกหน้า |
| สมัคร | "สมัครด้วยเบอร์โทร + OTP" | รหัสผ่านใส่หรือไม่ใส่ก็ได้ บัญชีผูกกับเรกคอร์ดลูกค้าที่เคาน์เตอร์สร้างไว้แล้วถ้าเบอร์ตรงกัน (เทียบเป็นตัวเลขล้วน) ถ้าไม่มีจึงสร้างใหม่ เบอร์ที่มีบัญชีแล้วตอบ `409 contact_taken` หลังพิสูจน์เบอร์แล้วเท่านั้น สมัครเสร็จได้เซสชันทันที |
| เข้าสู่ระบบ | "ทั้งสองฝั่ง คืน capabilities ของบัญชีในคลินิกนี้" | สองแบบ คือ `phone` กับ `code` หรือ `identifier` (อีเมลหรือเบอร์) กับ `password` บัญชีที่มี 2FA ได้ challenge เหมือน `/auth/staff/login` คำตอบมี `capabilities` คือ staff id, customer id, scope และสาขาของ token ที่เพิ่งออก |
| รีเซ็ตรหัสผ่าน | "ลิงก์อายุ 30 นาที ใช้ครั้งเดียว" | endpoint เดียวเรียกสองครั้งแบบเดียวกับการรับคำเชิญ (§ 30) ครั้งแรกส่ง `identifier` ได้ `link_sent` เสมอ ครั้งที่สองส่ง `token` กับ `new_password` แล้วทุกเซสชันของบัญชีถูกเพิกถอน ส่งลิงก์ทางอีเมลถ้าบัญชีมีอีเมล ไม่อย่างนั้นทาง SMS ไม่เกิน 3 ลิงก์ต่อบัญชีใน 10 นาที |
| ตัวส่งจริง | ไม่ได้พูดถึง | ยังไม่มีตัวส่ง SMS และอีเมล รหัสและลิงก์ถูกเขียนลง log เฉพาะเมื่อเปิด `Auth:SignIn:LogUndeliveredSecrets` ซึ่งเปิดไว้แค่ใน `appsettings.Development.json` |

ทุก token ที่ออกตอนนี้มี customer id ถ้าบัญชีนั้นผูกกับเรกคอร์ดลูกค้า ไม่ว่าจะเข้าสู่ระบบทางไหน พนักงานที่เป็นลูกค้าด้วยจึงใช้ portal ได้ด้วย token เดียวกัน ตามที่ contract บอกว่า "บัญชีเดียวเป็นทั้งลูกค้าและพนักงานได้"

## 41. การแจ้งเตือนและ LINE หกเส้น

ทุกเส้นในหมวด Notifications และ LINE integration มีคำอธิบายบรรทัดเดียว ตีความดังนี้ รายละเอียดอยู่ใน [การแจ้งเตือน](features/notifications.md) และ [LINE](features/line.md)

| เรื่อง | contract เขียนว่า | ตีความว่า |
|---|---|---|
| ส่งข้อความ | "ส่งเดี่ยวหรือเป็นกลุ่ม เลือก channel ได้" | `template`, `customer_ids` (1 ถึง 100), `channel` (`auto`, `line`, `sms`, `email`) และ `variables` เลือกช่องทางเดียวคือไม่ส่งทางอื่นแทน ส่งได้เฉพาะเทมเพลตที่ไม่ชี้เรกคอร์ดจริง (`appointment.reminder`, `vaccine.due`, `clinic.message`) คำตอบเป็น `200` พร้อมผลรายคน รวมคนที่ถูกข้าม |
| เทมเพลต | "เทมเพลตพร้อมตัวแปร pet_name, vet_name, time" | อ่านอย่างเดียว เป็นรายการในโค้ด มีค่าที่ใช้ ความยินยอมที่ต้องมี ถ้อยคำ LINE และ SMS และสวิตช์ LINE ของแต่ละชนิด ไม่มี endpoint แก้ถ้อยคำ |
| ประวัติการส่ง | "ส่งสำเร็จ/ล้มเหลว fallback ไป SMS เมื่อไหร่" | หนึ่งแถวต่อหนึ่งครั้งที่ลองส่ง สถานะ `sent`, `failed`, `skipped` พร้อมรหัสเหตุผล การส่งแทนเป็นแถวใหม่ที่มี `fallback_from` ที่อยู่ถูกปิดบางส่วน ผู้อ่านที่สังกัดสาขาเห็นสาขาตัวเองและแถวที่ไม่ผูกสาขา |
| ตั้งค่า LINE | "channel id/secret เปิดปิดชนิดการแจ้งเตือน" | รับ access token ด้วย เพราะ push ต้องใช้ ทุกฟิลด์ไม่บังคับ ไม่ส่งคือคงเดิม สตริงว่างคือลบค่าที่เก็บไว้ body ว่างคืออ่านค่า เพราะไม่มี `GET` (แบบเดียวกับ § 27) ไม่เคยส่ง secret หรือ token กลับ เพิ่มโควตาประกาศต่อเดือนไว้ที่นี่ |
| ประกาศ | "ประกาศถึงกลุ่มลูกค้าที่คัดไว้ จำกัดโควตา" | กลุ่มคือรายชื่อลูกค้าในคำขอ (1 ถึง 200) เพราะกลุ่มที่บันทึกไว้เป็นของ `POST /staff/segments` ซึ่งยังไม่มี เป็นข้อความการตลาด ส่งทาง LINE อย่างเดียว โควตานับประกาศที่ส่งสำเร็จต่อเดือนปฏิทิน เกินตอบ `409 quota_exceeded` ทั้งคำขอ |
| webhook | "รับ follow message postback จากปุ่มในแชต" | ตรวจลายเซ็นก่อนอ่าน body `follow` ตอบต้อนรับ `unfollow` หยุดส่งถึงลูกค้าคนนั้น `message` ตอบอัตโนมัติ postback ทำตามปุ่มหลังตรวจสิทธิ์ซ้ำ การยกเลิกนัดถามยืนยันก่อน |

รหัส error ที่ส่วนนี้เพิ่ม คือ `quota_exceeded` และ `line_not_configured` (ทั้งคู่ `409`)

**ต้องถาม** สามเรื่อง

1. ไม่มี endpoint ไหนในสัญญาที่บันทึก LINE user id ลงเรกคอร์ดลูกค้าได้ นอกจากเส้นผูกบัญชีที่ถูกตัดออกตามหัวข้อ A ระบบส่ง LINE และรับปุ่มได้ครบ แต่จะถึงลูกค้าจริงเมื่อมีทางบันทึกที่อยู่ ต้องขออนุมัติส่วนขยาย ดู [LINE](features/line.md#ที่อยู่-line-ของลูกค้า)
2. การอ่านเทมเพลตต้องมี `notify:manage` แต่ผู้ส่งต้องรู้ว่าเทมเพลตใช้ค่าอะไร หน้าส่งข้อความจึงเก็บสำเนารายการไว้ฝั่งหน้าเว็บ ถ้าต้องการให้ `notify:send` อ่านได้ ต้องเปลี่ยน scope ของเส้นนี้
3. สัญญาไม่มี `GET /staff/integrations/line` ตอนนี้อ่านด้วย `PUT` body ว่าง ถ้าต้องการ `GET` ต้องเพิ่มเป็นส่วนขยาย

# การตัดสินเรื่องขอบเขต

ส่วนนี้ไม่ใช่ความกำกวม แต่เป็นจุดที่ API reference มีเอกสารของสิ่งที่ requirement ของโปรเจกต์ไม่ต้องการให้สร้าง บันทึกไว้เพื่อให้นักพัฒนาคนถัดไปไม่สร้าง endpoint นั้นกลับขึ้นมาจาก reference อีก

## A. LINE เป็นช่องทางส่งการแจ้งเตือนออก ไม่ใช่ผู้ยืนยันตัวตน

**requirement** LINE ใช้ *ส่ง* ข้อความ เช่น เตือนนัด เรียกคิว สรุปการมาพบ ไม่ได้ใช้เข้าสู่ระบบ สร้างหรือผูกบัญชี หรือระบุตัวลูกค้า ที่อยู่ LINE ของลูกค้าเป็นข้อมูลสำหรับส่ง เหมือนอีเมล ถ้าลูกค้าไม่มีปลายทาง LINE ในระบบ ข้อความไปทางช่องทางอื่นหรือไม่ส่งเลย

```text
Application -> Notification port -> Infrastructure -> LINE Messaging API
```

ไม่มี flow `Customer -> LINE account -> phone verification -> identity link` ที่ไหนในโค้ดนี้

**จุดที่ต่างจาก reference** endpoint สี่เส้นในเอกสารมีไว้รับใช้โมดูลตัวตนที่ requirement ไม่เอา จึง **อยู่นอกขอบเขต**

| Endpoint | reference บอกว่า | สถานะ |
|---|---|---|
| `POST /auth/line/callback` | "LINE Login  ผูกกับบัญชีเดิมถ้าเบอร์ตรง" | นอกขอบเขต |
| `POST /portal/line/link` | "ผูก LINE user เข้ากับบัญชีลูกค้า" | นอกขอบเขต |
| `DELETE /portal/line/link` | "ยกเลิกการผูก  หยุดส่งเข้าแชตทันที" | นอกขอบเขต |
| `GET /line/liff/booking-context` | "เปิดหน้าจองใน LINE โดยรู้ว่าใครเปิดอยู่" | นอกขอบเขต เพราะจุดประสงค์ที่เขียนคือระบุตัวผู้ดู |

ทั้งสี่เส้นไม่อยู่ใน [api-mapping.md](./api-mapping.md) และไม่มี controller, use case หรือ route **API reference ไม่ได้ถูกแก้** ยังมีเอกสารของสี่เส้นนี้อยู่ reference กับโค้ดจึงไม่ตรงกันในสี่แถวนี้จนกว่าจะแก้ reference

**อยู่ในขอบเขต ไม่เปลี่ยน**

| Endpoint | หน้าที่ |
|---|---|
| `PUT /staff/integrations/line` | channel id และ secret และประเภทการแจ้งเตือนที่เปิด |
| `POST /staff/integrations/line/broadcast` | ประกาศขาออกถึงกลุ่มลูกค้า |
| `POST /webhooks/line` | callback ขาเข้าของ integration ดูด้านล่าง |

## B. การระบุผู้ส่ง postback ขาเข้าจาก LINE

`POST /webhooks/line` รับ event `follow`, `message` และ postback เป็น callback ของ integration ไม่ใช่ endpoint ยืนยันตัวตน แต่ postback action ที่ reference ระบุ (`confirm_appointment`, `reschedule_appointment`, `cancel_appointment`, `view_queue`, `open_invoice`) ทำงานกับเรกคอร์ดจริง handler จึงต้องมีวิธีตัดสินว่าการกดปุ่มหมายถึงนัด *ของใคร*

ภายใต้โมเดลที่ใช้ LINE ส่งแจ้งเตือนอย่างเดียว คำตอบที่มีคือค้นย้อนจากปลายทาง LINE ที่เก็บไว้ เหมือนระบบอีเมลระบุว่าคำตอบมาจากที่อยู่ที่ส่งไป นี่คือการค้นจากที่อยู่ส่ง ไม่ใช่ตัวตน LINE user id ไม่เคยเป็น credential ไม่เคยเป็น primary key ของ `Customer` และไม่เคยให้เซสชัน

**ทำตามแบบนี้แล้ว** (§ 41) `customers.line_user_id` ไม่ซ้ำกัน การค้นจึงได้ลูกค้าไม่เกินหนึ่งคน และทุกปุ่มตรวจสิทธิ์แบบ portal ซ้ำ

**ต้องตัดสินใจ** อีกทางคือถือ postback ขาเข้าเป็นนอกขอบเขตด้วย และให้การแจ้งเตือนมีลิงก์ธรรมดาเข้า portal แทนปุ่มในแชต ทางนี้สะอาดกว่าถ้าไม่ได้ต้องการปุ่มในแชตจริง ถ้าเลือกทางนี้ endpoint จะถูกถอดออก
