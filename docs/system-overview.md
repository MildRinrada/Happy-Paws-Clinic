# สถานะระบบ

หน้าเดียวสำหรับทั้งแพลตฟอร์ม ระบบคืออะไร อะไรทำงานอยู่ตอนนี้ และส่วนที่ควรอ่านที่สุด คือ **อะไรยังขาด และใครต้องตัดสิน**

ดัชนีราย endpoint อยู่ที่ [api-mapping.md](./api-mapping.md) เหตุผลของแต่ละจุดกำกวมอยู่ที่ [assumptions.md](./assumptions.md) และ endpoint 80 เส้นที่ **ไม่อยู่** ใน contract พร้อมเหตุผล อยู่ที่ [contract-extensions.md](./contract-extensions.md) หน้านี้คือมุมมองจากด้านบนของทั้งสามไฟล์

เลขหัวข้อคงไว้ เพราะโค้ดอ้างถึง (`BookingSettingsHandlers.cs` ชี้มาที่ § 5)

## 1. ระบบนี้คืออะไร

Happy Paws Clinic เป็นระบบจัดการคลินิกสัตวแพทย์ตาม contract ชื่อ PetCare OS **หนึ่งคลินิกคือหนึ่ง deployment** ไม่มี `clinic_id` ที่ไหนใน API ไม่มีสารบบคลินิก ไม่มีตัวสลับ tenant บริบทของคลินิกมาจาก host ที่ติดตั้ง

ผู้ใช้สองกลุ่มใช้ domain object ชุดเดียวกัน

- **พนักงาน** ใช้ `/staff/*` จำกัดด้วย scope และสาขาที่สังกัด
- **ลูกค้า** ใช้ `/portal/*` จำกัดเฉพาะสัตว์ที่ตัวเองดูแล

บัญชีเดียวเป็นทั้งสองอย่างได้ contract บอกชัดว่าสัตวแพทย์อาจเป็นเจ้าของสัตว์ด้วย การเป็นสมาชิกจึงเป็นรายการ ไม่ใช่ฟิลด์ role ฟิลด์เดียว

```text
ลูกค้าจอง -> มาถึง -> คิว -> ตรวจ -> เวชระเบียน -> ใบแจ้งหนี้ -> จ่ายแล้ว
/portal     check-in  /queue  /staff/consultations    /staff/invoices
```

วันทำงานของคลินิกวิ่งได้ตั้งแต่ต้นจนจบ และไม่ต้องพึ่งข้อมูล seed แล้ว ฐานข้อมูลว่างกลายเป็นคลินิกที่ใช้งานได้ด้วยคำสั่ง operator คำสั่งเดียว (`bootstrap` สร้างเจ้าของคนแรก สาขาแรก และชุด role) หลังจากนั้นทุกอย่าง ทั้งพนักงาน บริการ ลูกค้า สัตว์เลี้ยง สร้างผ่าน API

**ที่เสร็จครบทั้งเส้น** การเข้าสู่ระบบทั้งพนักงานและลูกค้า (รหัสผ่าน 2FA OTP และรีเซ็ตรหัสผ่าน) และการจัดการเซสชัน การตั้งค่าคลินิก พนักงาน role และคำเชิญ แคตตาล็อกบริการ ทะเบียนลูกค้าและสัตว์เลี้ยง หมวดการจองและนัดทั้งหมดรวมนัดขั้นสูง หมวดคิวทั้งหมดรวม SSE stream หมวดการตรวจและเวชระเบียนทั้งหมด งานรักษาต่อเนื่อง (วัคซีน น้ำหนัก แล็บ ยา แผนการรักษา เอกสาร PDF) portal ลูกค้าทั้งหมวด หมวดบิลและการชำระเงินทั้งหมด audit log พร้อม endpoint อ่านทั้งสองเส้น และความยินยอมพร้อมสิทธิ์ของเจ้าของข้อมูล

**ในทางปฏิบัติแปลว่า** เมื่อติดตั้งใหม่ operator สร้างเจ้าของคนแรก เจ้าของตั้งเวลาทำการ เพิ่มสาขาและบริการ แล้วเชิญพนักงานคนอื่น เคาน์เตอร์ลงทะเบียนลูกค้าและสัตว์เลี้ยง จากนั้นคลินิกรับจอง เช็กอิน จัดคิว เรียกคนไข้ ตรวจ สั่งยา ลงนามเวชระเบียน จองนัดติดตามผล ออกบิล รับเงินสด บัตร หรือ PromptPay และพิมพ์ใบกำกับภาษีได้ การรับคำเชิญ การลงทะเบียนลูกค้าและสัตว์ ปฏิทินนัด คิว การตรวจจนปิดเคส หน้าเก็บเงิน ตารางเวร และการตั้งค่าคลินิก บริการ และข้อมูลติดต่อ ใช้จากเบราว์เซอร์ได้ ที่เหลือยังใช้ได้ผ่าน API เท่านั้น

**การส่งข้อความถึงลูกค้า** (เรียกคิว ใบเสร็จ เตือนนัด ข้อความจากพนักงาน) ออกจริงทาง LINE, SMS และอีเมลเมื่อตั้งค่า ทุกครั้งที่ลองส่งอยู่ในประวัติการส่ง ถ้าไม่ตั้งเลย ยังเขียนลง log ของ API ข้อความไปทาง LINE เมื่อเรกคอร์ดลูกค้ามีที่อยู่ LINE ซึ่งเคาน์เตอร์เลือกจากรายชื่อผู้ที่เพิ่งเพิ่มเพื่อน LINE ของคลินิก ([contract-extensions.md § 18](./contract-extensions.md)) ลูกค้าที่ยังไม่ได้ผูกได้ข้อความทาง SMS หรืออีเมล ดู [LINE](features/line.md) กติกาเตือนอัตโนมัติเปิด ปิด แก้ และลบได้จากหน้าเตือนอัตโนมัติ ([contract-extensions.md § 19](./contract-extensions.md))

## 5. สิ่งที่ยังขาด

ขาดอยู่สามแบบ และต้องใช้คนต่างกันแก้

### A. สร้างแล้ว แต่ยืนอยู่บนตัวแทนชั่วคราว

สิ่งที่ดูเหมือนเสร็จแต่ยังไม่เสร็จ แต่ละข้อแก้ด้วยการเปลี่ยนการลงทะเบียนบรรทัดเดียวเมื่อของจริงมี เพราะจุดเรียกถูกต้องอยู่แล้ว

| อะไร | ที่ไหน | ผลตอนนี้ |
|---|---|---|
| **การส่งแจ้งเตือน** | `DeliveringNotificationChannel` | ส่งจริงทาง LINE, SMS, อีเมล ตามที่ตั้งค่า ถ้าไม่ตั้งเลยถอยไปที่ `LoggingNotificationChannel` ซึ่งเขียน log ระดับ warning และประวัติการส่งบันทึก `channel_not_configured` client ของ LINE และ SMS ทดสอบกับเซิร์ฟเวอร์จำลองเท่านั้น |
| **ความลับของ LINE ในฐานข้อมูล** | `line_channel_settings` | channel secret และ access token ที่ตั้งผ่าน `PUT /staff/integrations/line` เก็บแบบยังไม่เข้ารหัส เหมือนความลับ TOTP ไม่เคยถูกส่งกลับทาง API ควรเข้ารหัสก่อนติดตั้งจริง หรือตั้งผ่าน environment แทน ตอนนี้มี `ISecretProtector` (Data Protection) ที่ใช้กับ secret ของ webhook และค่าตั้งการชำระเงินและแล็บแล้ว ย้าย LINE และ TOTP มาใช้ได้ แต่ยังไม่ได้ทำ |
| **SMS และอีเมลของการเข้าสู่ระบบ และคำเชิญพนักงาน** | `Infrastructure/Messaging/` | ส่งจริงได้แล้วผ่าน SMTP และ ThaiBulkSMS เมื่อตั้ง `Messaging:Email` และ `Messaging:Sms` ([development.md](./development.md#ตั้งค่าอีเมลและ-sms)) ถ้าไม่ตั้ง ยังเขียนลง log เหมือนเดิม ตัวส่ง SMS ทดสอบกับเซิร์ฟเวอร์จำลองเท่านั้น ยังไม่ได้ลองกับบัญชีจริง |
| **ความลับ TOTP ในฐานข้อมูล** | `TotpService` | ความลับของปัจจัยที่สองเก็บตามที่ออกให้ ควรเข้ารหัสด้วยกุญแจที่อยู่นอกฐานข้อมูลก่อนติดตั้งจริง |
| **recovery code ของบัญชีที่ไม่ได้ลงทะเบียนเอง** | `OperatorCredentials`, `AcceptInvitationHandler` | บัญชีที่ลงทะเบียน 2FA ผ่าน `POST /me/2fa/enroll` ได้ recovery code 8 รหัสที่ใช้เข้าสู่ระบบได้จริง แต่เจ้าของที่สร้างด้วย `bootstrap` และพนักงานที่รับคำเชิญยังไม่ได้ จนกว่าจะลงทะเบียนใหม่ด้วยตัวเองหนึ่งครั้ง |
| **ความล่าช้าของการปิดบัญชี** | อายุ access token | ปิดบัญชีพนักงานแล้ว refresh token ถูกเพิกถอนทันที แต่ access token ที่ออกไปแล้วยังใช้ได้จนหมดอายุ (15 นาที ตาม `Auth:Jwt:AccessTokenLifetimeMinutes`) |
| **โควตา walk-in** | `BookingSettings.WalkInSlotsPerHour` | เก็บและคืนค่าได้ แต่ไม่ถูกบังคับ contract ตั้งชื่อค่าตั้งไว้แต่ไม่ได้บอกกฎ จึงไม่ได้แต่งขึ้นเอง |
| **ที่เก็บไฟล์** | `LocalFileStorage` | ไฟล์อยู่บนดิสก์ของเครื่องที่รัน API ถ้าไม่ตั้ง `Storage:LocalRoot` จะอยู่ในโฟลเดอร์ชั่วคราวของระบบ ซึ่งหายได้ ก่อนติดตั้งจริงต้องตั้งโฟลเดอร์ถาวรหรือเปลี่ยนเป็น S3 ดู [contract-extensions.md § 12](./contract-extensions.md) |
| **การผูกยากับรายการในคลัง** | `StockDispenser` | การจ่ายยาตัดสต๊อกและคิดเงินแล้ว แต่ผูกใบสั่งยากับรายการด้วยชื่อยาทั้งชื่อ เพราะคำขอสั่งยาใน contract ไม่มีรหัสรายการ ชื่อที่ไม่ตรงจ่ายได้แต่ไม่ตัดสต๊อกและไม่คิดเงิน (`stock.status: not_matched`) |
| **กุญแจ Data Protection** | `DataProtection:KeysDirectory` | secret ของ webhook ค่าความลับของผู้ให้บริการชำระเงินและแล็บ และ token ของลิงก์ปฏิทิน เข้ารหัสด้วยกุญแจนอกฐานข้อมูล ถ้าไม่ตั้งโฟลเดอร์ กุญแจอยู่ที่ค่าเริ่มต้นของ ASP.NET Core ซึ่งใน container หายพร้อม container แล้ว webhook จะส่งไม่ได้ (`secret_unavailable`) ต้องตั้งโฟลเดอร์ถาวรก่อนติดตั้งจริง ดู [development.md](./development.md) |
| **ค่าตั้งการชำระเงินและแล็บ** | `PUT /staff/integrations/payment`, `/lab` | เก็บและตรวจรูปแบบเท่านั้น ยังไม่มีตัวเชื่อม gateway หรือแล็บ การเปิดใช้ยังไม่มีผล |
| **payment gateway** | ไม่มี | การจ่ายด้วยบัตรหมายถึง "เครื่องรูดบัตรอนุมัติแล้ว เลขสลิปอยู่ใน `reference`" ไม่ใช่ "ระบบตัดบัตรแล้ว" เงินสดและ PromptPay ไม่กระทบ ยอดรวมทุกตัวก็ไม่กระทบ |
| **ต้นทุนยาในรายงาน** | `GetServiceAnalyticsHandler` | ค่ายาขึ้นบิลจากการจ่ายยาแล้ว และต้นทุนต่อหน่วยถูกเก็บตอนรับเข้า แต่รายงานบริการยังหักแค่ค่ายาที่ขาย ไม่ใช่ต้นทุน กำไรจริงต้องเพิ่มตัวเลขในคำตอบ ซึ่งยังไม่ได้ขอส่วนขยาย |

### B. งานข้ามโมดูลที่ยังไม่ได้ทำ

| เรื่อง | หมายเหตุ |
|---|---|
| **outbox สำหรับการเรียกภายนอก** | การแจ้งเตือนส่งหลัง commit แบบพยายามเต็มที่ ถ้า process ตายตรงช่องนั้น ข้อความหาย ยอมรับได้สำหรับการเรียกคิว (เจ้าของดูกระดานอยู่) แต่ **ยอมรับได้น้อยลงแล้ว** เพราะข้อความหนึ่งในนั้นคือใบเสร็จ ตัวเอกสารปลอดภัยเพราะเขียนใน transaction แต่สำเนาถึงลูกค้าอาจไม่ถึง ตอนนี้ความล้มเหลวของผู้ให้บริการถูกบันทึกในประวัติการส่งแล้ว แต่การที่ process ตายหลัง commit ยังไม่ทิ้งร่องรอย และยังไม่มีการส่งซ้ำ webhook มี outbox แล้ว (`IWebhookOutbox`, แถวถัดไป) การแจ้งเตือนย้ายมาใช้รูปเดียวกันได้ แต่ยังไม่ได้ทำ |
| **การส่ง webhook** | **ทำแล้ว** event ถูกเขียนลง outbox (`webhook_events`) ใน transaction เดียวกับงาน จึงไม่หายเมื่อ process ตาย และไม่ถูกส่งเมื่องานย้อนกลับ งานเบื้องหลังแตกเป็น `webhook_deliveries` ลงนาม HMAC-SHA256 ส่ง และลองใหม่ 5 ครั้งใน 13 ชั่วโมง ดู [การเชื่อมต่อระบบ](features/integrations.md) |
| **scheduler เบื้องหลัง** | **ทำแล้ว** `Infrastructure/Jobs/` มี `BackgroundService` สี่งาน คือเตือนอัตโนมัติ สร้างไฟล์ส่งออก ส่ง webhook และ housekeeping (ลบ hold และ idempotency key ที่หมดอายุเกินหนึ่งวัน ผู้ติดตาม LINE ที่ไม่ได้ผูกกับลูกค้าเมื่อไม่เห็นเกิน 14 วัน และ event ของ webhook ที่เก่ากว่า 30 วัน) ปิดได้ด้วย `Jobs:Enabled` ทุกงานจองงานในฐานข้อมูล จึงรันหลาย instance ได้ ที่ยังไม่มีคือ outbox และการส่งซ้ำของข้อความทั่วไป ดูแถวบนสุด |
| **rate limit ราย endpoint** | ใช้ policy 600 ครั้งต่อนาทีต่อ token ทั้งระบบแล้ว policy ข้อความ 60 ครั้งต่อนาที (`RateLimitingExtensions.MessagingPolicy`) ติดกับ `POST /staff/notifications/send` และ `POST /staff/threads/{id}/messages` แล้ว ส่วน OTP 3 ครั้งต่อเบอร์ต่อ 10 นาทีนับจากฐานข้อมูลใน `RequestOtpHandler` แล้ว |
| **ระยะเวลาเก็บข้อมูล** | สมุดความยินยอมและ workflow คำขอลบสร้างแล้ว แต่ข้อมูลแต่ละประเภทเก็บ *นานเท่าไร* ต้องใช้นโยบายที่ที่ปรึกษาของคลินิกกำหนด ดู [contract-extensions.md § 4](./contract-extensions.md) |

**audit log ออกจากรายการนี้แล้ว** สร้างแล้ว ทุกโมดูลทางคลินิกเขียนลงไป และรายชื่อสิ่งที่ต้อง audit เป็นทะเบียนที่ตั้งชื่อและยืนยันด้วยเทสต์ใน `Domain/Auditing/AuditActions.cs` ซึ่งเป็นช่องโหว่ข้อห้าในตารางถัดไป

### C. ช่องโหว่ใน contract เอง

เจ็ดสิ่งที่คลินิกสัตว์ที่ทำงานจริงต้องมี แต่ 164 endpoint ไม่ครอบคลุม เจอจากการสร้างตาม contract ไม่ใช่จากการอ่าน **ทั้งเจ็ดข้อทำงานอยู่แล้ว**

| # | ช่องโหว่ | คำตอบ | สถานะ |
|---|---|---|---|
| 1 | คิวไม่มี priority เคสฉุกเฉินแซงคิวตัดเล็บไม่ได้ | priority สามระดับ ลำดับ และเหตุผลที่ audit | ✅ ทำแล้ว |
| 2 | `left` เป็นสถานะคิวที่ไม่มีอะไรไปถึง | `POST /staff/queue/{id}/leave` | ✅ ทำแล้ว |
| 3 | `void` เป็นสถานะใบแจ้งหนี้ที่ไม่มีอะไรไปถึง | `POST /staff/invoices/{id}/void` | ✅ ทำแล้ว |
| 4 | ไม่มี endpoint ความยินยอม ระยะเก็บ หรือการลบข้อมูลเลย | สมุดความยินยอม การบังคับที่ notification port และ workflow คำขอข้อมูล | ✅ ทำแล้ว (ระยะเก็บเลื่อนไว้) |
| 5 | ไม่ได้ระบุขอบเขต audit ไม่มีที่ไหนบอกว่าต้องเขียนอะไร | `AuditActions` รายชื่อที่ตั้งชื่อ ตรวจได้ และยืนยันด้วยเทสต์ | ✅ ทำแล้ว |
| 6 | นัดในอนาคตของสัตว์ที่เสียชีวิตไม่มีนิยาม | ยกเลิกและแจ้งครั้งเดียว ใน transaction เดียว | ✅ ทำแล้ว |
| 7 | Billing มีแต่ `POST` หกเส้น แคชเชียร์ดูบิลไม่ได้ | `GET /staff/invoices` และ `GET /staff/invoices/{id}` | ✅ ทำแล้ว |

ถ้าจะอ่านข้อเดียว ให้อ่านข้อ 7 ทุก workflow ในหมวด billing ของ contract ต้องมี id ของใบแจ้งหนี้ และหมวดนั้นแจก id ให้เฉพาะใน response ของคำขอที่เพิ่งเขียน บิลที่ออกตอนสัตวแพทย์ปิดเคส 11:00 จึงหาไม่เจอที่เคาน์เตอร์ตอน 11:05 นี่ไม่ใช่ช่องโหว่เรื่องความสะดวก แต่เป็นความต่างระหว่างโมดูลที่ใช้งานได้ กับโมดูลที่ผ่านแค่เทสต์ของตัวเอง

แต่ละข้อมีเหตุผล ทางเลือกที่ไม่เลือก และสิ่งที่ตั้งใจ *ไม่* ทำ อยู่ใน [contract-extensions.md](./contract-extensions.md) จุดกำกวมที่แคบกว่า เช่น จำนวน endpoint 214 กับ 164 หก endpoint ที่ไม่ระบุ scope schema ของ request การจอง ลูกค้าเช็กอินเอง ความหมายของการข้ามคิว บิลที่คืนเงินบางส่วนยังเก็บเงินต่อได้ไหม อยู่ใน [assumptions.md](./assumptions.md)

## 6. ควรทำอะไรต่อ และทำไมตามลำดับนี้

1. **หน้าจอพนักงานที่เหลือ** backend ของวันทำงานทั้งวันมีแล้ว และมีหน้าจอแล้ว (รับคำเชิญ คิว ปฏิทินนัด ลงทะเบียนลูกค้าและสัตว์เลี้ยง หน้าสัตว์ หน้าตรวจ หน้าเก็บเงิน) หน้าถัดไปคือหน้าตั้งค่า (คลินิก พนักงานและ role บริการ)
2. **หน้าจอ portal ลูกค้า** API ของการสมัคร การเข้าสู่ระบบ และ portal ครบแล้ว หน้าแรกสาธารณะมีปุ่ม "สมัครใช้งานฟรี" และ "จองนัดหมาย" ที่ตอนนี้ลิงก์ไป `#` (`frontend/src/config/site-navigation.ts`, `features/home/content/hero.ts`, `booking-cta.ts`) จนกว่าหน้าจอจะมี
3. **ส่วนขยายของคลังยาที่เหลือ** อ่านสมุดสต๊อก บันทึกล็อตที่ผู้ผลิตเรียกคืน และต้นทุนยาในรายงาน (`inventory_item_id` ในคำขอสั่งยาทำแล้วเป็น § 20 การแก้และเลิกใช้รายการ กับการอ่านและยกเลิกใบสั่งซื้อทำแล้วเป็น § 25) ข้อเสนออยู่ใน [สต๊อกยาและเวชภัณฑ์](features/inventory.md#ข้อเสนอส่วนขยาย-ยังไม่ได้ขออนุมัติ-ยังไม่ได้ทำ) ต้องขออนุมัติก่อน
4. **เสริมความแข็งแรงก่อนติดตั้งจริง** เข้ารหัสความลับ TOTP และความลับของ LINE ในฐานข้อมูล ย้ายไฟล์ไปที่เก็บถาวร และตัดสินว่าการปิดหรือพักบัญชีต้องตัด access token ที่ยังใช้อยู่ทันที หรือรอให้หมดอายุเอง

ข้อเดียวที่ *ไม่ควร* รอคิวคือ **ระยะเวลาเก็บข้อมูล** ([contract-extensions.md § 4](./contract-extensions.md)) ต้องการคำตอบจากที่ปรึกษาของคลินิก ไม่ใช่เวลาของนักพัฒนา จึงถามคู่ขนานกับทุกข้อข้างบนได้
